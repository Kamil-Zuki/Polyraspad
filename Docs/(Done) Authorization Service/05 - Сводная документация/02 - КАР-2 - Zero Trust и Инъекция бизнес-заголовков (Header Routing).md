# Введение

Внутренние микросервисы (например, Tasks, CRM) не доверяют клиентским Cookie. **API Gateway (агрегатор / BFF на периметре)** принимает внешний HTTP-запрос, «снимает» Cookie, обращается к **Authorization Service** по gRPC (валидация сессии, чтение состояния из Redis/БД) и во внутреннюю сеть прокидывает только доверенные заголовки (например, `X-Workspace-Id`), реализуя принцип Zero Trust. Сам микросервис Authorization Service **не** обязан быть тем процессом, в котором открыт публичный HTTP-порт для браузера; публичные контроллеры — зона ответственности агрегатора.

## Контекст и проблема

В микросервисной архитектуре запрос от фронтенда (браузера) проходит через множество внутренних компонентов, прежде чем достигнет целевого бизнес-сервиса (например, сервиса управления задачами).

Если передавать проверку прав на сторону конечного сервиса, возникают следующие проблемы:

*   **Дублирование логики (Spaghetti Security):** Каждый микросервис (Tasks, CRM, Billing) должен будет уметь подключаться к Redis, парсить сессионную Cookie (Phantom Token), расшифровывать данные пользователя и проверять, не отозвана ли сессия. Это утяжеляет код всех сервисов.
*   **Уязвимость периметра:** Если внутренний сервис имеет публичный эндпоинт, который случайно забыли "закрыть" проверкой сессии, возникает критическая уязвимость (Broken Access Control).
*   **Проблема доверия:** Если сервисы сами парсят токены, злоумышленник, проникший во внутреннюю сеть, может легко подделать запрос, передав нужные ему идентификаторы напрямую.

## Принятое решение

Платформа STEOS реализует строгий паттерн **API Gateway (Edge Router / агрегатор) + Header Routing** с концепцией **Zero Trust (Нулевое доверие)** во внутренней сети:

1.  **Единая точка входа:** Все запросы от клиентских приложений проходят через слой **API Gateway (агрегатор)**, а не напрямую в процессы бизнес-микросервисов. Внутренние бизнес-сервисы изолированы от внешнего интернета. **Authorization Service** участвует как **источник решений** по сессии и контексту (gRPC), а не обязан совмещать роль публичного веб-хоста с доменной логикой в одном деплойменте.
2.  **Снятие (Terminating) сессии на границе:** API Gateway перехватывает запрос, извлекает `HttpOnly` Cookie, вызывает **Authorization Service** для валидации (и при необходимости использует кэш/Redis согласованно с Auth), затем «раздевает» запрос, полностью удаляя из него оригинальную Cookie перед передачей внутрь периметра.
3.  **Инъекция доверенных заголовков:** На основе ответа Auth (контекст сессии) Gateway формирует набор строгих внутренних HTTP-заголовков. Например:
    *   `X-Global-Actor-Id: uuid-user-123`
    *   `X-Workspace-Id: 42`
    *   `X-User-Roles: ADMIN,EDITOR`
4.  **Zero Trust внутри:** Бизнес-микросервис (например, `Task Service`) получает запрос. Он абсолютно не знает, что такое Cookie или Redis. Он слепо доверяет заголовку `X-Global-Actor-Id` и использует его для создания задачи. Инфраструктура (Service Mesh / Envoy) настроена так, что **никто, кроме API Gateway**, не имеет права передавать заголовки, начинающиеся с `X-*`. Любые попытки клиента (или скомпрометированного внутреннего контейнера) подделать эти заголовки жестко вырезаются на уровне балансировщика.

## Обоснование и последствия

### Плюсы

*   **Централизация безопасности (Single Choke Point):** Доменная логика валидации сессий, отзыва токенов и политик сосредоточена в **Authorization Service**; **периметр** (единая точка приёма HTTP/WebSocket) — у **API Gateway**. Это разделяет «тонкий» edge и «толстую» авторизацию и упрощает аудит и эволюцию политик.
*   **Радикальное упрощение бизнес-сервисов:** Код `Task Service` или `CRM Service` становится максимально чистым. Им не нужны библиотеки для работы с криптографией, токенами или Redis. Они просто читают строки из HTTP-заголовков (Request Headers).
*   **Высокая производительность:** "Тяжелая" работа по разрешению сессии выполняется один раз на входе в кластер. Внутренняя маршрутизация происходит мгновенно.

### Последствия

*   **Критическая зависимость от периметра и Auth:** отказ **API Gateway** делает недоступным весь внешний трафик; отказ **Authorization Service** блокирует выдачу и проверку контекста безопасности. Оба контура требуют горизонтального масштабирования и наблюдаемости; это разные узлы отказа, их не следует смешивать в документации как один процесс.
*   **Ограничение внутренней сети:** Разработчики должны строго следить за тем, чтобы внутренние сервисы не были доступны извне в обход Gateway, иначе защита, построенная на доверенных заголовках, будет полностью скомпрометирована.
*   **Сложность локальной разработки:** Разработчикам, тестирующим отдельный микросервис локально, придется имитировать (Mock) поведение API Gateway, вручную прокидывая заголовки `X-Global-Actor-Id` в свои REST-клиенты (Postman/Curl).
