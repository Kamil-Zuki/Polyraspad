# Введение

Эта группа описывает **локальную авторизацию для программного доступа** и **согласованные политики периметра** в экосистеме платформы STEOS: что хранится в реляционной базе **Authorization Service**, а что остаётся источником правды в **Workspace Service**, но оценивается Auth при принятии решения о доступе.

Интерактивные пользователи по-прежнему опираются на Phantom Token и таблицы группы *Session Management*; здесь же фокус на **машинных клиентах** (CLI, CI/CD, серверные интеграции) и на **ограничениях Geo/IP** для рабочих пространств, с которыми Auth работает через контракты API и gRPC.

**Архитектурные задачи группы:**

1. **Персональные API-ключи (PAT):** выдача долгоживущих ключей с набором **scopes**, хранение в БД только **хэша** секрета, отзыв и аудит операций с ключами. Открытое значение токена (`stp_…`) показывается владельцу **один раз** при создании.
2. **Разделение персистентности:** таблица `api_keys` принадлежит Auth; **политики Geo-Fencing / IP-allowlist** для Workspace хранятся в **Workspace Service** (например, JSONB `security_policies`), а Auth получает снимок политики для валидации сессии или PAT-запроса согласно маршруту.
3. **Единая модель решения «можно / нельзя»:** Gateway и бизнес-сервисы потребляют уже обогащённый контекст (субъект, workspace, scopes); Auth сопоставляет scopes и при необходимости применяет периметр Workspace, не дублируя долговременное хранение политик у себя.
4. **Согласованность контрактов:** структуры DTO и методы REST/gRPC для PAT и geo-политик описаны в [07 - Управление доступом и политики Workspace (Access Control)](../../04%20-%20Бекенд,%20API%20и%20Контракты/Методы%20API/DTO/07%20-%20Управление%20доступом%20и%20политики%20Workspace%20(Access%20Control).md); модель данных ниже увязывает таблицы и внешние источники с этими контрактами.

Для PAT допускается **Redis** как слой кэша записей `api_keys` при высокой нагрузке на проверку ключей (опционально, по политике развёртывания).

# Персональный API-ключ (`api_keys`)

## 1. Общее описание

**Персональный API-ключ (PAT)** — строка в таблице `api_keys`: один выпущенный пользователем (субъект с глобальным `steos_id`) долгоживущий ключ с человекочитаемым именем, сроком действия и списком областей (**scopes**).

Секретная часть токена (префикс `stp_` и криптостойкая случайная строка) **никогда не сохраняется в открытом виде**. При каждой аутентификации по PAT система вычисляет хэш предъявленного секрета и сравнивает его с полем `secret_hash`; при совпадении обновляется `last_used_at` (и при необходимости кэш).

**Архитектурное назначение:**

1. **Идентификация владельца:** ключ однозначно связан с глобальным субъектом (`global_steos_id`), что позволяет аудиту и биллингу ссылаться на того же пользователя, что и при входе через OIDC.
2. **Ограничение blast radius:** отзыв одного ключа не трогает остальные ключи пользователя и не обязан инвалидировать браузерные сессии.
3. **Соответствие compliance:** маскированное отображение в UI (`PatDetailsDto`) и отсутствие хранения plaintext-секрета снижают риск утечки при компрометации БД.

## 2. Атрибуты (поля) сущности

**Таблица:** `api_keys`

*В соответствии с «Белой книгой разработчика баз данных», первичный ключ — стабильный строковый идентификатор, пригодный для публичного API (`key_…`). Внешние ключи на глобальный STEOS ID — логические.*

| Название          | Тип данных     | Огр-ния              | Описание                                                                                                                                   |
| :---------------- | :------------- | :------------------- | :----------------------------------------------------------------------------------------------------------------------------------------- |
| `id`              | `varchar(64)`  | PK, NOT NULL         | **Публичный идентификатор ключа.** Возвращается в API как `keyId` (например, префикс `key_` + ULID). Не является секретом.                 |
| `global_steos_id` | `uuid`         | NOT NULL             | **Владелец ключа.** Логическая ссылка на `actors.id` в глобальном STEOS ID.                                                                |
| `name`            | `varchar(255)` | NOT NULL             | **Человекочитаемое имя** (например, «CI prod», «Ноутбук Иван»).                                                                            |
| `secret_hash`     | `varchar(255)` | NOT NULL             | **Хэш секретной части токена** (например, Argon2id/bcrypt от строки после префикса `stp_`). Plaintext не хранится.                         |
| `scopes`          | `jsonb`        | NOT NULL, Def `'[]'` | **Разрешённые области** (массив строк), например `["workspace:read", "api:invoke"]`. Семантика согласуется с платформенным реестром scope. |
| `expires_at`      | `int8`         | NOT NULL             | **Срок окончания действия.** Unix Timestamp (UTC). После наступления момента ключ считается недействительным.                              |
| `last_used_at`    | `int8`         | NULL                 | **Последнее успешное использование** для отображения в UI и аналитики.                                                                     |
| `revoked_at`      | `int8`         | NULL                 | **Момент отзыва.** Если не `NULL`, ключ недействителен независимо от `expires_at`.                                                         |
| `created_at`      | `int8`         | NOT NULL             | **Создание записи.** Unix Timestamp (UTC).                                                                                                 |
| `updated_at`      | `int8`         | NOT NULL             | **Обновление** (отзыв, продление, изменение метаданных при необходимости). Unix Timestamp (UTC).                                           |

*Рекомендуемые индексы:*

1. Уникальный индекс по `id` (PK).
2. Индекс по `global_steos_id` для выборки «все ключи пользователя» (`ListPersonalAccessTokens`).
3. Частичный индекс по `expires_at` / `revoked_at` для фоновой очистки и отчётов (по политике эксплуатации).

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **STEOS ID** | **Владелец.** Поле `global_steos_id` связывает ключ с глобальным субъектом; отзыв аккаунта на стороне IdP может инициировать массовый отзыв PAT (политика продукта). |
| **Авторизованная сессия**<br>(`authorized_sessions`) | **Логическая связь по субъекту.** Создание и отзыв PAT в UI выполняются в контексте залогиненного пользователя; сама сессия и PAT не связаны FK: PAT может существовать без активной браузерной сессии. |
| **Журнал локального доступа**<br>(`access_audit_logs`) | **Аудит.** События `PAT_CREATED`, `PAT_REVOKED`, `PAT_USED` (если включено) фиксируются для расследований. |
| **Workspace Service** | **Политики периметра.** Ограничения Geo/IP для Workspace не хранятся в `api_keys`; при доступе к ресурсам Workspace Auth проверяет политики так же, как для пользовательского контекста, если это предусмотрено маршрутом. |

## 4. Жизненный цикл и алгоритм работы

1. **Создание:** пользователь вызывает `CreatePersonalAccessToken` / `POST /access/pat`. Сервис генерирует секрет `stp_…`, вычисляет `secret_hash`, сохраняет строку в `api_keys`, возвращает **полный токен один раз** в теле ответа.
2. **Использование:** клиент передаёт токен на Gateway; Auth находит запись по префиксу/id или по lookup-таблице (если введён), проверяет хэш, `expires_at`, `revoked_at`, scopes, при успехе обновляет `last_used_at`.
3. **Отзыв:** пользователь или администратор вызывает отзыв по `id`; устанавливается `revoked_at` (или `is_active = false` — по единой конвенции схемы БД). Кэш записи инвалидируется.
4. **Истечение:** по наступлении `expires_at` проверки отклоняют ключ; фоновые задачи могут архивировать или удалять просроченные строки согласно политике хранения.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Хранение только хэша** | Утечка БД не раскрывает действующие токены; атакующий не может восстановить `stp_…` из `secret_hash` при корректных параметрах KDF. |
| **Один раз показать секрет** | Снижает поверхность хранения секрета на стороне сервера и дисциплинирует клиента сохранить ключ в secret store. |
| **Scopes как граница доверия** | Каждый вызов API, требующий scope, сопоставляется с массивом `scopes`; отсутствие scope даёт `403` без раскрытия внутренних деталей. |
| **Независимость от Phantom Cookie** | PAT не подменяет сессию браузера: это отдельный канал аутентификации, что упрощает модель угроз для автоматизации. |
