# Введение

Данный документ описывает структуры данных (DTO), применяемые при аутентификации пользователя и взаимодействии по протоколу OIDC (OpenID Connect) с внешним поставщиком идентификации (STEOS ID Global Identity Provider). 

Эти объекты инкапсулируют процессы обмена авторизационных кодов на токены, генерации URL для перенаправления (Authorization Endpoint), обратных вызовов (Callbacks), настройки MFA (многофакторной аутентификации) и реализации механизма Back-Channel Logout. Использование этих DTO позволяет скрыть сложность протокола OAuth2.0/OIDC от клиентского приложения.

**Трассировка SR-AUTH-xx:** для **локального Step-up MFA** после установления сессии (`POST /auth/mfa/challenge`, `POST /auth/mfa/verify`) действует **SR-AUTH-AC-02** — тот же код, что в REST ([01 - Аутентификация и OIDC (REST)](../REST%20API/01%20-%20Аутентификация%20и%20OIDC.md)) и gRPC (`StartStepUpMfaChallenge`, `VerifyStepUpMfa` в [06 - gRPC Access Control](../gRPC/06%20-%20Управление%20доступом,%20PAT%20и%20политики%20Workspace%20(Access%20Control).md)). Источник истины по смыслу — [[01 - Функциональная спецификация/Возможности сервиса/05 - Локальная Авторизация и Политики Доступа - Access Control#SR-AUTH-AC-02: Step-Up MFA для высокорисковых действий]]. DTO `MfaChallengeDto` и `MfaVerifyRequestDto` могут также участвовать во **флоу входа** (ответ `MFA_REQUIRED` и токен из `LoginResponseDto`); там привязка к требованиям задаётся сценарием OIDC/логина, а не SR-AUTH-AC-02.

# 1. Список DTO

В таблице ниже перечислены DTO, обеспечивающие интеграцию с Identity Provider.

| **Название DTO** | **Назначение** |
| :--- | :--- |
| **LoginRequestDto** | Запрос: Первичная аутентификация пользователя (логин/пароль) или начало OIDC Flow. |
| **LoginResponseDto** | Ответ: Содержит статус аутентификации (успех, редирект на 2FA или OIDC). |
| **OidcAuthRequestDto** | Запрос: Входные параметры (provider, redirect_uri) для инициализации Authorization Code Flow. |
| **OidcAuthResponseDto** | Ответ: Сгенерированный URL для редиректа пользователя на форму входа STEOS ID. |
| **OidcCallbackRequestDto** | Запрос: Callback от STEOS ID с параметром `code` и опциональным `state`. |
| **LogoutRequestDto** | Запрос: Стандартный выход пользователя (инвалидация Phantom Token и OIDC токенов). |
| **BackchannelLogoutRequestDto** | Запрос: Системный вебхук от STEOS ID на глобальную инвалидацию всех сессий пользователя (RFC 8417). |
| **MfaChallengeDto** | Ответ: Метаданные (например, замаскированный номер телефона или email) для отправки OTP/Push. |
| **MfaVerifyRequestDto** | Запрос: Пользователь вводит полученный одноразовый код (OTP) или подтверждает Push. |
| **TokenRefreshRequestDto** | Запрос: (Устарело/Внутреннее) Ручной запрос на обновление токенов. Чаще всего заменяется механизмом `KeepAliveRequestDto` и Silent Refresh. |
| **OidcFlowStateDto** | Внутренний объект: Структура, хранимая в Redis во время флоу логина (state, nonce, code_verifier, redirect_url). |
| **TokenExchangeRequestDto** | Запрос: Внутренняя структура (S2S) для обмена authorization code на токены у провайдера. |
| **TokenExchangeResponseDto** | Ответ: Структура, возвращаемая от STEOS ID (содержит access_token, id_token, refresh_token). |
| **TokenIntrospectionResponseDto** | Ответ: S2S структура ответа от эндпоинта валидации токенов (если не используется in-memory проверка). |
| **JwksCacheDto** | Ответ: Внутренняя структура для in-memory хранения и десериализации публичных ключей RSA (JWKS). |
| **GlobalLogoutEventDto** | Ответ (Событие): Структура сообщения от RabbitMQ для мгновенного Back-Channel Logout (блокировка/выход). |

# DTO: LoginRequestDto

## Контекст и назначение

Объект используется для первичной аутентификации в случаях, когда Платформа поддерживает вход не только через внешний OIDC (STEOS ID), но и через локальную форму (например, для системных администраторов, сервисных учетных записей или fallback-сценариев).

**Назначение:** Запрос (Команда на авторизацию).
**Реализация сущности:** N/A (Аутентификация).

## Структура данных

Классическая структура логин-пароля с опциональными метаданными устройства.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `username` | `string` | Логин, email или номер телефона. |
| `password` | `string` | Пароль пользователя (в открытом виде, передается только по TLS). |
| `deviceFingerprint` | `string` | Аппаратный отпечаток устройства для антифрода и привязки сессии. |

## Пример работы (JSON)

Пример запроса на локальный логин администратора.

```json
{
  "username": "admin@platform.steos.io",
  "password": "SuperSecretPassword123!",
  "deviceFingerprint": "hash_8f7d6c_win_chrome"
}
```

# DTO: LoginResponseDto

## Контекст и назначение

Ответ на попытку локальной авторизации или завершения OIDC Callback. Если аутентификация прошла успешно, DTO возвращает базовые данные пользователя. Если требуется второй фактор — возвращается статус, требующий перехода на форму 2FA. *Важно: сам Phantom Token (Cookie) устанавливается сервером в заголовках `Set-Cookie`, а не возвращается в JSON.*

**Назначение:** Ответ (Статус авторизации).
**Реализация сущности:** N/A (Событие).

## Структура данных

Включает статус, базовые данные и флаги требований.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `status` | `string` | Статус попытки (`SUCCESS`, `MFA_REQUIRED`, `LOCKED_OUT`). |
| `userId` | `uuid` | Глобальный ID пользователя (если `status = SUCCESS`). |
| `requiresMfa` | `boolean` | Флаг, указывающий на необходимость прохождения 2FA (дублирует логику статуса). |
| `mfaToken` | `string` | Временный токен для прохождения 2FA (если `requiresMfa = true`). |

## Пример работы (JSON)

Пример успешной авторизации без MFA.

```json
{
  "status": "SUCCESS",
  "userId": "user-uuid-1111-2222-3333",
  "requiresMfa": false,
  "mfaToken": null
}
```

# DTO: OidcAuthRequestDto

## Контекст и назначение

Этот запрос отправляется фронтендом, когда пользователь нажимает кнопку "Войти через STEOS ID". Auth Service должен принять параметры, сгенерировать PKCE `code_verifier` (сохранив его в локальном Redis) и вернуть URL для редиректа с `code_challenge`.

**Назначение:** Запрос (Инициализация OIDC Flow).
**Реализация сущности:** Формирование URL.

## Структура данных

Минимальный набор параметров, так как основная конфигурация (Client ID, Secret) хранится на бэкенде.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `provider` | `string` | Идентификатор провайдера (по умолчанию `steos-id`, но может быть Google/GitHub в будущем). |
| `returnUrl` | `string` | URL фронтенд-приложения (после успешного входа), валидируемый по белому списку. |

## Пример работы (JSON)

Запрос на генерацию ссылки для входа через глобальный STEOS ID.

```json
{
  "provider": "steos-id",
  "returnUrl": "https://app.steos.io/dashboard"
}
```

# DTO: OidcAuthResponseDto

## Контекст и назначение

Ответ, содержащий сгенерированный URL для перенаправления пользователя на страницу авторизации STEOS ID (или другого провайдера). Этот URL уже содержит все необходимые OAuth2-параметры (`client_id`, `response_type=code`, `scope`, `state`, `code_challenge`).

**Назначение:** Ответ (Редирект).
**Реализация сущности:** Сгенерированная строка.

## Структура данных

Содержит только сам URL.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `redirectUrl` | `string` | Сформированный URL для OIDC Authorization Endpoint. |

## Пример работы (JSON)

Пример ответа со сгенерированной ссылкой.

```json
{
  "redirectUrl": "https://id.steos.io/auth?client_id=app123&response_type=code&scope=openid+profile+email&state=xyz123&code_challenge=abc456&code_challenge_method=S256"
}
```

# DTO: OidcCallbackRequestDto

## Контекст и назначение

Когда пользователь успешно логинится в STEOS ID, он перенаправляется обратно на фронтенд с параметром `code`. Фронтенд берет этот код из URL и отправляет на бэкенд (Auth Service) через данный DTO, чтобы бэкенд обменял код на OIDC-токены (Access, ID, Refresh).

**Назначение:** Запрос (Завершение OIDC Flow).
**Реализация сущности:** Обмен Authorization Code.

## Структура данных

Содержит код авторизации и состояние для защиты от CSRF.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `code` | `string` | Authorization Code, полученный от провайдера. |
| `state` | `string` | Значение State, отправленное ранее в `OidcAuthResponseDto` (защита CSRF). |

## Пример работы (JSON)

Запрос от фронтенда на обмен кода.

```json
{
  "code": "SplxlOBeZQQYbYS6WxSbIA",
  "state": "xyz123"
}
```

# DTO: LogoutRequestDto

## Контекст и назначение

Инициируется клиентом для полного выхода из системы (Log Out). В отличие от `RevokeSessionRequestDto`, который используется для принудительного отзыва других сессий, данный DTO используется для штатного завершения *текущей* сессии. Сервер удаляет сессию в Redis, аннулирует OIDC Refresh Token в STEOS ID и очищает куку (Phantom Token).

**Назначение:** Запрос (Логаут).
**Реализация сущности:** Уничтожение сессии.

## Структура данных

Обычно пустая (вся нужная информация берется из куки), но может содержать опциональные флаги, например, "выйти со всех устройств".

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `globalLogout` | `boolean` | Если true — инициирует выход на всех устройствах (инвалидирует все сессии данного пользователя). По умолчанию false. |

## Пример работы (JSON)

Запрос на штатный выход.

```json
{
  "globalLogout": false
}
```

# DTO: BackchannelLogoutRequestDto

## Контекст и назначение

Этот DTO не инициируется фронтендом. Это формат входящего вебхука (POST-запроса) напрямую от STEOS ID (Global Identity Provider) к микросервису авторизации платформы. Он используется для реализации RFC 8417 (OIDC Back-Channel Logout), когда пользователь разлогинился в STEOS ID (или сменил пароль), и STEOS ID асинхронно уведомляет все подключенные сервисы о необходимости принудительно завершить локальные сессии этого пользователя.

**Назначение:** Запрос (Системный вебхук).
**Реализация сущности:** Инвалидация по `sub` или `sid`.

## Структура данных

Представляет собой JWT-токен (Logout Token), подписанный провайдером. Для документирования DTO описывается структура распарсенного payload'а.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `iss` | `string` | Issuer (например, "https://id.steos.io"). |
| `sub` | `string` | Глобальный ID пользователя (Subject), сессии которого нужно убить. |
| `aud` | `string` | Audience (Client ID платформы). |
| `iat` | `integer` | Время выдачи токена (Unix timestamp). |
| `jti` | `string` | Уникальный идентификатор токена (защита от replay-атак). |
| `events` | `object` | Объект с ключом `http://schemas.openid.net/event/backchannel-logout`, содержащий пустой объект (сигнатура события). |
| `sid` | `string` | Идентификатор конкретной сессии в STEOS ID (если нужно убить не все, а одну). Опционально. |

## Пример работы (JSON)

Пример полезной нагрузки Logout Token'а.

```json
{
  "iss": "https://id.steos.io",
  "sub": "user-uuid-1111-2222-3333",
  "aud": "platform-client-app123",
  "iat": 1678901234,
  "jti": "random-jti-uuid",
  "events": {
    "http://schemas.openid.net/event/backchannel-logout": {}
  },
  "sid": "session-uuid-in-idp-5555"
}
```

# DTO: MfaChallengeDto

## Контекст и назначение

Возвращается клиенту в процессе авторизации, если `requiresMfa = true`. Содержит метаданные для отображения UI подтверждения: куда был отправлен код (частично скрытый номер телефона, email или указание на использование Authenticator App).

**Трассировка:** при **Step-up MFA** в активной сессии (REST `POST /auth/mfa/challenge`) — **SR-AUTH-AC-02**; ответ BFF может быть согласован с полями ниже или обёрнут в `SuccessResponseDto` с идентификатором транзакции (см. REST [01 - Аутентификация и OIDC](../REST%20API/01%20-%20Аутентификация%20и%20OIDC.md)).

**Назначение:** Ответ (Информация о 2FA).
**Реализация сущности:** N/A (Состояние UI).

## Структура данных

Включает метод MFA и маскированный контакт.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `mfaMethod` | `string` | Тип требуемого фактора (`SMS`, `EMAIL`, `TOTP`, `PUSH`). |
| `maskedContact` | `string` | Замаскированный контакт (например, `+7 (***) ***-**-12` или `a**n@gmail.com`). |
| `challengeId` | `uuid` | Идентификатор попытки подтверждения (для предотвращения брутфорса). |

## Пример работы (JSON)

Пример ответа с требованием подтвердить вход через SMS.

```json
{
  "mfaMethod": "SMS",
  "maskedContact": "+7 (999) ***-**-12",
  "challengeId": "challenge-uuid-8888-9999"
}
```

# DTO: MfaVerifyRequestDto

## Контекст и назначение

Используется фронтендом для отправки введенного пользователем кода подтверждения (OTP) или статуса пуш-уведомления обратно на Auth Service для окончательного завершения процесса логина.

**Трассировка:** при **Step-up MFA** (`POST /auth/mfa/verify`) — **SR-AUTH-AC-02**; вместо `mfaToken` логина передаётся идентификатор MFA-транзакции из шага challenge (в документации gRPC — `mfa_transaction_id` в `VerifyStepUpMfaRequest`). При **входе с MFA** используется `mfaToken` из `LoginResponseDto` — тот же тип DTO, другой контекст требования.

**Назначение:** Запрос (Подтверждение 2FA).
**Реализация сущности:** Финализация сессии.

## Структура данных

Содержит код и временный токен из предыдущего шага (логин) либо идентификатор транзакции Step-up (см. **Трассировка**).

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `mfaToken` | `string` | Временный токен, полученный в `LoginResponseDto` (**флоу входа**). Для **SR-AUTH-AC-02** Step-up может не использоваться; вместо него — идентификатор транзакции challenge (согласовать имя поля с BFF/proto). |
| `code` | `string` | Введенный пользователем OTP код (например, "123456") или токен TOTP. |

## Пример работы (JSON)

Запрос на проверку введенного SMS-кода.

```json
{
  "mfaToken": "temp_mfa_token_abcd1234",
  "code": "583921"
}
```

# DTO: TokenRefreshRequestDto

## Контекст и назначение

Данный DTO используется редко, так как в архитектуре с Phantom Token (Cookie-based) обновление токенов (Silent Refresh) происходит неявно на сервере при обработке запросов `KeepAliveRequestDto` или обычных бизнес-запросов, если до истечения токена осталось мало времени. Тем не менее, он может использоваться для явного (ручного) обновления сессии в некоторых SPA/Mobile сценариях, где Cookie-механизм недоступен.

**Назначение:** Запрос (Ручное обновление).
**Реализация сущности:** Продление OIDC-токенов.

## Структура данных

Обычно пустая (читается кука), либо передается Refresh Token явно (для мобильных клиентов без куки).

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `refreshToken` | `string` | OIDC Refresh Token (передается **только** если клиент не поддерживает HttpOnly Cookies, иначе передавать не нужно). |

## Пример работы (JSON)

Запрос на явное обновление (для Mobile).

```json
{
  "refreshToken": "rt_long_random_string_from_idp..."
}
```

# DTO: OidcFlowStateDto

## Контекст и назначение

Этот DTO описывает структуру данных, которая временно (на 5-10 минут) сохраняется в Redis на стороне Authorization Service при старте OIDC Authorization Code Flow. Он необходим для защиты от CSRF-атак и реализации механизма PKCE (Proof Key for Code Exchange), связывая оригинальный запрос клиента (его `returnUrl`) со сгенерированными криптографическими параметрами.

**Назначение:** Внутренний объект (Состояние).
**Реализация сущности:** Запись в Redis с ключом `oidc:state:{state}`.

## Структура данных

Включает параметры безопасности OIDC и URL для возврата пользователя после успешного входа.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `state` | `string` | Уникальный токен состояния, отправленный провайдеру (ключ в Redis). |
| `nonce` | `string` | Случайная строка для привязки ID Token к сессии клиента (защита от replay-атак). |
| `codeVerifier` | `string` | PKCE verifier, соответствующий отправленному `code_challenge`. |
| `returnUrl` | `string` | Оригинальный URL фронтенда, куда нужно вернуть пользователя после обмена токенов. |
| `provider` | `string` | Идентификатор провайдера (напр., `steos-id`), к которому был инициирован запрос. |

## Пример работы (JSON)

Пример сохраненного в Redis состояния логина.

```json
{
  "state": "state_abc123xyz890",
  "nonce": "nonce_987654321",
  "codeVerifier": "vK_1z2x3c4v5b6n7m8M9...",
  "returnUrl": "https://app.steos.io/dashboard",
  "provider": "steos-id"
}
```

# DTO: TokenExchangeRequestDto

## Контекст и назначение

Это внутренний (Server-to-Server) DTO, используемый микросервисом авторизации для отправки HTTP POST запроса к Token Endpoint внешнего Identity Provider (STEOS ID) с целью обмена полученного `code` на токены.

**Назначение:** Запрос (Внутренняя интеграция).
**Реализация сущности:** Формирование `application/x-www-form-urlencoded` или JSON запроса к IDP.

## Структура данных

Включает параметры, требуемые спецификацией OAuth 2.0 / OIDC для Grant Type `authorization_code`.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |

# DTO: TokenExchangeResponseDto

## Контекст и назначение

Этот DTO описывает ответ, получаемый от STEOS ID (Token Endpoint) в результате успешного обмена `code` (через `TokenExchangeRequestDto`). Он содержит OIDC токены, которые Authorization Service затем валидирует, распаковывает (ID Token) и использует для создания локальной сессии пользователя, после чего сами токены (особенно Refresh) безопасно сохраняются (напр., в Redis или шифрованном хранилище), а клиенту выдается только Phantom Token (Cookie).

**Назначение:** Ответ (Внутренняя интеграция).
**Реализация сущности:** Парсинг ответа от IDP.

## Структура данных

Стандартный ответ OAuth 2.0 Token Endpoint.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `accessToken` | `string` | JWT токен для доступа к API провайдера (если требуется). |
| `tokenType` | `string` | Тип токена (обычно `Bearer`). |
| `expiresIn` | `integer` | Время жизни Access Token в секундах. |
| `refreshToken` | `string` | Долгоживущий токен для обновления сессии (Silent Refresh). |
| `idToken` | `string` | OIDC JWT токен с информацией о пользователе (аутентификация). |

## Пример работы (JSON)

Ответ от STEOS ID с токенами.

```json
{
  "accessToken": "eyJhbGciOiJSUzI1NiI...",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "refreshToken": "rt_long_random_string...",
  "idToken": "eyJhbGciOiJSUzI1NiI..."
}
```

# DTO: TokenIntrospectionResponseDto

## Контекст и назначение

Этот DTO используется, если микросервис интеграции или сам Authorization Service решает не валидировать токен локально (через JWKS), а отправить его на валидацию обратно в STEOS ID через Introspection Endpoint (RFC 7662). В архитектуре Платформы обычно предпочтительна in-memory валидация (через JWKS), но Introspection может использоваться для мгновенной проверки статуса отзыва (Revoke) токена на стороне провайдера.

**Назначение:** Ответ (S2S Валидация).
**Реализация сущности:** Парсинг ответа от IDP.

## Структура данных

Стандартный ответ Introspection Endpoint.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `active` | `boolean` | Является ли токен активным (не протух, не отозван). Основной флаг. |
| `scope` | `string` | Список разрешенных скоупов (через пробел). |
| `clientId` | `string` | ID клиента, которому был выдан токен. |
| `sub` | `string` | Идентификатор пользователя. |
| `exp` | `integer` | Время истечения (Unix timestamp). |

## Пример работы (JSON)

Успешный ответ валидации.

```json
{
  "active": true,
  "scope": "openid profile email offline_access",
  "clientId": "platform-client-app123",
  "sub": "user-uuid-1111-2222-3333",
  "exp": 1678904834
}
```

# DTO: JwksCacheDto

## Контекст и назначение

Этот DTO представляет собой внутреннюю структуру, используемую Authorization Service для In-Memory кэширования публичных ключей (JWKS - JSON Web Key Set), полученных от STEOS ID. Кэширование JWKS позволяет микросервису локально, без сетевых запросов, валидировать подписи ID Token и Access Token, что критически важно для производительности при высоких нагрузках (Zero Trust Архитектура).

**Назначение:** Ответ (Внутренняя структура кэша).
**Реализация сущности:** Кэш в памяти (In-Memory) или в Redis.

## Структура данных

Обертка над массивом ключей RSA.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `keys` | `array<object>` | Массив объектов JWK (содержат `kid`, `kty`, `alg`, `n`, `e`, `use`). |
| `cachedAt` | `datetime` | Время помещения в кэш (для управления фоновым обновлением). |

## Пример работы (JSON)

Пример кэшированного набора ключей.

```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "key-id-2026-03",
      "alg": "RS256",
      "n": "v1x2y3z...",
      "e": "AQAB"
    }
  ],
  "cachedAt": "2026-03-25T00:00:00Z"
}
```

# DTO: GlobalLogoutEventDto

## Контекст и назначение

Этот DTO описывает структуру сообщения (события), которое публикуется в брокер сообщений RabbitMQ самим Authorization Service (или принимается им, если инициировано другим сервисом) после получения `BackchannelLogoutRequestDto`. Цель этого события — асинхронно уведомить все заинтересованные микросервисы (Integration, Workspace, Task) о том, что пользователь был глобально разлогинен (или заблокирован), и они должны сбросить свои локальные кэши прав для данного `userId`.

**Назначение:** Событие (Асинхронное уведомление).
**Реализация сущности:** Сообщение в RabbitMQ.

## Структура данных

Включает идентификатор пользователя и метаданные события.

| **Имя поля (JSON)** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `eventId` | `uuid` | Уникальный ID события (для идемпотентности). |
| `timestamp` | `datetime` | Время генерации события. |
| `userId` | `uuid` | Глобальный ID пользователя, которого необходимо разлогинить. |
| `reason` | `string` | Причина логаута (напр., `GLOBAL_LOGOUT`, `ACCOUNT_DISABLED`, `PASSWORD_CHANGED`). |

## Пример работы (JSON)

Пример события глобального логаута.

```json
{
  "eventId": "evt-uuid-4444-5555",
  "timestamp": "2026-03-25T15:00:00Z",
  "userId": "user-uuid-1111-2222-3333",
  "reason": "PASSWORD_CHANGED"
}
```
