# Введение

Этот раздел описывает механизмы принятия решений о доступе поверх уже установленной локальной сессии. Если `Session Management` отвечает на вопрос "кто вошел в систему", то **Access Control** отвечает на вопрос "что именно этому субъекту разрешено делать здесь и сейчас".

В рамках данного блока Authorization Service выступает как централизованный Policy Decision Point: он проверяет права, запускает step-up MFA для критичных действий, управляет персональными API-ключами и хранит корпоративные Geo/IP-политики конкретных Workspaces.

## Возможности данного раздела

| Код               | Название и Описание                                                                                                                                       |
| :---------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SR-AUTH-AC-01** | **Гранулярная проверка прав (Permission Check):** Централизованная ABAC/RBAC-проверка права пользователя или сервиса на конкретное действие над ресурсом. |
| **SR-AUTH-AC-02** | **Step-Up MFA для высокорисковых действий:** Инициация и проверка дополнительного фактора перед критичными операциями внутри активной сессии.             |
| **SR-AUTH-AC-04** | **Персональные API-ключи (PAT):** Выпуск, просмотр и отзыв персональных ключей доступа пользователя для CLI, автоматизации и интеграций.                  |
| **SR-AUTH-AC-05** | **Geo-Policies и IP Whitelisting Workspace:** Настройка допустимых регионов, IP-адресов и сетей для входа в конкретное корпоративное пространство.        |
|                   |                                                                                                                                                           |

# Детальная спецификация требований

## SR-AUTH-AC-01: Гранулярная проверка прав (Permission Check)

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Централизация политик** | Бизнес-сервисы не дублируют у себя полный движок RBAC/ABAC, а делегируют решение Auth Service. |
| **Контекстность** | При расчете решения учитываются `workspace`, роли, ownership, feature flags и возможные ограничения сессии. |
| **Высокая скорость** | Часто запрашиваемые решения могут кэшироваться, но итоговая логика остается канонически закрепленной за Auth Service. |

### 2. Высокоуровневое описание

Представим **центрального диспетчера пропусков в офисном комплексе**.

1. Пользователь уже вошел в здание, но перед каждой чувствительной дверью нужно понять, можно ли его туда пустить.
2. Вместо того чтобы каждая дверь сама хранила все правила, она спрашивает центрального диспетчера.
3. Диспетчер смотрит на роль человека, его контекст и правила доступа.
4. После этого он выдает короткий ответ: разрешить действие или запретить.

### 3. Примеры взаимодействия (логические сценарии)

#### Разрешенное действие (Happy Path)

1. SPA хочет понять, показывать ли пользователю кнопку "Удалить проект".
2. UI или BFF вызывает проверку права `can_delete_project`.
3. Auth Service вычисляет решение с учетом роли, workspace и ownership.
4. Возвращается положительный результат, и действие разрешается.

## SR-AUTH-AC-02: Step-Up MFA для высокорисковых действий

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Повторное подтверждение личности** | MFA запускается не на логин в целом, а на конкретное высокорисковое действие или аномальный контекст. |
| **Короткоживущий scope-результат** | Успешная MFA-проверка выдает временное право на завершение именно этого класса операции. |
| **Поддержка нескольких каналов** | Возможны TOTP, push, device approval и другие методы, поддерживаемые платформой. |

### 2. Высокоуровневое описание

Представим **второй ключ от сейфа, который нужен только для особенно ценных операций**.

1. Обычная работа внутри аккаунта продолжается по стандартной сессии.
2. Как только пользователь хочет сделать опасное действие, одного факта логина уже недостаточно.
3. Система просит дополнительное подтверждение через TOTP, push или другой фактор.
4. После успеха на короткое время разрешается завершить именно это критичное действие.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешный Step-Up MFA (Happy Path)

1. Пользователь инициирует удаление проекта или смену биллинга.
2. Auth Service запускает challenge второго фактора.
3. Пользователь успешно подтверждает действие.
4. Сервис выдает временный scope и критичная операция завершается.

## SR-AUTH-AC-04: Персональные API-ключи (PAT)

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Однократный показ секрета** | Полное значение PAT показывается только в момент создания. |
| **Управляемый lifecycle** | Пользователь может перечислять, метить и отзывать свои активные ключи. |
| **Изоляция от Phantom Token** | PAT не заменяет браузерную сессию, а представляет отдельный канал аутентификации для интеграционных сценариев. |

### 2. Высокоуровневое описание

Представим **служебный пропуск для робота-курьера**, который работает от имени владельца, но отдельно от его личного присутствия в здании.

1. Пользователь хочет автоматизировать работу через CLI или CI/CD.
2. Вместо передачи своей сессии он выпускает отдельный персональный ключ.
3. Этот ключ живет по собственным правилам и может быть в любой момент отозван.
4. Автоматизация работает по PAT, не завися от браузерной Cookie пользователя.

### 3. Примеры взаимодействия (логические сценарии)

#### Выпуск нового PAT (Happy Path)

1. Пользователь открывает раздел API-ключей и создает новый PAT.
2. Auth Service генерирует секрет, сохраняет его хэш и показывает полное значение один раз.
3. Пользователь использует PAT в CLI или CI.
4. Ключ валидируется как отдельный канал доступа.

## SR-AUTH-AC-05: Geo-Policies и IP Whitelisting Workspace

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Политики на уровне Workspace** | Настройки применяются не ко всей платформе сразу, а к конкретному корпоративному пространству. |
| **Проверка до входа в контекст** | Ограничения учитываются до того, как пользователь окончательно получает доступ к защищенному Workspace. |
| **Прозрачность для владельца** | Owner/Admin может просматривать и менять политики своего пространства в управляемом интерфейсе. |

### 2. Высокоуровневое описание

Представим **корпоративный офис, куда можно войти только из определенных стран или через белый список сетей компании**.

1. Каждый Workspace может иметь собственные правила входа.
2. Перед окончательным допуском пользователя в контекст сервис проверяет его IP и регион.
3. Если источник соответствует политике, доступ продолжается.
4. Если нет, вход в защищенное пространство блокируется еще на контуре авторизации.

### 3. Примеры взаимодействия (логические сценарии)

#### Вход из разрешенной сети (Happy Path)

1. Пользователь входит в корпоративный Workspace.
2. Auth Service проверяет IP и страну по политике Workspace.
3. Источник соответствует whitelist/гео-ограничениям.
4. Доступ в Workspace разрешается.
