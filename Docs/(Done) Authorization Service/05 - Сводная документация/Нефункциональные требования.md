# Введение

Настоящий документ определяет нефункциональные требования к микросервису **«Сервис Авторизации» (Authorization Service)** — центральному Gatekeeper-у платформы, управляющему сессиями пользователей и защищающему внутренний периметр.

Если функциональные требования отвечают на вопрос «что система делает» (например, «создать Phantom Token»), то нефункциональные требования определяют, **«как система должна это делать»** (например, «создать и провалидировать токен со средним временем отклика менее 2 мс, обеспечивая при этом полную защиту от XSS»). Они касаются характеристик качества, производительности, безопасности, надежности и других аспектов, влияющих на пользовательский опыт, масштабируемость и устойчивость решения.

# 1. Назначение документа

## 1.1 Цель документа

Цель данного документа — зафиксировать ожидания заинтересованных сторон по ключевым параметрам качества системы, чтобы обеспечить:

*   Соответствие строгим бизнес-требованиям архитектуры Zero Trust;
*   Поддержку 100% входящего HTTP-трафика платформы (все запросы проходят через Auth Service);
*   Бескомпромиссную безопасность пользовательских сессий и защиту от угона (Session Hijacking);
*   Сверхвысокую производительность (Latency < 2ms), чтобы аутентификация не замедляла бизнес-операции;
*   Надежность и отказоустойчивость сервиса (Graceful Degradation при падении STEOS ID);
*   Прозрачность для процессов тестирования, развертывания, мониторинга и эксплуатации.

Документ предназначен для использования всеми участниками проекта: архитекторами, разработчиками, тестировщиками, DevOps-инженерами и службой эксплуатации.

## 1.2 Область применения

Требования распространяются на следующие компоненты системы, составляющие микросервис Authorization Service:

| Компонент системы | Область ответственности |
| :--- | :--- |
| **Бэкенд-сервис (Auth Service)** | Основная логика: обработка OIDC-флоу, снятие Cookie, валидация Fingerprint'ов, инъекция контекстных заголовков, прослушивание RabbitMQ. |
| **API Gateway Layer** | Слой перехвата входящего трафика (Middleware), маршрутизация запросов к внутренним сервисам (Downstream). |
| **Оперативный Кэш (Redis)** | Сверхбыстрое in-memory хранилище активных сессий, One-Time билетов и rate-limit счетчиков. |
| **СХД (PostgreSQL)** | Долговременный источник истины (Source of Truth) для сессий, контекстов и неизменяемый журнал локального аудита (WORM). |

## 1.3 Определения и сокращения

| Термин | Описание |
| :--- | :--- |
| **API-шлюз (API Gateway)** | В контексте данного документа — встроенный в Auth Service компонент перехвата трафика и маршрутизации во внутреннюю сеть. |
| **Phantom Token** | Архитектурный паттерн безопасности. Использование случайного UUID (в `HttpOnly` Cookie) вместо читаемого JWT на фронтенде. |
| **Задержка (Latency)** | Время, необходимое для выполнения одного запроса от его отправки до получения ответа (в миллисекундах). |
| **AUTH (Authorization Service)** | Данный микросервис («Сервис Авторизации»). |
| **NFR (Non-Functional Requirement)** | Нефункциональное требование — требование к качеству системы, а не к её функциональности. |
| **p99 / p95 (99-й/95-й перцентиль)** | Метрика производительности, означающая, что 99% / 95% запросов выполняются быстрее указанного времени. |
| **RPO (Recovery Point Objective)** | Максимально допустимый объем потери данных (например, логов аудита) в случае сбоя, измеряемый во времени. |
| **RPS (Requests Per Second)** | Запросы в секунду. Метрика, измеряющая входящую нагрузку на сервис. |
| **RTO (Recovery Time Objective)** | Максимально допустимое время простоя сервиса после полного сбоя. |
| **SLA (Service Level Agreement)** | Формальный контракт, определяющий гарантированный уровень доступности сервиса (uptime). |
| **Zero Trust** | Архитектурный подход. Внутренние сервисы не доверяют сети, а доверяют только заголовкам, проставленным проверенным Auth Service. |

# 2. Категории нефункциональных требований

## 2.1 Производительность (Performance)

Так как сервис перехватывает и валидирует *каждый* HTTP-запрос (превращая Phantom Token в контекстные заголовки `X-Workspace-Id` для внутренних сервисов), он обязан быть максимально быстрым. Любая задержка здесь умножается на все последующие вызовы.

| ID | Требование | Метрика | Приоритет |
| :--- | :--- | :--- | :--- |
| **NFR-AUTH-001** | **Сверхнизкая задержка валидации:** Время ответа (p99) на валидацию `HttpOnly` Cookie, чтение стейта из Redis и инъекцию заголовков для пересылки запроса дальше (Downstream) не должно превышать **2 мс**. | p99 latency < 2 ms | Высокий |
| **NFR-AUTH-002** | **Пропускная способность Gateway:** Сервис должен выдерживать пиковую нагрузку всех входящих клиентских запросов платформы не менее **15,000 RPS**. | ≥ 15,000 RPS | Высокий |
| **NFR-AUTH-003** | **Запрет синхронных БД-запросов:** Синхронные обращения к реляционной БД (PostgreSQL) при каждом бизнес-запросе **строго запрещены**. Данные должны браться исключительно из In-Memory кэша (Redis). | 0 Sync DB queries | Высокий |
| **NFR-AUTH-004** | **Задержка OIDC-логина:** Полный цикл OIDC (обмен Authorization Code на JWT, валидация подписи JWKS, запись в БД и Redis) не должен превышать **200 мс** (без учета задержки сети до глобального STEOS ID). | p99 latency < 200 ms | Средний |

## 2.2 Надёжность и Доступность (Reliability & Availability)

Отказ Authorization Service означает полную недоступность платформы для всех пользователей.

| ID | Требование | Метрика | Приоритет |
| :--- | :--- | :--- | :--- |
| **NFR-AUTH-010** | **Доступность сервиса (Uptime):** Сервис должен обеспечивать доступность на уровне не менее **99.99%** в месяц. | ≥ 99.99% uptime | Высокий |
| **NFR-AUTH-011** | **Отказ STEOS ID (Graceful Degradation):** Если глобальный STEOS ID (IdP) временно недоступен по сети, локальная платформа **не должна останавливаться**. Пользователи с активными (не истекшими) сессиями в Redis Auth Service должны продолжать работу. | Zero Downtime Auth | Высокий |
| **NFR-AUTH-012** | **Отказоустойчивость брокера (RabbitMQ):** Если RabbitMQ недоступен, сервис должен продолжать работу, накапливая события локально в памяти, и применять Exponential Backoff для переподключения без "паники" (OOM/Panic). | Exponential Backoff | Высокий |
| **NFR-AUTH-013** | **Целостность логов (RPO/RTO):** Потеря данных журнала локального аудита (`access_audit_logs`) при сбое БД не должна превышать **30 секунд (RPO)**. Время восстановления (RTO) — не более **15 минут**. | RPO ≤ 30s<br>RTO ≤ 15m | Высокий |

## 2.3 Безопасность (Security)

Authorization Service — главный щит платформы (Gatekeeper), реализующий концепцию Zero Trust.

| ID               | Требование                                                                                                                                                                                                                                                                                              | Метрика             | Приоритет |
| :--------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :------------------ | :-------- |
| **NFR-AUTH-020** | **Защищенные Cookie (HttpOnly):** Токен сессии (Phantom Token) обязан устанавливаться исключительно через заголовок `Set-Cookie` со строгими флагами: `HttpOnly`, `Secure`, и `SameSite=Lax/Strict`. Передача токена в JavaScript недопустима.                                                          | Strict Cookie Flags | Высокий   |
| **NFR-AUTH-021** | **Защита от Session Hijacking:** Привязанные к сессиям отпечатки браузеров (Fingerprint) и IP-адреса должны хэшироваться. Сравнение приходящего отпечатка с эталоном в сессии (при каждом запросе) должно происходить за константное время (Constant-Time Comparison).                                  | Constant-Time Hash  | Высокий   |
| **NFR-AUTH-022** | **Сетевая изоляция (Zero Trust):** Внутренние микросервисы (Tasks, CRM) должны принимать доверенные заголовки (`X-Workspace-Id`) **только** из внутренней подсети от Auth Service. Прямые вызовы из интернета с подделкой этих заголовков должны пресекаться (Header Stripping на уровне Auth Service). | Header Stripping    | Высокий   |
| **NFR-AUTH-023** | **Защита от перегрузки (Rate Limiting):** Встроенные механизмы Rate Limiting для защиты OIDC-эндпоинтов от DDoS и переполнения БД мусорными сессиями.                                                                                                                                                   | Active Rate Limiter | Высокий   |

## 2.4 Масштабируемость (Scalability)

Архитектура должна позволять линейно наращивать ресурсы при всплесках трафика (например, после email-рассылки).

| ID | Требование | Метрика | Приоритет |
| :--- | :--- | :--- | :--- |
| **NFR-AUTH-030** | **Полный Stateless:** Сам процесс (Pod) микросервиса должен быть полностью Stateless. Все сессии и контексты хранятся в Redis. | 100% Stateless Pods | Высокий |
| **NFR-AUTH-031** | **Автоматическое масштабирование (HPA):** При загрузке CPU > 60% оркестратор должен автоматически добавлять новые реплики сервиса (Scale Out) менее чем за **30 секунд**. | Auto-scaling < 30s | Высокий |
| **NFR-AUTH-032** | **Партицирование Аудита:** Таблица `access_audit_logs` должна быть изначально спроектирована с учетом партицирования (Table Partitioning по месяцам), так как она будет расти на гигабайты каждый день. | Table Partitioning | Средний |

## 2.5 Удобство использования и Документация (Usability)

| ID | Требование | Метрика | Приоритет |
| :--- | :--- | :--- | :--- |
| **NFR-AUTH-040** | **Документация API:** Все публичные и межсервисные API должны быть строго документированы через **OpenAPI 3.0** (REST) и **Protobuf** (gRPC). | OpenAPI/Proto | Высокий |
| **NFR-AUTH-041** | **Стандартизация ошибок:** API должен возвращать предсказуемые сообщения об ошибках в формате **ProblemDetails RFC 7807** (например, с явным указанием `local_ban_reason` для фронтенда). | RFC 7807 | Высокий |

## 2.6 Совместимость (Compatibility)

| ID | Требование | Метрика | Приоритет |
| :--- | :--- | :--- | :--- |
| **NFR-AUTH-050** | **OAuth 2.1 BCP:** OIDC-поток должен строго соответствовать стандарту "OAuth 2.0 Security Best Current Practice" (отказ от Implicit Flow, обязательное использование PKCE). | OAuth 2.1 BCP | Высокий |
| **NFR-AUTH-051** | **Формат JWKS:** Кэширование и парсинг публичных ключей должны поддерживать стандарт **RFC 7517** (JSON Web Key). | RFC 7517 | Высокий |

## 2.7 Поддерживаемость и Наблюдаемость (Maintainability & Observability)

| ID               | Требование                                                                                                                                                                                                                      | Метрика              | Приоритет |
| :--------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :------------------- | :-------- |
| **NFR-AUTH-070** | **Тестовое покрытие:** Код парсинга JWT, криптографической проверки подписей и механизмов имперсонации должен быть покрыт юнит-тестами на **95%**.                                                                              | Code coverage ≥ 95%  | Высокий   |
| **NFR-AUTH-071** | **Сквозная Трассировка (OpenTelemetry):** Будучи API Gateway, Auth Service **обязан** генерировать уникальный `trace_id` для каждого нового HTTP-запроса от браузера и пробрасывать его во все внутренние (Downstream) сервисы. | 100% Trace Injection | Высокий   |
| **NFR-AUTH-072** | **Бизнес-метрики (Prometheus):** Экспорт метрик: кол-во активных сессий в Redis, rate ошибок валидации Fingerprint (попытки угона), кол-во сессий, убитых по сигналу Back-Channel Logout из RabbitMQ.                           | Business Metrics     | Высокий   |
| **NFR-AUTH-073** | **Zero-Downtime Deployment:** Обновление Auth Service не должно приводить к разрыву активных сессий или недоступности API Gateway (стратегия Rolling Update / Blue-Green).                                                      | Zero-downtime        | Высокий   |

# 3. Приоритизация и контроль

Все нефункциональные требования разделены на три уровня приоритета:

| Приоритет | Описание |
| :--- | :--- |
| **Высокий** | Критично для базового функционирования, безопасности и надежности сервиса. Невыполнение этих требований (например, отказ от Redis или выдача JWT в браузер) полностью нарушает архитектуру Zero Trust и делает систему уязвимой. |
| **Средний** | Важно для обеспечения хорошей производительности в долгосрочной перспективе (например, партицирование БД). Допускается временное несоответствие на этапе MVP, но должно быть устранено до релиза. |
| **Низкий** | Желательно, но не обязательно на текущем этапе. Отложенные оптимизации. |

# 5. Источники требований

Каждое нефункциональное требование имеет свое бизнес- или архитектурное обоснование:

| Источник | Примеры |
| :--- | :--- |
| **SLA и договорные обязательства** | **NFR-AUTH-010 (99.99% uptime)**: Продиктовано тем, что Auth Service — это "бутылочное горлышко". Если он лежит, вся платформа (100% функций) недоступна клиентам. |
| **Индустриальные стандарты ИБ (IAM)** | **NFR-AUTH-020 (Phantom Token), NFR-AUTH-050 (OAuth 2.1)**: Использование классических JWT на фронтенде в SPA-приложениях признано устаревшим и небезопасным (угроза XSS). Переход на `HttpOnly` Cookie + Backend-BFF (Backend for Frontend) является стандартом де-факто для финтеха и энтерпрайза. |
| **Архитектура Zero Trust** | **NFR-AUTH-022 (Header Stripping)**: Внутренние сервисы платформы не должны тратить CPU на проверку криптографии. Они перекладывают эту обязанность на выделенный Edge-слой (Auth Service). |
| **Команда Эксплуатации (SRE)** | **NFR-AUTH-071 (Трассировка)**: Без сквозного `trace_id` расследовать жалобу клиента "У меня не открывается задача" в распределенной микросервисной среде невозможно. |
