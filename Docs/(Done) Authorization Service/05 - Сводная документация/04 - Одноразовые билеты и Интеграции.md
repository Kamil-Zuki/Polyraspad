# Введение

Данный документ описывает процессы и правила использования Redis для управления короткоживущими транзакционными состояниями. В эту группу входят: реализация паттерна "Эфемерные Одноразовые Билеты" (One-Time Tickets) для обхода ограничений браузеров на передачу заголовков Authorization (при загрузке файлов/подключении WSS), а также in-memory хранение криптографических параметров интеграции с глобальным провайдером (OIDC State/Nonce) и кэширование публичных OIDC-ключей.

# 1. Список операций Одноразовых билетов и Интеграций

Перечень механизмов, управляющих короткоживущими токенами и параметрами федерации.

| Метод (SR) | Описание операции |
| :--- | :--- |
| КАР-5 / SR-AUTH-SM-04 | Хранение и валидация Эфемерных Одноразовых Билетов (One-Time Tickets) для загрузки файлов/WSS. |

# Одноразовые Билеты (One-Time Tickets) (SR-AUTH-SM-04)

## Общая информация

Реализация паттерна КАР-5. Для того чтобы веб-клиент мог скачать файл или установить WebSocket-соединение (где браузер запрещает пробрасывать кастомные `Authorization` заголовки), клиент сначала синхронно запрашивает через API "одноразовый короткоживущий билет". Этот билет помещается в URL (Query String) и обменивается на сессию уже на стороне целевого сервиса, который валидирует билет через gRPC у Authorization Service. 

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:ticket:{ticket_id}`<br>где `{ticket_id}` = криптографически безопасная случайная строка (URL-safe, ~32 байта). |
| **DTO ответа** | Сериализованный `TicketPayload` (содержит `subjectId`, `workspaceId`, `targetResource`, `action`). |
| **TTL** | Экстремально короткий (от 10 до 60 секунд), чтобы минимизировать окно возможного перехвата (Interception Window). |

## Логика обработки запроса

*   **Запись (Генерация):** Клиент вызывает `POST /tickets/generate` с указанием целевого ресурса (например, `targetResource=wss://api/chat`). Сервис авторизации проверяет права клиента (Access Token), генерирует `ticket_id`, сериализует контекст пользователя и сохраняет в Redis `SETEX auth:ticket:{ticket_id} 30`. В БД этот билет НЕ сохраняется для скорости. Клиенту возвращается URL с `?ticket=...`.
*   **Чтение и Инвалидация (Обмен):** Целевой сервис (например, Chat Service) получает запрос на WSS-соединение и отправляет билет по gRPC `ValidateTicket(ticket_id)` в Authorization Service. 
    * Авторизация выполняет атомарную команду чтения с удалением: `GETDEL auth:ticket:{ticket_id}` (или `GET`, затем `DEL` в транзакции `MULTI/EXEC`, если версия Redis < 6.2).
    * Если билет найден, он десериализуется, а пользователю мгновенно выпускается эфемерный Phantom Token (или JIT-контекст) для соединения.
    * Благодаря атомарному `DEL`, билет сгорает сразу же после первого применения (Write-Once-Read-Once).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Если Redis недоступен, генерация и проверка билетов невозможна. Вызовы на скачивание файлов/WSS будут завершаться ошибкой `503 Service Unavailable`, так как резервирование билетов в PostgreSQL неоправданно замедлит систему. |

# Кэширование OIDC ключей (JWKS) (SR-AUTH-OI-02)

## Общая информация

Authorization Service должен проверять цифровые подписи (Signature) JWT-токенов (ID Tokens), которые приходят от STEOS ID после успешного логина по OIDC. Для этого нужны публичные ключи провайдера (JWKS — JSON Web Key Set). Эти ключи кэшируются in-memory (КАР-8), чтобы не скачивать их по HTTP при каждом логине.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:jwks:steosid`<br>(Ключ статичен, так как провайдер один). |
| **DTO ответа** | Сериализованный JSON JWKS (массив объектов JWK: `kid`, `kty`, `alg`, `e`, `n`). |
| **TTL** | Длительный (например, 24 часа: `86400` сек). |

## Логика обработки запроса

*   **Чтение (Lazy Load):** При разборе входящего ID Token (в эндпоинте OIDC Callback), сервис ищет ключ `kid` в локальном In-Memory кэше приложения. Если кэш пуст — читает `GET auth:jwks:steosid`. Если и там пусто (Cache Miss), делает HTTP GET запрос к `https://id.steos.com/.well-known/jwks.json`.
*   **Запись (Warm-up):** Скачанные ключи кэшируются в Redis (команда `SETEX`) и локально в памяти.
*   **Инвалидация (Active Refresh):** Как описано в документации RabbitMQ (`01 - Синхронизация OIDC`), при получении события `steosid:events:jwks-rotated` (Fanout от IdP), Authorization Service немедленно выполняет `DEL auth:jwks:steosid`, сбрасывает локальную память и фоново скачивает новые ключи (Pre-fetching). Это защищает платформу при компрометации ключей STEOS ID.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Деградация: Если Redis упал, ключи хранятся в In-Memory кэше (внутри процессов подов). При старте нового пода ключи будут загружены напрямую из IdP, минуя Redis. |

# Хранение параметров OIDC (State/Nonce) (SR-AUTH-OI-01)

## Общая информация

В рамках протокола OAuth 2.0 / OpenID Connect (Authorization Code Flow with PKCE) сервис авторизации должен генерировать параметры `state` (для защиты от Cross-Site Request Forgery - CSRF) и `nonce` (для защиты от Replay атак). Эти криптографические "секреты" привязываются к конкретному браузеру (через Cookie) и должны быть проверены при возврате пользователя из STEOS ID. Они хранятся в Redis.

| Тип операции | Read (Чтение), Write (Запись) |
| :--- | :--- |
| **Ключ Redis** | `auth:oidc:state:{state_hash}`<br>где `{state_hash}` = криптографический хэш (SHA256) от случайной строки `state`. |
| **DTO ответа** | Сериализованный `OidcTransactionState` (содержит `nonce`, `code_verifier_hash`, `redirect_uri`, `workspace_id`). |
| **TTL** | Короткий (15-30 минут), равный максимальному времени, отведенному пользователю на ввод пароля в окне STEOS ID. |

## Логика обработки запроса

*   **Запись (Инициализация):** При вызове `GET /auth/login` (отправка пользователя на IdP), сервис генерирует случайные `state` и `nonce`, вычисляет PKCE `code_challenge`, запаковывает в DTO и делает `SETEX auth:oidc:state:{hash} 900`. Пользователю ставится HttpOnly Cookie `oidc_state`.
*   **Чтение (Callback):** Когда пользователь возвращается на `GET /auth/callback?code=...&state=...`, сервис берет `state` из URL, проверяет Cookie (защита от CSRF), хеширует и делает `GET auth:oidc:state:{hash}`.
*   **Проверка:** Из DTO извлекается `nonce` (сверяется с ID Token), `code_verifier_hash` (для обмена кода на токен) и `redirect_uri` (куда вернуть юзера после логина).
*   **Инвалидация:** Ключ немедленно удаляется `DEL` (или `GETDEL`) после успешного чтения, чтобы State нельзя было переиспользовать (предотвращение Replay).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Если Redis недоступен, механизм защиты CSRF/Replay не работает. Сервис обязан прервать поток логина (Fail-Closed) с `503 Service Unavailable`, так как вход без `state` грубо нарушает стандарты безопасности OIDC. |
