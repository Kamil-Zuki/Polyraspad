# Введение

Данный документ описывает асинхронную часть интеграции с глобальным STEOS ID через брокер сообщений RabbitMQ. Эта интеграция критически важна для реализации концепции "Zero Trust" (нулевого доверия). Поскольку локальные сессии хранятся в Redis с заданным временем жизни (TTL), Authorization Service должен иметь канал для получения мгновенных сигналов от глобального провайдера об аннулировании доверия (например, бан, смена пароля или принудительный "Выход со всех устройств").

# Общая информация

Асинхронное получение событий безопасности (Back-Channel Logout) и принудительная терминация локальных сессий (Stateful Kill Switch).

| Параметр | Описание |
| :--- | :--- |
| **Версия API** | RabbitMQ 3.12.x (Event-Driven) |
| **Название сервиса** | STEOS ID (Глобальный провайдер идентичности) |
| **Официальная документация** | Внутренняя спецификация событий платформы / OIDC Back-Channel Logout |
| **Владелец** | Core Identity Team |

# Доступ и аутентификация

Настройки подключения локального Authorization Service (как Consumer) к инфраструктуре RabbitMQ STEOS ID.

| Параметр | Описание |
| :--- | :--- |
| **Метод аутентификации** | Подключение по логину/паролю или клиентским сертификатам (mTLS). |
| **Хранение учетных данных** | AMQP Connection String хранится в **HashiCorp Vault** или Kubernetes Secrets. |
| **Среды (Environments)** | Для сред Prod и Stage используются разные виртуальные хосты (vhost) брокера. |
| **Подписка (Exchange)** | Authorization Service подписывается на Exchange типа `fanout` или `topic` (например, `steos.auth.events`), куда STEOS ID транслирует события. |

# Ключевые события (Subscribe)

Список типов событий, на которые подписан Authorization Service (Consumer).

| Событие | Exchange / Топик | Routing Key | Описание | Использование в Authorization Service |
| :--- | :--- | :--- | :--- | :--- |
| `user.security.password_changed` | `steos.auth.events` | `user.security.password_changed` | Уведомление о смене пароля или компрометации глобальной учетной записи. | Вызывает массовую инвалидацию всех сессий пользователя на данной платформе (**SR-AUTH-OI-04**). |
| `user.security.banned` | `steos.auth.events` | `user.security.banned` | Уведомление об административной блокировке пользователя (Global Kill Switch). | Мгновенное удаление сессий из Redis (`DEL`). |
| `user.security.global_logout` | `steos.auth.events` | `user.security.global_logout` | Пользователь нажал "Выйти на всех устройствах" в личном кабинете STEOS ID. | Синхронизация статуса сессий с глобальным IdP. |

# Логика обработки событий

Механизмы обеспечения немедленной реакции на события безопасности и гарантии доставки (At-least-once delivery).

*   **Consumer Worker:** Внутри Authorization Service запущен фоновый Worker-процесс, слушающий очередь RabbitMQ. При поступлении события он "просыпается" и выполняет бизнес-логику.
*   **Массовое удаление (Mass Revoke):** Worker извлекает `global_steos_id` из Payload-сообщения, ищет в локальной базе данных (PostgreSQL) или Redis-индексах все активные `session_id` этого пользователя и выполняет атомарное массовое удаление (`DEL`) этих ключей из Redis.
*   **Idempotency (Идемпотентность):** Так как RabbitMQ гарантирует At-least-once delivery, одно и то же событие может прийти дважды. Логика удаления реализована идемпотентно: повторный вызов `DEL` в Redis для уже удаленных сессий не вызывает ошибок и безопасно завершается.
*   **Персистентность (Soft Delete):** После удаления из Redis, Worker отправляет асинхронный `UPDATE` в базу данных, помечая сессии как `is_active = false`, `revoked_at = NOW()`, `revoke_reason = 'GLOBAL_SECURITY_EVENT'` для истории и аудита.

# Обработка ошибок

Действия сервиса при невозможности немедленно обработать событие безопасности.

| Тип ошибки | Описание причины | Реакция сервиса |
| :--- | :--- | :--- |
| `REDIS_UNAVAILABLE` (Сбой кэша) | В момент прихода события RabbitMQ, кластер Redis локальной платформы недоступен или перегружен. | **NACK (Negative Acknowledgement)**. Worker не отправляет `basicAck` в брокер. Используется стратегия возврата сообщения в очередь (`requeue=true` или DLX — Dead Letter Exchange) для повторной попытки через несколько секунд. Критическое событие безопасности не должно быть потеряно. |
| `DB_CONNECTION_TIMEOUT` (Сбой БД) | PostgreSQL недоступен для пометки сессий как неактивных (Soft Delete). | Аналогично `REDIS_UNAVAILABLE` — NACK и Retry. В идеале логика Redis-удаления должна быть выполнена, а сбой БД обработан через локальный Transactional Outbox. |
| `MALFORMED_PAYLOAD` | Сообщение от STEOS ID имеет неверный формат (например, отсутствует `global_steos_id`). | Событие логируется с уровнем `ERROR`, отправляется в специальную DLX очередь для ручного разбора (Dead Letter Queue), и на основное сообщение отправляется `basicAck` (чтобы оно не зацикливалось в основной очереди). |
