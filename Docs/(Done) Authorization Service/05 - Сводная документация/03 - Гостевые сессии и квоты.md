# Введение

Данная группа REST API методов предназначена для обеспечения концепции Seamless Onboarding (Бесшовного погружения). Она позволяет неавторизованным (анонимным) пользователям взаимодействовать с платформой так, будто они уже зарегистрированы: генерировать контент, настраивать рабочие пространства, создавать черновики.

Все сгенерированные данные привязываются к временному `Guest ID` и жестко лимитируются гостевыми квотами. При успешном прохождении регистрации гостевой профиль конвертируется в полноценный, сохраняя весь наработанный пользователем прогресс.

# 1. Список эндпоинтов

Ниже приведен список методов REST API для инициализации и управления гостевыми демо-сессиями.

| Код требования | Метод | Эндпоинт | Назначение |
| :--- | :---: | :--- | :--- |
| SR-AUTH-GQ-01 | POST | `/guests/init` | Создание гостевой Cookie и выделение начальной квоты (например, "3 генерации"). |
| SR-AUTH-GQ-02 | GET | `/guests/status` | Получение текущего состояния лимитов (сколько действий осталось у гостя). |
| SR-AUTH-GQ-03 | POST | `/guests/convert` | Конвертация гостя в авторизованного пользователя после логина OIDC. |
| SR-AUTH-GQ-04 | POST | `/guests/merge` | Явное асинхронное слияние данных (черновиков) в постоянный User ID. |

# SR-AUTH-GQ-01: Создание гостевой сессии: Init

## Общая информация

Вызывается фронтендом (SPA), когда анонимный пользователь нажимает кнопку "Попробовать демо" или выполняет первое действие, требующее контекста платформы. Эндпоинт устанавливает в браузер временную гостевую Cookie и выделяет базовые квоты.

| Тип метода | POST |
| :--- | :--- |
| **DTO запроса** | GuestSessionCreateDto (опционально: маркетинговые UTM-метки) |
| **DTO успешного ответа** | GuestSessionResponseDto |

## Параметры URL

Параметры отсутствуют.

## Логика обработки запроса

*   BFF при необходимости извлекает UTM/маркетинговые поля из тела и проверяет антифрод (IP, fingerprint).
*   BFF вызывает gRPC [`InitGuestSession`](../gRPC/04%20-%20Защита%20периметра%20и%20Гостевые%20квоты%20(Security%20&%20Quotas).md#grpc-InitGuestSession).
*   В ответе HTTP устанавливается гостевая Cookie; тело содержит `GuestSessionResponseDto`.

## Успешный ответ

```json
{
  "success": true,
  "data": {
    "guestId": "gst_991a8b2c",
    "expiresAt": "2026-03-26T14:00:00Z",
    "quotas": {
      "aiGenerations": 3,
      "maxProjects": 1
    }
  }
}
```

## Ошибки

| Статус-код | Описание ошибки |
| :--- | :--- |
| **429 Too Many Requests** | Слишком много гостевых сессий с одного IP или Fingerprint (сработал анти-фрод). |

# SR-AUTH-GQ-02: Статус лимитов гостя: Status

## Общая информация

Метод для динамического отображения прогресс-баров в UI (например, "Осталось 2 бесплатных генерации"). Позволяет фронтенду понимать, когда пора показывать пользователю окно с предложением зарегистрироваться (Paywall / Regwall).

| Тип метода | GET |
| :--- | :--- |
| **DTO запроса** | N/A (читается гостевая Cookie) |
| **DTO успешного ответа** | GuestQuotaStatusDto |

## Параметры URL

Параметры отсутствуют.

## Логика обработки запроса

*   BFF читает гостевую Cookie и передаёт идентификатор гостевой сессии в Auth.
*   BFF вызывает gRPC [`GetGuestAccessStatus`](../gRPC/04%20-%20Защита%20периметра%20и%20Гостевые%20квоты%20(Security%20&%20Quotas).md#grpc-GetGuestAccessStatus).
*   Ответ маппится в `GuestQuotaStatusDto`.

## Успешный ответ

```json
{
  "success": true,
  "data": {
    "quotas": [
      {
        "type": "ai_generations",
        "used": 1,
        "total": 3,
        "remaining": 2
      },
      {
        "type": "projects",
        "used": 1,
        "total": 1,
        "remaining": 0
      }
    ],
    "requiresRegistration": false
  }
}
```

## Ошибки

| Статус-код | Описание ошибки |
| :--- | :--- |
| **401 Unauthorized** | Гостевая сессия истекла (TTL Cookie) или не была найдена. |

# SR-AUTH-GQ-03: Конвертация сессии: Convert

## Общая информация

Самый сложный технически метод этой группы. Вызывается **автоматически** после успешного завершения OIDC Callback (если в браузере присутствовала гостевая Cookie). Он связывает временный `Guest ID` со свежесозданным глобальным `User ID` в STEOS ID.

| Тип метода | POST |
| :--- | :--- |
| **DTO запроса** | ConvertGuestRequestDto (содержит `Guest ID` и новый `User ID`) |
| **DTO успешного ответа** | SuccessResponseDto |

## Параметры URL

Параметры отсутствуют. Вызов обычно осуществляется самим Authorization Service внутри цепочки Callback-обработчика.

## Логика обработки запроса

*   BFF (или внутренний обработчик callback) передаёт пару `Guest ID` + новый `User ID` из контекста OIDC.
*   BFF вызывает gRPC [`ConvertGuestSession`](../gRPC/04%20-%20Защита%20периметра%20и%20Гостевые%20квоты%20(Security%20&%20Quotas).md#grpc-ConvertGuestSession).
*   При успехе может публиковаться событие для асинхронного merge данных в других сервисах.

## Успешный ответ

```json
{
  "success": true,
  "message": "Гостевой профиль успешно сконвертирован в постоянный аккаунт"
}
```

## Ошибки

| Статус-код | Описание ошибки |
| :--- | :--- |
| **400 Bad Request** | Гостевая сессия уже была конвертирована ранее. |

# SR-AUTH-GQ-04: Слияние пользовательских данных: Merge

## Общая информация

Асинхронный метод для других микросервисов Платформы. После того как Auth Service конвертировал сессию (Convert) и отправил сообщение в RabbitMQ, бизнес-сервисы (например, Document Service, Storage Service) начинают переносить черновики и файлы, созданные под `Guest ID`, на новый постоянный `User ID`. 

Этот эндпоинт позволяет фронтенду узнать статус "переезда" данных, чтобы показать лоадер ("Переносим ваши проекты в новый аккаунт...").

| Тип метода | GET / POST |
| :--- | :--- |
| **DTO запроса** | N/A |
| **DTO успешного ответа** | SuccessResponseDto (Статус миграции) |

## Параметры URL

Параметры отсутствуют (читается текущая активная сессия пользователя).

## Логика обработки запроса

*   BFF определяет пользователя по Phantom Cookie и при необходимости передаёт идентификатор асинхронной задачи слияния.
*   BFF вызывает gRPC [`MergeGuestData`](../gRPC/04%20-%20Защита%20периметра%20и%20Гостевые%20квоты%20(Security%20&%20Quotas).md#grpc-MergeGuestData) (или опрашивает статус связанного job).
*   Ответ отражает прогресс переноса сущностей с `Guest ID` на постоянный `User ID`; при **202** клиент повторяет опрос.

## Успешный ответ

```json
{
  "success": true,
  "data": {
    "status": "COMPLETED",
    "mergedEntities": 14,
    "message": "Все данные гостя успешно перенесены в рабочее пространство пользователя."
  }
}
```

## Ошибки

| Статус-код | Описание ошибки |
| :--- | :--- |
| **202 Accepted** | Слияние всё еще в процессе (фронтенду нужно повторить опрос через 2 секунды). |
