# Введение

Данная группа gRPC-методов описывает механизмы криптографического взаимодействия микросервиса Authorization Service с глобальным поставщиком идентификации (STEOS ID), а также выдачу локальных, математически доказуемых (M2M) токенов для тех бизнес-сервисов платформы, которым недостаточно доверия на уровне HTTP-заголовков. 

В микросервисной архитектуре Enterprise-класса (где каждый узел может быть скомпрометирован) именно эти методы гарантируют валидность подписей JWT, поддерживают ротацию публичных ключей (JWKS) без простоев (Zero Downtime) и обеспечивают жесткую синхронизацию профиля пользователя с единым источником правды (IdP).

Важно: `STEOS ID`, любые legacy-системы, внешние trusted-интеграции и downstream-сервисы, упоминаемые в примерах, являются отдельными внешними системами или микросервисами. Они не реализуются в рамках данной документации `Authorization Service`; здесь описывается только контракт взаимодействия `Authorization Service` с ними.

# 1. Список методов

Ниже перечислены процедуры, ответственные за безопасность на уровне криптографии и синхронизацию идентичностей (Claims).

| Код требования | gRPC Метод | Тип RPC | Описание |
| :--- | :--- | :---: | :--- |
| SR-AUTH-OI-02 | `IntrospectToken` | Unary | Интроспекция: Проверка OIDC-токена на валидность и отзыв (Revocation status). |
| SR-AUTH-OI-02 | `GetCachedJwks` | Unary | Выдача набора закэшированных публичных ключей (JWKS) внутренним сервисам. |
| SR-AUTH-OI-05 | `ForceJwksRotation` | Unary | Экстренная инвалидация кэша JWKS и принудительное скачивание новых ключей STEOS ID. |
| SR-AUTH-OI-06 | `SyncIdentityClaims` | Unary | Фоновое обновление базового профиля пользователя (имя, email) из глобального провайдера. |

<span id="grpc-IntrospectToken"></span>

# SR-AUTH-OI-02: Интроспекция токена: IntrospectToken

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/02 - Инфраструктура OIDC и Интеграция - OIDC Infrastructure#SR-AUTH-OI-02: Кэширование и Валидация JWKS]]

Хотя Платформа работает на основе Phantom Tokens (Cookie), некоторые API могут напрямую принимать OAuth 2.0 Access/ID токены (например, от мобильных приложений или интеграционных шлюзов). Данный метод позволяет любому внутреннему микросервису передать Authorization Service токен для его полной валидации (подпись, срок жизни, статус отзыва).

| Сигнатура | `rpc IntrospectToken(IntrospectRequest) returns (IntrospectResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `IntrospectRequest` (OIDC Token, тип токена `access_token` или `id_token`) |
| **Сообщение ответа** | `IntrospectResponse` (статус активности `active`, извлеченные Claims пользователя/сервиса) |

## Логика обработки запроса

1. Проверить формат входного OIDC-токена и извлечь из него `header` и обязательные claims.
2. Локально валидировать подпись JWT по `kid`, используя кэшированный набор JWKS `STEOS ID`.
3. Проверить временные claims (`exp`, `nbf`) с учетом допустимого `clock skew`.
4. Если для данного контура включена строгая интроспекция, дополнительно выполнить server-to-server проверку статуса отзыва токена через отдельный endpoint `STEOS ID`.
5. Собрать нормализованное ответное сообщение с claims и вернуть `active: true` только если токен признан валидным по всем проверкам.

## Статус-коды gRPC при ошибках

Метод всегда возвращает `OK`, но с флагом `active: false`, если токен недействителен (согласно RFC 7662), чтобы клиент мог корректно обработать отказ в доступе. В случае сетевых проблем:
| Статус-код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Ошибка связи со STEOS ID при фолбэке. |
| **INTERNAL** | Сбой локальной криптобиблиотеки (RSA/ECDSA). |

<span id="grpc-GetCachedJwks"></span>

# SR-AUTH-OI-02: Чтение кэша ключей: GetCachedJwks

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/02 - Инфраструктура OIDC и Интеграция - OIDC Infrastructure#SR-AUTH-OI-02: Кэширование и Валидация JWKS]]

Некоторые микросервисы (особенно высоконагруженные Edge-роутеры или Webhook-приемники) могут захотеть самостоятельно валидировать подписи входящих токенов, минуя сетевой вызов к Auth Service (Zero-Hop Validation). Данный метод возвращает актуальный набор JSON Web Key Set (публичных ключей), который Auth Service периодически выкачивает из STEOS ID.

| Сигнатура | `rpc GetCachedJwks(Empty) returns (JwksResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `google.protobuf.Empty` |
| **Сообщение ответа** | `JwksResponse` (массив публичных ключей JWK и время последнего обновления; кэш STEOS ID — не путать с JWKS платформенных M2M в REST) |

## Логика обработки запроса

1. Прочитать актуальный набор JWKS из локального In-Memory-кэша или Redis.
2. Проверить, что кэш был успешно инициализирован и содержит хотя бы один действующий публичный ключ.
3. Вернуть сериализованный набор публичных ключей и технические метаданные последней синхронизации вызывающему сервису.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | Кэш JWKS пуст (сервис стартовал, но еще не успел синхронизироваться со STEOS ID). |

# SR-AUTH-OI-05: Аварийная ротация ключей: ForceJwksRotation

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/02 - Инфраструктура OIDC и Интеграция - OIDC Infrastructure#SR-AUTH-OI-05: Аварийная ротация JWKS]]

Утилитарный метод для администраторов ИБ (SecOps). Применяется в сценариях компрометации приватного ключа подписи на стороне Identity Provider (STEOS ID). Позволяет принудительно, в обход таймеров (TTL), сбросить кэш JWKS и заставить Auth Service немедленно загрузить новые ключи, инвалидируя тем самым все старые токены.

| Сигнатура             | `rpc ForceJwksRotation(ForceRotationRequest) returns (ForceRotationResponse)`                |
| :-------------------- | :------------------------------------------------------------------------------------------- |
| **Сообщение запроса** | `ForceRotationRequest` (обязательная причина для WORM аудита, флаг `drop_existing_sessions`) |
| **Сообщение ответа**  | `ForceRotationResponse` (статус успеха, количество новых загруженных ключей)                 |

## Логика обработки запроса

1. Проверить, что вызов выполняет уполномоченный ИБ-администратор и что причина ротации явно указана.
2. Сбросить локальный кэш JWKS в In-Memory и Redis, чтобы старый набор ключей перестал считаться каноническим.
3. Синхронно запросить новый набор JWKS у отдельного внешнего сервиса `STEOS ID`.
4. Сохранить новый набор ключей в локальный кэш с обновленным TTL.
5. Если передан флаг `drop_existing_sessions`, инициировать server-side процедуру пометки активных Phantom-сессий как требующих обновления доверенности.
6. Записать событие `JWKS_ROTATED_FORCE` в локальный WORM-аудит.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **PERMISSION_DENIED** | Отсутствуют права ИБ-администратора (SecOps). |
| **UNAVAILABLE** | STEOS ID недоступен в момент запроса ротации (сохраняются старые ключи во избежание даунтайма). |

# SR-AUTH-OI-06: Синхронизация профиля: SyncIdentityClaims

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/02 - Инфраструктура OIDC и Интеграция - OIDC Infrastructure#SR-AUTH-OI-06: Синхронизация Identity Claims]]

Метод для актуализации локальных данных пользователя (email, имя, глобальный статус блокировки) из STEOS ID. Вызывается асинхронно при логине пользователя, либо при получении вебхука `profile_updated` от провайдера. Позволяет микросервису авторизации всегда располагать свежими Claims для построения контекста (`SessionContext`).

| Сигнатура | `rpc SyncIdentityClaims(SyncClaimsRequest) returns (SyncClaimsResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `SyncClaimsRequest` (Global User ID, сырой объект Claims или флаг `fetch_from_idp`) |
| **Сообщение ответа** | `SyncClaimsResponse` (статус обновления локальной БД `users`) |

## Логика обработки запроса

1. Получить канонический идентификатор пользователя и определить источник свежих claims: входной JWT, внешний сигнал или принудительный `fetch_from_idp`.
2. Извлечь базовые identity-claims из входного payload либо запросить их у отдельного сервиса `STEOS ID` по server-to-server каналу.
3. Обновить локальный профиль пользователя в `local_users` или эквивалентной таблице-кэше.
4. Пересобрать и обновить все активные `SessionContext` этого пользователя, чтобы новый профиль сразу применился в UI и downstream-контуре.
5. Вернуть статус синхронизации вызывающему процессу.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не передан ID пользователя или невалидные Claims. |
| **UNAVAILABLE** | Ошибка обращения к UserInfo Endpoint. |

# SR-AUTH-M2M-02: Обмен контекста на M2M токен: ExchangeInternalToken

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/06 - Межсервисная Аутентификация и Внутренние Токены - M2M Internal Tokens#SR-AUTH-M2M-02: Выпуск внутренних JWT-токенов]]

Решает проблему интеграции с "устаревшими" (legacy) или внешними доверенными системами, которые не умеют работать с Header Routing (например, старые версии CRM или внешние BI-дашборды), а требуют передачи классического JWT `Bearer` токена в заголовке `Authorization`.

Метод берет текущий бизнес-контекст пользователя и выпускает для него короткоживущий (обычно 1-5 минут) локальный подписанный JWT, который можно безопасно отдать микросервису для передачи "наружу" платформы.

| Сигнатура | `rpc ExchangeInternalToken(ExchangeTokenRequest) returns (ExchangeTokenResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ExchangeTokenRequest` (ID текущей сессии, требуемый Audience (целевая система), опциональные скоупы) |
| **Сообщение ответа** | `ExchangeTokenResponse` (сгенерированный подписанный `internal_jwt_token`, время жизни) |

## Логика обработки запроса

1. Проверить, что вызывающий субъект действительно имеет право выпускать внутренние JWT для указанного `audience`.
2. Получить актуальный `SessionContext` по переданному идентификатору локальной сессии.
3. Сформировать claims внутреннего токена на основе уже существующего и валидного локального контекста (`sub`, `workspace`, роли, `aud`, TTL).
4. Подписать короткоживущий JWT приватным ключом `Authorization Service`.
5. Записать событие выпуска внутреннего токена в локальный аудит как чувствительное действие.
6. Вернуть сгенерированный токен и срок его жизни вызывающему trusted-сервису или интеграции.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **PERMISSION_DENIED** | Запрашивающий сервис не имеет прав на выпуск токенов для данной Audience. |
| **NOT_FOUND** | Сессия пользователя не найдена или неактивна. |
| **INTERNAL** | Ошибка генерации криптографической подписи. |
