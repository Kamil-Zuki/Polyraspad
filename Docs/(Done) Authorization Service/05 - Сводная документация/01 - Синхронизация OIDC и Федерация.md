# Введение

В данном документе описываются механизмы взаимодействия **Authorization Service** с глобальным провайдером идентичности (STEOS ID) через брокер сообщений RabbitMQ. Использование асинхронных очередей (Event-Driven Architecture) критически важно для мгновенной реакции локального сервиса авторизации на изменения профиля, ротацию ключей или смену пароля (Back-Channel Logout) без необходимости постоянного поллинга (HTTP Polling) внешнего IdP.

# 1. Список событий Синхронизации OIDC и Федерации

Ниже перечислены все асинхронные операции, связанные с получением обновлений от STEOS ID.

| Метод (SR) | Тип операции | Очередь / Топик | Описание |
| :--- | :--- | :--- | :--- |
| SR-AUTH-OI-04 | Consume | `steosid:events:backchannel-logout` | Потребление сигнала о смене пароля или блокировке в STEOS ID для отзыва локальных сессий. |
| SR-AUTH-OI-06 | Consume | `steosid:events:user-updated` | Оповещение об изменении профиля пользователя в IdP (смена Email, Имени и т.д.). |
| SR-AUTH-OI-05 | Consume | `steosid:events:jwks-rotated` | Критический сигнал об аварийной ротации OIDC ключей (JWKS) в STEOS ID. |

# Событие: Асинхронный Back-Channel Logout (SR-AUTH-OI-04)

## Общая информация

Потребление критического события от STEOS ID, информирующего о том, что сессия пользователя была завершена на стороне глобального IdP (например, пользователь нажал "Выйти со всех устройств", сменил пароль или был заблокирован администратором). Authorization Service должен немедленно инвалидировать все локальные сессии (Refresh Tokens) данного пользователя.

| Тип операции | Consume (Потребление) |
| :--- | :--- |
| **Exchange / Топик** | `steosid:events:auth` |
| **Routing Key** | `auth.session.revoked` |
| **Очередь** | `steosid:events:backchannel-logout` |
| **DTO сообщения** | `BackchannelLogoutEventPayload` |

## Параметры сообщения

Ниже описана структура Payload, который потребляется из очереди.

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **subjectId** | string (uuid) | Глобальный идентификатор пользователя (sub) в STEOS ID. |
| **sessionId** | string (uuid) | (Опционально) Идентификатор конкретной глобальной сессии, если отзыв был точечным. |
| **reason** | string | Причина отзыва: `PASSWORD_CHANGED`, `ADMIN_BANNED`, `USER_LOGOUT`, `SUSPICIOUS_ACTIVITY`. |
| **revokedAt** | integer (timestamp) | Временная метка события отзыва в STEOS ID. |
| **eventId** | string (uuid) | Уникальный идентификатор события (для идемпотентности). |

## Логика обработки запроса

Процесс локальной инвалидации сессий при получении Back-Channel Logout.

*   **Потребление:** Воркер извлекает сообщение из очереди `steosid:events:backchannel-logout`.
*   **Проверка идемпотентности:** Система проверяет `eventId` в кэше/БД. Если событие уже обрабатывалось, оно игнорируется (ACK).
*   **Поиск сессий:** Система ищет все активные сессии (`Refresh Tokens`) в локальной БД, привязанные к указанному `subjectId` (и опционально `sessionId`).
*   **Инвалидация:** 
    * Статус найденных локальных сессий меняется на `REVOKED`.
    * Генерируется запись в локальный `Audit Log` (WORM).
*   **Синхронизация с UI:** Воркер инициирует публикацию WebSocket-события `session_revoked` для всех активных подключений данного `subjectId` (чтобы выкинуть пользователя из интерфейса).
*   **Широковещательная рассылка:** Воркер публикует внутреннее событие `GlobalLogoutEvent` в локальный Exchange платформы, чтобы другие микросервисы (Storage, Tasks) сбросили свои in-memory кэши прав этого пользователя (см. Группу 3).
*   **Завершение:** Сообщение удаляется из брокера (ACK).

## Статус-коды при ошибках

Возможные системные ошибки, обрабатываемые воркером.

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Сбой подключения к БД при попытке инвалидации. Сообщение возвращается в очередь для повторной обработки (NACK с requeue) с использованием Exponential Backoff. |
| **INVALID_PAYLOAD** | Нарушена структура DTO (отсутствует `subjectId`). Сообщение отправляется в DLQ (Dead Letter Queue) для ручного разбора (ACK). |

# Событие: Обновление профиля в IdP (SR-AUTH-OI-06)

## Общая информация

Потребление события от STEOS ID об изменении базовых атрибутов (Claims) профиля пользователя (например, пользователь подтвердил новый Email, изменил номер телефона или обновил аватарку). Authorization Service обновляет эти данные в своем локальном кэше/профиле, чтобы включать их в будущие Access Tokens (Phantom Tokens).

| Тип операции | Consume (Потребление) |
| :--- | :--- |
| **Exchange / Топик** | `steosid:events:users` |
| **Routing Key** | `user.profile.updated` |
| **Очередь** | `steosid:events:user-updated` |
| **DTO сообщения** | `UserUpdatedEventPayload` |

## Параметры сообщения

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **subjectId** | string (uuid) | Глобальный идентификатор пользователя (sub). |
| **updatedClaims** | object | Словарь обновленных полей (ключ-значение). Например: `{"email": "new@mail.com", "email_verified": true}`. |
| **updatedAt** | integer (timestamp) | Временная метка обновления в IdP. |
| **eventId** | string (uuid) | Уникальный идентификатор события. |

## Логика обработки запроса

*   **Потребление:** Извлечение сообщения из очереди. Проверка идемпотентности по `eventId`.
*   **Обновление локальных данных:** Система находит локальную проекцию профиля пользователя (Local User State) по `subjectId` и применяет дифференциальное обновление из объекта `updatedClaims`.
*   **Оповещение клиентов (Silent Update):** Если есть изменения, критичные для UI (например, имя или email), система может опубликовать WebSocket-событие `context_updated`, чтобы фронтенд плавно обновил интерфейс без перезагрузки.
*   **Завершение:** ACK.

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **USER_NOT_FOUND** | Пользователь с таким `subjectId` не найден в локальной базе (ни разу не авторизовывался в этом Workspace). Событие безопасно игнорируется (ACK). |
| **INTERNAL** | Ошибка обновления локальной БД. NACK с requeue. |

# Событие: Ротация ключей JWKS (SR-AUTH-OI-05)

## Общая информация

Чрезвычайно важное событие (Fanout Broadcast) от STEOS ID. Сигнализирует о том, что ключи подписания токенов (OIDC JWKS) были обновлены (планово или из-за компрометации). Authorization Service должен немедленно сбросить свой In-Memory кэш JWKS и выполнить синхронный запрос за новыми ключами.

| Тип операции | Consume (Потребление) |
| :--- | :--- |
| **Exchange / Топик** | `steosid:events:system` |
| **Routing Key** | `system.jwks.rotated` |
| **Очередь** | `steosid:events:jwks-rotated` |
| **DTO сообщения** | `JwksRotatedEventPayload` |

## Параметры сообщения

Это максимально простое сигнальное сообщение.

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **rotatedAt** | integer (timestamp) | Временная метка ротации. |
| **reason** | string | Причина: `SCHEDULED` (плановая ротация), `EMERGENCY` (компрометация). |
| **eventId** | string (uuid) | Уникальный идентификатор события. |

## Логика обработки запроса

*   **Потребление:** Извлечение сообщения из очереди.
*   **Сброс кэша:** Воркер очищает локальный Redis-кэш и In-Memory кэш приложения, в котором хранятся публичные ключи (JWKS) от STEOS ID.
*   **Принудительная загрузка (Active Fetch):** Воркер инициирует фоновый вызов HTTP GET `/oauth2/jwks` к STEOS ID для загрузки свежего набора ключей и сразу прогревает кэш (КАР-8).
*   **Завершение:** ACK. После этого все новые OIDC токены (ID Tokens) от STEOS ID будут валидироваться уже свежими ключами.

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Если не удалось очистить локальный кэш (сбой Redis), воркер делает NACK с requeue и пишет алерт `CRITICAL`, так как использование старых ключей приведет к массовым ошибкам аутентификации. |
| **HTTP_JWKS_FAILED** | Если после сброса кэша не удалось синхронно скачать новые ключи от STEOS ID (IdP недоступен), система переходит в режим деградации, используя старые ключи (если они еще валидны по времени) и повторяет попытку через Exponential Backoff (NACK). |
