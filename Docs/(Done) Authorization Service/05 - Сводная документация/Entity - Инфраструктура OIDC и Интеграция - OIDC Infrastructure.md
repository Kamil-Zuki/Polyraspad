# Введение

Эта группа сущностей формирует технический фундамент **Инфраструктуры OIDC и Интеграции (OIDC Infrastructure)** внутри локального микросервиса Authorization Service. 

В архитектуре STEOS, где **STEOS ID** выступает глобальным Identity Provider (IdP), а конкретные платформы (SaaS, Private Cloud) выступают в роли Relying Parties (RP / Клиентов), процесс передачи пользователя между этими системами является наиболее уязвимой точкой с точки зрения кибербезопасности.

Данная группа обеспечивает реализацию стандарта **OAuth 2.0 Authorization Code Flow with PKCE**, гарантируя, что:
*   Никто не сможет подделать ответ от STEOS ID (защита от CSRF).
*   Никто не сможет перехватить авторизационный код и обменять его на токен (защита от Authorization Code Interception).
*   Локальный микросервис всегда использует актуальные криптографические ключи для мгновенной валидации входящих JWT-токенов без сетевых задержек.

**Архитектурные особенности группы:**

1.  **Stateful OAuth Client:** В отличие от старых систем, где `state` хранился только в браузере (Cookies), Authorization Service хранит криптографические параметры начала сессии (`nonce`, `code_verifier`) на своей стороне в быстродействующей транзакционной таблице. Это позволяет сверять возвращающиеся коды с тем, что сервер *реально* запрашивал, обеспечивая высочайший уровень изоляции сеансов.
2.  **In-Memory & High Throughput:** Сущности этой группы отличаются крайне коротким жизненным циклом. Записи о состоянии OIDC-потока живут не более 5-10 минут (время, за которое пользователь должен ввести пароль в STEOS ID и вернуться обратно). Поэтому эта группа оптимизирована под частые операции INSERT и физический DELETE.
3.  **Криптографическая автономность:** Сервис не ходит в интернет за публичным ключом STEOS ID каждый раз, когда нужно проверить токен ИИ-Агента или пользователя. Он использует кэширующую сущность (`idp_jwks_cache`), которая фоново синхронизируется с Глобальным Ядром, что позволяет API-шлюзу обрабатывать миллионы проверок в секунду.

В совокупности эти механизмы превращают локальный сервис авторизации в пуленепробиваемый шлюз, который слепо верит математике, а не сетевым запросам.

# Состояние OIDC-потока (`oidc_auth_flows`)

## 1. Общее описание

**Состояние OIDC-потока (OIDC Auth Flow State)** — это высоконагруженная эфемерная (короткоживущая) транзакционная сущность, которая хранит промежуточный криптографический контекст в процессе аутентификации пользователя между платформой STEOS и глобальным STEOS ID.

Когда пользователь нажимает кнопку "Войти", локальный `Authorization Service` не может просто отправить его на страницу STEOS ID и забыть о нем. Платформа должна "запомнить", что она начала этот процесс, чтобы по возвращении пользователя с авторизационным кодом (Authorization Code) точно убедиться, что код предназначается именно для этой сессии, и что запрос не был подделан злоумышленником. 

Эта таблица реализует ключевые требования безопасности стандарта **OAuth 2.0 Authorization Code Grant с PKCE (Proof Key for Code Exchange)**.

**Архитектурное назначение:**
1.  **Защита от CSRF (Cross-Site Request Forgery):** Хранение параметра `state`, который генерируется локально и сравнивается с тем `state`, что возвращает STEOS ID. Если они не совпадают — попытка входа прерывается.
2.  **Защита от перехвата кода (PKCE):** Хранение параметра `code_verifier`. Когда STEOS ID возвращает код, локальный сервис отправляет этот код обратно в STEOS ID вместе с `code_verifier` для обмена на токен. Это гарантирует, что даже если хакер перехватит Authorization Code в браузере, он не сможет получить по нему токен, так как у него нет `code_verifier`.
3.  **Защита от Replay-атак (Nonce):** Хранение одноразового параметра `nonce` (Number used once), который зашивается в ID Token. Локальный сервис проверяет, чтобы `nonce` в полученном токене совпадал с тем, что был сохранен в этой таблице перед началом флоу.
4.  **Контекст возврата:** Позволяет сохранить параметр `return_url` — адрес страницы (например, `/dashboard/settings`), на которой находился пользователь до начала входа, чтобы вернуть его ровно туда же после успешной авторизации.

## 2. Атрибуты (поля) сущности
**Таблица:** `oidc_auth_flows`

*В соответствии с «Белой книгой разработчика баз данных», для таблицы с экстремально высокой частотой `INSERT` и `DELETE` (эфемерные данные) в качестве первичного ключа используется `UUID`, который также служит значением параметра `state` для оптимизации индексов.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `uuid` | PK, NOT NULL | **Идентификатор потока (`state`).** Генерируется сервером (UUID v4) в момент начала логина. Именно это значение передается в STEOS ID в качестве параметра `state`. При возврате пользователя (Callback), поиск записи происходит по этому ID. |
| `device_fingerprint` | `varchar(255)` | NOT NULL | **Отпечаток устройства.** Хэш характеристик браузера/железа. Защищает от атаки "Session Fixation": если флоу начал один браузер, завершить его (сделать Callback) может только этот же самый браузер. |
| `nonce` | `varchar(100)` | NOT NULL | **Одноразовый крипто-токен (Nonce).** Случайная строка. Отправляется в STEOS ID. STEOS ID обязан вернуть этот `nonce` внутри подписанного `id_token`. Сервер сверяет их для предотвращения атак с подменой токенов. |
| `code_verifier` | `varchar(200)` | NOT NULL | **Секрет PKCE (Proof Key).** Строка высокой энтропии (43-128 символов). При начале флоу сервер отправляет в STEOS ID ее хэш (`code_challenge`), а при обмене кода на токен — отправляет сам `code_verifier`. STEOS ID сравнивает их. Это 100% защита от перехвата. |
| `return_url` | `varchar(1024)`| NULL | **URL возврата.** Внутренний путь платформы (например, `/workspace/123/tasks`), куда нужно перенаправить пользователя после успешного завершения логина. |
| `expires_at` | `int8` | NOT NULL | **Время истечения (TTL).** Unix Timestamp (UTC). Время жизни потока очень короткое (например, 10 минут от `created_at`). Пользователь должен успеть ввести пароль в STEOS ID и вернуться. Если время вышло — флоу считается брошенным (Abandoned). |
| `created_at` | `int8` | NOT NULL | **Дата инициализации потока.** Unix Timestamp (UTC). |

*Обязательный индекс:*
B-Tree индекс по `expires_at`. Так как это "мусорная" таблица, она требует агрессивного фонового процесса (Garbage Collector), который каждые несколько минут делает `DELETE FROM oidc_auth_flows WHERE expires_at < NOW()`.

## 3. Связи с другими сущностями и микросервисами

В силу своей эфемерной природы (State Machine), эта сущность **не имеет жестких внешних ключей (`FOREIGN KEY`)** на другие таблицы. Она существует в вакууме времени между двумя HTTP-запросами.

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **STEOS ID**<br>(Global IdP) | **Протокольная зависимость.** STEOS ID является потребителем параметров `state`, `nonce` и `code_challenge`, сгенерированных и сохраненных в этой таблице. |
| **Авторизованная сессия**<br>(`authorized_sessions`) | **Последовательная (Workflow).** Если флоу (на базе этой таблицы) завершается успешно, запись `oidc_auth_flows` физически удаляется, а на свет появляется долгоживущая `authorized_sessions`. |
## 4. Жизненный цикл и Алгоритм работы

1.  **Инициализация (Auth Request Phase):**
    *   Пользователь на платформе нажимает "Войти".
    *   `Authorization Service` генерирует `id` (state), `nonce`, `code_verifier` и вычисляет `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))`.
    *   Сервис делает `INSERT` в `oidc_auth_flows` (с TTL = 10 минут) и читает `device_fingerprint`.
    *   Сервис отвечает браузеру HTTP-редиректом: `302 Found`. 
    *   URL редиректа: `https://id.steos.io/oauth/authorize?response_type=code&client_id=...&state={id}&nonce={nonce}&code_challenge={hash}&code_challenge_method=S256`.
2.  **Ожидание (Suspended State):**
    *   Пользователь находится на стороне STEOS ID, вводит пароли, проходит 2FA. Локальная платформа в это время "спит" и ждет.
3.  **Возврат и Валидация (Callback Phase):**
    *   STEOS ID редиректит пользователя обратно на платформу: `https://app.steos.io/auth/callback?code=SPLIT_CODE_XYZ&state={id}`.
    *   `Authorization Service` извлекает `state` из URL. Это и есть наш `id` (Primary Key).
    *   Делает `SELECT * FROM oidc_auth_flows WHERE id = {state}`.
    *   Если запись не найдена или `expires_at < NOW()`, возвращает ошибку `400 Invalid State` (защита от CSRF).
    *   Проверяет `device_fingerprint` из браузера с тем, что в базе. Если не совпали — ошибка `403 Forbidden` (кто-то другой пытается подсунуть нам код).
4.  **Обмен Кода и Гашение (Token Exchange & Consumption):**
    *   Локальный сервис шлет S2S-запрос в STEOS ID: `POST /oauth/token` с параметрами `code=SPLIT_CODE_XYZ` и `code_verifier={code_verifier_из_БД}`.
    *   Получает JWT-токены (`id_token`, `access_token`).
    *   Проверяет, что `nonce` внутри `id_token` совпадает с `nonce` из базы.
    *   **Удаление:** Запись физически удаляется (`DELETE FROM oidc_auth_flows WHERE id = {state}`). Это гарантирует одноразовость потока.
    *   Пользователь авторизован и перенаправляется на сохраненный `return_url`.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Stateless Client (Бессостоятельный клиент)** | До повсеместного внедрения PKCE, разработчики часто хранили `state` и `nonce` в Cookies браузера. В микросервисной архитектуре это антипаттерн (Cookies могут быть заблокированы настройками приватности Apple ITP или потеряны при кросс-доменных редиректах). Хранение стейта OIDC-потока на бэкенде (в БД или Redis) делает процесс входа железобетонно стабильным в любом браузере. |
| **Idempotency & Single Use (Одноразовость)** | Успешный Callback (Шаг 3) *обязан* удалять запись из БД. Если сервер STEOS ID "лагнет" и пользователь дважды кликнет "Назад" в браузере (инициировав двойной Callback с одним и тем же кодом), второй запрос не найдет запись в `oidc_auth_flows` и безопасно "умрет". Это исключает дублирование сессий и гонку данных (Race Condition). |
| **Memory vs PostgreSQL** | Хотя по Белой книге мы описываем эту сущность как таблицу в PostgreSQL, в высоконагруженных инсталляциях (`steos.io`) этот класс данных **идеально ложится в Redis**. Запись живет 10 минут, не требует бекапов (если сервер упадет в момент логина, юзер просто залогинится заново) и требует молниеносного чтения по ключу. Архитектор может принять решение перенести физическое хранение `oidc_auth_flows` из реляционной СУБД в in-memory Key-Value хранилище (с ключом `oidc:flow:{state}`). |


# Кэш ключей IdP (`idp_jwks_cache`)

## 1. Общее описание

**Кэш ключей IdP (Identity Provider JWKS Cache)** — это критическая инфраструктурная сущность микросервиса Authorization Service, предназначенная для локального хранения криптографических публичных ключей (Public Keys), выпущенных глобальным STEOS ID или сторонними доверенными провайдерами.

По стандарту OIDC (OpenID Connect) каждый выпускаемый JWT-токен подписывается приватным ключом сервера авторизации (IdP). Чтобы локальный `Authorization Service` платформы STEOS мог убедиться, что токен подлинный (не подделан хакером), ему нужен парный публичный ключ. Эти ключи IdP публикует в формате **JWKS (JSON Web Key Set)** на специальном эндпоинте (например, `https://id.steos.io/.well-known/jwks.json`).

Данная таблица (в связке с In-Memory кэшем) реализует паттерн **Distributed JWKS Caching**. Она отвечает на вопрос: **«Каким математическим ключом я должен проверить этот конкретный токен, чтобы не лезть за ним в интернет?»**.

**Архитектурное назначение:**
1.  **Ultra-Low Latency (Сверхнизкая задержка):** Валидация каждого запроса (сотен тысяч в секунду) к API-шлюзам требует проверки JWT-токена ИИ-Агента или внутреннего сервиса. Выполнение HTTP-запроса за публичным ключом к `id.steos.io` при каждой проверке убьет производительность. Хранение ключей локально снижает время проверки подписи до микросекунд (выполнение чистой математики).
2.  **Отказоустойчивость (Resilience & Air-Gapping):** Если глобальный сервер STEOS ID упадет, или если локальный контур (On-Premise банк) временно потеряет связь с глобальной сетью, локальный `Authorization Service` продолжит успешно проверять токены, используя закэшированные ключи, обеспечивая непрерывность бизнес-процессов (Zero-Downtime Token Validation).
3.  **Поддержка ротации ключей (Key Rotation):** Глобальный STEOS ID периодически (например, раз в 90 дней) генерирует новые пары ключей из соображений безопасности. Эта сущность позволяет хранить *набор* ключей одновременно, бесшовно переходя на новые ключи, пока старые токены доживают свой век.

## 2. Атрибуты (поля) сущности
**Таблица:** `idp_jwks_cache`

*В соответствии с «Белой книгой разработчика баз данных», для первичного ключа используется строковый тип `varchar`, так как идентификатор ключа (`kid`) в стандарте JWK является строкой (часто хэшем), которую генерирует внешний провайдер.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `kid` | `varchar(100)` | PK, NOT NULL | **Key ID (Идентификатор ключа).** Уникальная строка, которая зашита в заголовок (Header) каждого входящего JWT-токена. Именно по этому полю бэкенд ищет нужный ключ для проверки подписи. |
| `issuer_url` | `varchar(255)` | NOT NULL | **URL Издателя (IdP).** Домен, выпустивший ключ (например, `https://id.steos.io`). Позволяет Authorization Service работать с несколькими IdP одновременно (например, глобальный STEOS ID и корпоративный Azure AD в режиме федерации). |
| `algorithm` | `varchar(20)` | NOT NULL | **Алгоритм подписи.** Значение поля `alg` из стандарта JWK (например, `RS256`, `ES256`). Указывает локальному крипто-провайдеру (C# `JwtSecurityTokenHandler`), какую математику применять при проверке. |
| `key_type` | `varchar(10)` | NOT NULL | **Тип ключа.** Значение поля `kty` из стандарта JWK (например, `RSA`, `EC`). |
| `public_key_pem` | `varchar(4096)`| NOT NULL | **Публичный ключ (Материал).** Само тело ключа. Изначально провайдер отдает ключ в формате JWK (параметры `n` и `e` для RSA). Для удобства кэширования и работы C#-библиотек, бэкенд при сохранении конвертирует JWK в привычный формат PEM (Base64 с заголовками `-----BEGIN PUBLIC KEY-----`). |
| `expires_at` | `int8` | NOT NULL | **Срок годности в кэше (TTL).** Unix Timestamp (UTC). Сервер авторизации не доверяет кэшу вечно. Это время (например, +24 часа от момента загрузки), после которого бэкенд обязан сделать фоновый сетевой запрос к IdP, чтобы проверить, не был ли ключ отозван (Revoked). |
| `created_at` | `int8` | NOT NULL | **Дата получения ключа.** Unix Timestamp (UTC). Время, когда локальная платформа скачала и закэшировала этот ключ. |
| `updated_at` | `int8` | NOT NULL | **Дата обновления.** Unix Timestamp (UTC). Обновляется при фоновом Refresh-цикле (если IdP подтвердил, что ключ все еще жив). |

*Обязательные индексы:*
1. B-Tree индекс по `(issuer_url, kid)` — гарантирует сверхбыстрый лукап ключа при разборе заголовка JWT, в котором указаны `iss` (из payload) и `kid` (из header).
2. B-Tree индекс по `expires_at` — для работы фонового воркера (Jwks Refresh Worker).

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **STEOS ID**<br>(Global IdP) | **Source of Truth (Источник правды).** Таблица является локальным зеркалом (Read-Only Replica) публичных ключей глобального сервера. Локальная платформа не имеет прав на редактирование этих ключей. |
| **In-Memory Cache**<br>(Redis / RAM) | **Мгновенная репликация.** Для производительности таблица БД кэшируется прямо в оперативной памяти каждого пода (Pod) Authorization Service (через `IMemoryCache` в ASP.NET Core) или в локальном Redis. Запросы к PostgreSQL происходят только при холодном старте микросервиса. |
## 4. Жизненный цикл и Алгоритм работы

Механика работы этой сущности опирается на процесс **OIDC Discovery**.

1.  **Холодный старт (Bootstrapping):**
    *   При запуске `Authorization Service` инициализирует JWKS-клиент.
    *   Клиент обращается к `https://id.steos.io/.well-known/openid-configuration`, находит там URL эндпоинта `jwks_uri`.
    *   Скачивает JSON-массив публичных ключей (обычно их 1-3 штуки).
    *   Парсит их (извлекает `kid`, `alg`, `kty`), конвертирует в PEM и делает `UPSERT` в таблицу `idp_jwks_cache`, устанавливая `expires_at = NOW() + 24h`.
2.  **Валидация токенов (Token Verification - Runtime):**
    *   На API Gateway прилетает запрос с JWT-токеном (от фронтенда или ИИ-Агента).
    *   Gateway парсит заголовок (Header) токена (без криптографической проверки) и извлекает `kid` = `"key-2026-01"`.
    *   Gateway лезет в свой RAM-кэш (или БД).
    *   **Сценарий А (Cache Hit):** Ключ найден. Gateway использует `public_key_pem` для математической проверки подписи. Если подпись верна — запрос пропускается к бизнес-микросервисам.
    *   **Сценарий Б (Cache Miss):** Ключ не найден (глобальный STEOS ID только что сгенерировал новый ключ). Gateway блокирует поток, делает срочный (синхронный) сетевой запрос к `jwks_uri`, скачивает новый набор ключей, сохраняет в БД, обновляет RAM-кэш и повторяет попытку валидации. (Этот процесс занимает ~100-200 мс, но происходит крайне редко — только при ротации).
3.  **Фоновое обновление (Background Refresh):**
    *   Внутри микросервиса работает `HostedService` (Background Worker).
    *   Раз в час он просыпается, делает `SELECT * FROM idp_jwks_cache WHERE expires_at < (NOW() + 2h)`.
    *   Если находит ключи, срок годности которых скоро истечет, воркер *асинхронно* запрашивает свежий JWKS у STEOS ID.
    *   Если STEOS ID убрал какой-то ключ из выдачи (например, ключ скомпрометирован), воркер физически удаляет (`DELETE`) эту строку из базы и кэша. Любые токены, подписанные удаленным ключом, перестанут валидироваться мгновенно.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Silent Key Rotation (Тихая ротация)** | Благодаря этой архитектуре, команда безопасности STEOS ID может генерировать новые приватные ключи хоть каждый день. Миллионы локальных инсталляций платформ (Воркспейсов) по всему миру автоматически, в фоновом режиме (по расписанию или при Cache Miss), подтянут новые публичные ключи в эту таблицу. Пользователи не заметят разрывов связи, система работает бесшовно. |
| **Resilience to OIDC Outages** | В случае глобального сбоя (например, DNS-провайдер STEOS ID недоступен, и `jwks_uri` не отдает ключи), локальная платформа (особенно On-Premise банки) продолжит работать в штатном режиме, опираясь на ключи, сохраненные в `idp_jwks_cache`, вплоть до истечения их локального `expires_at`. Это фундаментальное требование для систем с SLA 99.99%. |
| **Defense in Depth (Глубокая защита)** | При конвертации JWK в PEM бэкенд строго валидирует криптографические параметры. Если в OIDC-ответе от провайдера алгоритм (`alg`) указан как `none` (известная уязвимость JWT), система обязана выбросить исключение (Security Exception) и отказаться кэшировать такой "ключ", защищая платформу от подделки токенов на уровне ядра. |
