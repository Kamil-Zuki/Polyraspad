# Введение

Этот раздел описывает защитные механизмы, работающие на самом "краю" (Edge) платформы STEOS. 
Глобальный STEOS ID защищает глобальные аккаунты (пароли, 2FA, паспорта). Но если злоумышленник (или бот) не пытается взломать пароль, а просто решает заддосить (DDoS) саму платформу, выкачать публичные страницы парсером или украсть уже открытую сессию у честного пользователя — глобальный STEOS ID об этом даже не узнает.

Поэтому на **периметре инсталляции** (как правило **API Gateway — агрегатор** + логика **Authorization Service** по gRPC) обязан действовать **собственный локальный контур безопасности**, не зависящий от глобального IdP.

**Метафора:**
Представьте **Фейсконтроль на входе в конкретный ночной клуб**.
Глобальный STEOS ID — это государственная полиция, которая выдает паспорта. Полиции нет дела до того, что кто-то слишком часто заказывает бесплатные коктейли по акции (Гостевые квоты) или пришел в клуб в грязной обуви (Подозрительный Fingerprint).
Фейсконтроль клуба (**локальная политика и решения AUTH**, применяемые на входе через **Gateway**) сам решает, пускать ли человека внутрь. Если кто-то пытается пробежать мимо охраны (DDoS/Rate Limit), или человек внутри вдруг снимает маску и оказывается другим (Session Hijacking), фейсконтроль выкидывает его на улицу (Local Ban), не обращаясь за разрешением к государственной полиции.

## Возможности данного раздела

Ниже представлен перечень функциональных требований (SR) к механизмам локальной безопасности и квотирования.

| Код | Название и Описание |
| :--- | :--- |
| **SR-AUTH-SQ-01** | **Защита от угона сессии (Session Hijacking):** Валидация цифрового отпечатка (Device Fingerprint) при каждом запросе. Смена IP/Браузера при живой Cookie приводит к немедленному аннулированию сессии (Revoke). |
| **SR-AUTH-SQ-02** | **Гостевые Лимиты (Guest Feature Quotas):** Синхронизация с `Platform Service` для строгого учета и ограничения потребления платных фич платформы анонимными пользователями (например, "3 бесплатные генерации ИИ"). |
| **SR-AUTH-SQ-03** | **Локальная блокировка (Local Firewall/Ban):** Временные блокировки на основе аномальной активности. Защита от парсинга и брутфорса эндпоинтов авторизации. |
| **SR-AUTH-SQ-04** | **Rate Limiting & API Throttling:** Ограничение количества попыток инициализации OIDC-потока, старта гостевых сессий или генерации One-Time билетов с одного IP в единицу времени. |
| **SR-AUTH-SQ-05** | **Снятие локальной блокировки (Unban):** Ручное удаление IP-адреса или Device Fingerprint из blocklist при ложноположительном срабатывании защитных механизмов. |
| **SR-AUTH-SQ-06** | **Репортинг подозрительной активности:** Прием сигналов от внутренних сервисов о мошенничестве, брутфорсе или аномалиях с последующим throttling, баном или эскалацией. |
| **SR-AUTH-SQ-07** | **Алерты безопасности и обработка инцидентов:** Формирование локальных предупреждений ИБ, их выдача администраторам и жизненный цикл обработки инцидента. |

# Детальная спецификация требований

## SR-AUTH-SQ-01: Защита от угона сессии (Session Hijacking)

В основе архитектуры платформы лежит Phantom Token (HttpOnly Cookie), который надежно защищает от XSS (внедрения вредоносного JS). Однако существует другой вектор атаки: злоумышленник может перехватить трафик в открытой Wi-Fi сети (если нет HSTS) или получить физический доступ к компьютеру жертвы, скопировать значение Cookie (UUID) из браузера и вставить в свой браузер дома. Если API Gateway доверяет только значению Cookie, хакер получит полный доступ.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Хэш-отпечаток (Fingerprint)** | При старте сессии (во время логина или создания гостевой сессии) фронтенд собирает уникальный слепок устройства пользователя (User-Agent, разрешение экрана, Canvas-хэш, часовой пояс, установленные шрифты) и передает его бэкенду. Бэкенд вычисляет SHA-256 отпечаток и сохраняет его в таблицу `authorized_sessions` и в Redis. |
| **Сетевая привязка (Network Binding)** | Бэкенд также сохраняет IP-адрес (или подсеть), с которого была инициирована сессия. |
| **Валидация каждого запроса** | API Gateway, получая любой бизнес-запрос с Cookie, извлекает Fingerprint и IP из заголовков/полезной нагрузки текущего запроса и сравнивает их с эталоном в Redis. |
| **Fail-Fast (Нулевая толерантность)** | Если значение Cookie совпадает, но Fingerprint кардинально отличается (кто-то пытается использовать украденную Cookie на другом устройстве), API Gateway немедленно обрывает запрос с `401 Unauthorized`, а саму сессию в Redis и БД помечает как `is_active = false` (Revoke). Хакер и жертва одновременно теряют доступ, что требует повторной (безопасной) аутентификации. |

### 2. Высокоуровневое описание

Представим **пропуск на секретный завод**.

1. **Выдача пропуска:** Вы устраиваетесь на работу. Охрана (Auth Service) выдает вам пластиковый пропуск (Cookie). Но кроме этого, охрана записывает ваш рост, цвет глаз и берет отпечаток пальца (Device Fingerprint).
2. **Обычный проход (Happy Path):** Каждое утро вы прикладываете пропуск к турникету. Турникет (API Gateway) мгновенно считывает пропуск, смотрит на вас камерой и сверяет с базой: "Пропуск валиден. Человек тоже совпадает (рост, глаза)". Двери открываются.
3. **Кража пропуска (Атака):** Карманник крадет ваш пропуск в метро. Он приходит на завод и прикладывает его к турникету.
4. **Блокировка (Fail-Fast):** Турникет видит валидный пропуск. Но камера замечает: "У этого человека другой рост и цвет глаз (другой браузер, ОС, IP-адрес)". Турникет понимает, что пропуск украден.
5. **Сжигание пропуска:** Турникет не просто не пускает карманника. Он мгновенно блокирует этот пропуск в базе данных (Revoke сессии в Redis). Теперь этот пропуск — просто кусок пластика. Когда вы (настоящий владелец) придете на завод и скажете, что потеряли пропуск, охрана выдаст вам новый, зная, что старым никто не смог воспользоваться.

### 3. Примеры взаимодействия (логические сценарии)

**Общие исходные данные:**
*   **Инициатор:** Веб-браузер пользователя (или скрипт хакера).
*   **Входящий запрос:** Любой бизнес-запрос к API (например, `GET /api/profile`).
*   **Контекст:** Наличие `steos_sess` Cookie и заголовка `X-Device-Fingerprint`.

#### Сценарий А: Легитимный запрос (Happy Path)

1.  **Запрос:** Пользователь открывает страницу профиля. Браузер шлет Cookie `steos_sess=sess-123` и заголовок `X-Device-Fingerprint: hash-abc`.
2.  **Чтение Redis:** API Gateway читает сессию `sess-123` из Redis. Видит в ней поле `fingerprint: hash-abc`.
3.  **Сравнение:** `hash-abc` (из заголовка) == `hash-abc` (из Redis). IP-адреса также совпадают (или находятся в одной AS).
4.  **Пропуск:** Gateway добавляет внутренние заголовки (`X-Global-Actor-Id`) и пропускает запрос в `Profile Service`. Пользователь видит свой профиль.

#### Сценарий Б: Использование украденной Cookie (Negative Path - Session Revoked)

1.  **Запрос хакера:** Хакер украл Cookie `sess-123` (например, вытащил из чужого ноутбука) и вставил в свой браузер (или скрипт `curl`). Он делает запрос `GET /api/profile`. Его скрипт шлет свой фингерпринт (или не шлет его вовсе), IP-адрес отличается.
2.  **Чтение Redis:** API Gateway находит сессию `sess-123` в Redis.
3.  **Сравнение (Mismatch):** Gateway видит, что эталонный фингерпринт в Redis — `hash-abc`, а хакер прислал `hash-xyz` (или пустоту). IP-адреса тоже кардинально различаются (жертва в Москве, хакер в Китае).
4.  **Срабатывание защиты (Kill Switch):**
    *   Gateway **не** пускает запрос дальше.
    *   Gateway отправляет команду в Redis: `DEL steos:sess:sess-123` (мгновенное убийство сессии).
    *   Асинхронно пишет в WORM-лог аудита БД: `SESSION_HIJACKING_ATTEMPT_DETECTED` для сессии `sess-123`. Обновляет в БД статус сессии на `is_active = false`.
5.  **Возврат ошибки:** Хакер получает HTTP `401 Unauthorized` с пустым телом (чтобы не давать подсказок). При попытке повторить запрос он снова получит 401, так как сессии в Redis больше нет.

## SR-AUTH-SQ-02: Гостевые Лимиты (Guest Feature Quotas)

STEOS предоставляет "демо-доступ" для вовлечения пользователей (Public Mode). Если пользователь не авторизован (не прошел OIDC), он получает гостевую сессию (SR-AUTH-SM-03).
Проблема: Анонимы могут потреблять дорогие ресурсы платформы (например, вызовы OpenAI API или генерацию картинок). Хакеры могут написать скрипт, который будет постоянно стирать Cookie и бесконечно генерировать картинки бесплатно.

### 1. Цель и ключевые принципы

| Принцип | Описание                                                                                                                                                                                                                                                                                                                                 |
| :--- | :--- |
| **Таблица `guest_feature_usages`** | Auth Service имеет локальную таблицу-счетчик в PostgreSQL и быстрые счетчики в Redis (например, `INCR guest:quota:hash-abc:ai_gen`), связанные с гостевой сессией (которая жестко привязана к Fingerprint'у железа хакера, см. SR-AUTH-SM-03).                                                                                           |
| **Синхронный чекап (Feature Check)** | Когда аноним пытается сгенерировать картинку, бизнес-микросервис (`Integration Service`) делает синхронный gRPC вызов к Auth Service (или проверяет заголовки Gateway): "Можно ли этому гостю использовать фичу `AI_GENERATE`?".                                                                                                         |
| **Блокировка по фингерпринту** | Если лимит (например, 3 раза в день) исчерпан, Auth Service возвращает отказ. Бизнес-сервис отдает на фронтенд `403 Forbidden` с предложением зарегистрироваться (запустить OIDC-флоу). Если хакер сотрет Cookie, при следующем заходе Auth Service вычислит его по Fingerprint'у железа, найдет старые счетчики и снова применит лимит. |

### 2. Высокоуровневое описание

Представим **бесплатную дегустацию в супермаркете**.

1. **Дегустация (Гостевой запрос):** Покупатель без клубной карты (Гость) подходит к стенду с сыром. Промоутер (Бизнес-сервис) готов дать ему кусочек, но сначала смотрит на бейджик гостя (Cookie).
2. **Проверка у менеджера (Feature Check):** Промоутер спрашивает по рации менеджера зала (Auth Service): "Гость с бейджиком 999 хочет сыр. Можно?".
3. **Учет (Счетчик Redis):** Менеджер смотрит в блокнот. "Так, этот гость берет сыр первый раз. Можно!". Менеджер ставит галочку в блокноте (Redis `INCR`).
4. **Отказ (Лимит исчерпан):** Гость съедает сыр, потом подходит снова, потом еще раз. На четвертый раз менеджер говорит по рации: "Стоп! Гость 999 уже съел 3 куска. Лимит исчерпан. Скажи ему, чтобы покупал целую пачку на кассе (зарегистрировался)". Промоутер вежливо отказывает.
5. **Защита от хитрости (Фингерпринт):** Гость снимает бейджик 999, надевает очки и подходит как новый человек с бейджиком 888 (стер Cookie). Менеджер смотрит на него через камеры с распознаванием лиц (Device Fingerprint) и говорит: "Я тебя узнал, ты тот самый парень, который съел 3 куска сыра 10 минут назад. Никакого сыра".

### 3. Примеры взаимодействия (логические сценарии)

**Общие исходные данные:**
*   **Инициатор:** Анонимный пользователь (гость) с временной Cookie `guest_sess`.
*   **Входящий запрос:** Тяжелый бизнес-запрос (например, `POST /api/ai/generate`).
*   **Контекст:** Гостю разрешено генерировать 3 картинки.

#### Сценарий А: Успешное использование квоты (Happy Path)

1.  **Запрос:** Фронтенд шлет запрос на генерацию в `Integration Service`.
2.  **Валидация Gateway:** API Gateway пропускает запрос, прокидывая заголовок `X-Guest-Id: hash-abc`.
3.  **Проверка квоты (gRPC):** `Integration Service` перед началом генерации (до обращения к OpenAI) делает gRPC вызов `CheckGuestQuota(guest_id="hash-abc", feature="AI_GEN")` к `Auth Service`.
4.  **Учет в Redis:** `Auth Service` делает в Redis `INCR guest:quota:hash-abc:AI_GEN`. Получает ответ `1` (это первый запрос). Лимит — 3.
5.  **Разрешение:** `Auth Service` отвечает `Integration Service` по gRPC: `{"allowed": true, "remaining": 2}`.
6.  **Исполнение:** `Integration Service` генерирует картинку, списывает деньги со счета платформы и отдает результат гостю.

#### Сценарий Б: Исчерпание квоты и попытка обхода (Negative Path)

1.  **Исчерпание:** Гость сделал 3 картинки. Счетчик в Redis `guest:quota:hash-abc:AI_GEN` равен `3`.
2.  **Попытка обхода:** Хакер стирает Cookie в браузере и обновляет страницу. Платформа выдает ему новую гостевую сессию (например, с ID `hash-xyz`), но аппаратный отпечаток `fingerprint` остался прежним.
3.  **Новый запрос:** Хакер шлет запрос на генерацию `POST /api/ai/generate`.
4.  **Проверка квоты (gRPC):** `Integration Service` делает вызов `CheckGuestQuota(guest_id="hash-xyz", fingerprint="REAL_HARDWARE_HASH")`.
5.  **Блокировка Auth Service:** `Auth Service` смотрит не на Cookie, а на счетчики, привязанные к `REAL_HARDWARE_HASH`. Он видит, что этот компьютер уже сгенерировал 3 картинки.
6.  **Отказ:** Возвращает по gRPC `{"allowed": false}`.
7.  **Возврат ошибки:** `Integration Service` прерывает работу и отдает на фронтенд HTTP `403 Forbidden` (ProblemDetails: `code: "GUEST_QUOTA_EXCEEDED"`, `detail: "You have reached the limit of free generations. Please sign in."`). Хакер не потратил деньги платформы.

## SR-AUTH-SQ-03: Локальная блокировка (Local Firewall/Ban)

Защита инсталляции от вредоносного трафика до того, как он создаст нагрузку на глобальный STEOS ID или внутренние микросервисы.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Справочник `local_ban_reasons`** | Единый реестр локальных инцидентов безопасности: `GUEST_QUOTA_ABUSE` (попытка автоматизации обхода лимитов), `MALICIOUS_PAYLOAD` (попытка SQL-инъекции в заголовках), `API_RATE_LIMIT` (DDoS-атака). |
| **Динамический DenyList (`local_suspicious_activities`)** | Если API Gateway (или внутренний WAF) фиксирует откровенно вредоносную активность от определенного IP-адреса или Fingerprint'а, он помещает этот идентификатор во временный "черный список" в Redis (с TTL от 15 минут до 24 часов). |
| **Drop Connection** | Любые последующие запросы (даже к публичным страницам вроде Главной) от забаненного IP/Fingerprint отбиваются на самом раннем этапе (Edge) с ошибкой `403 Forbidden`. Запрос даже не доходит до бизнес-логики. |

### 2. Высокоуровневое описание

Представим **Вышибалу на входе в клуб**.

1. **Агрессивный гость (DDoS/Сканер):** Кто-то пытается выломать дверь в клуб или кричит оскорбления (шлет 1000 запросов в секунду на эндпоинт логина).
2. **Черный список (DenyList):** Вышибала (API Gateway / WAF) фотографирует этого человека (запоминает его IP-адрес) и вешает фотографию на доску "Не пускать 24 часа".
3. **Глухая стена (Drop Connection):** Когда этот человек через минуту пытается просто подойти к клубу и спросить "Который час?" (запросить публичную Главную страницу), вышибала даже не разговаривает с ним. Он молча преграждает путь (отдает 403 Forbidden). Человек полностью изолирован от клуба, чтобы не мешать другим отдыхать.

### 3. Примеры взаимодействия (логические сценарии)

**Общие исходные данные:**
*   **Инициатор:** Вредоносный бот или скрипт.
*   **Входящий запрос:** Сканирование уязвимостей (например, попытка запросить `/api/auth/login?state=' OR 1=1 --`).

#### Сценарий А: Обнаружение атаки и бан (Negative Path)

1.  **Атака:** Бот шлет POST-запрос с заведомо вредоносным payload'ом (например, XSS скрипт в поле `email` при попытке входа).
2.  **Детектирование:** Auth Service (или WAF на уровне Gateway) валидирует входные данные и фиксирует нарушение безопасности.
3.  **Занесение в DenyList:** Auth Service:
    *   Пишет в БД `access_audit_logs` событие `SECURITY_VIOLATION` с указанием IP хакера (например, `192.168.1.55`).
    *   Создает в Redis ключ `steos:ban:ip:192.168.1.55` со значением `MALICIOUS_PAYLOAD` и TTL = 3600 секунд (1 час).
4.  **Отказ:** Бот получает `400 Bad Request` на свой изначальный запрос.
5.  **Блокировка трафика:** Бот делает следующий запрос (например, пытается просто открыть `GET /api/config`).
6.  **Edge Drop:** Самая первая middleware в API Gateway (до парсинга Cookie, до роутинга) проверяет IP бота в Redis (`EXISTS steos:ban:ip:192.168.1.55`). Получает `true`.
7.  **Отбой:** Gateway немедленно прерывает обработку и отдает пустое тело с HTTP `403 Forbidden`. Бот бьется о глухую стену в течение часа.

## SR-AUTH-SQ-04: Rate Limiting & API Throttling

Защита узких мест (Bottlenecks) микросервиса авторизации. В отличие от локального бана (который применяется за злонамеренные действия), Rate Limiting применяется для сглаживания легитимных, но слишком частых запросов (защита от "Шторма").

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Точечные лимиты (Sliding Window/Token Bucket)** | Настройка лимитов на конкретные критичные эндпоинты через алгоритмы скользящего окна в Redis. |
| **Защита OIDC-интерфейсов** | Жесткое лимитирование (например, 5 запросов в минуту с одного IP) на эндпоинт инициализации OIDC (`/api/auth/login`) и эндпоинт обработки Callback'а. Это защищает базу данных `oidc_auth_flows` от переполнения "мусорными" `state` и `nonce` параметрами (DDoS на диск/память). |
| **Защита One-Time Tickets** | Лимитирование (например, 10 запросов в минуту на пользователя) на генерацию одноразовых билетов (`/api/auth/tickets/generate`, SR-AUTH-SM-04), чтобы злоумышленник (или баг во фронтенде) не смог исчерпать память Redis миллионами 15-секундных токенов. При превышении сервис возвращает `429 Too Many Requests`. |

### 2. Высокоуровневое описание

Представим **кассу в метро в час пик**.

1. **Час пик (Шторм запросов):** На станцию внезапно приезжает электричка с тысячей человек. Все бегут к одной кассе (Эндпоинт `/api/auth/login`), чтобы купить билет.
2. **Турникет-дозатор (Rate Limiting):** Перед кассой стоит турникет-вертушка, который пропускает строго по 5 человек в минуту. Кассир (База Данных) спокойно обслуживает каждого, не сходя с ума от толпы.
3. **Очередь (Throttling/429):** Те, кто бежит шестым в эту минуту, упираются в закрытый турникет. На табло загорается надпись: "Подождите немного, слишком много людей" (HTTP `429 Too Many Requests`). Они ждут пару секунд и проходят в следующую минуту. Касса не ломается, все в итоге получают билеты, просто чуть медленнее.

### 3. Примеры взаимодействия (логические сценарии)

**Общие исходные данные:**
*   **Инициатор:** Фронтенд-приложение, зациклившееся из-за бага (или бот).
*   **Входящий запрос:** `POST /api/auth/tickets/generate` (генерация одноразового билета).
*   **Контекст:** На этот эндпоинт установлен лимит: 10 запросов в минуту от одного `session_id`.

#### Сценарий А: Превышение лимита (Negative Path - 429)

1.  **Баг фронтенда:** Фронтенд-приложение из-за ошибки в цикле `useEffect` начинает слать запросы на генерацию билета каждые 100 миллисекунд.
2.  **Учет (Redis):** Auth Service принимает первые 10 запросов. Для каждого он инкрементирует счетчик в Redis `rate:tickets:sess-123` (алгоритм Sliding Window) и успешно генерирует билеты.
3.  **Срабатывание лимита:** На 11-й запрос (в ту же секунду) алгоритм в Redis сообщает, что счетчик превысил лимит (10).
4.  **Отказ:** Сервис **не** генерирует 11-й билет (защищая память от переполнения мусором). Он немедленно возвращает HTTP `429 Too Many Requests` с заголовком `Retry-After: 60` (повторите через 60 секунд).
5.  **Восстановление (Cool-down):** Через минуту окно сдвигается, счетчик в Redis сбрасывается. Если фронтенд успокоился и шлет 1 запрос, он снова успешно выполняется. Сервис спас сам себя от Out Of Memory (OOM) из-за бага на клиенте.

## SR-AUTH-SQ-05: Снятие локальной блокировки (Unban)

Автоматические системы защиты всегда имеют риск ложноположительных срабатываний. Поэтому сервис должен поддерживать контролируемый разбан субъекта с обязательным аудитом и указанием причины.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Ручной контроль** | Разбан выполняется только уполномоченным администратором или инженером ИБ. |
| **Точечное действие** | Можно снять блокировку с конкретного IP, CIDR, fingerprint или иного субъекта без массового пересмотра blacklist. |
| **Аудит решения** | Каждое снятие блокировки логируется как отдельное событие безопасности. |
| **Неотменяемость контекста инцидента** | Разбан не стирает историю первичного инцидента, а лишь меняет текущее состояние доступа. |

### 2. Высокоуровневое описание

Представим **службу охраны бизнес-центра, которая умеет не только вносить людей в черный список, но и снимать ошибочные запреты**.

1. **Срабатывание защиты:** Система или охранник блокирует посетителя по IP или отпечатку устройства.
2. **Проверка жалобы:** Позже выясняется, что срабатывание могло быть ложным.
3. **Ручное решение:** Уполномоченный сотрудник безопасности снимает блокировку.
4. **Возврат в обычный контур:** Субъект снова проходит стандартные проверки, не оставаясь навсегда в бане.

### 3. Примеры взаимодействия (логические сценарии)

#### Ложноположительная блокировка (Happy Path)

1. Пользователь или саппорт сообщает, что доступ был заблокирован ошибочно.
2. Администратор ИБ проверяет контекст и инициирует `unban`.
3. Запись удаляется из blocklist, а событие фиксируется в WORM-аудите.
4. Новые запросы субъекта снова проходят стандартный контур валидации.

## SR-AUTH-SQ-06: Репортинг подозрительной активности

Не все признаки атаки видны самому Authorization Service. Некоторые аномалии впервые замечают бизнес-сервисы: биллинг, интеграции, CRM, AI-воркеры. Это требование описывает централизованный канал передачи таких сигналов.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Прием внешних сигналов риска** | Бизнес-сервисы могут сообщать о массовых ошибках, мошеннических паттернах или brute-force поведении. |
| **Единая точка принятия защитных мер** | Решение о throttling, бане или создании alert принимает Auth Service. |
| **Агрегация краткоживущих нарушений** | Сигналы накапливаются в Redis-окне и оцениваются по порогам, а не только по единичному факту. |
| **Эскалация без немедленного бана** | Сервис может сначала снизить лимиты, затем создать alert, и только при превышении порога применить жесткую блокировку. |

### 2. Высокоуровневое описание

Представим **диспетчерскую службу безопасности, куда другие отделы звонят при обнаружении подозрительного поведения**.

1. **Внешний сигнал:** Биллинг, CRM или другой сервис замечает аномалию, которую Auth Service сам не видел.
2. **Передача сигнала:** Этот сервис передает в Auth Service сведения об IP, сессии или fingerprint нарушителя.
3. **Агрегация риска:** Auth Service складывает сигнал в локальные счетчики и оценивает серьезность.
4. **Принятие мер:** В зависимости от порога сервис throttling-ит, банит или создает alert для ручного разбора.

### 3. Примеры взаимодействия (логические сценарии)

#### Порог риска превышен (Happy Path)

1. Внутренний сервис замечает подозрительную серию действий от одного IP, Session или Fingerprint.
2. Он отправляет сигнал в Auth Service.
3. Auth Service обновляет счетчики риска и принимает решение: игнорировать, throttle или забанить.
4. При необходимости создается alert для ручного разбора.

## SR-AUTH-SQ-07: Алерты безопасности и обработка инцидентов

После того как система заметила риск, нужен отдельный слой для видимости инцидентов: список активных предупреждений, статусы обработки и действия администратора.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Жизненный цикл alert-а** | Инцидент может быть создан, просмотрен, подтвержден, отклонен как false positive и закрыт. |
| **Нормализованный формат** | Alert содержит тип угрозы, severity, связанный actor/session/ip, время и технический контекст. |
| **Связь с автоматической защитой** | Alert может быть следствием anti-hijacking, fail2ban или внешнего `ReportSuspiciousActivity`. |
| **Поддержка SOC / админ-панели** | Предупреждения доступны для UI и внешних процессов мониторинга безопасности. |

### 2. Высокоуровневое описание

Представим **центр реагирования, где каждое подозрительное событие превращается в карточку инцидента для дежурного офицера**.

1. **Обнаружение риска:** Автоматическая защита или внешний сервис замечают угрозу.
2. **Создание карточки:** Auth Service формирует нормализованный `SecurityAlert`.
3. **Ручная обработка:** Администратор просматривает предупреждение и выбирает резолюцию.
4. **Сохранение следов:** Даже после закрытия инцидента его история остается доступной для расследования и аналитики.

### 3. Примеры взаимодействия (логические сценарии)

#### Обработка настоящего инцидента (Happy Path)

1. Anti-hijacking фиксирует mismatch fingerprint или другой сервис отправляет high-severity report.
2. Auth Service создает локальный `SecurityAlert`.
3. Администратор просматривает список активных предупреждений и принимает решение.
4. По результату инцидент переводится в `resolved` или `false_positive`, а история остается доступной для расследования.
