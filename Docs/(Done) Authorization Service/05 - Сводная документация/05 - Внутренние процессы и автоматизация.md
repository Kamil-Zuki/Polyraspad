# Введение

Данный документ описывает процессы и правила использования Redis для обеспечения консистентности и отказоустойчивости распределенной микросервисной архитектуры Authorization Service. В эту группу входят инфраструктурные механизмы: синхронизация WebSocket-подключений между репликами (SignalR Backplane), алгоритм распределенных блокировок (Redlock) для фоновых задач и гарантия идемпотентности REST API (Idempotency Keys).

# 1. Список операций Внутренних процессов и автоматизации

Перечень инфраструктурных механизмов координации.

| Метод (SR) | Описание операции |
| :--- | :--- |
| КАР-3 / SR-AUTH-WS-01 | SignalR Redis Backplane: Синхронизация WebSocket-событий между множеством подов (реплик) Authorization Service. |
| КАР-11 / SR-AUTH-LA-05 | Distributed Locks (Redlock): Распределенные блокировки для защиты фоновых выгрузок WORM-аудита и консьюмеров RabbitMQ от состояния гонки. |
| SR-AUTH-REST-01 | Idempotency Keys: Кэширование `Idempotency-Key` для защиты мутирующих REST API методов (например, слияние гостя) от случайных двойных списаний/вызовов. |

# SignalR Redis Backplane (SR-AUTH-WS-01)

## Общая информация

Реализация паттерна "Dynamic Context Routing" (КАР-3) требует надежной доставки WebSocket-событий (например, `session_revoked`, `context_updated`) до клиентов. Так как Authorization Service развернут в Kubernetes в нескольких экземплярах (подах), клиент может быть подключен к Pod-A, а бизнес-событие об инвалидации сгенерируется на Pod-B. Для того чтобы Pod-B мог отправить сообщение клиенту на Pod-A, используется Redis Pub/Sub (SignalR Backplane).

| Тип операции | Pub/Sub (Публикация/Подписка) |
| :--- | :--- |
| **Ключ Redis (Канал)** | Управляется внутренней реализацией SignalR (обычно префикс `signalr:`). |
| **DTO ответа** | Бинарный payload, инкапсулирующий имя метода (например, `SessionRevoked`) и аргументы. |
| **TTL** | Неприменимо (Pub/Sub — это fire-and-forget потоковая передача, данные не хранятся). |

## Логика обработки запроса

*   **Публикация:** Когда один из экземпляров Authorization Service вызывает `IHubContext.Clients.User(subjectId).SendAsync(...)`, SignalR фреймворк сериализует сообщение и публикует его в Redis-канал, соответствующий этому `subjectId`.
*   **Подписка:** Все экземпляры сервиса подписаны на Redis-каналы через `SUBSCRIBE`. Получив сообщение, каждый Pod проверяет, есть ли у него в памяти активные WebSocket-соединения для данного `subjectId`. Если да — он отправляет сообщение через открытый TCP-сокет клиенту.
*   **Итог:** Сообщение гарантированно доставляется пользователю независимо от того, к какому узлу балансировщик (Ingress) привязал его соединение.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Если Redis недоступен, SignalR Backplane отключается (деградация). В этом случае WebSocket-сообщения будут доставляться только тем клиентам, которые физически подключены к тому же Pod-у, где возникло событие. Это нарушит функционал мгновенного разлогина (КАР-1) и обновления контекста. |

# Distributed Locks (Redlock) (SR-AUTH-LA-05)

## Общая информация

Механизм распределенных блокировок необходим для защиты фоновых задач (Cron Jobs, Background Workers), консьюмеров RabbitMQ или критических участков кода от состояния гонки (Race Conditions), когда несколько подов пытаются одновременно выполнить одну и ту же эксклюзивную операцию (например, запустить тяжелую сборку WORM-архива аудита КАР-11).

| Тип операции | Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:lock:{resource_name}`<br>где `{resource_name}` = уникальный идентификатор ресурса (например, `audit_export_job_123` или `daily_billing_sync`). |
| **DTO ответа** | Строка `owner_id` (например, UUID пода или имя воркера), захватившего блокировку. |
| **TTL** | Статический (например, 30-60 секунд: `30` сек). Критически важен для защиты от "вечных" блокировок при падении воркера (Deadlock). |

## Логика обработки запроса

*   **Захват (Acquire):** Перед началом задачи Pod пытается установить ключ командой `SET auth:lock:{resource} {pod_id} NX PX 30000`. Флаг `NX` гарантирует, что запись произойдет только если ключа не существует. Если команда вернула `OK` — блокировка захвачена, Pod начинает работу. Если `null` — блокировка занята другим подом, текущий Pod должен подождать или отменить задачу.
*   **Продление (Extend):** Если задача долгая, Pod обязан периодически (например, каждые 10 секунд) обновлять TTL блокировки (Heartbeat), вызывая Lua-скрипт (чтобы продлить только свою блокировку).
*   **Освобождение (Release):** По завершении работы Pod удаляет ключ `DEL`. Для безопасности используется Lua-скрипт, проверяющий, что `owner_id` в ключе совпадает с текущим подом (чтобы случайно не удалить чужую блокировку, если своя уже истекла по TTL).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | При недоступности Redis распределенные блокировки не работают (Fail-Closed). Критические фоновые задачи не должны запускаться (во избежание дублирования работы и двойных списаний), либо запускаются только на заранее назначенном Leader-узле (Leader Election). |

# Idempotency Keys (SR-AUTH-REST-01)

## Общая информация

Для защиты мутирующих методов REST API (например, `POST /guests/convert` — слияние гостя или создание API-ключа) от двойных вызовов при сетевых ретраях (когда клиент не получил ответ и повторил запрос), используется кэширование ключей идемпотентности. Если запрос с таким ключом уже был успешно обработан, сервис вернет закэшированный ответ, не выполняя бизнес-логику повторно.

| Тип операции | Read (Чтение), Write (Запись) |
| :--- | :--- |
| **Ключ Redis** | `auth:idempotency:{idempotency_key}`<br>где `{idempotency_key}` = значение из HTTP-заголовка `Idempotency-Key` (UUIDv4 от клиента). |
| **DTO ответа** | Сериализованный HTTP-ответ (Status Code, Headers, JSON Body) предыдущего успешного вызова. |
| **TTL** | Длительный (обычно 24 часа: `86400` сек), чтобы покрыть все возможные окна ретраев клиента. |

## Логика обработки запроса

*   **Чтение (Проверка):** При поступлении POST/PUT запроса с заголовком `Idempotency-Key: X`, сервис выполняет `GET auth:idempotency:X`. Если ключ найден (и статус выполнения сохранен), сервис прерывает обработку и мгновенно возвращает закэшированный ответ (HTTP 200/201).
*   **Блокировка (In-Progress):** Если ключ не найден, сервис создает его со статусом `PROCESSING` (используя `SET NX`). Если другой параллельный запрос попытается использовать тот же ключ, он получит HTTP `409 Conflict` (или подождет).
*   **Запись (Успех):** После успешного коммита транзакции в БД, сервис обновляет ключ в Redis (сохраняя итоговый HTTP Response) и устанавливает TTL на 24 часа.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Если Redis недоступен, защита идемпотентности отключается (Fail-Open для обеспечения доступности). Запросы обрабатываются в штатном режиме, перекладывая обязанность по дедупликации на констрейнты (Unique Constraints) реляционной базы данных (PostgreSQL). |
