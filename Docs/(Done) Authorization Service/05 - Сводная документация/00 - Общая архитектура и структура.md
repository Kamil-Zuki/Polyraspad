# Обзор высокого уровня

Микросервис **«Сервис Авторизации» (Authorization Service)** отвечает за централизованное управление локальными сессиями, защиту периметра и обеспечение контекста для всех остальных микросервисов инсталляции платформы STEOS.

Сервис выступает в роли локального **Gatekeeper (Привратника)** и **Менеджера Сессий**, делегируя первичную идентификацию глобальному Identity Provider (STEOS ID). Его ключевая архитектурная особенность заключается в замене уязвимых JWT-токенов в браузере на безопасные **Phantom Tokens**, при которых весь критический стейт (роли, рабочие пространства, уровень доступа) хранится исключительно на стороне сервера.

Архитектура спроектирована с использованием **слоеной архитектуры (Layered Architecture)**, где слой API Gateway бесшовно внедряет бизнес-заголовки (Header Routing) во внутренний трафик. Основная цель архитектуры — обеспечить **Zero Trust** взаимодействие внутри системы, **бескомпромиссную защиту от угона сессий** (Session Hijacking) и **максимальную производительность** маршрутизации благодаря сверхбыстрому In-Memory слою на базе Redis для проверки каждого входящего запроса (latency < 2ms).

# 1. Назначение документа

## 1.1 Цель документа

Цель данного документа — объяснить ключевые архитектурные решения, внутреннюю логическую структуру и принципы взаимодействия микросервиса «Authorization Service» с глобальным STEOS ID, веб-браузером клиента и внутренними компонентами платформы.

Документ предназначен для разработчиков, архитекторов, системных аналитиков и специалистов по информационной безопасности (AppSec), которым необходимо понимать, КАК сервис устроен "под капотом", как работают его механизмы сессий, как происходит склейка контекста и защита от атак. Это фундаментальное руководство для безопасного масштабирования и расширения функционала контроля доступа платформы.

# 2. Внутренняя структура и компоненты

Сервис имеет четкое разделение ответственности и разбит на следующие логические слои и компоненты:

*   **API Gateway Layer (Слой шлюза):** Отвечает за прием всего внешнего входящего трафика платформы.
    *   Предоставляет публичные REST-эндпоинты для аутентификации, переключения контекста Workspace и управления сессиями.
    *   Перехватывает все бизнес-запросы, извлекает Cookie, обращается к Redis и, при успешной проверке, внедряет доверенные внутренние заголовки (`X-Workspace-Id`, `X-Global-Actor-Id`) перед перенаправлением запроса в целевой микросервис (Routing).
*   **Session Management Engine (Движок управления сессиями):** Ядро бизнес-логики сервиса.
    *   Реализует паттерн Phantom Token: управляет выдачей и отзывом HttpOnly Cookie.
    *   Обеспечивает жизненный цикл сессий (создание, тихое продление, инвалидация).
    *   Управляет специальными типами сессий: гостевыми сессиями, одноразовыми билетами для WebSocket и сессиями имперсонации (God Mode).
*   **Security & Policy Engine (Движок безопасности и политик):** Отвечает за защиту периметра и криптографию.
    *   Выполняет JIT-дешифровку Refresh-токенов.
    *   Обеспечивает кэширование и математическую валидацию ключей (JWKS) от STEOS ID.
    *   Выступает как локальный Firewall, ограничивая rate limit и блокируя подозрительные фингерпринты или IP-адреса.
*   **Data Access Layer (Слой доступа к данным):** Абстрагирует работу с хранилищами.
    *   **PostgreSQL:** Выступает как персистентный реестр. Хранит данные о сессиях (`authorized_sessions`, `guest_sessions`), журнал локального аудита доступа WORM (Append-Only) и настройки файрвола.
    *   **Redis:** Выступает как сверхбыстрый слой хранения состояний (Stateful Session Store), обеспечивающий мгновенный доступ (latency < 2ms) к параметрам сессии для проверки каждого HTTP-запроса платформы без нагрузки на основную БД.
*   **Integration Layer (Интеграционный слой):** Отвечает за взаимодействие с другими системами.
    *   Обеспечивает криптографически защищенный OIDC-диалог (Authorization Code Flow) со STEOS ID.
    *   Выполняет gRPC/REST вызовы к `Workspace Service` для проверки прав доступа при смене контекста.
    *   Подключен к **RabbitMQ** для прослушивания асинхронных событий, таких как Back-Channel Logout (глобальный бан пользователя) или изменения ролей.
*   **Background Jobs (Фоновые задачи):** Асинхронные воркеры для поддержания гигиены системы.
    *   **Session Cleanup (Сборщик мусора):** Регулярно удаляет истекшие сессии и просроченные одноразовые билеты из БД.
    *   **JWKS Refresher:** Периодически скачивает свежие публичные ключи со STEOS ID для проверки JWT-подписей.

# 3. Ключевые архитектурные решения (КАР)

В этом разделе описаны наиболее важные архитектурные решения (Key Architectural Decisions, KAD), принятые при проектировании микросервиса «Authorization Service». Каждое из этих решений базируется на мировых практиках построения высоконагруженных и безопасных систем Identity & Access Management (IAM) и направлено на обеспечение максимальной защиты, отказоустойчивости и прозрачности (Auditability) системы.

Данные решения формируют фундамент микросервиса, определяя то, как он защищает данные, взаимодействует с браузером и предоставляет контекст другим компонентам Платформы.

| Название КАР                                                               | Краткое описание                                                                                                                                                                                                                                                          |
| :------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **КАР-1: Паттерн Phantom Token для управления сессиями**                   | Замена уязвимых JWT-токенов в браузере на непрозрачные, криптографически случайные UUID (Phantom Tokens) в HttpOnly Cookie. Это делает невозможной кражу прав через XSS и позволяет мгновенно "убивать" скомпрометированные сессии.                                       |
| **КАР-2: Zero Trust и Инъекция бизнес-заголовков (Header Routing)**        | Внутренние микросервисы (например, Tasks, CRM) не доверяют клиентским Cookie. API Gateway Auth Service "снимает" Cookie, извлекает стейт из Redis и прокидывает во внутреннюю сеть только доверенные заголовки (например, `X-Workspace-Id`), реализуя принцип Zero Trust. |
| **КАР-3: Динамическая серверная маршрутизация контекста**                  | Переключение пользователя между рабочими пространствами (Workspaces) происходит на уровне сервера без изменения клиентской Cookie. Фронтенд работает "вслепую", отправляя пустые API-запросы, а Auth Service сам направляет их в нужный Workspace.                        |
| **КАР-4: Изоляция и аппаратная привязка гостевых сессий**                  | Гостевой (анонимный) доступ жестко привязывается к аппаратному отпечатку браузера (`device_fingerprint`). Это предотвращает абьюз бесплатных квот (лимитов) путем простой очистки Cookie.                                                                                 |
| **КАР-5: Эфемерные Одноразовые Билеты (One-Time Tickets)**                 | Для обхода ограничений WebSocket-рукопожатий и прямых загрузок файлов используются одноразовые билеты (Burn-on-Read). Они живут в Redis всего 15 секунд и сжигаются в миллисекунду чтения, обеспечивая безопасную передачу контекста через URL.                           |
| **КАР-6: Двойная идентичность для безопасной имперсонации (God Mode)**     | Механизм поддержки клиентов, при котором сотрудник входит "под клиентом" без запроса пароля. В сессии хранятся два ID: истинный (клиента) для бизнес-логики и "кукловод" (админ) для WORM-лога аудита. Обеспечивается юридическая прозрачность.                           |
| **КАР-7: Асинхронная инвалидация через Back-Channel Logout (RabbitMQ)**    | Подписка на глобальные события брокера. Если STEOS ID банит пользователя на глобальном уровне, локальный микросервис за миллисекунды уничтожает все его локальные сессии в Redis на всех устройствах платформы.                                                           |
| **КАР-8: Кэширование и In-Memory валидация OIDC ключей (JWKS)**            | Отказ от синхронных HTTP-вызовов к глобальному IdP при каждом логине. Сервис скачивает публичные ключи асинхронно в фоне и проверяет математические RSA-подписи входящих JWT-токенов локально в оперативной памяти.                                                       |
| **КАР-9: Паттерн Тихое продление (Silent Refresh) с JIT-дешифровкой**      | Долгоживущие `refresh_token` хранятся в БД в зашифрованном виде. При истечении локальной сессии сервис расшифровывает их Just-in-Time, делает S2S-запрос к STEOS ID и продлевает сессию в Redis без изменения Cookie (бесшовно для пользователя).                         |
| **КАР-10: Многоуровневый защитный периметр (Local Firewall & Throttling)** | Защита платформы на уровне API Gateway. Внедрение динамических реестров временно заблокированных IP или Фингерпринтов (от парсеров и абузеров) и ограничение Rate Limit на попытки авторизации и старта сессий до их дохождения до логики STEOS ID.                       |
| **КАР-11: Иммутабельный Локальный Журнал Доступа (WORM Audit)**            | Все критические события безопасности (успешный вход, смена Workspace, имперсонация, блокировка) записываются в локальную Append-Only (WORM) таблицу `access_audit_logs`. Журнал не подлежит удалению и служит основным доказательством при разборе инцидентов.            |
