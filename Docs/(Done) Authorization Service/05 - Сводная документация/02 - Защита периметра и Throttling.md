# Введение

Данный документ описывает процессы и правила использования Redis для защиты микросервиса Authorization Service от брутфорс-атак (перебор паролей/OTP), злоупотребления API-лимитами (DDoS на уровне приложения) и отслеживания квот гостевых пользователей. Механизмы Rate Limiting и Throttling (КАР-10) реализуются исключительно в Redis благодаря его атомарным операциям (INCR, EXPIRE) и высокой производительности.

# 1. Список операций Защиты периметра и Throttling

Перечень механизмов, ограничивающих частоту запросов и блокирующих подозрительную активность.

| Метод (SR) | Описание операции |
| :--- | :--- |
| КАР-10 / SR-AUTH-SQ-04 | Rate Limiting (Sliding Window) для защиты эндпоинтов авторизации от брутфорса. |
| КАР-10 / SR-AUTH-SQ-03 | Fail2Ban: Временная блокировка IP-адресов при подозрительной активности. |
| SR-AUTH-SQ-04 | Throttling и кэширование счетчиков ошибок MFA. |
| SR-AUTH-GQ-02 | Token Bucket: In-Memory счетчики API-запросов и лимитов потребления (Квот) для гостевых сессий перед сбросом в БД/RabbitMQ. |

# Защита от брутфорса (Rate Limiting) (SR-AUTH-SQ-04)

## Общая информация

Ограничение частоты запросов к критичным эндпоинтам (например, `/auth/login`, `/auth/refresh`, `/auth/magic-link`) по IP-адресу или идентификатору пользователя. Реализует паттерн Sliding Window (Скользящее окно) с помощью отсортированных множеств (ZSET) или атомарных счетчиков в Redis.

| Тип операции | Read (Чтение), Write (Запись) |
| :--- | :--- |
| **Ключ Redis** | `auth:ratelimit:{ip_or_subject}:{endpoint}`<br>где `{ip_or_subject}` = IP-адрес (или ID юзера), `{endpoint}` = короткий алиас маршрута (напр. `login`). |
| **DTO ответа** | Целое число `requests_count` (счетчик запросов в текущем окне). |
| **TTL** | Динамический, равен длине окна (например, `60` сек для лимита 10 запросов в минуту). Обновляется при каждом `INCR`. |

## Логика обработки запроса

*   **Чтение и инкремент:** При каждом запросе на защищенный эндпоинт сервис вызывает атомарную команду `INCR auth:ratelimit:{ip}:{endpoint}`. Если ключ создается впервые, ему устанавливается `EXPIRE` на длительность окна.
*   **Проверка лимита:** Если результат `INCR` превышает установленный порог (например, `> 10`), запрос отклоняется с HTTP 429 Too Many Requests.
*   **Инвалидация:** Ключи удаляются автоматически силами самого Redis по истечении окна.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Если Redis недоступен, защита Rate Limiting отключается (Fail-Open), чтобы не заблокировать легитимных пользователей, однако генерируется `CRITICAL` алерт в систему мониторинга (потенциальная уязвимость для брутфорса). |

# Механизм Fail2Ban (SR-AUTH-SQ-03)

## Общая информация

Развитие концепции Rate Limiting (КАР-10). Если IP-адрес или аккаунт постоянно превышает лимиты ошибок аутентификации (например, 5 неправильных паролей подряд), он попадает в жесткий "бан-лист" на определенное время (от 15 минут до 24 часов). Любые запросы от него отвергаются на самом раннем этапе.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:ban:{ip_or_subject}`<br>где `{ip_or_subject}` = IP-адрес (или ID юзера). |
| **DTO ответа** | Строка `reason` (например, `BRUTEFORCE_LOGIN`, `MFA_FRAUD`) и `expires_at`. Сам факт существования ключа означает блокировку. |
| **TTL** | Динамический. Вычисляется по прогрессивной шкале (например, 1-й бан: 15 минут (`900` сек), 2-й: 1 час (`3600` сек)). |

## Логика обработки запроса

*   **Запись (Бан):** Если счетчик ошибок превышает порог, сервис вызывает `SET auth:ban:{ip_or_subject} "reason" EX {ttl}` и публикует WebSocket-событие `subject_banned`.
*   **Чтение (Блокировка):** Middleware при каждом входящем запросе выполняет `EXISTS auth:ban:{ip}`. Если `true`, немедленно возвращает HTTP 403 Forbidden (или 429).
*   **Инвалидация:** Автоматическое истечение по TTL, либо ручной вызов `DEL` администратором через панель управления (если бан был ошибочным).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Если Redis недоступен, механизм блокировки не работает (Fail-Open). |

# Лимитирование попыток MFA (SR-AUTH-SQ-04)

## Общая информация

Защита от перебора одноразовых кодов (OTP, TOTP, SMS-кодов). Каждая неудачная попытка ввода MFA-кода должна инкрементировать счетчик для конкретной сессии. После превышения (обычно 3-5 попыток), сессия логина аннулируется.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:mfa:attempts:{session_id}`<br>где `{session_id}` = уникальный идентификатор незавершенной попытки логина (из OIDC State). |
| **DTO ответа** | Целое число `failed_attempts` (счетчик ошибок). |
| **TTL** | Статический (например, 15 минут: `900` сек - равно времени жизни OIDC-транзакции логина). |

## Логика обработки запроса

*   **Запись:** При неверном вводе MFA (вызов `/auth/mfa/verify`) сервис выполняет `INCR auth:mfa:attempts:{session_id}`.
*   **Проверка:** Если результат `INCR > 3`, сессия логина (State) инвалидируется, и пользователю предлагается начать процесс аутентификации заново (со вводом основного пароля). Возвращается ошибка "MFA Locked".
*   **Инвалидация:** При успешном вводе MFA счетчик сбрасывается (`DEL`). Автоматическое удаление по TTL.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | При недоступности Redis, проверка MFA не может полагаться на счетчик. Из соображений безопасности попытка логина отклоняется с `503 Service Unavailable` (Fail-Closed), чтобы не допустить подбор. |

# Token Bucket для Квот (SR-AUTH-GQ-02)

## Общая информация

Механизм для высокоскоростного (In-Memory) учета потребления ресурсов (например, гостевыми сессиями) перед отправкой данных в биллинг. Избегает синхронных запросов в БД или RabbitMQ на каждый API-вызов. Использует алгоритм Token Bucket или простые счетчики с пакетной выгрузкой (Batching).

| Тип операции | Read (Чтение), Write (Запись) |
| :--- | :--- |
| **Ключ Redis** | `auth:quota:{workspace_id_or_guest}:{resource_type}`<br>где `{workspace_id_or_guest}` = ID воркспейса или гостя, `{resource_type}` = например `api_calls`, `storage_mb`. |
| **DTO ответа** | Целое число `consumed_amount` (сколько потреблено) или `remaining_tokens` (сколько осталось в корзине). |
| **TTL** | Динамический. Вычисляется до конца текущего биллингового периода (например, конец месяца) или окна пакетирования (например, `60` сек для сброса в RabbitMQ). |

## Логика обработки запроса

*   **Чтение и списание:** Перед (или после) выполнения "платного" действия, сервис вызывает `DECRBY auth:quota:{id}:{res} {amount}` (если Token Bucket) или `INCRBY` (если счетчик).
*   **Проверка лимита:** Если `remaining_tokens < 0`, операция блокируется с HTTP 402 Payment Required. Пользователю может быть отправлено WebSocket-событие `quota_exceeded_warning`.
*   **Синхронизация (Batching):** Фоновый воркер (Background Task) периодически забирает накопленные значения (`GET`), формирует батч-событие `QuotaConsumedEventPayload` и публикует его в RabbitMQ, затем сбрасывает счетчики (`DEL` или `SET 0`).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Механизм учета квот деградирует. Сервис может временно пропускать запросы (Fail-Open), чтобы не блокировать бизнес-процессы, однако биллинг недосчитается части метрик потребления. Обязательна запись `WARNING` в локальный лог для последующего восстановления метрик (КАР-11). |
