# Введение

Данный документ описывает процессы и правила использования Redis в качестве высокоскоростного хранилища сессий (Session Store) для Authorization Service. Использование Redis позволяет реализовать паттерн **Phantom Token** (КАР-1), обеспечивая валидацию непрозрачных (Opaque) токенов доступа с минимальной задержкой, а также позволяет мгновенно отзывать скомпрометированные сессии через механизмы Blacklisting.

# 1. Список операций Управления сессиями и Phantom Tokens

Перечень механизмов, управляющих жизненным циклом сессий.

| Метод (SR)            | Описание операции                                                                 |
| :-------------------- | :-------------------------------------------------------------------------------- |
| КАР-1 / SR-AUTH-SM-01 | Хранение и валидация активных Refresh-сессий пользователей.                       |
| КАР-1 / SR-AUTH-SM-04 | Хранение Blacklist (Черного списка) для отозванных токенов (до истечения их TTL). |
| КАР-6 / SR-AUTH-SM-05 | Хранение контекста Impersonation (God Mode) — кто под кем залогинен.              |
| SR-AUTH-GQ-01         | Хранение эфемерных гостевых сессий с аппаратной привязкой.                        |

# Хранение активных сессий (SR-AUTH-SM-01)

## Общая информация

Хранение активных сессий (`Refresh Tokens`) в Redis позволяет API Gateway и gRPC-клиентам мгновенно валидировать входящие запросы. При успешном логине сессия пишется одновременно и в PostgreSQL (для персистентности), и в Redis (для скорости).

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:session:{session_id}`<br>где `session_id` = UUID сессии из базы данных. |
| **DTO ответа** | Сериализованный JSON объекта `SessionCacheState` (содержит `subjectId`, `workspaceId`, `deviceId`, `status`). |
| **TTL** | Динамический, равен сроку жизни Refresh токена (по умолчанию 30 дней: `2592000` сек). Окно неактивности может сдвигаться (Sliding Expiration). |

## Логика обработки запроса

*   **Запись:** При успешной аутентификации (вызов `/auth/login` или OIDC Callback) создается новая запись в БД, а её кэш-проекция сохраняется в Redis командой `SETEX`.
*   **Чтение:** При каждом запросе `/auth/refresh` или проверке токена сервис делает `GET auth:session:{session_id}`. Если ключ существует и `status == ACTIVE`, сессия считается легитимной. При кэш-промахе (Cache Miss) сессия запрашивается из PostgreSQL и восстанавливается в Redis (Cache-Aside).
*   **Инвалидация:** Команда `DEL` вызывается при явном вызове `/sessions/revoke`, `/auth/logout` или при получении `Backchannel Logout` от STEOS ID.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Redis недоступен. Сервис переходит в режим деградации: чтение и валидация сессий идет напрямую из PostgreSQL (что увеличивает задержку, но сохраняет работоспособность). |

# Хранение Blacklist отозванных токенов (SR-AUTH-SM-04)

## Общая информация

Поскольку JWT-токены невозможно отозвать (они "живут" до истечения `exp`), Authorization Service использует `Blacklist` в Redis для хранения идентификаторов скомпрометированных или отозванных токенов до момента их естественного устаревания (КАР-1).

| Тип операции | Read (Чтение), Write (Запись) |
| :--- | :--- |
| **Ключ Redis** | `auth:blacklist:{jti}`<br>где `jti` = JWT ID (уникальный идентификатор токена). |
| **DTO ответа** | Строка (например, `"revoked"`). Сам факт существования ключа является признаком отзыва. |
| **TTL** | Динамический. Вычисляется как: `Время_Истечения_Токена (exp) - Текущее_Время (now)`. |

## Логика обработки запроса

*   **Запись:** При разлогине, смене пароля или обнаружении кражи токена, его `jti` помещается в Redis командой `SETEX`. TTL устанавливается ровно до конца жизни этого токена, чтобы не засорять память вечно.
*   **Чтение:** В gRPC методе `ValidateToken`, перед проверкой подписи JWT, сервис выполняет `EXISTS auth:blacklist:{jti}`. Если ключ найден — токен немедленно отвергается с ошибкой `UNAUTHENTICATED`.
*   **Инвалидация:** Ключи удаляются автоматически силами самого Redis по истечении TTL (когда токен уже просрочен и не может быть использован злоумышленником по определению).

## Статус-коды при ошибках

| Код             | Описание ошибки                                                                                                                                                                                                                                                                                         |
| :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **UNAVAILABLE** | Если Redis недоступен, проверка Blacklist невозможна. Из соображений безопасности (Fail-Closed) все токены, кроме самых свежих (выпущенных менее 5 минут назад), могут отвергаться, либо система продолжит работу с риском пропуска отозванного токена (зависит от настроек режима `strict_blacklist`). |

# Хранение контекста Impersonation (SR-AUTH-SM-05)

## Общая информация

Механизм Impersonation (God Mode, КАР-6) позволяет администратору временно действовать от лица пользователя. Этот контекст "двойной идентичности" хранится в Redis для быстрого переопределения `subjectId` в токенах.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:impersonation:{admin_session_id}`<br>где `admin_session_id` = ID сессии администратора. |
| **DTO ответа** | Строка `target_subject_id` (кого имперсонируют). |
| **TTL** | Статический (например, 2 часа: `7200` сек) или до истечения админской сессии. |

## Логика обработки запроса

*   **Запись:** При вызове `POST /audit/impersonate/start` (если у админа есть права), в Redis записывается маппинг сессии админа на ID целевого пользователя.
*   **Чтение:** При каждом запросе админа (и формировании Phantom Token), если найден ключ `auth:impersonation:{id}`, система генерирует токен с `sub = target_subject_id`, но добавляет Claim `act = {"sub": "admin_id"}` для аудита.
*   **Инвалидация:** Ключ удаляется при `POST /audit/impersonate/stop` или истечении TTL.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Режим Impersonation не работает. Запросы админа выполняются в его обычном контексте. |

# Хранение гостевых сессий (SR-AUTH-GQ-01)

## Общая информация

Для реализации Seamless Onboarding (бесшовного онбординга) неавторизованные пользователи получают эфемерные сессии, привязанные к Fingerprint'у их браузера/устройства. Они хранятся преимущественно в Redis для скорости и автоматического удаления "мусорных" гостей.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:guest:{hardware_id}`<br>где `hardware_id` = хэш отпечатков устройства клиента. |
| **DTO ответа** | Сериализованный `GuestSessionData` (содержит `guestId`, `createdAt`, `workspaceId`). |
| **TTL** | Статический (например, 7 дней: `604800` сек). Продлевается при активности. |

## Логика обработки запроса

*   **Запись:** При вызове `POST /guests/init` создается `guestId` и привязывается к `hardware_id`.
*   **Чтение:** При каждом запросе от гостя с данным `hardware_id` (переданным в заголовке или Cookie), система достает его `guestId` и выдает ограниченный гостевой токен.
*   **Инвалидация:** Ключ принудительно удаляется командой `DEL` при конвертации гостя в полноценного пользователя (`SR-AUTH-GQ-04` - Guest Merged), либо по истечении TTL (гость ушел и не вернулся).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Невозможно инициализировать или использовать гостевую сессию. Клиенту возвращается `503 Service Unavailable` или `401 Unauthorized` (Fail-Closed). |
