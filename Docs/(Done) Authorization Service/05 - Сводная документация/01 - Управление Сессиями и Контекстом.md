# Введение

Группа алгоритмов управления сессиями и контекстом (Session Management) — это базовый слой безопасности и маршрутизации микросервиса Authorization Service. Его основная задача заключается в конвертации глобальной идентичности пользователя (подтвержденной в STEOS ID) в локальную, защищенную сессию, полностью контролируемую сервером.

Алгоритмы этой группы работают как невидимый "привратник" для всех остальных микросервисов Платформы. Они перехватывают каждый входящий запрос от браузера клиента, проверяют легитимность Phantom Token (Cookie) в сверхбыстром кэше Redis, определяют текущий рабочий контекст пользователя (например, активный Workspace) и прокидывают эти данные во внутреннюю сеть в виде доверенных HTTP-заголовков. Благодаря этому достигается архитектура Zero Trust, при которой бизнес-микросервисы избавлены от необходимости парсить токены, работать с криптографией или обращаться к Redis.

# 1. Список алгоритмов ядра управления сессиями

В данном разделе представлены алгоритмы, обеспечивающие жизненный цикл сессии и передачу контекста внутри Платформы. Они гарантируют безопасный доступ к ресурсам и бесшовный пользовательский опыт (UX).

| **Название алгоритма** | **Краткое описание** |
| :--- | :--- |
| **Алгоритм валидации и инъекции Phantom Token** | Перехватывает HTTP-запросы, проверяет Cookie в Redis за доли миллисекунды и внедряет бизнес-заголовки (Header Routing) во внутреннюю сеть. |
| **Алгоритм серверной маршрутизации контекста** | Обновляет `workspace_id` в серверном стейте сессии, избавляя фронтенд от необходимости передавать контекст в бизнес-запросах. |
| **Алгоритм генерации и гашения одноразовых билетов** | Создает 15-секундные эфемерные токены в Redis с атомарным удалением (Burn-on-Read) для безопасного обхода ограничений WebSockets. |
| **Алгоритм бесшовной имперсонации (God Mode)** | Создает "двойную" сессию, маскирующую ID сотрудника поддержки под ID клиента для расследования инцидентов с прозрачным WORM-аудитом. |
| **Алгоритм тихого серверного продления (Silent Refresh)** | В фоновом режиме S2S-вызовом продлевает сессию в Redis, расшифровывая JIT `refresh_token`, обеспечивая работу SPA без морганий экрана. |

# Алгоритм валидации и инъекции Phantom Token

## Контекст и область применения

Данный раздел описывает предпосылки создания алгоритма, его основное предназначение в рамках системы, а также ключевые бизнес-требования, которые он удовлетворяет. Здесь же приведены сценарии использования и ограничения, которые необходимо учитывать при его работе.

### Почему был создан

Передача JWT-токенов в браузер подвергает Платформу рискам XSS-атак и делает невозможным мгновенный отзыв скомпрометированных сессий (Stateful Auth). Внутренним микросервисам сложно каждый раз валидировать JWT. Алгоритм Phantom Token решает обе эти проблемы: клиент получает нечитаемый `UUID` в `HttpOnly` Cookie, а внутренние сервисы — проверенные, доверенные HTTP-заголовки.

### Бизнес-требование

Система должна заменять уязвимые JWT-токены на безопасные Phantom Tokens и маршрутизировать контекст пользователя во внутренние сервисы с помощью доверенных заголовков (SR-AUTH-SM-01, SR-AUTH-LA-03).

### Область применения

Алгоритм активно используется в следующих сценариях и процессах платформы, обеспечивая постоянную проверку доступа:

| **№** | **Описание** |
| :--- | :--- |
| **1** | Выполнение любого защищенного бизнес-запроса от SPA-клиента (фронтенда). |
| **2** | Фоновые AJAX-опросы состояния (например, `keep-alive`). |
| **3** | Инъекция `X-Workspace-Id` и `X-Global-Actor-Id` для внутренних микросервисов (Tasks, CRM). |

### Ограничения применения

Работа алгоритма подчиняется ряду технических и логических ограничений, несоблюдение которых приводит к блокировке запроса:

| **№** | **Описание** |
| :--- | :--- |
| **1** | Алгоритм требует доступности Redis-кластера. При падении Redis все запросы получают 500-ю ошибку (Fail-Closed). |
| **2** | Запрос должен содержать `HttpOnly` Cookie `steos_sess`. |
| **3** | Срок проверки (Redis lookup) не должен превышать 2-3 миллисекунд для сохранения общей производительности API Gateway. |

## Входные данные

Для успешной проверки сессии алгоритму требуется контекст входящего HTTP-запроса от браузера:

| **Параметр** | **Тип данных** | **Описание** | **Ограничения** | **Обязательность** |
| :--- | :--- | :--- | :--- | :--- |
| `HttpRequest` | `HttpRequestMessage` | Входящий запрос от клиента (браузера) | - | Да |
| `Cookie` | `string` | Содержимое заголовка `Cookie` (поиск `steos_sess`) | - | Нет (если пуст - 401) |

## Выходные данные

В результате работы алгоритм формирует модифицированный HTTP-запрос для внутренней маршрутизации (Proxying):

| **Параметр** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `ProxiedRequest` | `HttpRequestMessage` | Запрос, очищенный от Cookie, но обогащенный `X-` заголовками |
| `IsAuthorized` | `bool` | Флаг успешной проверки |
| `RejectionReason` | `string?` | Причина отказа (при `IsAuthorized = false`) |

## Логика работы (Псевдокод)

В данном блоке представлен псевдокод Middleware на языке C#. Алгоритм перехватывает запрос, пытается найти Phantom Token в Cookie, делает поиск по этому UUID в Redis. Если сессия найдена и активна, алгоритм удаляет оригинальную Cookie из запроса (Zero Trust) и добавляет во внутренний запрос доверенные заголовки с данными пользователя и его текущего рабочего пространства.

```csharp
public async Task<ValidationResultDto> ValidateAndInjectAsync(HttpRequestMessage request)
{
    // 1. Извлечение Cookie
    var sessionId = ExtractCookieValue(request, "steos_sess");
    if (string.IsNullOrEmpty(sessionId))
    {
        return CreateRejection("UNAUTHORIZED", "Missing session cookie");
    }

    // 2. Сверхбыстрый lookup в Redis
    string redisKey = $"steos:sess:{sessionId}";
    var sessionJson = await _redisDatabase.StringGetAsync(redisKey);

    if (string.IsNullOrEmpty(sessionJson))
    {
        // Сессия истекла или была отозвана (Revoked)
        return CreateRejection("UNAUTHORIZED", "Session expired or invalid");
    }

    // 3. Десериализация стейта
    var sessionState = JsonSerializer.Deserialize<SessionStateDto>(sessionJson);

    // 4. Очистка запроса (Zero Trust - внутренние сервисы не должны видеть сырую Cookie)
    request.Headers.Remove("Cookie");

    // 5. Инъекция доверенных бизнес-заголовков (Header Routing)
    request.Headers.Add("X-Global-Actor-Id", sessionState.GlobalSteosId.ToString());
    
    // Инъекция текущего Workspace (если пользователь не в глобальном контексте)
    if (sessionState.ActiveWorkspaceId.HasValue)
    {
        request.Headers.Add("X-Workspace-Id", sessionState.ActiveWorkspaceId.Value.ToString());
    }

    // Инъекция ролей (опционально, для RBAC на стороне микросервисов)
    if (sessionState.Roles != null && sessionState.Roles.Any())
    {
        request.Headers.Add("X-User-Roles", string.Join(",", sessionState.Roles));
    }

    // Инъекция ID саппорта при God Mode (КАР-6)
    if (sessionState.ImpersonatorSteosId.HasValue)
    {
        request.Headers.Add("X-Impersonator-Id", sessionState.ImpersonatorSteosId.Value.ToString());
    }

    return new ValidationResultDto
    {
        IsAuthorized = true,
        ProxiedRequest = request
    };
}
```

# Алгоритм серверной маршрутизации контекста

## Контекст и область применения

Данный раздел описывает алгоритм динамической смены `workspace_id` без изменения клиентского состояния.

### Почему был создан

В B2B-системах пользователи часто переключаются между Командами (Workspaces). Передача ID пространства с каждым GET/POST запросом усложняет фронтенд-код (SPA) и создает уязвимости (IDOR), если разработчик бэкенда забудет проверить права доступа к переданному ID. Серверная маршрутизация контекста делает фронтенд "слепым", а бэкенд — безошибочным.

### Бизнес-требование

Система должна обеспечивать бесшовное переключение пользователя между рабочими пространствами на сервере без перелогина и изменения Cookie (SR-AUTH-SM-02).

### Область применения

Алгоритм используется исключительно при смене контекста пользователем:

| **№** | **Описание** |
| :--- | :--- |
| **1** | Пользователь в UI кликает на иконку другого Workspace в левом меню навигации. |

### Ограничения применения

| **№** | **Описание** |
| :--- | :--- |
| **1** | Пользователь обязан иметь права (быть Member/Admin) в целевом Workspace. |
| **2** | Требуется синхронный gRPC вызов к `Workspace Service` для проверки прав. |

## Входные данные

| **Параметр** | **Тип данных** | **Описание** | **Ограничения** | **Обязательность** |
| :--- | :--- | :--- | :--- | :--- |
| `SessionId` | `Guid` | ID текущей сессии (из Phantom Token) | Должна быть активна | Да |
| `GlobalSteosId` | `Guid` | ID текущего пользователя | - | Да |
| `TargetWorkspaceId` | `Guid` | ID пространства, в которое хочет перейти юзер | - | Да |

## Выходные данные

| **Параметр** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `IsSwitched` | `bool` | Флаг успешного переключения |
| `NewState` | `SessionStateDto` | Обновленный JSON стейта |

## Логика работы (Псевдокод)

Алгоритм принимает запрос на смену контекста, синхронно валидирует права в `Workspace Service`, после чего атомарно обновляет поле `ActiveWorkspaceId` как в персистентной БД (PostgreSQL), так и в сверхбыстром кэше (Redis), и фиксирует факт перехода в WORM-аудите.

```csharp
public async Task<ContextSwitchResultDto> SwitchContextAsync(Guid sessionId, Guid globalSteosId, Guid targetWorkspaceId)
{
    // 1. Авторизация (Проверка прав доступа к целевому Workspace)
    // Синхронный вызов к микросервису Workspace Service (PDP - Policy Decision Point)
    var accessResult = await _workspaceServiceClient.CheckMembershipAsync(globalSteosId, targetWorkspaceId);
    
    if (!accessResult.IsMember)
    {
        // Логирование попытки несанкционированного доступа
        await _auditLogger.LogEventAsync(sessionId, globalSteosId, "UNAUTHORIZED_WORKSPACE_ACCESS_ATTEMPT", targetWorkspaceId);
        throw new DomainException("ACCESS_DENIED_TO_WORKSPACE");
    }

    // 2. Обновление персистентного стейта (PostgreSQL)
    var sessionContext = await _sessionContextRepo.GetBySessionIdAsync(sessionId);
    sessionContext.ActiveWorkspaceId = targetWorkspaceId;
    await _sessionContextRepo.UpdateAsync(sessionContext);

    // 3. Обновление In-Memory стейта (Redis)
    string redisKey = $"steos:sess:{sessionId}";
    var sessionJson = await _redisDatabase.StringGetAsync(redisKey);
    var sessionState = JsonSerializer.Deserialize<SessionStateDto>(sessionJson);
    
    // Подмена контекста
    sessionState.ActiveWorkspaceId = targetWorkspaceId;
    sessionState.Roles = accessResult.Roles; // Обновляем локальные роли для этого пространства
    
    // Перезаписываем ключ в Redis (сохраняя текущий TTL)
    var currentTtl = await _redisDatabase.KeyTimeToLiveAsync(redisKey);
    await _redisDatabase.StringSetAsync(redisKey, JsonSerializer.Serialize(sessionState), currentTtl);

    // 4. Журналирование аудита (WORM)
    await _auditLogger.LogEventAsync(sessionId, globalSteosId, "WORKSPACE_CONTEXT_SWITCHED", targetWorkspaceId);

    return new ContextSwitchResultDto { IsSwitched = true, NewState = sessionState };
}
```

# Алгоритм генерации и гашения одноразовых билетов

## Контекст и область применения

Алгоритм создания безопасных временных ссылок (Burn-on-Read) для обхода ограничений браузеров.

### Почему был создан

Вставка тега `<img src="...">` или инициализация `new WebSocket(...)` в JS не позволяет передавать пользовательские заголовки. Использование `HttpOnly` Cookie также часто заблокировано из-за CORS-политик. Передавать сессионный токен в URL как `?token=...` небезопасно, так как он осядет в логах. Решение — одноразовые короткоживущие (15с) билеты, которые уничтожаются сразу после первого чтения.

### Бизнес-требование

Система должна уметь генерировать эфемерные токены для безопасного открытия WebSocket-соединений и прямого скачивания защищенных файлов (SR-AUTH-SM-04).

### Область применения

| **№** | **Описание** |
| :--- | :--- |
| **1** | Аутентификация WebSocket-соединений (Handshake) к сервису уведомлений. |
| **2** | Загрузка защищенных PDF-отчетов или приватных изображений через нативный UI браузера. |

## Логика работы (Псевдокод)

Алгоритм состоит из двух частей: генерации (выполняется фронтендом асинхронно перед действием) и гашения (выполняется API Gateway при получении запроса по URL с билетом).

```csharp
// ЧАСТЬ 1: ГЕНЕРАЦИЯ (POST /api/auth/tickets/generate)
public async Task<string> GenerateTicketAsync(SessionStateDto currentUserState)
{
    // Генерируем случайную крипто-строку
    string ticketCode = "tkt-" + Guid.NewGuid().ToString("N");
    string redisKey = $"steos:ticket:{ticketCode}";

    // Сохраняем весь текущий контекст юзера внутрь билета
    var ticketData = JsonSerializer.Serialize(currentUserState);

    // ЖЕСТКИЙ TTL = 15 СЕКУНД
    await _redisDatabase.StringSetAsync(redisKey, ticketData, TimeSpan.FromSeconds(15));

    return ticketCode; // Возвращаем клиенту для использования в URL (?ticket=tkt-...)
}

// ЧАСТЬ 2: ГАШЕНИЕ И ИНЪЕКЦИЯ (API Gateway Middleware)
public async Task<ValidationResultDto> ConsumeTicketAsync(HttpRequestMessage request)
{
    // Извлекаем билет из Query-параметров
    var queryArgs = HttpUtility.ParseQueryString(request.RequestUri.Query);
    string ticketCode = queryArgs["ticket"];

    if (string.IsNullOrEmpty(ticketCode)) return CreateRejection();

    string redisKey = $"steos:ticket:{ticketCode}";

    // АТОМАРНАЯ ОПЕРАЦИЯ (GETDEL) - Чтение и немедленное удаление
    // Гарантирует, что никто другой (даже на соседнем узле кластера) не прочитает этот билет дважды
    var ticketJson = await _redisDatabase.StringGetDeleteAsync(redisKey);

    if (string.IsNullOrEmpty(ticketJson))
    {
        // Билет не найден (сгорел или истекли 15 секунд)
        return CreateRejection("TICKET_EXPIRED_OR_USED");
    }

    // Билет успешно погашен. Разворачиваем контекст юзера.
    var sessionState = JsonSerializer.Deserialize<SessionStateDto>(ticketJson);

    // Удаляем ticket из URL, чтобы он не прошел в логи внутренних сервисов
    CleanRequestUrl(request, "ticket");

    // Выполняем инъекцию заголовков (Header Routing), аналогично Phantom Token
    request.Headers.Add("X-Global-Actor-Id", sessionState.GlobalSteosId.ToString());
    request.Headers.Add("X-Workspace-Id", sessionState.ActiveWorkspaceId.ToString());

    return new ValidationResultDto { IsAuthorized = true, ProxiedRequest = request };
}
```

# Алгоритм бесшовной имперсонации (God Mode)

## Контекст и область применения

### Почему был создан

Сотрудникам саппорта L2/L3 часто нужно видеть платформу "глазами клиента" для дебага. Запрашивать пароль — недопустимо. Использование мастер-ключа нарушает аудит. Алгоритм создает "сессию-маску", где саппорт (Кукловод) действует от имени клиента, но система WORM-аудита жестко записывает реального исполнителя.

### Область применения

| **№** | **Описание** |
| :--- | :--- |
| **1** | Сотрудник поддержки нажимает "Войти как X" в административной панели платформы. |

## Логика работы (Псевдокод)

```csharp
public async Task<ImpersonationResultDto> StartImpersonationAsync(Guid adminSessionId, Guid adminSteosId, Guid targetClientSteosId)
{
    // 1. Жесткая проверка прав саппорта (PDP)
    if (!await _workspaceServiceClient.HasSystemRoleAsync(adminSteosId, "IMPERSONATE_USERS"))
    {
        await _auditLogger.LogSecurityAlertAsync(adminSteosId, "UNAUTHORIZED_IMPERSONATION_ATTEMPT");
        throw new DomainException("INSUFFICIENT_PERMISSIONS");
    }

    // 2. Создание God-Session (PostgreSQL)
    var godSessionId = Guid.NewGuid();
    var sessionRecord = new AuthorizedSession
    {
        SessionId = godSessionId,
        GlobalSteosId = targetClientSteosId, // Истинный владелец данных (для бизнес-логики)
        ImpersonatorSteosId = adminSteosId,  // Кукловод (для логов аудита)
        CreatedAt = DateTime.UtcNow,
        ExpiresAt = DateTime.UtcNow.AddHours(2) // Короткий TTL для таких сессий
    };
    await _sessionRepo.AddAsync(sessionRecord);

    // 3. Сохранение стейта в Redis (Двойная Идентичность)
    var sessionState = new SessionStateDto
    {
        GlobalSteosId = targetClientSteosId,
        ImpersonatorSteosId = adminSteosId,
        ActiveWorkspaceId = await GetDefaultWorkspaceAsync(targetClientSteosId)
    };
    await _redisDatabase.StringSetAsync($"steos:sess:{godSessionId}", JsonSerializer.Serialize(sessionState));

    // 4. Юридическая прозрачность (WORM)
    await _auditLogger.LogEventAsync(godSessionId, targetClientSteosId, "IMPERSONATION_STARTED", impersonatorId: adminSteosId);

    // Админу возвращается новая Cookie "steos_sess=godSessionId"
    return new ImpersonationResultDto { GodSessionId = godSessionId };
}
```

# Алгоритм тихого серверного продления (Silent Refresh)

## Контекст и область применения

### Почему был создан

Для безопасности Access-токены OIDC живут 15-30 минут. Однако SPA-приложение требует бесшовного опыта многочасовой работы. Чтобы избежать риска XSS-кражи `refresh_token` (если передать его браузеру), `Authorization Service` зашифровывает его локально и продлевает сессию фоновым S2S-вызовом.

### Область применения

| **№** | **Описание** |
| :--- | :--- |
| **1** | Фоновый пинг `POST /api/auth/session/keep-alive` от активной вкладки браузера. |

## Логика работы (Псевдокод)

```csharp
public async Task KeepAliveAsync(Guid sessionId, string redisKey)
{
    // 1. Проверка оставшегося времени жизни сессии в Redis
    var ttl = await _redisDatabase.KeyTimeToLiveAsync(redisKey);
    
    // Если сессия живет еще долго, просто игнорируем пинг (экономим CPU)
    if (ttl.HasValue && ttl.Value.TotalMinutes > 5)
    {
        return; 
    }

    // 2. Блокировка (Distributed Lock), чтобы параллельные вкладки не сделали Refresh дважды
    using (var lck = await _redisLockProvider.AcquireLockAsync($"lock:refresh:{sessionId}", TimeSpan.FromSeconds(10)))
    {
        if (lck == null) return; // Другой процесс уже делает Refresh

        // 3. Извлечение и JIT-Дешифровка
        var sessionRecord = await _sessionRepo.GetBySessionIdAsync(sessionId);
        string plainRefreshToken = _kmsService.Decrypt(sessionRecord.EncryptedGlobalRefresh);

        // 4. Server-to-Server вызов к STEOS ID (IdP)
        var tokenResponse = await _oidcClient.RefreshAccessTokenAsync(plainRefreshToken);

        if (tokenResponse.IsError)
        {
            // STEOS ID отказал (юзер забанен или токен отозван). Убиваем сессию локально.
            await _redisDatabase.KeyDeleteAsync(redisKey);
            await _sessionRepo.MarkAsRevokedAsync(sessionId);
            throw new DomainException("SESSION_TERMINATED_BY_IDP");
        }

        // 5. Продление локальной сессии в Redis (бесшовно для Cookie)
        var sessionJson = await _redisDatabase.StringGetAsync(redisKey);
        // Продлеваем TTL в Redis еще на 30 минут
        await _redisDatabase.KeyExpireAsync(redisKey, TimeSpan.FromMinutes(30));

        // 6. Сохранение нового Refresh-токена в БД (Encryption At-Rest)
        sessionRecord.ExpiresAt = DateTime.UtcNow.AddMinutes(30);
        if (!string.IsNullOrEmpty(tokenResponse.RefreshToken))
        {
            sessionRecord.EncryptedGlobalRefresh = _kmsService.Encrypt(tokenResponse.RefreshToken);
        }
        await _sessionRepo.UpdateAsync(sessionRecord);
    }
}
```
