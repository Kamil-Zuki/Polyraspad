# Введение

Не все внутренние и legacy-системы платформы могут работать только через доверенные заголовки, подставленные API Gateway. Для части сценариев требуется отдельный криптографически проверяемый токен, который можно передавать дальше как `Bearer`.

Этот раздел описывает возможности Authorization Service для выпуска и проверки внутренних межсервисных JWT.

## Возможности данного раздела

| Код | Название и Описание |
| :--- | :--- |
| **SR-AUTH-M2M-01** | **Валидация межсервисных токенов:** Проверка внутренних M2M JWT для фоновых процессов, integration gateway и сервисов вне прямого Header Routing. |
| **SR-AUTH-M2M-02** | **Выпуск внутренних JWT-токенов:** Обмен локального сессионного контекста на короткоживущий подписанный токен для trusted/legacy систем. |

# Детальная спецификация требований

## SR-AUTH-M2M-01: Валидация межсервисных токенов

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Криптографическая проверка** | Проверяются подпись, `aud`, срок жизни, issuer и опционально статус отзыва. |
| **Минимальный TTL** | M2M токены должны жить заметно меньше пользовательских сессий, чтобы ограничивать blast radius утечки. |
| **Сервисная трассируемость** | Валидация сохраняет субъект сервиса, audience и технический trace для аудита чувствительных операций. |

### 2. Высокоуровневое описание

Представим **служебное удостоверение сотрудника курьерской службы, которое проверяют на каждом внутреннем посту охраны**.

1. Сервис приносит токен и утверждает, что имеет право выполнить машинную операцию.
2. Auth Service проверяет, настоящее ли это удостоверение и не истек ли его срок.
3. Сверяются audience, issuer и подпись.
4. Только после этого внутренний вызов считается доверенным.

### 3. Примеры взаимодействия (логические сценарии)

#### Валидный M2M-токен (Happy Path)

1. Внутренний сервис отправляет запрос с M2M JWT.
2. Auth Service проверяет подпись, `aud`, `exp` и другие обязательные claims.
3. Токен признается валидным.
4. Межсервисная операция продолжается.

## SR-AUTH-M2M-02: Выпуск внутренних JWT-токенов

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Обмен, а не первичный логин** | Внутренний JWT выпускается только на базе уже существующего и валидного локального контекста. |
| **Ограниченный audience** | Токен создается под конкретную целевую систему или класс интеграции. |
| **Короткий срок жизни** | TTL токена должен быть минимальным и достаточным только для одной интеграционной операции или короткой сессии. |
| **Аудит выпуска** | Каждый выпуск такого токена считается чувствительным событием и должен быть трассируемым. |

### 2. Высокоуровневое описание

Представим **временный дипломатический пропуск, который выдают только для одной конкретной внешней поездки**.

1. У пользователя уже есть валидный локальный контекст в платформе.
2. Для legacy- или внешней системы этого недостаточно, ей нужен обычный JWT.
3. Auth Service берет существующий контекст и упаковывает его в короткоживущий подписанный токен.
4. Этот токен можно безопасно использовать только в ограниченном сценарии и короткий срок.

### 3. Примеры взаимодействия (логические сценарии)

#### Выпуск внутреннего JWT (Happy Path)

1. Trusted-сервис или пользователь инициирует выпуск токена для определенного audience.
2. Auth Service проверяет полномочия на такой обмен.
3. Формирует claims и подписывает короткоживущий JWT.
4. Целевая система получает токен и использует его в своем контракте.
