# Введение

Этот раздел объединяет требования, которые не описывают напрямую бизнес-права пользователя, но критичны для надежной эксплуатации Authorization Service как платформенного компонента: health-check, метрики, распределенный WebSocket-контур и идемпотентность мутирующих API.

## Возможности данного раздела

| Код | Название и Описание |
| :--- | :--- |
| **SR-AUTH-MH-01** | **Health Checks сервиса:** Эндпоинты liveness/readiness для проверки процесса, связности с Redis/PostgreSQL и готовности принимать трафик. |
| **SR-AUTH-MH-02** | **Экспорт метрик и телеметрии:** Публикация метрик производительности, валидации токенов, rate-limit и безопасности для Prometheus/Alerting. |
| **SR-AUTH-WS-01** | **WebSocket Backplane между репликами:** Синхронизация real-time событий между несколькими подами Authorization Service. |
| **SR-AUTH-REST-01** | **Idempotency Keys для мутирующих REST-методов:** Защита API от повторных списаний и двойного выполнения команды при сетевых ретраях клиента. |

# Детальная спецификация требований

## SR-AUTH-MH-01: Health Checks сервиса

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Liveness** | Отвечает на вопрос, не завис ли сам процесс и стоит ли его перезапускать. |
| **Readiness** | Проверяет критичные зависимости: Redis, PostgreSQL, очередь или иные обязательные компоненты. |
| **Быстрый ответ** | Проверки должны быть достаточно легкими, чтобы не становиться источником дополнительной нагрузки. |

### 2. Высокоуровневое описание

Представим **дежурного инженера на входе в дата-центр, который отвечает на два вопроса: "жив ли сервер?" и "готов ли он брать работу?"**.

1. Одна проверка смотрит, не завис ли сам процесс.
2. Вторая проверка убеждается, что критичные зависимости действительно доступны.
3. Оркестратор на основе этих ответов решает, держать сервис в трафике или нет.
4. Благодаря этому платформа не посылает запросы в заведомо нездоровый экземпляр.

### 3. Примеры взаимодействия (логические сценарии)

#### Сервис полностью готов (Happy Path)

1. Kubernetes вызывает `liveness` и `readiness`.
2. Процесс жив, Redis и PostgreSQL доступны.
3. Сервис отвечает успешными статусами.
4. Экземпляр продолжает принимать боевой трафик.

## SR-AUTH-MH-02: Экспорт метрик и телеметрии

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Наблюдаемость в реальном времени** | Сервис публикует метрики для Prometheus и alerting-систем. |
| **Разделение с бизнес-аналитикой** | Метрики эксплуатации не подменяют `LA-07`, а дополняют его. |
| **Минимальный overhead** | Сбор телеметрии не должен ощутимо ухудшать p95/p99 latency боевых запросов. |

### 2. Высокоуровневое описание

Представим **приборную панель пилота, которая показывает скорость, температуру двигателей и предупреждения, но не заменяет журнал полета**.

1. Сервис непрерывно считает технические показатели своей работы.
2. Эти показатели экспортируются во внешнюю систему мониторинга.
3. Операторы видят latency, количество ошибок, rate-limit и другие сигналы.
4. При отклонении метрик алерты срабатывают раньше, чем проблема становится аварией.

### 3. Примеры взаимодействия (логические сценарии)

#### Нормальный сбор метрик (Happy Path)

1. Prometheus периодически читает `/metrics`.
2. Authorization Service отдает счетчики и гистограммы.
3. Grafana строит графики по latency и числу валидаций.
4. Команда эксплуатации видит текущее состояние контура авторизации.

## SR-AUTH-WS-01: WebSocket Backplane между репликами

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Кластерная доставка событий** | `session_revoked`, `context_updated`, QR login и MFA-события должны синхронно проходить между репликами. |
| **Опора на Redis Pub/Sub** | Backplane использует общее промежуточное хранилище/шину для доставки между pod-ами. |
| **Graceful degradation** | При сбое backplane локальные соединения продолжают работать, но кластерная доставка может деградировать и должна быть наблюдаема. |

### 2. Высокоуровневое описание

Представим **сеть раций между несколькими постами охраны, чтобы сообщение дошло до посетителя независимо от того, у какого поста он сейчас стоит**.

1. Пользователь может быть подключен к любой реплике сервиса.
2. Важное событие может родиться на другой реплике.
3. Backplane передает это событие по общей шине всем участникам кластера.
4. Нужный pod доставляет уведомление именно тому клиенту, который у него подключен.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешная кластерная доставка (Happy Path)

1. Сессия пользователя отзывается на `pod-B`.
2. Пользовательский WebSocket подключен к `pod-A`.
3. Backplane реплицирует событие `session_revoked` между pod-ами.
4. Клиент получает уведомление мгновенно, несмотря на распределенную архитектуру.

## SR-AUTH-REST-01: Idempotency Keys для мутирующих REST-методов

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Ключ идемпотентности от клиента** | Мутирующий запрос может нести `Idempotency-Key`, по которому сервис распознает повтор. |
| **Кэширование результата** | При повторном запросе с тем же ключом возвращается уже сформированный результат без повторной бизнес-операции. |
| **Контроль гонок** | Параллельные вызовы с одним ключом должны безопасно сериализоваться или явно конфликтовать. |

### 2. Высокоуровневое описание

Представим **кассу, которая при повторном показе того же талона не пробивает покупку второй раз, а просто показывает уже оформленный чек**.

1. Клиент посылает мутирующую команду с уникальным ключом идемпотентности.
2. Сервис запоминает, что операция с этим ключом уже выполняется или уже была завершена.
3. Если запрос приходит повторно, система не запускает бизнес-логику второй раз.
4. Это защищает от двойных списаний и дублирующих side effects при сетевых ретраях.

### 3. Примеры взаимодействия (логические сценарии)

#### Повторный запрос после сетевого сбоя (Happy Path)

1. Клиент отправляет `POST` с `Idempotency-Key`.
2. Операция успешно завершается, но клиент не успевает получить ответ из-за сетевого сбоя.
3. Тот же запрос повторяется с тем же ключом.
4. Сервис возвращает уже готовый результат без повторного выполнения команды.
