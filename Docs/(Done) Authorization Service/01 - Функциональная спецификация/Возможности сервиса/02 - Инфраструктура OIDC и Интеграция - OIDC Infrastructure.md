# Введение

В этом разделе описывается криптографический и сетевой слой взаимодействия локальной инсталляции платформы (Authorization Service) с глобальным "Паспортным столом" — **STEOS ID**. 

Локальный сервис авторизации не хранит ни паролей, ни логинов, ни телефонов пользователей. Он всецело доверяет глобальному Identity Provider (IdP). Чтобы это доверие не стало вектором атаки, взаимодействие должно быть выстроено по строжайшим стандартам индустрии (OAuth 2.1 BCP, OpenID Connect 1.0).

**Метафора:**
Представьте **Посольство (Authorization Service)**.
Вы гражданин Мира (STEOS ID), но хотите въехать в конкретную Страну (Платформу). Вы приходите в Посольство. Посол не спрашивает вас, где вы родились или какой у вас пароль. Посол просто просит показать паспорт (JWT-токен).
Посол берет специальную лупу (Кэшированные ключи JWKS) и просвечивает голограмму на вашем паспорте. Если голограмма совпадает с образцом печати Мирового Правительства, посол мгновенно выдает вам Внутреннюю Визу (Phantom Token / Session). Ему не нужно каждый раз звонить в Мировое Правительство по телефону, чтобы подтвердить вашу личность. Но если Мировое Правительство по красному телефону (RabbitMQ) сообщит: "Внимание, этот паспорт аннулирован", посол мгновенно порвет вашу визу.

## Возможности данного раздела

Ниже представлен перечень функциональных требований (SR) к механизмам OIDC-интеграции.

| Код | Название и Описание |
| :--- | :--- |
| **SR-AUTH-OI-01** | **OIDC Authorization Code Flow с PKCE:** Реализация защищенного потока аутентификации со строгой валидацией `state` и `nonce` для защиты от CSRF. |
| **SR-AUTH-OI-02** | **Кэширование и Валидация JWKS:** Фоновое скачивание публичных ключей STEOS ID для мгновенной in-memory проверки математических подписей (RSA) входящих JWT-токенов. |
| **SR-AUTH-OI-03** | **Just-In-Time (JIT) Onboarding:** Автоматическая оркестрация: если пользователь STEOS ID заходит на платформу впервые, Auth Service просит `Workspace Service` немедленно создать ему персональное пространство. |
| **SR-AUTH-OI-04** | **OIDC Back-Channel Logout (via RabbitMQ):** Слушатель брокера сообщений RabbitMQ. Мгновенная терминация локальных сессий при получении сигнала блокировки из STEOS ID. |
| **SR-AUTH-OI-05** | **Аварийная ротация JWKS:** Принудительный сброс локального кэша ключей и немедленное скачивание нового набора JWKS при подозрении на компрометацию ключей STEOS ID. |
| **SR-AUTH-OI-06** | **Синхронизация Identity Claims:** Фоновое обновление локального профиля пользователя и связанных с ним контекстов при изменениях в глобальном IdP. |
| **SR-AUTH-OI-08** | **Кросс-девайсная аутентификация:** Сценарии входа, где подтверждение выполняется на одном устройстве, а локальная сессия выпускается на другом (например, QR Login). |
| **SR-AUTH-OI-09** | **Passwordless / Magic Link Login:** Вход по одноразовой ссылке без пароля с безопасным обменом временного кода на локальную сессию. |

# Детальная спецификация требований

## SR-AUTH-OI-01: OIDC Authorization Code Flow с PKCE

Это фундаментальный процесс логина (Primary Authentication Flow). Он описывает, как именно фронтенд перенаправляет пользователя на страницу входа STEOS ID, и как бэкенд Authorization Service безопасно обменивает полученный код на токены.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Отказ от Implicit Flow** | Согласно лучшим практикам OAuth 2.1 (BCP), браузер никогда не должен получать токены напрямую в URL. Используется только *Authorization Code Grant*. |
| **Proof Key for Code Exchange (PKCE)** | Для защиты от перехвата Authorization Code вредоносным расширением браузера или трояном, Authorization Service генерирует криптографический секрет (`code_verifier`) и передает его хэш (`code_challenge`) в STEOS ID перед началом логина. |
| **Защита от CSRF (`state` и `nonce`)** | В таблицу `oidc_auth_flows` записывается уникальный `state` перед каждым редиректом. Если пользователь вернулся с другим `state`, транзакция обрывается. |

### 2. Высокоуровневое описание

Представим **получение заказного письма на почте по доверенности**.

1. **Запрос (Инициация):** Вы (Frontend) приходите на локальную почту (Authorization Service) и просите выдать вам важную посылку (доступ к Платформе).
2. **Секретный пароль (PKCE):** Почтальон говорит: "Я дам вам направление в Главпочтамт (STEOS ID). Но чтобы по пути никто не украл вашу квитанцию, давайте придумаем секретное слово 'Яблоко' (`code_verifier`). Я запишу себе хэш от этого слова (`code_challenge`) и передам его Главпочтамту".
3. **Поход в Главпочтамт (Редирект):** Вы идете в Главпочтамт, показываете свой паспорт (вводите логин/пароль в STEOS ID). Главпочтамт видит, что вы — это вы.
4. **Выдача квитанции (Authorization Code):** Главпочтамт не дает вам саму посылку (Токены). Он дает вам зашифрованную квитанцию (Code) и говорит: "Отнеси это своему почтальону".
5. **Обмен (Token Request):** Вы приносите квитанцию локальному почтальону (Бэкенду). Почтальон звонит в Главпочтамт (по защищенному S2S каналу) и говорит: "Мне принесли квитанцию №777. Секретное слово было 'Яблоко'".
6. **Успех:** Главпочтамт проверяет, сходится ли хэш от 'Яблоко' с тем, что он записал ранее. Если да — он безопасно передает почтальону саму посылку (Access/ID/Refresh токены). Почтальон кладет посылку в сейф (Redis) и выдает вам ключик от ячейки (Phantom Token).

Этот сложный танец гарантирует, что даже если хакер (злое расширение в браузере) украдет квитанцию на шаге 4, он не сможет обменять её на токены, так как не знает секретного слова 'Яблоко', которое осталось в памяти бэкенда.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает полную петлю аутентификации пользователя через глобальный STEOS ID.

**Общие исходные данные:**
*   **Инициатор:** Неавторизованный пользователь в браузере.
*   **Входящий запрос:** Клик по кнопке "Войти через STEOS ID".
*   **Контекст:** Отсутствие активной сессии.

#### Сценарий А: Успешный логин (Happy Path)

**Сценарий:** Пользователь проходит полный цикл OAuth2 аутентификации и возвращается на платформу с кодом, который бэкенд успешно обменивает на токены.

1.  **Инициация (Фронтенд):** Клиент делает `GET /api/auth/login`.
2.  **Подготовка PKCE (Бэкенд):** Auth Service генерирует криптографически стойкие `state`, `nonce` и PKCE `code_verifier`. Вычисляет `code_challenge` (SHA-256).
3.  **Сохранение стейта:** Данные (`state`, `code_verifier`, URL возврата) сохраняются в Redis с коротким TTL (например, 10 минут) по ключу `oidc:flow:{state}`.
4.  **Редирект:** Бэкенд возвращает HTTP `302 Found` с Location: `https://id.steos.io/authorize?response_type=code&client_id=123&state={state}&code_challenge={challenge}&code_challenge_method=S256&scope=openid profile email`.
5.  **Аутентификация в STEOS ID:** Пользователь вводит учетные данные на домене `id.steos.io`.
6.  **Callback (Возврат):** STEOS ID редиректит браузер обратно на `https://app.steos.io/api/auth/callback?code=AUTH_CODE_777&state={state}`.
7.  **Валидация State:** Auth Service извлекает `state` из URL, ищет ключ `oidc:flow:{state}` в Redis. Находит его (защита от CSRF пройдена) и извлекает `code_verifier`.
8.  **Token Exchange (S2S):** Auth Service делает POST-запрос напрямую к `https://id.steos.io/oauth/token` с параметрами: `grant_type=authorization_code`, `code=AUTH_CODE_777`, `client_secret=...`, и `code_verifier=...`.
9.  **Получение токенов:** STEOS ID валидирует код и верифайер, и возвращает JSON с `access_token`, `id_token`, `refresh_token`.
10. **Завершение:** Auth Service проверяет подпись `id_token` (SR-AUTH-OI-02), извлекает данные пользователя, создает Phantom Token (SR-AUTH-SM-01) и редиректит пользователя в приложение с установленной `HttpOnly` Cookie.

#### Сценарий Б: Атака с подменой State (Negative Path - CSRF/Interception)

**Сценарий:** Злоумышленник обманом заставляет жертву кликнуть по ссылке-коллбеку с чужим авторизационным кодом (атака Login CSRF).

1.  **Атака:** Хакер сам начинает флоу логина, получает от STEOS ID `code=HACKER_CODE` и `state=HACKER_STATE`. Он прерывает редирект и отправляет эту ссылку жертве: `https://app.steos.io/api/auth/callback?code=HACKER_CODE&state=HACKER_STATE`.
2.  **Переход жертвы:** Жертва кликает по ссылке (находясь в своем браузере).
3.  **Валидация State (Бэкенд):** Auth Service жертвы получает запрос. Он берет `state=HACKER_STATE` и ищет его в *своем* локальном Redis (или в Cookie сессии флоу).
4.  **Промах:** Так как этот `state` был сгенерирован для браузера хакера, в сессии жертвы этого `state` нет.
5.  **Блокировка:** Сервис немедленно прерывает процесс обмена. S2S запрос к STEOS ID не выполняется.
6.  **Возврат ошибки:** Сервис возвращает HTTP `400 Bad Request` (ProblemDetails: `code: "INVALID_STATE"`, `detail: "Authentication flow state mismatch. Possible CSRF attack."`). Жертва защищена от принудительного логина в чужой аккаунт.

## SR-AUTH-OI-02: Кэширование и Валидация JWKS

Валидация JWT-токенов — самая частая операция в системе. Токены, которые STEOS ID выдал нашему Authorization Service (и которые мы прячем от браузера в Redis), подписаны приватным ключом STEOS ID.

Если бы Auth Service при каждом логине делал синхронный HTTP-запрос к STEOS ID с вопросом "Этот токен валиден?", платформа легла бы под нагрузкой. Валидация должна происходить локально, в памяти (In-Memory).

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Фоновое скачивание (JWKS Caching)** | Auth Service имеет фоновый процесс (Background Worker), который регулярно (раз в час) обращается к эндпоинту `https://id.steos.io/.well-known/jwks.json` и скачивает массив публичных ключей. |
| **Локальное хранение (`idp_jwks_cache`)** | Ключи кэшируются в БД/Redis (и кэшируются в оперативной памяти каждого экземпляра микросервиса). При получении OIDC-токена в Callback-роуте, сервис извлекает заголовок токена (Header), достает `kid` (Key ID), находит этот ключ в локальном кэше и криптографически проверяет подпись (Signature). |
| **Отказоустойчивость** | Если STEOS ID временно недоступен (например, при DDoS-атаке на него), кэшированные ключи позволяют локальному сервису продолжать работу без сбоев (Graceful Degradation), успешно авторизуя пользователей, у которых есть валидные токены. |
| **Zero-Downtime Ротация** | Поддержка механизма автоматического обновления ключей при их ротации на стороне IdP без ручного вмешательства администраторов. |

### 2. Высокоуровневое описание

Представим **проверку банкнот детектором валют в магазине**.

1. **Новые купюры (Ключи подписи):** Центральный Банк (STEOS ID) регулярно выпускает новые банкноты (новые приватные ключи) с обновленными водяными знаками (JWKS).
2. **Обновление детектора (JWKS Caching):** Каждое утро (раз в час) магазин (Authorization Service) скачивает по защищенной связи свежий список водяных знаков от ЦБ. Этот список загружается прямо в память сканера на кассе.
3. **Оплата (Валидация JWT):** Когда покупатель протягивает купюру 1000 рублей (Access Token), кассир кладет её в сканер.
4. **Оффлайн-проверка (In-Memory):** Сканер светит ультрафиолетом и за миллисекунду сравнивает водяной знак (`kid` в JWT заголовке) с теми эталонами, что он скачал утром. Ему не нужно звонить по телефону в Центробанк каждый раз, чтобы спросить: "Алло, а эта купюра настоящая?".
5. **Фальшивка (Invalid Signature):** Если злоумышленник попытается нарисовать свою купюру (подделать JWT) с выдуманным водяным знаком, сканер мгновенно забракует ее.
6. **Ротация ключей (Grace Period):** Если Центробанк сообщает: "Завтра мы меняем водяные знаки, но старые купюры действуют еще месяц", магазин скачивает и хранит в сканере ОБА списка. Сканер будет принимать старые купюры до истечения их срока годности (до истечения TTL старого JWK).

Этот механизм — основа производительности и отказоустойчивости всей архитектуры.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает механику локальной валидации подписи JWT без сетевых запросов.

**Общие исходные данные:**
*   **Инициатор:** OIDC Callback (при завершении логина) или вызов `Silent Refresh`.
*   **Входящий запрос:** Получен JSON Web Token (JWT) от STEOS ID.
*   **Контекст:** Сервис должен удостовериться, что токен действительно выпущен глобальным IdP и не был изменен в пути.

#### Сценарий А: Успешная валидация кэшированным ключом (Happy Path)

**Сценарий:** Auth Service получает токен, находит публичный ключ в In-Memory кэше и успешно валидирует RSA-подпись.

1.  **Парсинг токена:** Auth Service получает JWT. JWT состоит из трех частей, разделенных точками: `Header.Payload.Signature` (Base64Url).
2.  **Извлечение Header'а:** Библиотека валидации (например, `jose`) декодирует Header и достает поля `alg` (например, `RS256`) и `kid` (например, `key-2026-03`).
3.  **Поиск в кэше:** Сервис ищет публичный ключ (JWK) с идентификатором `key-2026-03` в своем локальном In-Memory кэше.
4.  **Успех (Ключ найден):** Ключ присутствует в памяти. Сервис берет Payload токена и криптографически проверяет, совпадает ли полученная `Signature` (третья часть) с хэшем Payload'а, зашифрованным публичным ключом `key-2026-03`.
5.  **Валидация пройдена:** Подпись верна. Сервис приступает к проверке claims (например, `iss`, `aud`, `exp`). Время выполнения проверки — менее 1 миллисекунды.

#### Сценарий Б: Ключ не найден (Negative Path - Force Refresh)

**Сценарий:** STEOS ID внезапно произвел ротацию ключей (например, из-за компрометации старого приватного ключа). Auth Service получает токен, подписанный совершенно новым ключом.

1.  **Парсинг токена:** Сервис декодирует Header и достает `kid` = `key-EMERGENCY-2026-04`.
2.  **Поиск в кэше:** Сервис ищет ключ `key-EMERGENCY-2026-04` в памяти.
3.  **Промах (Cache Miss):** Ключ не найден, так как фоновый Worker еще не успел сработать (или сработает только через полчаса).
4.  **Синхронный S2S вызов (Force Update):** Auth Service понимает, что это может быть новый легальный ключ. Он немедленно, синхронно делает HTTP-запрос `GET https://id.steos.io/.well-known/jwks.json`.
5.  **Получение JWKS:** STEOS ID отвечает `200 OK` с новым списком ключей, среди которых есть `key-EMERGENCY-2026-04`.
6.  **Обновление кэша:** Сервис обновляет локальный кэш (в памяти, Redis и БД).
7.  **Повторная валидация:** Сервис возвращается к шагу 4 Сценария А, на этот раз успешно проверяя подпись новым ключом. Токен принимается, авторизация завершается без ошибки для пользователя.
8.  **Защита от DDoS:** Если хакер шлет тысячи токенов со случайными `kid` (атака "Cache Miss Flood"), сервис не делает HTTP-запрос на каждый промах, а использует Rate Limiter для фоновых обновлений JWKS (например, не чаще 1 раза в минуту). Если за минуту ключ не появился — `401 Unauthorized`.

## SR-AUTH-OI-03: Just-In-Time (JIT) Onboarding

STEOS ID — это глобальная система. Пользователь мог зарегистрироваться в ней год назад для игры в другую игру. Сегодня он впервые зашел на нашу Платформу.
Платформе необходимо где-то хранить настройки интерфейса пользователя (какую тему он выбрал, какие задачи создал). Ему нужно личное Рабочее Пространство (Workspace).

Заставлять пользователя нажимать кнопку "Создать аккаунт на Платформе" после того, как он уже вошел через STEOS ID — плохой UX (User Experience). Система должна сделать это "на лету".

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Перехват первого входа (Zero-Click Registration)** | При успешном завершении OIDC-флоу (SR-AUTH-OI-01), Auth Service проверяет: "Есть ли у этого `global_steos_id` хотя бы одна запись в локальной таблице профилей или пространств?". |
| **Оркестрация микросервисов** | Если пользователя нет, Auth Service "приостанавливает" создание сессии и делает синхронный gRPC/S2S вызов в микросервис управления пространствами (`Workspace Service`): "Пользователь ID 123 вошел впервые. Создай ему Personal Workspace и назначь роль Владельца". |
| **Контекст по умолчанию** | Получив подтверждение от `Workspace Service` (и ID созданного пространства), Auth Service завершает логин, создает сессию в Redis и сразу устанавливает `session_contexts.active_workspace_id` равным новому пространству. Пользователь бесшовно попадает в готовый к работе интерфейс. |

### 2. Высокоуровневое описание

Представим **автоматическое заселение в гостиницу для VIP-клиентов**.

1. **Прибытие (Логин):** Вы прилетаете в новую страну (заходите на Платформу) и подходите к терминалу самообслуживания (Auth Service). Вы прикладываете свой глобальный VIP-паспорт (STEOS ID).
2. **Проверка постояльцев:** Терминал смотрит в свою базу данных. Вы еще ни разу здесь не останавливались (вашего `global_steos_id` нет в локальной базе).
3. **Заказ номера (JIT Provisioning):** Терминал не говорит вам: "Идите заполните анкету на стойке регистрации". Вместо этого терминал по внутренней связи мгновенно звонит Управляющему отелем (`Workspace Service`): "К нам приехал VIP-клиент №123. Срочно подготовьте ему персональный номер Люкс!".
4. **Готовность (Подтверждение):** Управляющий за миллисекунды заводит на вас карточку гостя (Local User Profile) и бронирует номер Люкс №404 (Personal Workspace). Он сообщает номер комнаты терминалу.
5. **Выдача ключа (Завершение):** Терминал выдает вам пластиковый ключ от комнаты (Phantom Token) и на экране загорается надпись: "Добро пожаловать! Ваш персональный номер 404 готов к работе". Вы не сделали ни одного лишнего клика. Вы просто приложили паспорт и оказались в своем номере.

Этот бесшовный процесс радикально снижает барьер входа (Friction) для новых пользователей экосистемы STEOS.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает механику автоматического создания локального профиля и пространства для нового пользователя.

**Общие исходные данные:**
*   **Инициатор:** Auth Service (во время обработки OIDC Callback).
*   **Входящий запрос:** Получен и валидирован Access Token (и `id_token`) от STEOS ID.
*   **Контекст:** Пользователь успешно прошел аутентификацию в глобальной системе.

#### Сценарий А: Успешный онбординг (Happy Path)

**Сценарий:** Пользователь (ID `steos-new-123`) впервые заходит на Платформу. Система создает ему профиль и личное пространство "на лету".

1.  **Извлечение данных:** Auth Service валидирует токены и извлекает `global_steos_id` = `steos-new-123` и базовые клеймы из `id_token` (например, `email`, `nickname`).
2.  **Поиск локального профиля:** Auth Service делает быстрый запрос в БД PostgreSQL `SELECT id FROM local_users WHERE global_steos_id = 'steos-new-123'`.
3.  **Пользователь не найден:** БД возвращает пустоту. Это сигнал к старту JIT Onboarding.
4.  **Оркестрация (Workspace Service):** Auth Service делает синхронный gRPC вызов `CreateInitialSetup` к микросервису `Workspace Service`. Он передает туда `global_steos_id`, `email`, и метаданные (если нужно).
5.  **Создание сущностей (Workspace Service):**
    *   `Workspace Service` создает запись в таблице профилей.
    *   Создает новую запись `Workspaces` с типом `PERSONAL`.
    *   Назначает пользователя владельцем (`OWNER`) этого пространства.
    *   Возвращает `200 OK` с `new_workspace_id = 'ws-42'`.
6.  **Завершение сессии:** Auth Service записывает сессию в Redis (SR-AUTH-SM-01) и устанавливает `active_workspace_id = ws-42`.
7.  **Редирект:** Браузер перенаправляется на `https://app.steos.io/`, и пользователь сразу видит пустой дашборд своего нового личного пространства.

#### Сценарий Б: Ошибка создания пространства (Negative Path - Service Unavailable)

**Сценарий:** `Workspace Service` временно недоступен или вернул ошибку базы данных в момент онбординга.

1.  **Поиск локального профиля:** Auth Service обнаруживает, что пользователя нет в БД.
2.  **Оркестрация:** Делает вызов `CreateInitialSetup` к `Workspace Service`.
3.  **Сбой:** `Workspace Service` возвращает `503 Service Unavailable` или обрывается по таймауту (например, 2 секунды).
4.  **Обработка ошибки (Отмена сессии):** Auth Service **не** создает сессию (Phantom Token не генерируется, в Redis ничего не пишется). Нельзя пустить пользователя в систему без локального профиля и контекста.
5.  **Возврат ошибки пользователю:** Auth Service редиректит пользователя на специальную страницу ошибки фронтенда `https://app.steos.io/error?code=ONBOARDING_FAILED`. Пользователь видит сообщение: "Мы не смогли подготовить ваше рабочее пространство. Пожалуйста, повторите попытку через пару минут".
6.  **Логирование:** Ошибка оркестрации фиксируется в логах мониторинга для разбора DevOps-инженерами.

## SR-AUTH-OI-04: OIDC Back-Channel Logout (via RabbitMQ)

Это требование обеспечивает безопасность экосистемы (Zero Trust). Если глобальный STEOS ID обнаруживает, что аккаунт взломан (хэш сессии совпал с аномальным IP) или администратор нажал кнопку "Глобальный бан" (Global Kill Switch), локальные платформы не могут узнать об этом сами, пока у пользователя не истечет локальная сессия в Redis.

Глобальный IdP должен иметь механизм принудительного и мгновенного "выстрела" (отзыва сессий) во все интегрированные платформы.

**Важно:** Для гарантированной асинхронной доставки сообщений используется **RabbitMQ**, а не Apache Kafka. Kafka слишком тяжеловесна для событий безопасности типа "Logout", где важна мгновенная маршрутизация (Fanout Exchange), а не долговременное хранение гигантских логов (Event Sourcing).

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Слушатель Брокера (RabbitMQ Consumer)** | Auth Service постоянно подписан на Exchange (тип `fanout` или `topic`) в брокере сообщений **RabbitMQ**. |
| **Асинхронная Инвалидация** | При получении события (сообщения) вида `ACTOR_BANNED`, `PASSWORD_CHANGED` или `GLOBAL_LOGOUT_REQUESTED` с указанием `global_steos_id`, процесс-слушатель просыпается. |
| **Массовое удаление (Mass Revoke)** | Слушатель идет в таблицу `authorized_sessions` (или напрямую в индексы Redis), находит все ключи сессий, где владелец — этот `steos_id`. Он обновляет их статус `is_active = false` в БД и (самое главное) **мгновенно удаляет (GETDEL) все эти сессии из Redis**. |
| **Idempotency** | Если сообщение RabbitMQ пришло дважды (at-least-once delivery), повторное удаление ключей не вызывает ошибок (Redis `DEL` идемпотентен). |

### 2. Высокоуровневое описание

Представим **пульт дистанционного глушения двигателя (Иммобилайзер)**.

1. **Аренда:** Вы взяли каршеринг (авторизовались). Бортовой компьютер (Auth Service) позволяет вам завести двигатель. Сессия активна. Вы едете.
2. **Угон (Инцидент):** Внезапно диспетчерский центр (глобальный STEOS ID) видит, что ваша кредитка заблокирована банком за мошенничество (или вы нажали кнопку "У меня украли машину").
3. **Радиосигнал (RabbitMQ Message):** Диспетчер нажимает красную кнопку. В эфир (RabbitMQ Exchange) мгновенно улетает радиосигнал высокой приоритетности: "Заблокировать машину номер 123!".
4. **Перехват сигнала:** Приемник бортового компьютера (RabbitMQ Consumer внутри Auth Service) ловит этот сигнал за миллисекунды. Ему не нужно самому спрашивать диспетчера "Все ли нормально?". Сигнал сам находит его.
5. **Отключение двигателя (Mass Revoke):** Бортовой компьютер немедленно отключает подачу топлива (удаляет ключи сессии из оперативной памяти Redis).
6. **Остановка:** В ту же секунду машина глохнет. Угонщик, который только что пытался нажать на газ (создать бизнес-запрос), видит на панели надпись "Доступ запрещен" (HTTP 401 Unauthorized), так как API Gateway не может найти сессию в Redis.

Этот механизм гарантирует, что "Радиус взрыва" (Blast Radius) при компрометации глобального аккаунта сводится к абсолютному минимуму.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает асинхронную реакцию сервиса на глобальное событие безопасности.

**Общие исходные данные:**
*   **Инициатор:** Событие (сообщение) из брокера `RabbitMQ` (опубликованное глобальным STEOS ID).
*   **Входящий запрос:** Слушатель (Consumer) вычитывает сообщение из очереди (Queue), привязанной к Exchange `steos.auth.events`.
*   **Контекст:** Пользователь активно работает на платформе, у него в браузере лежит валидная `HttpOnly` Cookie.

#### Сценарий А: Успешный мгновенный разлогин (Happy Path)

**Сценарий:** STEOS ID зафиксировал смену пароля на устройстве А. Пользователь сидит на устройстве Б. Система убивает сессию на устройстве Б.

1.  **Генерация события:** Глобальный STEOS ID публикует в RabbitMQ Exchange сообщение с ключом маршрутизации (Routing Key) `user.security.password_changed`. Тело (Payload): `{"event_id": "...", "global_steos_id": "uuid-user-123", "timestamp": "..."}`.
2.  **Получение сообщения:** Worker-процесс `Auth Service` вычитывает (Consume) это сообщение из RabbitMQ.
3.  **Поиск сессий:** Worker делает запрос к Redis. (Если Redis поддерживает вторичные индексы (Redis Stack/RediSearch) или ведется список ключей по `user_id` — `SMEMBERS steos:user_sessions:uuid-user-123`). Находит три активные сессии (ID: `sess-A`, `sess-B`, `sess-C`).
4.  **Удаление из Redis (Kill Switch):**
    *   Worker отправляет команду в Redis: `DEL steos:sess:sess-A steos:sess:sess-B steos:sess:sess-C`.
    *   Удаляет индексный список `steos:user_sessions:uuid-user-123`.
    *   Все три сессии мертвы. Время выполнения шагов 1-4 — менее 50 миллисекунд.
5.  **Персистентность (БД):** Worker отправляет асинхронный UPDATE в PostgreSQL: `UPDATE authorized_sessions SET is_active = false, revoked_at = NOW(), revoke_reason = 'GLOBAL_SECURITY_EVENT' WHERE global_steos_id = 'uuid-user-123'`.
6.  **Подтверждение (ACK):** Worker отправляет подтверждение (`basicAck`) в RabbitMQ, что сообщение успешно обработано.
7.  **Отказ в доступе:** Пользователь на устройстве Б кликает кнопку "Сохранить профиль". Фронтенд шлет AJAX-запрос. API Gateway берет Cookie (`sess-B`), ищет в Redis, получает `nil` (ключ не найден) и немедленно возвращает `401 Unauthorized`. Фронтенд редиректит пользователя на страницу логина.

#### Сценарий Б: Сбой при обработке сообщения (Negative Path - Retry Policy)

**Сценарий:** Auth Service получает сообщение о блокировке, но в этот момент Redis недоступен или кластер перегружен (Network Partition).

1.  **Получение сообщения:** Worker-процесс `Auth Service` вычитывает событие `ACTOR_BANNED` из RabbitMQ.
2.  **Попытка удаления (Сбой):** Worker пытается выполнить `DEL` в Redis, но получает ошибку таймаута соединения (Connection Refused).
3.  **Обработка ошибки (NACK):** Worker ловит Exception. Он **не** отправляет `basicAck` в RabbitMQ. Вместо этого он отправляет `basicNack` с флагом `requeue=false` (или использует механизм Dead Letter Exchange - DLX с `requeue=true` и задержкой).
4.  **Повторная попытка (Retry):** Сообщение возвращается в очередь RabbitMQ (или DLX-очередь). RabbitMQ доставит его снова через заданный интервал (например, 5 секунд) этому же или другому экземпляру (Replica) `Auth Service`.
5.  **Успех со 2-й попытки:** Со второго раза соединение с Redis восстанавливается. Сессии удаляются. Подтверждение (`ACK`) отправляется.
6.  **Надежность:** Благодаря RabbitMQ, критически важное событие безопасности (бан злоумышленника) не теряется даже в случае кратковременного сбоя инфраструктуры. Сессии будут убиты, как только инфраструктура "оживет".

## SR-AUTH-OI-05: Аварийная ротация JWKS

Это требование описывает реакцию платформы на чрезвычайную ситуацию, когда существует риск компрометации ключевого материала глобального Identity Provider. Обычного TTL кэша в такой ситуации недостаточно.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Fail-Safe ротация** | Auth Service должен уметь принудительно удалить локальный кэш старых ключей и немедленно скачать новый набор JWKS. |
| **Аварийный триггер** | Инициатором может быть администратор ИБ, внутренний RPC или событие из RabbitMQ от STEOS ID. |
| **Минимизация даунтайма** | Ротация не должна останавливать весь сервис; в худшем случае активируется graceful fallback со старым набором до успешной загрузки новых ключей. |
| **Аудит критичного действия** | Каждая принудительная ротация фиксируется в локальном WORM-журнале как событие повышенной важности. |

### 2. Высокоуровневое описание

Представим **замену эталонного оттиска печати на пограничном посту**.

1. **Компрометация старого образца:** Безопасники узнают, что старый оттиск печати больше нельзя считать надежным.
2. **Сброс доверия:** Пограничник выбрасывает старую карточку-образец из памяти.
3. **Получение нового эталона:** Система срочно запрашивает новый комплект образцов у центрального ведомства.
4. **Проверка только по новым данным:** С этого момента все входящие паспорта проверяются уже по новому набору признаков.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешная аварийная ротация (Happy Path)

1. STEOS ID сообщает о компрометации ключа подписи.
2. Auth Service сбрасывает In-Memory и Redis-кэш JWKS.
3. Сервис синхронно или фоново скачивает новый набор публичных ключей.
4. Новые входящие токены валидируются уже только новым набором ключей.

## SR-AUTH-OI-06: Синхронизация Identity Claims

Локальный Authorization Service хранит кэшируемый срез данных пользователя, достаточный для построения `SessionContextDto`. Этот срез должен актуализироваться при изменении email, имени, глобального статуса или других базовых claims в STEOS ID.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Фоновая актуализация профиля** | Изменения в IdP должны попадать в локальную платформу без ручного перелогина пользователя. |
| **Источник истины — STEOS ID** | Auth Service не спорит с глобальным IdP по поводу базовых identity-claims, а только кэширует их локально. |
| **Синхронизация активных сессий** | После обновления профиля локальные `SessionContextDto` и UI-представление должны быстро получить новые данные. |
| **Несколько каналов запуска** | Синхронизация может запускаться при логине, webhook/событии RabbitMQ или внутренним административным trigger-ом. |

### 2. Высокоуровневое описание

Представим **локальную копию карточки сотрудника, которую нужно держать синхронной с центральным отделом кадров**.

1. **Изменение в центре:** Пользователь обновляет имя, email или иной базовый атрибут в глобальном IdP.
2. **Получение сигнала:** Локальная платформа узнает об изменении по webhook, событию или при логине.
3. **Обновление локальной копии:** Authorization Service обновляет свои таблицы и кэшированные контексты.
4. **Мгновенное применение:** Интерфейс и downstream-сервисы сразу начинают видеть свежие данные.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешная синхронизация профиля (Happy Path)

1. Пользователь меняет имя или email в STEOS ID.
2. Auth Service получает внешний сигнал или сам инициирует refresh claims.
3. Локальная таблица профилей и активные сессии пользователя обновляются.
4. Новый профиль сразу используется при последующих запросах и отображении интерфейса.

## SR-AUTH-OI-08: Кросс-девайсная аутентификация

Это требование описывает вход, при котором пользователь подтверждает свою личность на доверенном устройстве, а рабочая локальная сессия создается на другом клиенте, ожидающем результат в реальном времени.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Разделение подтверждения и потребления** | Одно устройство подтверждает логин, другое получает право войти в платформу. |
| **Временный Intent** | Между устройствами используется короткоживущий идентификатор попытки входа, а не сама Cookie. |
| **Real-time обратная связь** | Клиент, ожидающий завершения логина, получает мгновенное событие через WebSocket/SignalR. |
| **Безопасный финальный exchange** | Финальная Phantom Cookie выдается только через отдельный HTTP exchange, а не через WebSocket payload. |

### 2. Высокоуровневое описание

Представим **вход через турникет, где телефон служит доверенным пропуском для компьютера перед вами**.

1. **Ожидающий клиент:** На десктопе создается временное намерение входа (`Intent`), но сама сессия еще не выдана.
2. **Подтверждение на втором устройстве:** Телефон подтверждает, что действие совершает настоящий пользователь.
3. **Серверный обмен:** Auth Service связывает подтверждение с исходным `Intent`.
4. **Финальная выдача сессии:** Десктоп получает только право завершить вход через отдельный безопасный exchange.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешный QR Login (Happy Path)

1. Десктоп генерирует QR/Intent и подписывается на событие завершения.
2. Мобильное устройство сканирует QR и подтверждает логин в доверенном контуре.
3. Auth Service валидирует подтверждение и отправляет десктопу одноразовый exchange-код.
4. Десктоп делает финальный HTTP-запрос и получает локальную `HttpOnly` Cookie.

## SR-AUTH-OI-09: Passwordless / Magic Link Login

Требование покрывает беспарольные сценарии входа через одноразовые ссылки в email или аналогичные временные каналы подтверждения личности.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Отказ от постоянного секрета на клиенте** | Пользователь может войти без ввода пароля, подтверждая владение почтой или другим доверенным каналом. |
| **Одноразовость** | Magic Link и exchange-код должны жить очень короткое время и гаситься сразу после использования. |
| **Привязка к исходному Intent** | Ссылка авторизует не случайный браузер, а конкретный ожидающий контекст или Intent логина. |
| **Защита от replay** | Повторное использование той же ссылки или exchange-кода невозможно. |

### 2. Высокоуровневое описание

Представим **заказное письмо с одноразовым талоном на вход**.

1. **Запрос на вход:** Пользователь сообщает системе свой email и просит впустить его без пароля.
2. **Доставка талона:** На доверенный канал отправляется одноразовая ссылка или код.
3. **Проверка владения каналом:** Переход по ссылке подтверждает, что пользователь действительно контролирует нужный email.
4. **Выпуск локальной сессии:** После подтверждения клиент получает одноразовый exchange и завершает вход в нужном браузере.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешный вход по Magic Link (Happy Path)

1. Пользователь вводит email и инициирует passwordless login.
2. Система отправляет одноразовую ссылку или код в доверенный канал.
3. После перехода по ссылке Auth Service подтверждает Intent и выпускает exchange-код.
4. Целевой браузер получает локальную сессию без ввода пароля.
