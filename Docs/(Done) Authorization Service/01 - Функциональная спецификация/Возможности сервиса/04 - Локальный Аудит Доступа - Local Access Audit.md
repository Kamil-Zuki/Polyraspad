# Введение

Этот раздел описывает собственную систему журналирования (аудита) платформы STEOS.
Важно понимать разницу: глобальный STEOS ID пишет логи смены паролей, подключения 2FA и изменения имени (Паспортные данные). Локальный **Authorization Service** пишет логи перемещения пользователя внутри конкретного здания (Платформы) и использования рабочих пространств (Контекста).

**Метафора:**
Представьте **Вахтенный журнал на проходной предприятия**.
Когда вы устраиваетесь на работу, в Отделе Кадров (STEOS ID) заводят вашу личную карточку. Но когда вы каждое утро приходите на завод, вахтер (Authorization Service) записывает в свой толстый прошитый журнал: "Иван пришел в 9:00. В 10:15 перешел из цеха А (Workspace 1) в цех Б (Workspace 2). В 18:00 ушел домой".

Если на заводе (в платформе) случится ЧП, служба безопасности не пойдет в Отдел Кадров спрашивать, какой у Ивана номер телефона. Она откроет вахтенный журнал и посмотрит, в каком цеху он находился в момент аварии. Этот журнал нельзя переписать или вырвать из него страницу (WORM - Write Once, Read Many).

# Возможности данного раздела

Ниже представлен перечень функциональных требований (SR) к механизмам локального аудита и маршрутизации контекста.

| Код               | Название и Описание                                                                                                                                                                                                                                                         |
| :---------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SR-AUTH-LA-01** | **Журнал Локального Доступа (WORM):** Регистрация только платформенных событий: успешный вход, смена Workspace, старт имперсонации, срабатывание Back-Channel Logout. Пишется в таблицу `access_audit_logs` (Append-Only).                                                  |
| **SR-AUTH-LA-02** | **Категоризация Причин Блокировок:** Использование стандартизированного справочника `local_ban_reasons` (например, `GUEST_QUOTA_ABUSE`, `MALICIOUS_PAYLOAD`) для аналитики инцидентов и локализации сообщений об ошибках в UI.                                              |
| **SR-AUTH-LA-03** | **Инъекция Трассировки в Downstream (Header Routing):** Концепция Zero Trust. Auth Service "снимает" Cookie, извлекает стейт из Redis и отправляет во внутренние бизнес-микросервисы (Tasks, CRM) только доверенные HTTP-заголовки (`X-Workspace-Id`, `X-Global-Actor-Id`). |
| **SR-AUTH-LA-04** | **Потоковая передача WORM-аудита в SIEM:** Асинхронная трансляция новых событий локального аудита во внешние системы мониторинга и расследования инцидентов.                                                                                                                |
| **SR-AUTH-LA-05** | **Экспорт архива аудита:** Асинхронная подготовка архивов журнала доступа за период для комплаенса, внутренних расследований и регуляторных проверок.                                                                                                                       |
| **SR-AUTH-LA-06** | **Детализация события аудита:** Получение расширенного макроконтекста конкретного инцидента (`before/after`, actor, trace, reason) без нарушения WORM-характеристик исходного журнала.                                                                                      |
| **SR-AUTH-LA-07** | **Агрегированная аналитика доступа:** Выдача сводных показателей по активным сессиям, блокировкам, гостевым квотам и событиям безопасности для административных панелей.                                                                                                    |

# Детальная спецификация требований

## SR-AUTH-LA-01: Журнал Локального Доступа (WORM)

События безопасности (вход, выход, ошибки доступа) — это критичные доказательства (Evidence) при расследовании инцидентов. Они не могут быть просто строчками в логах контейнера (STDOUT), которые исчезнут при ротации. Они должны храниться в базе данных платформы.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Неизменяемость (Append-Only)** | Записи в таблицу `access_audit_logs` могут только добавляться (`INSERT`). Операции `UPDATE` и `DELETE` (кроме фоновой очистки старых данных) строго запрещены на уровне прав доступа к СУБД. |
| **Привязка к Глобальной Идентичности** | Каждая запись обязательно содержит `global_steos_id` пользователя, `session_id`, `ip_address` и `device_fingerprint` (чтобы можно было доказать, что это был именно он, а не украденная сессия). |
| **Справочник Событий** | Для унификации используется таблица `local_audit_event_types`. Записываются стандартизированные коды: `SESSION_STARTED` (OIDC-логин успешен), `OIDC_FAILED` (ошибка валидации `state` или JWT), `CONTEXT_SWITCHED` (переход в другое Пространство), `SESSION_REVOKED` (нажата кнопка Выход), `BACK_CHANNEL_LOGOUT` (сигнал от STEOS ID), `IMPERSONATION_STARTED` (вход саппорта под клиентом). |
| **Data Lake Export** | Для разгрузки основной OLTP базы данных (PostgreSQL), исторические записи старше 30 дней асинхронно выгружаются в холодное хранилище (S3/Data Lake) и удаляются из горячей базы. |

### 2. Высокоуровневое описание

Представим **бортовой самописец (черный ящик) в самолете**.

1. **Регистрация событий:** Во время полета (работы Платформы) пилоты нажимают разные кнопки: выпускают шасси, меняют эшелон (пользователь логинится, меняет Workspace).
2. **Непрерывная запись (Append-Only):** Все эти действия, вместе с точным временем, координатами и параметрами двигателей (IP-адрес, Fingerprint, Trace ID) непрерывно записываются на защищенную магнитную ленту самописца (таблица `access_audit_logs`).
3. **Неизменяемость (WORM):** Пилот не может открыть черный ящик в полете и стереть запись о том, что он отключил автопилот. Лента движется только в одну сторону (Write Once, Read Many).
4. **Расследование (Инцидент):** Если самолет совершает жесткую посадку (происходит утечка данных или взлом), комиссия (Отдел Безопасности) открывает черный ящик. Они видят поминутную картину: "В 12:00 кто-то с IP-адреса хакера успешно прошел логин (потому что пароль был украден), а в 12:05 сменил Workspace на административный".

Этот журнал — единственный неопровержимый источник правды о том, кто, когда и откуда получил доступ к локальной инсталляции STEOS.

### 3. Примеры взаимодействия (логические сценарии)

**Общие исходные данные:**
*   **Инициатор:** Внутренние механизмы Auth Service (при наступлении значимого события).
*   **Событие:** Пользователь нажал кнопку "Выйти со всех устройств" (Global Revoke).
*   **Контекст:** Необходимо надежно зафиксировать этот факт для истории.

#### Сценарий А: Успешная запись в журнал (Happy Path)

1.  **Действие:** Пользователь инициирует `DELETE /api/auth/sessions/all`.
2.  **Обработка:** Auth Service удаляет ключи сессий из Redis и помечает записи в БД как `is_active = false`.
3.  **Формирование записи:** В коде микросервиса формируется объект события:
    *   `event_type`: `SESSIONS_REVOKED_ALL`
    *   `actor_id`: `uuid-user-123`
    *   `ip_address`: `192.168.1.5`
    *   `trace_id`: `trace-abc-777` (для связки с логами микросервисов)
    *   `details`: `{"revoked_count": 3, "reason": "USER_INITIATED"}`
4.  **Запись в БД (WORM):** Выполняется `INSERT INTO access_audit_logs`.
5.  **Успех:** Транзакция зафиксирована. Если завтра пользователь скажет "Я не выходил из системы, это баг", администратор откроет журнал и покажет точное время и IP-адрес устройства, с которого была нажата кнопка.

#### Сценарий Б: Сбой при записи критичного события (Negative Path)

1.  **Действие:** Пользователь успешно прошел OIDC логин. Сессия в Redis создана.
2.  **Попытка записи:** Auth Service пытается сделать `INSERT INTO access_audit_logs` события `SESSION_STARTED`.
3.  **Сбой СУБД:** PostgreSQL внезапно отвечает ошибкой (например, `Disk Full` или `Deadlock`).
4.  **Обработка ошибки (Fall-back):** Так как аудит критичен, но мы не хотим блокировать успешный логин пользователя (если это не строгий режим комплаенса), сервис ловит исключение БД.
5.  **Асинхронное спасение:** Запись отправляется в резервную очередь (RabbitMQ `audit.fallback` или пишется в локальный файл на диске пода/контейнера).
6.  **Мониторинг:** В систему алертинга уходит критический сигнал "Audit Log DB is down!".
7.  **Восстановление:** Когда БД починят, резервный процесс вычитает очередь и допишет потерянные события в `access_audit_logs`, сохранив хронологию.

## SR-AUTH-LA-02: Категоризация Причин Блокировок

Аудит должен быть понятным и структурированным для автоматического анализа (Security Information and Event Management - SIEM) и для отображения причин блокировки в интерфейсе администратора.

### 1. Цель и ключевые принципы

| Принцип                            | Описание                                                                                                                                                                                                                                                                        |
| :--------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Справочник `local_ban_reasons`** | Единый реестр причин локальных блокировок (Группа 3, SR-AUTH-SQ-03). Содержит машиночитаемый код (например, `BRUTEFORCE_LOGIN`) и человекочитаемое описание.                                                                                                                    |
| **Аналитика и UI**                 | Запись в журнале о блокировке сессии или IP обязательно ссылается на этот справочник (Foreign Key). Это позволяет DevOps-инженерам строить дашборды: "График блокировок по причине `GUEST_QUOTA_ABUSE` за неделю", а техподдержке мгновенно видеть причину жалобы пользователя. |
| **Локализация ошибок**             | Машиночитаемый код причины используется фронтендом для перевода (i18n) текста ошибки на язык пользователя (например, "Ваш IP временно заблокирован из-за подозрительной активности").                                                                                           |

### 2. Высокоуровневое описание

Представим **медицинскую карту пациента с кодами МКБ (Международная классификация болезней)**.

1. **Инцидент (Симптомы):** Человек попал в больницу (его IP-адрес заблокирован Gateway'ем).
2. **Диагноз (Категоризация):** Врач (Auth Service) не пишет в карту длинный текст: "Пациент пришел и начал странно себя вести, дергать ручку двери 100 раз в секунду". Врач ставит точный стандартизированный код диагноза: `F42.1` (в нашем случае код `API_RATE_LIMIT_EXCEEDED`).
3. **Статистика (Аналитика):** В конце месяца Главврач (DevOps/SecOps) просит отчет. Ему не нужно читать тысячи текстовых описаний. Он делает простой SQL-запрос по кодам и видит: "Ага, у нас эпидемия `MALICIOUS_PAYLOAD` (попыток инъекций). Нужно усилить WAF".
4. **Общение с пациентом (Локализация):** Когда пациент (Пользователь) спрашивает "Чем я болен?", система берет код `GUEST_QUOTA_ABUSE`, смотрит в словарь переводов и выдает на понятном ему языке: "Вы исчерпали лимит бесплатных запросов".

### 3. Примеры взаимодействия (логические сценарии)

**Общие исходные данные:**
*   **Инициатор:** Внутренний механизм защиты Auth Service (SR-AUTH-SQ-03).
*   **Событие:** IP-адрес `10.0.0.5` заблокирован за сканирование портов/эндпоинтов (404 ошибки).
*   **Контекст:** Необходимо зафиксировать инцидент так, чтобы его легко было найти и проанализировать.

#### Сценарий А: Структурированная фиксация инцидента (Happy Path)

1.  **Детектирование:** Модуль безопасности фиксирует 50 запросов к несуществующим URL от одного IP за 10 секунд.
2.  **Блокировка:** IP заносится в Redis DenyList.
3.  **Формирование записи:** Сервис не пишет произвольный текст. Он обращается к константам (или Enum) и выбирает причину `SUSPICIOUS_SCANNING`.
4.  **Запись в WORM:** В `access_audit_logs` добавляется запись, где поле `reason_code` = `SUSPICIOUS_SCANNING`, а в `details` лежит сырой лог (пути, которые сканировал бот).
5.  **Аналитика:** SIEM-система (например, ELK или Grafana), подключенная к БД, немедленно рисует красный столбик на графике "Сканирование уязвимостей", так как она настроена реагировать именно на этот строковый код.

#### Сценарий Б: Неизвестная аномалия (Negative Path - Fallback Reason)

1.  **Аномалия:** Модуль защиты на основе ИИ (или сложный эвристический алгоритм WAF) блокирует пользователя за поведение, которое не описано ни в одном справочнике `local_ban_reasons` (например, "Невозможная скорость движения мыши").
2.  **Попытка категоризации:** Сервис пытается найти подходящий код, но точного совпадения нет.
3.  **Fallback (Безопасное значение):** Чтобы не потерять лог и не упасть с ошибкой Foreign Key constraint, сервис использует зарезервированный код `UNKNOWN_ANOMALY` (или `OTHER_SECURITY_VIOLATION`).
4.  **Запись:** В `access_audit_logs` пишется `reason_code` = `UNKNOWN_ANOMALY`, а все технические детали от WAF складываются в JSON-поле `details`.
5.  **Расследование:** Офицер безопасности видит всплеск "Неизвестных аномалий", читает JSON-детали, понимает суть новой атаки и заводит задачу разработчикам: "Добавьте новый код `BOT_MOUSE_MOVEMENT` в справочник для будущих блокировок".

## SR-AUTH-LA-03: Инъекция Трассировки в Downstream (Header Routing)

Это требование — фундамент архитектуры **Zero Trust** (Нулевого доверия) внутри бэкенда STEOS. 
Внутренние бизнес-микросервисы (например, Task Service, Billing Service, CRM Service) **вообще не должны** уметь работать с сессиями, парсить JWT-токены или читать Cookie. Они должны заниматься только своей бизнес-логикой. Идентификация выполняется на **периметре (API Gateway — агрегатор)** с опорой на **Authorization Service** (валидация сессии, контекст, политики).

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Снятие Cookie (Stripping)** | Когда запрос (например, `POST /api/tasks`) приходит от браузера, он содержит `HttpOnly` Cookie с Phantom Token. **API Gateway** перехватывает запрос и извлекает токен. Очищенный запрос идет дальше без Cookie. |
| **Извлечение Контекста (Session Resolution)** | Gateway вызывает **Authorization Service** (например, `ValidateSession` / согласованный RPC), где за \< 2 ms выполняется lookup сессии (Redis/БД). В ответе — `global_steos_id`, `active_workspace_id`, `impersonator_steos_id` (если есть). Прямой доступ Gateway только к Redis возможен в частных развёртываниях, но канонически источник истины — логика AUTH. |
| **Инъекция Заголовков (Header Propagation)** | Gateway формирует внутренний HTTP-запрос (или gRPC) к `Task Service`. Cookie **не** передаётся; добавляются **доверенные HTTP-заголовки**: `X-Global-Actor-Id: 123`, `X-Workspace-Id: 456`, `X-Trace-Id: abc...`. |
| **Безусловное Доверие (Internal Trust)** | `Task Service`, получая запрос с такими заголовками из внутренней подсети (VPC/Service Mesh), **полностью доверяет им**. Он не проверяет, существует ли `Actor 123` и жива ли его сессия — он знает, что цепочка **Gateway → Authorization Service** уже выполнила это на входе. Он просто создает задачу в `Workspace 456`. |
| **Защита от спуфинга (Spoofing)** | Если злоумышленник попытается обмануть систему и отправит с фронтенда запрос `POST /api/tasks` с поддельным заголовком `X-Global-Actor-Id: 999` (Пытаясь выдать себя за админа), API Gateway **обязан вырезать** (Drop) все входящие заголовки, начинающиеся на `X-Global` или `X-Workspace`, прежде чем добавить свои собственные легитимные данные из Redis. Внутренний периметр остается неприступным. |

### 2. Высокоуровневое описание

Представим **переводчика на международной конференции**.

1. **Иностранная речь (Внешний запрос с Cookie):** Делегат (Пользователь/Браузер) подходит к стенду (Task Service) и начинает говорить на сложном языке, показывая какие-то зашифрованные документы (отправляет `HttpOnly Cookie` с UUID сессии). Стендист (Task Service) ничего не понимает.
2. **Переводчик-синхронист (API Gateway / Auth Service):** Между ними встает переводчик (Gateway). Он слушает делегата, берет его зашифрованные документы и звонит в свое посольство (Redis): "Чьи это документы?".
3. **Очистка от мусора (Stripping):** Посольство отвечает: "Это Мистер Смит из отдела продаж". Переводчик забирает непонятные документы себе (вырезает Cookie).
4. **Понятный язык (Инъекция заголовков):** Переводчик поворачивается к стендисту и говорит на чистом, понятном стендисту языке: "Этот человек — Смит (`X-Global-Actor-Id: Smith`). Он пришел от отдела продаж (`X-Workspace-Id: Sales`). Он хочет создать задачу".
5. **Исполнение (Internal Trust):** Стендист полностью доверяет переводчику (так как переводчик — сотрудник той же конференции). Стендист не просит у Смита паспорт, он просто записывает задачу на отдел продаж.
6. **Защита от обмана (Spoofing):** Если Смит сам нацепит на себя бейджик "Я Директор" (`X-Global-Actor-Id: Boss`), переводчик на входе сорвет этот фальшивый бейджик, проверит настоящие документы в посольстве, и нацепит на Смита правильный бейджик "Смит", прежде чем подпустить к стенду.

Эта архитектура позволяет писать бизнес-микросервисы (Task, CRM, AI), которые абсолютно ничего не знают про криптографию, Redis, JWT или Cookie, полагаясь только на простые строковые заголовки от шлюза.

### 3. Примеры взаимодействия (логические сценарии)

**Общие исходные данные:**
*   **Инициатор:** Авторизованный пользователь (через SPA).
*   **Входящий запрос:** `GET /api/billing/invoices` (запрос списка счетов во внутренний Billing Service).
*   **Контекст:** Наличие валидной `steos_sess` Cookie.

#### Сценарий А: Успешная маршрутизация контекста (Happy Path)

1.  **Входной запрос:** Браузер отправляет `GET /api/billing/invoices`. Браузер автоматически прикрепляет `Cookie: steos_sess=sess-888`.
2.  **Перехват на Gateway:** API Gateway (модуль Auth Service) перехватывает запрос.
3.  **Очистка заголовков (Sanitization):** Gateway проверяет, нет ли во входящем запросе хакерских заголовков (например, `X-Global-Actor-Id: admin`). Если есть — он их безжалостно удаляет (Drop).
4.  **Разрешение сессии (Redis):** Gateway берет `sess-888`, идет в Redis, находит JSON: `{"global_id": "user-123", "workspace": "ws-42"}`.
5.  **Инъекция:** Gateway формирует новый (внутренний) HTTP-запрос к `Billing Service`.
    *   Он **не** добавляет туда заголовок `Cookie`.
    *   Он добавляет `X-Global-Actor-Id: user-123`.
    *   Он добавляет `X-Workspace-Id: ws-42`.
    *   Он генерирует уникальный ID для логов и добавляет `X-Trace-Id: trace-555`.
6.  **Исполнение бизнес-логики:** `Billing Service` получает чистый запрос. Он читает `X-Workspace-Id: ws-42` и делает SQL-запрос в свою базу: `SELECT * FROM invoices WHERE workspace_id = 'ws-42'`.
7.  **Возврат результата:** `Billing Service` отдает JSON со счетами. Gateway проксирует его обратно в браузер.

#### Сценарий Б: Истекшая сессия (Negative Path - 401 Unauthorized)

1.  **Входной запрос:** Пользователь отошел на 3 дня. Приходит и кликает "Обновить счета". Запрос летит с `Cookie: steos_sess=sess-888`.
2.  **Перехват и очистка:** Gateway перехватывает запрос и удаляет хакерские заголовки (если они есть).
3.  **Разрешение сессии (Промах):** Gateway идет в Redis за ключом `steos:sess:sess-888`.
4.  **Ключ не найден:** Время жизни (TTL) ключа в Redis истекло 2 дня назад. Он был автоматически удален самим Redis.
5.  **Короткое замыкание (Short Circuit):** Gateway понимает, что пользователь больше не авторизован.
6.  **Блокировка маршрутизации:** Gateway **не** отправляет запрос в `Billing Service`. Внутренняя сеть (и базы данных биллинга) защищены от бесполезной нагрузки.
7.  **Возврат ошибки:** Gateway немедленно отвечает браузеру HTTP `401 Unauthorized`. Фронтенд перекидывает пользователя на экран логина (STEOS ID).

## SR-AUTH-LA-04: Потоковая передача WORM-аудита в SIEM

Локальный аудит должен быть полезен не только административной панели, но и внешним системам мониторинга безопасности. Для этого новые WORM-события должны публиковаться в поток почти в реальном времени.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Near Real-Time поток** | Новые записи аудита транслируются без ожидания ручного экспорта. |
| **Невмешательство в WORM** | Поток не заменяет журнал и не является источником истины, а лишь ретранслирует уже записанное событие. |
| **Интеграция с SIEM** | Формат и канал доставки пригодны для Splunk, ELK, Sentinel и аналогичных систем. |
| **Независимость от внешнего потребителя** | Сбой внешнего консьюмера не должен ломать базовую запись локального аудита. |

### 2. Высокоуровневое описание

Представим **черный ящик самолета, который одновременно пишет данные и передает телеметрию в наземный центр**.

1. **Первичная запись:** Событие сначала попадает в локальный защищенный журнал.
2. **Дублирующая трансляция:** После фиксации оно ретранслируется во внешний поток наблюдения.
3. **Удаленный анализ:** SIEM получает тот же сигнал почти мгновенно и связывает его с другими источниками.
4. **Сохранение канона:** Даже если внешний канал упал, сам локальный журнал остается полным и непротиворечивым.

### 3. Примеры взаимодействия (логические сценарии)

#### Нормальная потоковая публикация (Happy Path)

1. Auth Service фиксирует в `access_audit_logs` событие `SESSION_REVOKED`.
2. После успешной локальной записи событие публикуется в поток аудита.
3. SIEM-консьюмер получает его и индексирует для корреляции с другими сигналами.
4. Если SIEM временно недоступен, локальный журнал все равно остается полным и каноническим.

## SR-AUTH-LA-05: Экспорт архива аудита

Для compliance, юридических проверок и внутренних расследований нужен пакетный экспорт журнала за период в защищенном машиночитаемом формате.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Асинхронная тяжелая задача** | Формирование архива не должно блокировать административный UI и боевые запросы. |
| **Гибкие фильтры** | Экспорт поддерживает период, actor, workspace и тип события. |
| **Безопасная выдача результата** | Итоговый архив выдается через временную ссылку или отдельный download-token. |
| **Контроль целостности** | Архив может сопровождаться подписью или checksum для регуляторных процедур. |

### 2. Высокоуровневое описание

Представим **архивную службу, которая по запросу собирает коробку документов за нужный период и выдает временный пропуск на ее получение**.

1. **Запрос на архив:** Администратор формулирует, какие записи нужны и за какой период.
2. **Фоновая сборка:** Система не отвечает самим архивом сразу, а ставит задачу на сборку.
3. **Упаковка и размещение:** Воркер формирует файл, архивирует его и кладет в защищенное хранилище.
4. **Временный доступ:** Пользователь получает ограниченную по времени ссылку на результат.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешный экспорт (Happy Path)

1. Администратор запускает экспорт за нужный период.
2. Сервис ставит фоновую задачу в очередь и сразу возвращает `job_id`.
3. Воркер собирает архив, сохраняет его в защищенное хранилище и помечает job как завершенную.
4. Пользователь получает временную ссылку на скачивание.

## SR-AUTH-LA-06: Детализация события аудита

Постраничный просмотр журнала отвечает на вопрос "что случилось", но для расследования часто нужен richer-контекст: кто инициировал событие, что изменилось и какой trace проходил через систему.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Расширенный макроконтекст** | По `event_id` можно получить `before/after`, actor, route, reason и trace-данные. |
| **Иммутабельность базы** | Детализация читает и агрегирует данные, но не меняет саму WORM-запись. |
| **Контроль доступа** | Детальный контекст выдается только ролям с правами расследования и аудита. |
| **Ускорение расследований** | Офицер безопасности получает целостную карточку инцидента без ручного обхода нескольких систем. |

### 2. Высокоуровневое описание

Представим **следственную папку, которая раскрывает детали одного конкретного события из общего журнала проходной**.

1. **Поиск записи:** В общем журнале находится строка об интересующем событии.
2. **Запрос карточки:** Следователь открывает не весь архив, а именно карточку этого инцидента.
3. **Раскрытие макроконтекста:** Система возвращает все важные сопутствующие детали: до/после, actor, trace, причина.
4. **Без переписывания журнала:** Исходная WORM-запись остается неизменной, меняется только глубина чтения.

### 3. Примеры взаимодействия (логические сценарии)

#### Разбор события имперсонации (Happy Path)

1. Администратор находит в журнале событие `IMPERSONATION_STARTED`.
2. Он открывает карточку события.
3. Auth Service возвращает расширенные поля: ticket, actor, target, trace-id и контекст до/после изменения.
4. Расследование продолжается уже на полной картине инцидента.

## SR-AUTH-LA-07: Агрегированная аналитика доступа

Поверх WORM-журнала нужен слой агрегатов для dashboard-ов: сколько активных сессий, сколько блокировок, сколько гостей и как распределяются инциденты по типам.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Агрегаты вместо сырого лога** | Сервис возвращает уже посчитанные показатели, а не заставляет UI читать журнал постранично. |
| **Поддержка operational dashboard** | Метрики пригодны для ежедневной работы администраторов и security-офицеров. |
| **Комбинация источников** | Для расчета используются Redis, журнал аудита и производные хранилища/представления. |
| **Отделение от observability** | Это бизнес-аналитика доступа, а не инфраструктурные Prometheus-метрики. |

### 2. Высокоуровневое описание

Представим **ситуационный центр, где вместо сырых строк журнала на экране сразу показываются агрегированные показатели обстановки**.

1. **Сбор сырых сигналов:** Сервис получает события из Redis, WORM-журнала и производных счетчиков.
2. **Построение сводки:** Из них вычисляются агрегаты, удобные для dashboard-виджетов.
3. **Оперативное отображение:** Администратор видит общую картину без ручного чтения тысяч записей.
4. **Разделение обязанностей:** Для drill-down используется журнал, а для overview — агрегированная аналитика.

### 3. Примеры взаимодействия (логические сценарии)

#### Открытие security dashboard (Happy Path)

1. Администратор открывает security dashboard.
2. Auth Service строит сводку: активные сессии, guest-пользователи, свежие блокировки, частота security alerts.
3. Панель показывает актуальную картину без ручной фильтрации `access_audit_logs`.
