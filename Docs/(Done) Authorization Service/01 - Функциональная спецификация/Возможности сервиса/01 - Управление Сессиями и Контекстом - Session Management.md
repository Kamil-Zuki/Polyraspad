# Группа 1: Управление Сессиями и Контекстом (Session Management)

## Введение

В этом разделе описывается фундаментальное ядро микросервиса `Authorization Service`. Его главная задача — превратить глобальную идентичность пользователя (подтвержденную в STEOS ID) в **локальную, жестко контролируемую сессию** на конкретной инсталляции платформы. 

В отличие от классической архитектуры, где браузеру отдается JWT-токен со всеми правами, STEOS использует паттерн **Phantom Token**. Браузер получает лишь случайную строку в защищенной Cookie, а все реальные данные (роли, текущее рабочее пространство, уровень доверия) хранятся на бэкенде в быстрой in-memory базе данных (Redis). Это делает невозможной кражу прав через XSS-уязвимости и позволяет платформе мгновенно "убивать" сессии злоумышленников (Stateful Auth).

**Метафора:**
Представьте **Пропускной пункт в секретную лабораторию**.
Вы показываете свой глобальный паспорт (STEOS ID) на входе. Охранник (Authorization Service) забирает паспорт и кладет его в сейф (Redis). Взамен он выдает вам кусок пластика с одним лишь номером "42" (Phantom Token / Cookie). 
Внутри лаборатории нет дверей, проверяющих паспорта. Каждый раз, когда вы хотите войти в лабораторию "Tesla" (Workspace), вы прикладываете этот пластик. Внутренний компьютер мгновенно проверяет по номеру "42" в сейфе: чей это пластик, и можно ли этому человеку туда входить (Context Routing). Если охранник нажмет красную кнопку, он просто удалит номер "42" из базы. Ваш пластик мгновенно превратится в мусор.

## Возможности данного раздела

Ниже представлен перечень функциональных требований (SR) к механизмам управления сессиями.

| Код               | Название и Описание                                                                                                                                                                                     |
| :---------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **SR-AUTH-SM-01** | **Создание Phantom Token (HttpOnly Cookie):** Защита от XSS. Браузер получает случайный UUID, а все права и стейт хранятся на бэкенде (Redis + PostgreSQL).                                             |
| **SR-AUTH-SM-02** | **Server-Side Context Routing:** Бесшовное переключение пользователя между рабочими пространствами (Workspaces) без перелогина и изменения Cookie.                                                      |
| **SR-AUTH-SM-03** | **Управление Гостевыми Сессиями:** Выделенная логика для `guest_sessions` с привязкой к аппаратному отпечатку браузера (Public Mode / Анонимный демо-доступ).                                           |
| **SR-AUTH-SM-04** | **Одноразовые билеты (One-Time Tickets):** Генерация эфемерных токенов (живут 15 секунд в Redis) для безопасного открытия WebSocket-соединений и прямого скачивания файлов (без передачи Cookie в URL). |
| **SR-AUTH-SM-05** | **Бесшовная Имперсонация (God Mode):** Вход техподдержки "под пользователем". Создание двойного контекста (`global_steos_id` + `impersonator_id`) для юридической чистоты логов аудита.                 |
| **SR-AUTH-SM-06** | **API Управления Локальными Сессиями:** Механизм просмотра списка активных сессий на конкретной платформе и возможность их точечного отзыва (Revoke).                                                   |
| **SR-AUTH-SM-07** | **Тихое продление (Silent Refresh):** Автоматический фоновый запрос свежего Access-токена у STEOS ID (используя зашифрованный `refresh_token`), предотвращающий разрыв сессии во время работы.          |
| **SR-AUTH-SM-08** | **Доверенные устройства (Trusted Devices):** Управление списком браузеров и устройств, которые пользователь явно пометил как доверенные для снижения friction при повторных входах.                     |
| **SR-AUTH-SM-09** | **Продление TTL активной сессии (Session Keep-Alive):** Sliding TTL локальной Phantom-сессии при живых действиях пользователя без обязательного refresh в глобальном IdP на каждый запрос.              |
| **SR-AUTH-SM-10** | **Горячее обновление контекста сессии:** Динамическая перезагрузка ролей, лицензий и бизнес-атрибутов в уже открытых сессиях без разлогина пользователя.                                                |

# Детальная спецификация требований

## SR-AUTH-SM-01: Создание Phantom Token (HttpOnly Cookie)

Это базовый механизм безопасности всей платформы. Выдача сырых JWT-токенов браузеру (например, сохранение их в `localStorage`) строго запрещена из-за уязвимости к атакам типа Cross-Site Scripting (XSS). Если хакер сможет выполнить свой JS-код на странице, он украдет JWT-токен и получит полный доступ. При использовании Phantom Token красть нечего.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Stateful хранение** | При успешной авторизации через STEOS ID (Группа 2), микросервис создает запись в таблице `authorized_sessions` (PostgreSQL) и зеркалирует этот стейт в Redis (для скорости отклика < 2ms). |
| **Нечитаемый идентификатор** | В ответ клиенту (браузеру) отправляется HTTP-заголовок `Set-Cookie`. Значение Cookie — это просто криптографически случайный `UUID v4` (например, `steos_sess=f47ac10b...`). |
| **Защитные флаги Cookie** | Cookie обязана устанавливаться со следующими флагами: `HttpOnly` (JavaScript браузера не видит эту Cookie), `Secure` (передается только по HTTPS) и `SameSite=Lax` или `Strict` (защита от CSRF-атак с других сайтов). |
| **Немедленный отзыв (Revocation)** | Так как токен не содержит в себе подписи и срока годности, а является лишь ключом к Redis, удаление записи из Redis мгновенно (в ту же миллисекунду) лишает пользователя доступа к платформе. |

### 2. Высокоуровневое описание

Представим наш сервис как **камеру хранения в элитном клубе**.

1. **Гость (Пользователь) приходит в клуб:** Он показывает на входе свой паспорт (JWT-токен от STEOS ID), подтверждая, что он VIP-персона.
2. **Администратор (Authorization Service) забирает паспорт:** Он не отдает паспорт обратно гостю, чтобы тот его случайно не потерял на танцполе. Администратор кладет паспорт в надежную ячейку сейфа (Redis) под номером 42.
3. **Выдача номерка (Phantom Token):** Администратор выдает гостю пластиковый номерок с цифрой "42" (Cookie `steos_sess`). На номерке нет ни имени гостя, ни его статуса, ни баланса счета.
4. **Заказ напитков (API-запросы):** Когда гость подходит к бару (внутренний микросервис) и просит коктейль, он просто показывает бармену номерок "42". 
5. **Проверка в сейфе:** Бармен по внутренней связи мгновенно спрашивает администратора: "Кто в ячейке 42?". Администратор смотрит в сейф и отвечает: "Это VIP-гость Иван, у него безлимитный депозит". Бармен наливает коктейль.
6. **Кража номерка (XSS-атака):** Если карманник украдет номерок у Ивана, Иван немедленно пожалуется администратору. Администратор просто выкинет паспорт Ивана из ячейки 42 (удалит ключ из Redis) и выдаст Ивану новую ячейку (новый логин). Карманник, подойдя к бару с номерком 42, получит отказ, так как ячейка уже пуста.

Таким образом, даже если злоумышленник перехватит `steos_sess` из-за XSS-уязвимости в браузере, платформа может мгновенно инвалидировать этот токен (stateful auth), в отличие от классических stateless JWT, которые "живут" до истечения срока действия (`exp`), независимо от того, были ли они украдены.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает механику трансформации успешного OIDC-входа в локальную защищенную сессию.

**Общие исходные данные:**
*   **Инициатор:** Веб-браузер пользователя.
*   **Входящий запрос:** Внутренний коллбек (например, код авторизации от STEOS ID успешно обменян на JWT Access Token на бэкенде).
*   **Контекст:** Получен валидный `access_token` (JWT) от глобального провайдера STEOS ID.

#### Сценарий А: Успешное создание сессии (Happy Path)

**Сценарий:** Пользователь успешно прошел аутентификацию на глобальном портале STEOS ID, и Authorization Service готов пустить его в локальную систему.

1.  **Обработка JWT (Бэкенд):** Authorization Service получает `access_token` от STEOS ID, криптографически проверяет его подпись (через кэшированный JWKS) и извлекает `sub` (Глобальный ID пользователя, например, `uuid-user-123`), а также `exp` (срок жизни токена).
2.  **Запись в PostgreSQL (Персистентность):** 
    * Сервис генерирует криптографически стойкий `UUID v4` для сессии (например, `f47ac10b...`).
    * Создается новая запись в таблице `authorized_sessions` с полями: `session_id`, `global_steos_id`, `ip_address`, `device_fingerprint`, `created_at`, `expires_at` (равный `exp` из JWT).
3.  **Зеркалирование в Redis (Скорость):**
    * Сервис сохраняет в Redis сериализованный JSON-объект стейта по ключу `steos:sess:f47ac10b...`.
    * Устанавливается TTL ключа в Redis, равный сроку жизни сессии.
    * Объект в Redis содержит `global_actor_id: "uuid-user-123"`, текущие роли и `active_workspace_id`.
4.  **Формирование ответа (Frontend):**
    * Бэкенд формирует HTTP-ответ `302 Found` (редирект на главную страницу SPA-приложения).
    * В ответ добавляется заголовок `Set-Cookie: steos_sess=f47ac10b...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=...`.
5.  **Дальнейшая работа:** При каждом следующем AJAX-запросе (например, `GET /api/profile`), браузер неявно и безопасно отправляет эту Cookie. API Gateway на лету достает JSON из Redis по ключу из Cookie, прокидывает бизнес-заголовки (роли, ID) во внутренние сервисы и пропускает запрос.

#### Сценарий Б: Отказ в создании сессии (Negative Path - Сбой БД)

**Сценарий:** STEOS ID вернул валидный токен, но локальная база данных недоступна для сохранения сессии.

1.  **Попытка записи:** Сервис пытается выполнить `INSERT` в таблицу `authorized_sessions` базы данных PostgreSQL.
2.  **Ошибка БД:** Возникает таймаут подключения или отказ базы (Connection Refused).
3.  **Откат (Rollback):** Транзакция отменяется. Сервис **НЕ** записывает ничего в Redis (обеспечение консистентности).
4.  **Возврат ошибки:** Пользователю не устанавливается Cookie. Выдается стандартизированная ошибка (ProblemDetails): HTTP `500 Internal Server Error`, `code: "SESSION_CREATION_FAILED"`, `detail: "Temporary infrastructure issue. Please try logging in again later."`.
5.  **Логирование:** Ошибка фиксируется во внутреннем логе (с `trace_id`) для аллертинга DevOps-команды. Утечки глобального токена в логи не происходит.

## SR-AUTH-SM-02: Server-Side Context Routing

Пользователь STEOS может состоять в 10 разных Пространствах (Workspaces) — личных, корпоративных, партнерских. Фронтенд-приложение (SPA) не должно прикреплять `?workspace_id=123` к каждому API-запросу. Это небезопасно и сложно поддерживать. Платформа должна сама знать, в каком пространстве сейчас "находится" пользователь.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Сущность `session_contexts`** | В PostgreSQL существует таблица-маршрутизатор (1:1 с сессией). Она хранит текущий `active_workspace_id` для данной сессии. |
| **Синхронизация с Redis** | При переключении пространства в UI, фронтенд делает один запрос: `PUT /api/auth/context/switch`. Бэкенд обновляет БД и Redis. |
| **Авто-проброс заголовков** | API Gateway (часть Auth Service), получая любой бизнес-запрос (например, `POST /api/tasks`), достает из Redis текущий контекст и добавляет в HTTP-запрос внутренние доверенные заголовки (например, `X-Workspace-Id: 123`). Внутренние микросервисы (Tasks, CRM) читают только этот заголовок. |
| **Zero Trust внутри** | Внутренние микросервисы не доверяют Cookie, так как не могут их распарсить без Redis, и читают исключительно доверенные HTTP-заголовки от API Gateway. |

### 2. Высокоуровневое описание

Представим наш сервис как **лифт в огромном офисном здании корпорации**.

1.  **Посадка в лифт (Авторизация):** Сотрудник (Пользователь) прикладывает свой пропуск (Phantom Token) к сканеру в лифте (API Gateway). Лифт знает, кто этот сотрудник.
2.  **Выбор этажа (Переключение Workspace):** Сотрудник нажимает кнопку этажа "Отдел продаж" (ID Workspace: 42). Лифт записывает: "Этот человек сейчас едет на 42 этаж".
3.  **Выход на этаж (Контекстный API-запрос):** Двери лифта открываются на 42 этаже. Сотрудник выходит и начинает работать с документами (например, создает задачу `POST /api/tasks/create`).
4.  **Слепота этажа (Zero Trust):** Охранник на этаже (Task Service) не проверяет пропуск сотрудника. Он видит, что лифт (API Gateway) привез этого сотрудника именно на этот этаж, и лифт громко объявляет: "Этот человек работает на 42 этаже!" (добавление заголовка `X-Workspace-Id: 42`). Охранник доверяет лифту.
5.  **Переезд (Смена контекста):** Если сотрудник хочет перейти в "Отдел маркетинга" (ID Workspace: 15), он не идет пешком по лестнице (не подменяет `workspace_id` в каждом запросе). Он снова вызывает лифт, нажимает кнопку 15, и лифт перенастраивает свой внутренний статус на новый этаж.

Таким образом, фронтенду не нужно вшивать номер этажа в каждую бумажку (API запрос). Лифт (API Gateway) и охранники (микросервисы) решают эту задачу самостоятельно на уровне серверной маршрутизации.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает механику смены контекста пользователя между рабочими пространствами.

**Общие исходные данные:**
*   **Инициатор:** Фронтенд-приложение (SPA) от лица пользователя.
*   **Входящий запрос:** `PUT /api/auth/context` с телом `{"workspace_id": 42}` (смена активного пространства).
*   **Контекст:** Валидная `HttpOnly` Cookie сессии.

#### Сценарий А: Успешная смена контекста (Happy Path)

**Сценарий:** Пользователь кликает на "Корпоративный Workspace" в левом меню, и платформа успешно переключает его контекст.

1.  **Запрос от клиента:** Фронтенд отправляет запрос: `PUT /api/auth/context {"workspace_id": 42}`.
2.  **Аутентификация запроса:** API Gateway извлекает Cookie, обращается к Redis по ключу сессии, подтверждает, что сессия активна, и достает `global_steos_id`.
3.  **Авторизация (Проверка прав):** Auth Service делает внутренний синхронный gRPC/REST вызов к `Workspace Service`: "Является ли юзер (с `global_steos_id`) участником Workspace с ID 42?".
4.  **Подтверждение:** `Workspace Service` отвечает: `{"is_member": true, "role": "admin"}`.
5.  **Обновление стейта (БД и Redis):**
    *   Auth Service выполняет `UPDATE session_contexts SET active_workspace_id = 42 WHERE session_id = '...'` в PostgreSQL.
    *   Auth Service обновляет JSON в Redis для этой сессии, заменяя старый `active_workspace_id` на `42`.
6.  **Успешный ответ:** Клиенту возвращается `200 OK` с новым стейтом.
7.  **Последующий бизнес-запрос:** Пользователь создает задачу (шлет пустой от контекста запрос `POST /api/tasks`). API Gateway достает из Redis ID `42`, добавляет к заголовкам запроса `X-Workspace-Id: 42` и пересылает его в `Task Service`. `Task Service` читает заголовок и сохраняет задачу именно в пространстве 42.

#### Сценарий Б: Отказ в доступе к пространству (Negative Path - Forbidden)

**Сценарий:** Хакер или сотрудник, исключенный из пространства, пытается подделать запрос на переключение в чужой Workspace.

1.  **Злонамеренный запрос:** Клиент отправляет подделанный запрос: `PUT /api/auth/context {"workspace_id": 999}` (где 999 — чужое пространство).
2.  **Аутентификация:** Сессия пользователя признана валидной (Cookie верна).
3.  **Авторизация (Проверка прав):** Auth Service запрашивает `Workspace Service`: "Является ли этот юзер участником Workspace с ID 999?".
4.  **Отказ:** `Workspace Service` отвечает: `{"is_member": false}`.
5.  **Возврат ошибки:** Auth Service **НЕ** обновляет стейт в БД и Redis. Он немедленно прерывает выполнение и возвращает стандартизированную ошибку платформы: HTTP `403 Forbidden`, `code: "ACCESS_DENIED"`, `detail: "You do not have access to this workspace or it does not exist."`.
6.  **Предотвращение инцидента:** Стейт сессии в Redis остается прежним. Последующие бизнес-запросы пользователя будут выполняться в его старом, разрешенном пространстве.
7.  **Аудит (Security Event):** Событие попытки несанкционированного доступа записывается в WORM-лог с пометкой `UNAUTHORIZED_WORKSPACE_ACCESS_ATTEMPT`.

## SR-AUTH-SM-03: Управление Гостевыми Сессиями

Платформа STEOS может предоставлять демо-доступ (Public Mode) для незарегистрированных пользователей (например, "Создать 3 ИИ-картинки бесплатно"). Для этого нужна "теневая" сессия, не привязанная к глобальному `steos_id`.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Сущность `guest_sessions`** | Отдельная таблица в PostgreSQL и префикс ключей в Redis (например, `guest_sess:UUID`), изолирующие гостей от полноправных пользователей. |
| **Привязка к Фингерпринту** | Так как паспорта (STEOS ID) у гостя нет, сессия жестко привязывается к аппаратному отпечатку браузера (`device_fingerprint`). Это мешает анониму просто очистить Cookie и получить новые бесплатные лимиты. |
| **Ограниченный TTL** | Гостевые сессии имеют жестко заданный, короткий срок жизни (например, 24 часа) и не подлежат продлению (`Silent Refresh` отключен). |
| **Конвертация в аккаунт** | Если гость решает зарегистрироваться, Auth Service обязан "склеить" его гостевую сессию с новой авторизованной сессией, чтобы не потерять наработанный демо-прогресс (созданные картинки или задачи). |

### 2. Высокоуровневое описание

Представим **парк развлечений с бесплатной демо-зоной**.

1. **Вход без билета (Гостевой старт):** Посетитель заходит в парк, не покупая билет на входе. Он направляется в бесплатную демо-зону (открывает лендинг платформы).
2. **Невидимый штамп (Фингерпринт):** Охранник демо-зоны (Auth Service) незаметно ставит посетителю флуоресцентный штамп на руку (считывает `device_fingerprint`). Охранник выдает гостю временный браслет (Phantom Token `guest_sess`) и записывает в блокнот (Redis): "Человек со штампом X8J9 получил браслет 999. Ему можно прокатиться на демо-карусели 3 раза".
3. **Демо-потребление (Квоты):** Посетитель катается на карусели (ИИ-генерация). Охранник вычеркивает поездки из блокнота. Если посетитель попытается снять браслет и подойти снова, охранник увидит штамп X8J9 и скажет: "Вы уже исчерпали свой лимит, даже без браслета".
4. **Покупка билета (Конвертация):** Посетитель решает купить полный билет (авторизуется через STEOS ID). Кассир видит его браслет 999, смотрит в блокнот, видит, что посетитель уже создал 3 классные картинки. Кассир берет эти картинки, привязывает их к новому именному билету посетителя (смена владельца ресурсов), а временный браслет уничтожает.

Этот механизм позволяет плавно вовлекать пользователей в платформу (Product-Led Growth), не жертвуя безопасностью и не позволяя им бесконечно "доить" дорогостоящие ресурсы (например, GPU-генерацию) простой очисткой Cookie.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает жизненный цикл гостя: от анонимного старта до регистрации и "склейки" контекста.

**Общие исходные данные:**
*   **Инициатор:** Анонимный посетитель (через SPA).
*   **Входящий запрос:** Запрос на старт демо-сессии или первый бизнес-вызов без авторизации.
*   **Контекст:** Отсутствие Cookie, наличие уникального `device_fingerprint` в теле запроса или заголовках.

#### Сценарий А: Успешный старт и конвертация гостя (Happy Path)

**Сценарий:** Новый анонимный пользователь заходит на сайт, начинает пользоваться демо-функционалом, исчерпывает лимит и регистрируется, сохраняя свой прогресс.

1.  **Инициация гостя:** Фронтенд отправляет `POST /api/auth/guest/start` с телом `{"fingerprint": "hash-abc-123"}`.
2.  **Проверка отпечатка:** Auth Service ищет активную гостевую сессию с таким `fingerprint` в Redis/БД. Не находит.
3.  **Создание гостевой сессии:**
    *   Создается запись в таблице `guest_sessions` с ID `guest-f47ac10b...` и привязкой к фингерпринту.
    *   Стейт сохраняется в Redis: `steos:guest_sess:guest-f47ac10b...` со статусом `GUEST`.
    *   Платформа выделяет гостю временный `workspace_id`.
4.  **Возврат Cookie:** Клиенту возвращается защищенная Cookie: `Set-Cookie: steos_sess=guest-f47ac10b...`.
5.  **Бизнес-работа:** Гость создает объекты (например, рисует графики). API Gateway прокидывает во внутренние сервисы заголовки `X-Guest-Id: guest-f47ac10b...` и временный `X-Workspace-Id`.
6.  **Регистрация (Конвертация):** Гость решает сохранить графики и жмет "Войти". Проходит стандартный OIDC flow через STEOS ID.
7.  **Склейка (Merge):** Auth Service получает `access_token` от STEOS ID. Он видит у браузера гостевую Cookie `guest-f47ac10b...`.
8.  **Перенос ресурсов:** Auth Service делает броадкаст-вызов внутренним сервисам (или событие в RabbitMQ): "Гость `guest-f47ac10b...` стал пользователем `uuid-user-123`. Передайте все его объекты в его новый постоянный Workspace!".
9.  **Очистка:** Гостевая сессия `guest-f47ac10b...` уничтожается (Soft Delete в БД, удаление из Redis). Пользователю выдается новая, полноценная Cookie `steos_sess`.

#### Сценарий Б: Блокировка абузера демо-доступа (Negative Path - Quota Exhausted)

**Сценарий:** Хакер пытается обойти лимиты, очищая Cookie, чтобы получить бесконечные бесплатные ИИ-генерации.

1.  **Повторный старт:** Хакер очищает браузерные Cookie и отправляет новый `POST /api/auth/guest/start` с тем же самым аппаратным отпечатком `{"fingerprint": "hash-abc-123"}`.
2.  **Обнаружение фингерпринта:** Auth Service проверяет БД/Redis и находит, что гостевая сессия с `fingerprint: hash-abc-123` уже существовала сегодня и исчерпала свои лимиты (или была недавно завершена).
3.  **Отказ в новой сессии:** Сервис отказывается выдавать новую гостевую сессию.
4.  **Возврат ошибки:** Хакер получает `429 Too Many Requests` (или `403 Forbidden` с кодом `GUEST_QUOTA_EXHAUSTED`) и сообщение: "Вы исчерпали лимит демо-доступа для этого устройства. Пожалуйста, зарегистрируйтесь или авторизуйтесь".
5.  **Блокировка:** Платформа надежно защищена от простейшего абьюза бесплатных ресурсов.

## SR-AUTH-SM-04: Одноразовые билеты (One-Time Tickets)

Некоторые протоколы и браузерные механики не поддерживают передачу пользовательских HTTP-заголовков или `HttpOnly` Cookie.
Например, подключение по `ws://` (WebSockets) из JS, или вставка тега `<img src="/api/files/secret.jpg">`. Передавать Phantom Token (ID сессии) прямо в URL как GET-параметр — огромная дыра в безопасности (он осядет в логах провайдеров и прокси-серверов).

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Эфемерность (Short TTL)** | Генерация случайной строки (Ticket), которая живет в Redis ровно **15 секунд**. |
| **Одноразовость (Burn-on-Read)** | Билет уничтожается в ту же миллисекунду, когда он был прочитан (использован для открытия WebSocket-соединения или скачивания файла). Повторное использование невозможно. |
| **Контекстная привязка** | Билет жестко привязан к текущей сессии пользователя (ID, роли, Workspace) в момент его генерации, прокидывая весь контекст в целевой микросервис, минуя Cookie. |

### 2. Высокоуровневое описание

Представим **билет в кинотеатр, купленный онлайн**.

1. **Покупка (Генерация):** Пользователь (уже авторизованный на сайте кинотеатра) нажимает "Купить билет на Аватар". Кинотеатр (Auth Service) берет его профиль, деньги (сессию) и выдает уникальный QR-код (One-Time Ticket). Этот QR-код действует всего 15 минут.
2. **Проход в зал (Использование):** Пользователь подходит к контролеру у дверей зала (например, к WebSocket-серверу) и показывает QR-код (URL-параметр `?ticket=...`).
3. **Гашение билета (Burn-on-Read):** Контролер сканирует QR-код. Система кинотеатра мгновенно отвечает: "Это Иван, место 12, пускаем!". И в ту же секунду этот QR-код **сжигается в базе**. 
4. **Защита от копирования:** Если кто-то стоял за спиной Ивана и сфотографировал его QR-код, а потом попытался пройти по нему, контролер ответит: "Билет уже погашен" (так как он одноразовый).

Этот механизм решает фундаментальную проблему передачи состояния аутентификации в средах, где Cookie или Заголовки (Headers) недоступны или нежелательны (как в WebSocket Handshake).

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает генерацию и "сжигание" одноразового билета для открытия защищенного WebSocket-канала.

**Общие исходные данные:**
*   **Инициатор:** Фронтенд-приложение (SPA) от лица пользователя.
*   **Входящий запрос:** AJAX-вызов `POST /api/auth/tickets/generate` с валидной Cookie.
*   **Контекст:** Пользователю нужно открыть WebSocket-соединение к сервису уведомлений.

#### Сценарий А: Успешное открытие WebSocket (Happy Path)

**Сценарий:** Пользователь генерирует билет и успешно открывает WebSocket.

1.  **Запрос билета:** Фронтенд делает AJAX-запрос `POST /api/auth/tickets/generate`.
2.  **Генерация:** API Gateway проверяет Cookie, находит сессию пользователя, генерирует случайный крипто-токен `ticket-xyz...`.
3.  **Сохранение (Redis):** Auth Service сохраняет в Redis объект: `ticket:ticket-xyz...` со ссылкой на ID сессии (или напрямую с контекстом юзера) и жестким `TTL = 15s`.
4.  **Возврат билета:** Клиент получает `{"ticket": "ticket-xyz..."}`.
5.  **WebSocket Handshake:** JS-код немедленно инициирует соединение: `new WebSocket("wss://api.steos.io/ws?ticket=ticket-xyz...")`.
6.  **Гашение (Burn):**
    *   API Gateway (или Auth Middleware) перехватывает Handshake.
    *   Берет `ticket-xyz...` из URL.
    *   Выполняет атомарную операцию в Redis (например, LUA-скрипт или GETDEL): получить данные по ключу `ticket:ticket-xyz...` и **сразу удалить ключ**.
7.  **Установка соединения:** Данные получены (ID юзера `uuid-user-123`, Workspace `42`). API Gateway прокидывает эти данные как заголовки (`X-Global-Actor-Id: uuid-user-123`) внутреннему WebSocket-серверу. Соединение успешно установлено (Upgrade до 101 Switching Protocols).

#### Сценарий Б: Просроченный или украденный билет (Negative Path - Burned Ticket)

**Сценарий:** Злоумышленник перехватил URL с билетом и пытается подключиться, но билет уже истек или был использован владельцем.

1.  **Перехват:** Хакер увидел в логах прокси-сервера (или через плечо) URL `wss://api.steos.io/ws?ticket=ticket-xyz...`.
2.  **Попытка подключения:** Хакер через 20 секунд (или через секунду после владельца) пытается открыть WebSocket по этому же URL.
3.  **Поиск в Redis:** API Gateway берет `ticket-xyz...` и ищет его в Redis.
4.  **Промах:** Ключ не найден (либо истек TTL в 15 секунд, либо был атомарно удален при первом чтении владельцем).
5.  **Отказ:** API Gateway отвергает WebSocket Handshake с HTTP-ошибкой `401 Unauthorized` (или `403 Forbidden`).
6.  **Защита:** Хакер не может подключиться к приватному каналу пользователя, даже зная точный URL.

## SR-AUTH-SM-05: Бесшовная Имперсонация (God Mode)

Один из сложнейших аспектов энтерпрайз-систем. Когда клиент жалуется на баг в своем интерфейсе, сотруднику техподдержки (L2/L3) нужно войти на платформу "глазами клиента". Запрашивать у клиента пароль — грубейшее нарушение безопасности.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Двойной контекст (Double Identity)** | Сессия в БД (`authorized_sessions`) имеет два поля: `global_steos_id` (Истинный владелец, клиент) и `impersonator_steos_id` ("Кукловод", сотрудник саппорта). |
| **Слепота бизнес-логики** | API Gateway прокидывает во внутренние микросервисы (Tasks, CRM) заголовок `X-Global-Actor-Id`, равный ID клиента. Микросервисы "думают", что это клиент, и отдают ему его данные. Интерфейс выглядит точно так же, как у клиента. |
| **Юридическая прозрачность (WORM)** | API Gateway дополнительно прокидывает заголовок `X-Impersonator-Id`, равный ID саппорта. Когда внутренний микросервис совершает операцию (например, удаляет задачу), он обязан записать в WORM-лог аудита: "Действие совершено Саппортом (ID: 99) под маской Клиента (ID: 1)". |

### 2. Высокоуровневое описание

Представим **удаленное управление компьютером (TeamViewer)**.

1. **Заявка (Жалоба):** Пользователь звонит в техподдержку: "У меня не загружаются файлы".
2. **Сессия Имперсонации (God Mode):** Сотрудник техподдержки (админ) нажимает в своей админке кнопку "Войти как Иван". Auth Service не просит у админа пароль Ивана, а просто создает ему новую сессию-маску (God-Session).
3. **Управление (Слепота):** Админ двигает мышкой на своем экране, но операционная система (внутренние микросервисы) думает, что это мышку двигает сам Иван, показывая админу файлы Ивана.
4. **Видеорегистратор (WORM-лог):** Рядом с экраном админа стоит неотключаемая видеокамера (Audit Log), которая записывает каждое действие. Если админ случайно удалит важный файл, в журнале будет четко написано: "Файл удален мышкой админа Петрова (ID: 99), в то время как он смотрел в экран пользователя Ивана (ID: 1)".
5. **Безопасность Ивана:** Петров не узнает пароль Ивана, а Иван может в любой момент нажать кнопку "Отключить поддержку" (Revoke Session), и Петрова выкинет из его аккаунта.

Этот механизм обеспечивает высочайший уровень обслуживания клиентов без ущерба для безопасности и юридической ответственности сотрудников платформы.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает вход сотрудника поддержки под учетной записью клиента.

**Общие исходные данные:**
*   **Инициатор:** Сотрудник технической поддержки (L2/L3) платформы.
*   **Входящий запрос:** `POST /api/auth/impersonate` с телом `{"target_user_id": "uuid-client-1"}`.
*   **Контекст:** Сотрудник уже авторизован в своей панели администратора.

#### Сценарий А: Успешная имперсонация (Happy Path)

**Сценарий:** Сотрудник техподдержки с правами `IMPERSONATE_USERS` успешно входит под аккаунтом клиента для диагностики бага.

1.  **Запрос имперсонации:** Сотрудник отправляет `POST /api/auth/impersonate`.
2.  **Проверка прав админа:** Auth Service проверяет, есть ли у сотрудника (его `steos_sess`) системная роль, разрешающая имперсонацию (проверка через `Workspace Service` или локальные роли).
3.  **Создание God-сессии:**
    *   Auth Service создает новую запись в `authorized_sessions`.
    *   Устанавливает `global_steos_id = "uuid-client-1"` (ID клиента).
    *   Устанавливает `impersonator_steos_id = "uuid-admin-99"` (ID саппорта).
4.  **Сохранение в Redis:** В Redis сохраняется JSON-объект стейта, содержащий оба ID.
5.  **Логирование старта (WORM):** Записывается строгое событие аудита: "Сотрудник uuid-admin-99 начал сессию имперсонации под пользователем uuid-client-1".
6.  **Ответ клиенту (Саппорту):** Админу возвращается новая Cookie `Set-Cookie: steos_sess=god-f47a...`.
7.  **Бизнес-запрос:** Саппорт заходит в раздел "Задачи клиента". Запрос летит на API Gateway.
8.  **Инъекция заголовков:** Gateway видит двойную сессию в Redis и прокидывает два заголовка:
    *   `X-Global-Actor-Id: uuid-client-1` (для `Task Service`, чтобы он отдал чужие задачи).
    *   `X-Impersonator-Id: uuid-admin-99` (для `Task Service`, чтобы он записал в свой лог, кто реально смотрел эти задачи).
9.  **Завершение:** В интерфейсе появляется красная плашка "Вы работаете под пользователем X. Выйти". При нажатии сессия (God-Session) отзывается (Revoke).

#### Сценарий Б: Попытка имперсонации без прав (Negative Path - Forbidden)

**Сценарий:** Обычный пользователь (или менеджер без нужных допусков) пытается вызвать скрытое API имперсонации.

1.  **Хакерский запрос:** Менеджер пытается вызвать `POST /api/auth/impersonate {"target_user_id": "uuid-boss-1"}`.
2.  **Проверка ролей:** Auth Service проверяет текущие роли менеджера (в Redis или `Workspace Service`).
3.  **Отказ:** Роль `IMPERSONATE_USERS` отсутствует.
4.  **Возврат ошибки:** Сервис возвращает `403 Forbidden` с кодом `INSUFFICIENT_PERMISSIONS`. God-сессия не создается.
5.  **Аудит безопасности:** В систему мониторинга (SIEM) уходит Alert: "Попытка несанкционированной имперсонации от пользователя X".

## SR-AUTH-SM-06: API Управления Локальными Сессиями

Пользователь должен иметь контроль над своими входами.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Листинг устройств** | Эндпоинт `GET /api/auth/sessions/me`, возвращающий список всех активных Phantom Tokens (сессий) для данного пользователя на этой конкретной платформе (с парсингом User-Agent и GeoIP). |
| **Точечный отзыв (Revoke)** | Возможность нажать "Выйти на этом устройстве" (`DELETE /api/auth/sessions/{id}`). Сервис немедленно пометит сессию в PostgreSQL как `is_active = false` и удалит ключ из Redis. Запрос с этой Cookie на API Gateway мгновенно вернет `401 Unauthorized`. |
| **Глобальный отзыв** | Возможность "Выйти со всех устройств" (массовый Revoke в Redis). |

### 2. Высокоуровневое описание

Представим **приложение Telegram на вашем телефоне**.

1. **Просмотр сеансов (Листинг):** Вы заходите в настройки Telegram, раздел "Устройства". Там вы видите список: "iPhone в Москве", "MacBook в Питере", "Windows PC в офисе". Это список ваших активных сессий (ваших `Phantom Tokens` в базе).
2. **Подозрения (Поиск аномалий):** Вы замечаете "Linux в браузере Firefox", хотя вы им никогда не пользовались. Вы понимаете, что кто-то украл вашу сессию (или вы забыли разлогиниться в интернет-кафе).
3. **Отключение (Точечный Revoke):** Вы нажимаете на "Завершить сеанс" для этого подозрительного устройства.
4. **Мгновенное действие:** Сервер Telegram мгновенно удаляет ключи авторизации для этого Firefox (удаляет сессию из Redis). Злоумышленник, который в этот момент читал ваши сообщения, внезапно видит экран авторизации. Его сессия "убита" удаленно.

Этот инструмент критически важен для самостоятельного управления безопасностью (Self-Service Security) пользователями платформы.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает сценарий точечного завершения сессии (Revoke) пользователем.

**Общие исходные данные:**
*   **Инициатор:** Пользователь платформы (через раздел "Настройки -> Безопасность").
*   **Входящий запрос:** `DELETE /api/auth/sessions/sess-12345`.
*   **Контекст:** Пользователь хочет "разлогинить" свой старый ноутбук.

#### Сценарий А: Успешный отзыв сессии (Happy Path)

**Сценарий:** Пользователь видит чужую/старую сессию в списке устройств и удаляет ее.

1.  **Команда отзыва:** Клиент вызывает `DELETE /api/auth/sessions/sess-12345` (где `sess-12345` — ID сессии старого ноутбука).
2.  **Валидация владельца:** Auth Service проверяет в PostgreSQL `authorized_sessions`, принадлежит ли `sess-12345` тому же `global_steos_id`, что делает запрос. Да, принадлежит.
3.  **Удаление из Redis (Мгновенность):**
    *   Auth Service атомарно удаляет ключ `steos:sess:sess-12345` из Redis.
    *   С этой миллисекунды старый ноутбук теряет доступ ко всем внутренним микросервисам (API Gateway будет отклонять его `Cookie: steos_sess=sess-12345`).
4.  **Обновление в БД (Персистентность):**
    *   Запись в `authorized_sessions` помечается как `is_active = false` (и записывается `revoked_at = NOW()`).
5.  **Возврат успеха:** Клиенту (на текущем устройстве) возвращается `204 No Content`. Сеанс на старом ноутбуке успешно завершен.

#### Сценарий Б: Попытка отзыва чужой сессии (Negative Path - Not Found/Forbidden)

**Сценарий:** Злоумышленник пытается подобрать ID сессии другого пользователя и "разлогинить" его.

1.  **Злонамеренный запрос:** Хакер отправляет `DELETE /api/auth/sessions/sess-boss-999`.
2.  **Валидация владельца:** Auth Service ищет сессию `sess-boss-999` в БД и видит, что она принадлежит другому `global_steos_id` (Боссу).
3.  **Отказ:** Сервис понимает, что хакер не имеет прав управлять чужими сессиями.
4.  **Возврат ошибки:** Возвращается `404 Not Found` (или `403 Forbidden`). Сессия Босса в Redis остается целой и невредимой. Хакер не может нарушить работу других пользователей.

## SR-AUTH-SM-07: Тихое продление (Silent Refresh)

Access-токены, выдаваемые глобальным STEOS ID, обычно живут короткое время (например, 15-30 минут) ради безопасности. Однако пользователь платформы (например, редактор) может работать в интерфейсе часами. Система не должна выкидывать его на страницу логина каждые 30 минут.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Хранение Refresh-токена** | При первичном логине Auth Service получает от STEOS ID долгоживущий `refresh_token`. Этот токен **зашифровывается** локальным ключом шифрования микросервиса (KMS) и кладется в PostgreSQL в поле `encrypted_global_refresh`. В Redis он не попадает. |
| **Фоновое продление (Background Sync)** | Когда до конца жизни OIDC-доверенности остается мало времени (например, < 5 минут), Auth Service расшифровывает `refresh_token`, делает S2S-запрос к глобальному STEOS ID, получает новый Access-токен и продлевает `expires_at` локальной сессии. Сам вызов может инициироваться отдельным endpoint `refresh`, внутренним scheduler-ом или middleware-триггером, но смысл SR — именно в обновлении глобальной доверенности. |
| **Zero-Interruption** | Весь процесс происходит исключительно на серверах. В браузере (в Cookie) ничего не меняется (Phantom Token остается тем же UUID). Пользователь не видит никаких прерываний работы. |

### 2. Высокоуровневое описание

Представим **аренду автомобиля в каршеринге (Поминутный тариф)**.

1. **Старт аренды (Первичный логин):** Вы авторизуетесь (STEOS ID) и берете машину. Вы получаете ключи от машины (Phantom Token) на 30 минут. Вы едете (пользуетесь платформой).
2. **Истечение времени (Опасность обрыва):** Прошло 25 минут. Вы стоите в пробке. Если ничего не сделать, через 5 минут мотор просто заглохнет прямо посреди дороги (разрыв сессии).
3. **Тихое продление (Silent Refresh):** Умный бортовой компьютер машины (Auth Service) видит, что осталось 5 минут. Он незаметно (в фоновом режиме) связывается по спутниковой связи с главным сервером каршеринга (STEOS ID): "Этот водитель еще не в черном списке? С его кредитки можно списать еще денег? (Refresh Token валиден?)".
4. **Успех (Продление сеанса):** Главный сервер отвечает "Всё ок, разрешаю еще 30 минут" (выдает новый Access Token).
5. **Бесшовность:** Бортовой компьютер машины обновляет свой внутренний таймер (Redis `expires_at`). А вы (Пользователь) даже не знаете об этом диалоге. Вы продолжаете спокойно ехать, машина не глохнет, интерфейс на экране не моргает и не просит вас снова вводить пароль.

Эта функция критически важна для UX (User Experience) в "тяжелых" одностраничных приложениях (SPA), где пользователь может долго набирать текст или настраивать графики без обновления страницы.

### 3. Примеры взаимодействия (логические сценарии)

Этот процесс описывает механику бесшовного обновления токенов без переадресаций и изменения Cookie.

**Общие исходные данные:**
*   **Инициатор:** Фоновый скрипт во фронтенд-приложении (или Middleware).
*   **Входящий запрос:** Фоновый вызов `POST /auth/refresh` или внутренний серверный триггер обновления.
*   **Контекст:** Пользователь активно работает в платформе. До истечения `expires_at` сессии в Redis осталось менее 5 минут.

#### Сценарий А: Успешное тихое продление (Happy Path)

**Сценарий:** Пользователь работает в платформе, локальная сессия скоро истечет, и Auth Service успешно обновляет ее, запросив новый токен у глобального STEOS ID.

1.  **Пинг от клиента:** Фронтенд отправляет пинг (или любой API запрос, перехваченный Auth Middleware).
2.  **Проверка TTL в Redis:** API Gateway замечает, что срок жизни ключа `steos:sess:f47a...` в Redis составляет всего 4 минуты.
3.  **Асинхронный процесс обновления (S2S):**
    *   Auth Service извлекает из БД (PostgreSQL) `encrypted_global_refresh` для этой сессии.
    *   Расшифровывает его локальным мастер-ключом.
    *   Делает серверный HTTP-вызов к STEOS ID (OIDC `/token` endpoint) с `grant_type=refresh_token`.
4.  **Успех от STEOS ID:** STEOS ID валидирует `refresh_token` (проверяет, что юзер не забанен на глобальном уровне) и возвращает свежий `access_token` (и опционально новый `refresh_token`).
5.  **Продление сессии (Redis & БД):**
    *   Auth Service обновляет время жизни ключа `steos:sess:f47a...` в Redis (например, добавляет еще 30 минут).
    *   Обновляет `expires_at` (и зашифрованный `refresh_token`, если он изменился) в таблице `authorized_sessions`.
6.  **Ответ клиенту:** Фронтенд получает `200 OK` (если это был пинг) или результат своего бизнес-запроса. Пользователь продолжает работу без единого моргания экрана.

#### Сценарий Б: Глобальная блокировка или отзыв (Negative Path - Session Terminated)

**Сценарий:** Пользователь активно работает, но 10 минут назад администратор удалил его глобальный аккаунт в STEOS ID (или он сменил пароль с другого устройства, аннулировав все старые сессии).

1.  **Проверка TTL в Redis:** Сервис замечает, что до конца локальной сессии осталось < 5 минут, и решает продлить ее.
2.  **S2S-вызов:** Auth Service обращается к STEOS ID с `refresh_token`.
3.  **Отказ от STEOS ID:** Глобальный провайдер отвечает `400 Bad Request` или `401 Unauthorized` с ошибкой `invalid_grant` ("Refresh token is invalid, revoked, or expired").
4.  **Смерть локальной сессии:**
    *   Auth Service понимает, что глобальной доверенности больше нет.
    *   Он немедленно выполняет жесткий отзыв (Revoke) локальной сессии: удаляет ключ `steos:sess:f47a...` из Redis и помечает ее неактивной в БД.
5.  **Разрыв (Logout):** Текущий бизнес-запрос (или пинг) фронтенда завершается с ошибкой `401 Unauthorized`.
6.  **Реакция UI:** Фронтенд-приложение, получив 401, немедленно скрывает рабочую область и перенаправляет пользователя на глобальный экран логина STEOS ID. Системная безопасность восстановлена.

## SR-AUTH-SM-08: Доверенные устройства (Trusted Devices)

Требование снижает friction при повторных входах и позволяет системе отличать известные браузеры пользователя от потенциально чужих устройств. Оно не отменяет Fingerprint-валидацию, а добавляет управляемый пользователем белый список доверия.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Явное согласие пользователя** | Устройство попадает в доверенный список только после явного действия пользователя ("Запомнить этот браузер"). |
| **Хранение метаданных** | Для доверенного устройства сохраняются нормализованный fingerprint, user-agent, примерная география и дата последнего использования. |
| **Отзыв доверия** | Пользователь может в любой момент удалить устройство из списка, не дожидаясь следующего логина. |
| **Влияние на Risk Engine** | Наличие устройства в белом списке может снижать риск-скоринг и убирать лишние step-up проверки, но не отключает базовую безопасность. |

### 2. Высокоуровневое описание

Представим **список постоянных посетителей в бизнес-центре**.

1. **Первичное посещение:** Вы приходите в здание и проходите обычную полную проверку у охраны.
2. **Внесение в белый список:** После подтверждения личности вы говорите: "Это мой рабочий ноутбук, запомните его". Охрана заносит признаки вашего устройства в список доверенных.
3. **Повторный вход:** В следующий раз охрана узнает знакомый ноутбук и пропускает вас быстрее, не заставляя снова проходить дополнительные процедуры.
4. **Отзыв доверия:** Если ноутбук потерян или вы больше не хотите ему доверять, запись удаляется из списка, и устройство снова считается обычным.

### 3. Примеры взаимодействия (логические сценарии)

#### Успешное добавление доверенного устройства (Happy Path)

1. Пользователь проходит логин и отмечает "Доверять этому устройству".
2. Auth Service сохраняет fingerprint и метаданные устройства в доверенный список пользователя.
3. При следующем входе risk engine видит знакомое устройство.
4. Дополнительный step-up MFA может быть пропущен или ослаблен.

## SR-AUTH-SM-09: Продление TTL активной сессии (Session Keep-Alive)

Это требование отвечает не за обновление глобальной OIDC-доверенности, а за продление жизни уже валидной локальной Phantom-сессии при активной работе пользователя в интерфейсе.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Sliding TTL** | При подтвержденной активности пользователя TTL ключа локальной сессии в Redis аккуратно сдвигается вперед в пределах допустимого окна. |
| **Без постоянного контакта с IdP** | Обычный keep-alive не обязан каждый раз обращаться в STEOS ID, чтобы не превращать платформу в прокси к глобальному провайдеру. |
| **Защита от бесконечных сессий** | Наряду со sliding TTL сохраняется верхний предел жизни сессии и/или периодическая переоценка через `Silent Refresh`. |
| **Прозрачность для UI** | Пользователь просто продолжает работать, не сталкиваясь с внезапным logout из-за простаивающего TTL в Redis. |

### 2. Высокоуровневое описание

Представим **электронный пропуск в коворкинг, который продлевается, пока вы реально работаете внутри**.

1. **Начало рабочего дня:** Пользователь уже вошел в систему и получил локальную Phantom-сессию.
2. **Подтверждение активности:** Пока пользователь двигает мышкой, печатает и делает запросы, система видит, что сессия используется живым человеком.
3. **Сдвиг окна жизни:** Вместо выпуска нового пропуска сервис просто продлевает срок жизни существующего серверного состояния в Redis.
4. **Пределы безопасности:** Если сессия живет слишком долго или требует перепроверки глобальной доверенности, включается уже отдельный механизм `Silent Refresh`.

### 3. Примеры взаимодействия (логические сценарии)

#### Обычная активная работа (Happy Path)

1. SPA отправляет `POST /sessions/keep-alive` или активный бизнес-запрос с действующей Cookie.
2. Auth Service видит, что пользователь активен и сессия не отозвана.
3. TTL ключа `steos:sess:{session_id}` продлевается без выпуска новой Cookie.
4. Пользователь продолжает работу без внезапного logout.

## SR-AUTH-SM-10: Горячее обновление контекста сессии

Enterprise-платформа не должна ждать следующего логина, чтобы применить новые роли, лицензии, feature flags или статус подписки пользователя. Это требование описывает обновление `SessionContextDto` "на лету".

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **Массовое обновление активных сессий** | Auth Service находит все активные сессии пользователя или Workspace и обновляет их контекст в Redis. |
| **Без перевыдачи Cookie** | Сам Phantom Token не меняется, меняется только серверный payload, связанный с этим токеном. |
| **Мгновенное применение новых прав** | Следующий запрос через Gateway автоматически пойдет в downstream уже с новым набором ролей и атрибутов. |
| **Поддержка real-time UX** | Клиентские приложения могут получать событие `context_updated` и синхронно перерисовывать интерфейс без hard reload. |

### 2. Высокоуровневое описание

Представим **электронную доску доступа в офисе, где права на двери обновляются прямо во время рабочего дня**.

1. **Изменение полномочий:** Пользователю выдали новую роль, подписку или доступ к дополнительному разделу.
2. **Обновление центральной модели:** Auth Service получает новый набор атрибутов и меняет серверный контекст.
3. **Без перевыпуска пропуска:** Сам физический пропуск не меняется, меняется только список дверей, которые он теперь открывает.
4. **Мгновенный эффект:** При следующем обращении пользователь уже работает с обновленным набором прав, не выходя из системы.

### 3. Примеры взаимодействия (логические сценарии)

#### Повышение прав пользователя (Happy Path)

1. Billing Service сообщает, что пользователь купил новую лицензию, либо администратор меняет ему роль.
2. Auth Service получает новый набор ролей и бизнес-атрибутов.
3. Все активные `SessionContextDto` пользователя обновляются в Redis.
4. Следующий запрос пользователя или WebSocket-событие применяет новый контекст без перелогина.
