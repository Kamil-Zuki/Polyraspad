# Введение

Хранение зашифрованных Refresh-токенов в БД и фоновое (S2S) продление сессий без изменения клиентской Cookie для обеспечения бесшовного UX.

## Контекст и проблема

Access-токены (JWT), выдаваемые глобальным Identity Provider (`STEOS ID`), специально имеют короткий срок жизни (например, 15-30 минут) ради безопасности. По истечении этого срока токен становится недействительным. 

В одностраничных приложениях (SPA) пользователь может часами читать длинный документ или настраивать сложный дашборд без перезагрузки страницы. Если по истечении 30 минут сессия внезапно оборвется (HTTP `401 Unauthorized`), пользователь:

1. Потеряет несохраненный прогресс.
2. Будет выброшен на глобальный экран логина, что создаст отвратительный пользовательский опыт (UX).

Классическое решение в SPA — реализовать механизм перехвата `401` ошибки во фронтенд-приложении (Axios Interceptors) и отправить запрос `/refresh` со старым токеном (или специальным Refresh-токеном, сохраненным в браузере), чтобы получить новый.

**Проблема:**
*   Если передавать браузеру "долгоживущий" `refresh_token`, он подвергается риску кражи через XSS или другие уязвимости. Украденный `refresh_token` дает хакеру возможность бесконечно продлевать доступ.
*   При перехвате `401` ошибки в SPA возникает риск состояния "Гонки" (Race Conditions), если несколько одновременных API-вызовов упадут в одну миллисекунду, заставляя фронтенд сделать сразу десяток запросов `/refresh`.

## Принятое решение

Для достижения максимального уровня безопасности и идеального UX мы реализовали архитектурный паттерн **Server-Side Silent Refresh (Тихое серверное продление)** в сочетании с **JIT-дешифровкой (Just-In-Time Decryption)**:

1.  **Секретное хранение в БД:** Во время первичного логина пользователя (OIDC Code Flow), `Authorization Service` получает от `STEOS ID` долгоживущий `refresh_token`. Сервис шифрует этот токен с помощью локального Мастер-Ключа (KMS) и сохраняет в поле `encrypted_global_refresh` таблицы `authorized_sessions` (PostgreSQL). Браузеру (в Cookie `steos_sess`) отдается только случайный UUID сессии (Phantom Token), а Refresh-токен никогда не покидает сервер.
2.  **Фоновый пинг (Keep-Alive):** Фронтенд-приложение периодически (например, раз в минуту) отправляет легкий запрос `POST /api/auth/session/keep-alive` (или сервис перехватывает любой бизнес-запрос).
3.  **Анализ TTL в Redis:** API Gateway (внутри Auth Service) проверяет TTL сессии в Redis. Если до истечения сессии остается мало времени (например, < 5 минут), запускается асинхронный процесс:
    *   Auth Service делает SQL-запрос за зашифрованным токеном.
    *   **JIT-Дешифровка:** Расшифровывает `refresh_token` в оперативной памяти (JIT).
    *   **S2S-вызов:** Делает серверный HTTP-запрос (Server-to-Server) к `STEOS ID` на эндпоинт `/token` с `grant_type=refresh_token`.
4.  **Бесшовное продление (Redis Update):** Если `STEOS ID` одобряет запрос (пользователь не забанен) и возвращает новый Access-токен, локальный сервис просто **увеличивает время жизни ключа в Redis** (продлевая сессию) и зашифровывает/сохраняет новый `refresh_token` в БД (если он обновился).
5.  **Нулевое влияние на Cookie:** Клиентский `steos_sess` (UUID) в браузере не меняется. Фронтенд даже не догадывается, что произошла сложная криптографическая операция по продлению его сессии.

## Обоснование и последствия

### Плюсы

*   **Идеальный UX (Zero-Interruption):** Пользователь не испытывает никаких обрывов связи, морганий экрана или переадресаций в процессе многочасовой работы в приложении.
*   **Бескомпромиссная безопасность (Zero-Knowledge Frontend):** Браузер полностью изолирован от сложной логики токенов, алгоритмов OIDC и секретных `refresh_token`. Кража `refresh_token` из браузера невозможна по причине его физического отсутствия на клиенте.
*   **Защита от утечки из БД (At-Rest Encryption):** Поскольку `refresh_token` хранится в БД в зашифрованном виде, даже полный дамп таблицы `authorized_sessions` бесполезен для злоумышленника (см. аналогичный паттерн в Integration Service КАР-6).

### Последствия

*   **Риск простоя БД (Database Dependency):** В классическом JWT подходе продление можно реализовать "stateless" на клиенте. В нашем подходе, если на момент фонового продления (когда до конца сессии осталось 5 минут) база данных PostgreSQL будет недоступна для чтения зашифрованного токена, сессия неизбежно "умрет", и пользователь будет выброшен из платформы.
*   **Нагрузка на криптографию (CPU Overhead):** JIT-дешифровка и последующее шифрование нового токена при каждом продлении требуют затрат процессорного времени. В масштабах тысяч одновременных пользователей это может потребовать оптимизации (например, использования аппаратного ускорения AES-NI).
*   **Сложность фоновой синхронизации (Concurrency):** Если пользователь активно работает с приложением сразу на ноутбуке и телефоне (с одной и той же локальной сессией), оба устройства могут попытаться сделать `/keep-alive` одновременно. Это может привести к двум параллельным S2S-вызовам к `STEOS ID` и инвалидации одного из `refresh_token` из-за политики "Refresh Token Rotation" в IdP. Требуется внедрение распределенных блокировок (Distributed Locks в Redis) на операцию обновления.
