# Введение

Переключение пользователя между рабочими пространствами (Workspaces) происходит на уровне сервера без изменения клиентской Cookie. Фронтенд работает "вслепую", отправляя пустые API-запросы, а Auth Service сам направляет их в нужный Workspace.

## Контекст и проблема

В мульти-тенантных (Multi-Tenant) B2B-системах пользователи часто состоят в нескольких логических пространствах (Workspaces, Команды, Проекты) одновременно. Фронтенд-приложение должно гарантировать, что текущий запрос (например, "Создать документ") уйдет именно в то пространство, которое сейчас выбрано в UI (левое меню).

Классический способ — передавать `?workspace_id=42` в каждом GET-запросе или `{"workspace_id": 42}` в теле каждого POST-запроса от браузера. Это порождает колоссальные проблемы:

*   **Сложность UI (Спагетти-код):** Код SPA-приложения (React/Vue) засоряется логикой "протаскивания" переменной `currentWorkspaceId` через все компоненты, хуки и API-клиенты (Axios).
*   **Уязвимости доступа (Insecure Direct Object References - IDOR):** Разработчик бэкенда может забыть написать проверку: "Имеет ли этот пользователь доступ к переданному в теле `workspace_id`?". Хакер просто меняет `42` на `99` (ID пространства конкурента) и получает доступ к чужим документам.
*   **Сложность URL:** URL-адреса страниц становятся громоздкими и хрупкими, требуя постоянного контроля параметров маршрутизации.

## Принятое решение

Мы внедрили механизм **Динамической серверной маршрутизации контекста (Server-Side Context Routing)**:

1.  **Stateful Workspace в БД и Redis:** В `Authorization Service` (в PostgreSQL таблице `session_contexts` и в Redis-объекте сессии) хранится актуальное поле `active_workspace_id`.
2.  **Смена контекста через API:** Когда пользователь в UI кликает "Перейти в Команду А", фронтенд делает ровно один HTTP-вызов: `PUT /api/auth/context {"workspace_id": 42}`. 
    *   Auth Service синхронно проверяет права (через `Workspace Service`).
    *   При успехе — обновляет стейт в Redis (`active_workspace_id = 42`) и отвечает `200 OK`.
3.  **Слепота фронтенда (Frontend Blindness):** При всех последующих вызовах (создание тасок, чтение CRM) фронтенд **вообще не передает** `workspace_id`.
4.  **Склейка (Header Injection):** API Gateway (Auth Service), получив запрос, достает из Redis текущий `active_workspace_id` для данной сессии (Cookie) и встраивает его в бизнес-заголовок `X-Workspace-Id`. 
5.  Внутренний микросервис принимает решение исключительно на основе этого жестко контролируемого сервером заголовка (Zero Trust, см. КАР-2).

## Обоснование и последствия

### Плюсы

*   **Радикальное упрощение фронтенда (DX):** Код React-приложения избавляется от необходимости знать, в каком Workspace он находится при выполнении 90% CRUD-операций. API-клиент становится максимально "чистым".
*   **Бескомпромиссная безопасность (Zero IDOR):** Поскольку браузер физически лишен возможности управлять целевым `workspace_id` в бизнес-запросах, хакер не может подменить ID. Все изменения стейта проходят через единственную жесткую проверку в эндпоинте `/api/auth/context`.
*   **Централизация Audit Log:** Любое перемещение пользователя между пространствами мгновенно фиксируется в WORM-журнале (Local Access Audit) внутри Auth Service.

### Последствия

*   **Риск "Гонки" (Race Condition) в UI:** Если пользователь откроет две вкладки браузера, в первой вкладке переключится в "Команду А", а во второй (не обновляя страницу) нажмет "Создать документ", документ улетит в "Команду А" (так как контекст на сервере уже изменился). 
    *   *Решение:* Требуется реализация механизма **Multi-Tab Sync** на фронтенде (через `BroadcastChannel API`), чтобы синхронизировать смену стейта между всеми открытыми вкладками одного браузера, либо использование `LocalStorage` для хранения версии сессии.
*   **Жесткая привязка 1 к 1:** Данный паттерн предполагает, что в одну секунду времени одна сессия работает только с одним Workspace. Это делает невозможным (без сложных обходных путей) выполнение массовых агрегаций "Покажи задачи из всех моих пространств сразу", требуя создания отдельных, специфичных эндпоинтов в обход `X-Workspace-Id`.
*   **Накладные расходы на БД:** При активной работе и частых сменах Workspace нагрузка на запись (UPDATE) в таблицу `session_contexts` возрастает.
