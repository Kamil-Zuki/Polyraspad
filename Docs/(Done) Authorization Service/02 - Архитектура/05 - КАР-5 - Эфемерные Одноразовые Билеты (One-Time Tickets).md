# Введение

Для обхода ограничений WebSocket-рукопожатий и прямых загрузок файлов используются одноразовые билеты (Burn-on-Read). Они живут в Redis всего 15 секунд и сжигаются в миллисекунду чтения, обеспечивая безопасную передачу контекста через URL.

## Контекст и проблема

В веб-приложениях существуют два распространенных сценария, при которых стандартная авторизация через HTTP-заголовки или `HttpOnly` Cookie не работает или работает с серьезными ограничениями:

*   **WebSockets:** JavaScript API (`new WebSocket()`) не позволяет устанавливать кастомные HTTP-заголовки (например, `Authorization: Bearer ...`) при инициализации соединения (Handshake).
*   **Скачивание файлов (Direct Download):** При вставке защищенного изображения `<img src="/api/files/secret.jpg">` или принудительном скачивании файла (когда нужно показать нативный UI браузера "Сохранить как..."), браузер не позволяет фронтенду добавить заголовки.

Самое очевидное (и опасное) решение — передавать токен сессии или JWT прямо в URL: `wss://api.steos.io/ws?token=MY_SECRET_TOKEN`. Это грубейшее нарушение безопасности, так как URL полностью логируется:

1. На прокси-серверах (Nginx, Cloudflare).
2. В истории браузера.
3. В логах провайдеров (ISP).
Утечка этого URL приведет к полной компрометации аккаунта.

## Принятое решение

Для решения этой проблемы `Authorization Service` предоставляет механизм **One-Time Tickets (Эфемерных билетов)**:

1.  **Генерация билета (Ticket Generation):** Фронтенд, будучи авторизованным (с валидной Cookie), делает предварительный AJAX-запрос: `POST /api/auth/tickets/generate`.
2.  **Эфемерность (Redis TTL):** `Authorization Service` генерирует случайную криптографическую строку (Ticket) и сохраняет ее в Redis. Ключ в Redis имеет жесткий Time-To-Live (TTL) ровно **15 секунд**. В качестве значения ключа сохраняется текущий контекст пользователя (его ID, Workspace).
3.  **Использование (URL Param):** Фронтенд немедленно использует этот Ticket в URL для открытия WebSocket: `new WebSocket("wss://.../?ticket=XYZ")`.
4.  **Сжигание при чтении (Burn-on-Read):** API Gateway перехватывает WebSocket Handshake. Он берет `ticket=XYZ` и выполняет атомарную команду в Redis (например, `GETDEL`), которая **читает значение и немедленно удаляет ключ** в одной транзакции. 
5.  **Инъекция заголовков:** Контекст, полученный из "сгоревшего" билета, конвертируется в стандартные бизнес-заголовки (`X-Global-Actor-Id`) и передается внутреннему WebSocket-серверу. Соединение успешно устанавливается.

## Обоснование и последствия

### Плюсы

*   **Абсолютная защита от утечек URL:** Даже если URL `?ticket=XYZ` осядет в логах Nginx, он абсолютно бесполезен для злоумышленника. К моменту записи в лог билет уже "сожжен" (или истек его 15-секундный TTL). Повторное использование невозможно.
*   **Сохранение Zero Trust:** Внутренние сервисы (например, сервер уведомлений WebSocket) продолжают работать в парадигме Zero Trust, ожидая доверенных `X-` заголовков от API Gateway, не зная о существовании билетов.
*   **Универсальность:** Этот же механизм элегантно решает проблему безопасного скачивания больших файлов по прямым ссылкам, генерации одноразовых ссылок на сброс пароля или экспорт отчетов.

### Последствия

*   **Сложность фронтенда:** Клиентский код должен быть усложнен. Вместо простого `new WebSocket()` требуется асинхронная оркестрация: сначала дождаться билета от API, и только в `.then()` открывать соединение.
*   **Сетевые задержки (Latency):** Добавляется один лишний HTTP-запрос (Round-trip) (генерация билета) перед фактическим началом скачивания файла или установкой сокета.
*   **Риск истечения времени (Timeouts):** Если у пользователя очень медленный интернет, 15-секундного TTL может не хватить между моментом генерации билета и моментом, когда браузер реально инициирует Handshake.
