# Введение

Данный документ описывает асинхронную часть интеграции Authorization Service с внутренними микросервисами платформы (Workspace, Task, CRM и др.) через брокер сообщений RabbitMQ. Эта интеграция используется для отправки броадкаст-событий (Broadcast/Fanout), когда происходит важное изменение в жизненном цикле пользователя, требующее реакции от множества независимых систем (например, конвертация гостевой сессии в авторизованный аккаунт).

# Общая информация

Асинхронная отправка событий о "склейке" сессий для бесшовного переноса гостевых ресурсов. Реализует паттерн **Event-Driven Architecture (EDA)**.

| Параметр | Описание |
| :--- | :--- |
| **Версия API** | RabbitMQ 3.12.x (Event-Driven) |
| **Название сервиса** | Внутренние микросервисы (Task Service, Workspace Service, CRM Service и т.д.) |
| **Официальная документация** | Внутренняя спецификация событий платформы (Platform Event Schema) |
| **Внутренний владелец** | Команда Backend разработки Platform Services |

# Доступ и аутентификация

Настройки подключения к инфраструктуре локального брокера сообщений.

| Параметр | Описание |
| :--- | :--- |
| **Метод аутентификации** | Аутентификация через RabbitMQ (логин/пароль или сертификаты mTLS внутри кластера Kubernetes). |
| **Хранение учетных данных** | Учетные данные локального RabbitMQ хранятся в **HashiCorp Vault** или Kubernetes Secrets. |
| **Среды (Environments)** | Для сред Prod и Stage используются разные виртуальные хосты (vhost) брокера. |
| **Публикация (Exchange)** | Authorization Service публикует события в Exchange (например, `platform:events:auth`), к которому подключены очереди (Queues) других микросервисов. |

# Ключевые события (Publish)

Список типов событий, генерируемых Authorization Service после успешной логики управления пользователями.

| Событие | Exchange / Топик | Routing Key | Описание | Использование в Authorization Service |
| :--- | :--- | :--- | :--- | :--- |
| `GuestMergedEvent` | `platform:events:auth` | `auth.guest_merged` | Уведомление о том, что анонимный пользователь (гость) успешно авторизовался через STEOS ID. Содержит маппинг старого `shadow_guest_id` на новый `real_global_id`. | Публикуется сразу после успешной OIDC-авторизации, если у клиента в браузере была найдена активная гостевая Cookie `guest_sess` (**SR-AUTH-SM-03**). |
| `UserRegisteredEvent` | `platform:events:auth` | `auth.user_registered` | (Опционально) Уведомление о первом успешном логине нового пользователя на платформе. | Используется для запуска приветственных email-рассылок (Onboarding Journey) или начисления приветственных бонусов. |

# Логика обработки событий

Механизмы обеспечения надежной доставки (Store and Forward) событий в случае временной недоступности локального брокера или баз данных микросервисов.

*   **Fire-and-Forget (Publishing):** События `GuestMergedEvent` публикуются асинхронно после успешного обмена OIDC-кода на токен. Блокировать выдачу Phantom Token и редирект пользователя из-за медленного RabbitMQ нецелесообразно (задача — минимизировать задержку логина).
*   **Гарантия доставки (Transactional Outbox):** Для гарантии того, что гостевые данные не "потеряются", Authorization Service использует паттерн **Transactional Outbox**.
    *   Событие `GuestMergedEvent` сначала сохраняется в таблицу `outbox_events` (PostgreSQL) в одной транзакции с удалением гостевой сессии.
    *   Фоновый воркер читает эту таблицу и отправляет сообщение в RabbitMQ с использованием `Publisher Confirms`.
    *   Только после получения подтверждения (ACK) от RabbitMQ, событие помечается как отправленное в БД.
*   **Потребители (Subscribers):** Каждый внутренний микросервис (например, `Task Service`) имеет свою очередь (Queue), привязанную к этому Exchange. При получении события он выполняет запрос к своей базе: `UPDATE tasks SET owner_id = :real_global_id WHERE owner_id = :shadow_guest_id`.

# Обработка ошибок

Действия Authorization Service при невозможности передать событие о слиянии (Merge) гостевых данных.

| Тип ошибки | Описание причины | Реакция сервиса |
| :--- | :--- | :--- |
| `BROKER_UNAVAILABLE` | Локальный RabbitMQ временно недоступен (сбой по сети, рестарт подов). | Событие надежно сохраняется в локальную таблицу `outbox_events` базы данных PostgreSQL (Transactional Outbox). Фоновый процесс (Relay/Worker) будет пытаться отправить его снова с экспоненциальной задержкой (Exponential Backoff). Данные гостя не потеряются. |
| `PUBLISH_FAILED` | Ошибка на уровне протокола RabbitMQ (Exchange не существует или нет прав на запись). | Записывается критическая ошибка (`ERROR`) в лог (с трассировкой `trace_id`), срабатывает Alert для DevOps. Событие остается в `outbox_events` до ручного вмешательства. |
| `SUBSCRIBER_FAILED` | Внутренний микросервис (например, Task Service) упал во время обработки `GuestMergedEvent`. | Эта проблема решается на стороне потребителя (Task Service). Authorization Service свою задачу выполнил. Task Service использует Dead Letter Exchange (DLX) и механизмы повторной попытки (Retry) для обработки своих очередей. Гостевые задачи будут "перевешены" позже. |
