# Введение

В данном документе описывается синхронная интеграция по протоколу gRPC с микросервисом Workspace Service. Эта интеграция критически важна для двух бизнес-задач: проверки прав пользователя при переключении контекста (рабочего пространства) и обеспечения автоматического (JIT) создания персонального пространства для новых пользователей платформы (онбординг). Authorization Service выступает здесь как PEP (Policy Enforcement Point) или инициатор создания ресурсов, делегируя бизнес-логику Workspace Service.

# Общая информация

Обеспечение валидации прав доступа к пространствам и оркестрация создания профилей новых пользователей.

| Параметр | Описание |
| :--- | :--- |
| **Версия API** | gRPC v1 (Protocol Buffers) |
| **Название сервиса** | Workspace Service (внутренний микросервис платформы) |
| **Официальная документация** | Внутренняя спецификация gRPC-контрактов платформы |
| **Внутренний владелец** | Команда Backend разработки Platform Services |

# Доступ и аутентификация

Механизмы защиты межсервисного взаимодействия в кластере Kubernetes для безопасной проверки прав и создания критических сущностей платформы.

| Параметр | Описание |
| :--- | :--- |
| **Метод аутентификации** | Внутренний сервисный токен (Service-to-Service Authentication) или mTLS (Mutual TLS) для межсервисного взаимодействия в Kubernetes. |
| **Хранение учетных данных** | Сервисные токены хранятся в **HashiCorp Vault** или Kubernetes Secrets. Микросервис запрашивает их при инициализации. |
| **Среды (Environments)** | Для сред Prod и Stage используются разные экземпляры `Workspace Service` с разделением баз данных. |
| **Протокол** | gRPC с Protocol Buffers для обеспечения высокой производительности (миллисекундные задержки). |

# Ключевые методы gRPC

Перечень удаленных процедур, вызываемых для валидации контекста пользователя и его онбординга.

| Метод | Описание | Использование в Authorization Service |
| :--- | :--- | :--- |
| `CheckUserWorkspaceAccess(global_steos_id, workspace_id)` | Проверка, является ли пользователь участником запрашиваемого Пространства. | Вызывается синхронно при каждом вызове API-эндпоинта `PUT /api/auth/context/switch` (**SR-AUTH-SM-02**). |
| `CreateInitialSetup(global_steos_id, email, ...)` | Запрос на создание локального профиля пользователя и персонального рабочего пространства (Personal Workspace) с ролью Owner. | Вызывается при первом успешном входе пользователя (когда его `global_steos_id` еще нет в локальной БД) для обеспечения бесшовного **JIT Onboarding** (**SR-AUTH-OI-03**). |

# Логика обработки запросов

Правила взаимодействия между сервисами, включая паттерны безопасности и стратегии отката транзакций.

*   **Паттерн PEP/PDP (при смене контекста):** `Authorization Service` не принимает решений о том, может ли пользователь зайти в Пространство X. Он делегирует этот вопрос (PDP) `Workspace Service`. Только при положительном ответе Auth Service обновляет стейт сессии в Redis и БД (маршрутизация контекста).
*   **Синхронность (JIT Onboarding):** Создание первичного пространства критически важно для работы платформы. Auth Service "замораживает" процесс выдачи сессионной Cookie до тех пор, пока `Workspace Service` не подтвердит успешное создание ресурсов и не вернет `new_workspace_id`.
*   **Откат онбординга (Fail-Safe):** Если вызов `CreateInitialSetup` завершается ошибкой (или таймаутом), процесс OIDC-логина прерывается. Сессия не создается, Cookie не выдается. Пользователь перенаправляется на страницу ошибки, чтобы избежать "полусозданных" или неконсистентных состояний (отсутствие активного пространства ломает логику всего фронтенда).
*   **Оптимизация (Смена контекста):** Вызов `CheckUserWorkspaceAccess` может кэшироваться на очень короткое время (например, на время выполнения нескольких последовательных запросов, хотя архитектура Zero Trust предпочитает всегда проверять права).

# Обработка ошибок

Реакция Authorization Service на отказы в доступе или технические сбои при обращении к Workspace Service.

| Тип ошибки | Описание причины | Реакция сервиса |
| :--- | :--- | :--- |
| `NOT_A_MEMBER` (403) | Пользователь не состоит в Пространстве при вызове `CheckUserWorkspaceAccess`. | Возврат `403 Forbidden` пользователю. Стейт сессии в Redis (текущий `active_workspace_id`) остается неизменным. Записывается Security Audit WORM Event. |
| `WORKSPACE_NOT_FOUND` (404) | Запрашиваемое Пространство удалено или не существует. | Возврат `404 Not Found`. Смена контекста отменяется. |
| `INITIAL_SETUP_FAILED` | Ошибка внутри `Workspace Service` при `CreateInitialSetup` (конфликт почты, сбой транзакции). | Процесс логина прерывается. Возврат на фронтенд с кодом `ONBOARDING_FAILED`. Сессия пользователя (Phantom Token) не создается. |
| `SERVICE_UNAVAILABLE` (503) | `Workspace Service` временно недоступен. | При смене контекста: возврат `503 Service Unavailable`. При онбординге: откат процесса логина (Fail-Safe). |
| `DEADLINE_EXCEEDED` (504) | Превышено время ожидания ответа от `Workspace Service` (таймаут gRPC). | Возврат `504 Gateway Timeout`. Запрос блокируется для безопасности (Pessimistic Security). |
