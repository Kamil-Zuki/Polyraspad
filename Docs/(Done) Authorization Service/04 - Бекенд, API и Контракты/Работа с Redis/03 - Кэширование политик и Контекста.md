# Введение

Данный документ описывает процессы и правила кэширования политик безопасности (RBAC/ABAC), Geo-ограничений воркспейсов и персональных ключей доступа (PAT). Использование Redis в этой группе критически важно для реализации паттерна **Zero Trust (JIT)** (КАР-2), так как позволяет микросервису Authorization Service валидировать каждый gRPC-запрос за единицы миллисекунд (< 2мс), не создавая узкого места (Bottleneck) в виде постоянных SQL-запросов к PostgreSQL.

# 1. Список операций Кэширования политик и Контекста

Перечень механизмов кэширования "горячих" данных авторизации.

| Метод (SR) | Описание операции |
| :--- | :--- |
| КАР-2 / SR-AUTH-AC-01 | JIT-кэширование (Just-In-Time) рассчитанных RBAC/ABAC ролей пользователя в воркспейсе. |
| SR-AUTH-AC-04 / SR-AUTH-M2M-01 | In-Memory кэширование хэшей валидных PAT (Personal Access Tokens) и M2M-токенов для быстрой валидации gRPC. |
| SR-AUTH-AC-05 | Кэширование Geo-политик (разрешенные IP/Страны) для Workspace. |
| SR-AUTH-SM-08 | Кэширование списка Доверенных Устройств (Trusted Devices) пользователя. |

# JIT-кэш вычисленных ролей (SR-AUTH-AC-01)

## Общая информация

Кэширование "плоского" списка уже вычисленных ролей и пермиссий (RBAC/ABAC) для конкретной пары `(Пользователь, Воркспейс)`. Вычисление прав может быть сложным (учитывать наследование, группы, политики), поэтому результат кэшируется (Just-In-Time) при первом обращении и переиспользуется для всех последующих gRPC-проверок.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:jit:roles:{subject_id}:{workspace_id}`<br>где `{subject_id}` = UUID пользователя, `{workspace_id}` = контекст запроса. |
| **DTO ответа** | Сериализованный JSON массив строк-ролей (например, `["admin", "billing_editor"]`) и/или хэш-таблица пермиссий. |
| **TTL** | Короткий, статический (например, 5 минут: `300` сек). Обеспечивает Eventual Consistency при изменении прав. |

## Логика обработки запроса

*   **Чтение (Cache-Aside):** При вызове gRPC `ValidateToken` сервис проверяет кэш. Если `auth:jit:roles:{id}:{ws}` найден (Cache Hit), роли мгновенно возвращаются вызывающему микросервису.
*   **Запись (Вычисление):** При Cache Miss сервис делает тяжелый SQL-запрос к БД, вычисляет эффективные права, сериализует их и сохраняет в Redis (команда `SETEX`).
*   **Инвалидация (Silent Refresh):** Ключ принудительно удаляется (`DEL`) самим сервисом авторизации при любом изменении ролей пользователя администратором (вызов `/workspaces/{id}/members/{sub}/roles`), а также публикуется RabbitMQ событие `RolesUpdated` (см. КАР-9).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Если Redis недоступен, сервис переходит в режим прямой калькуляции прав из PostgreSQL на каждый gRPC-запрос (деградация производительности, но система продолжает работать). |

# Кэш API-ключей (PAT и M2M) (SR-AUTH-AC-04 / SR-AUTH-M2M-01)

## Общая информация

В отличие от JWT (где подпись проверяется криптографически без БД), персональные ключи (Personal Access Tokens) и M2M-ключи (Machine-to-Machine) являются Opaque-токенами (случайными строками). Для их сверхбыстрой валидации (менее 2 мс) их хэши кэшируются в Redis. В БД хранятся только bcrypt/argon2 хэши, а в Redis — SHA256 (для скорости).

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:pat:{sha256_hash}`<br>где `{sha256_hash}` = SHA256 от переданного в заголовке ключа (например, `steos_pat_XYZ...`). |
| **DTO ответа** | Сериализованный JSON объекта `ApiKeyCacheState` (`subject_id`, `workspace_id`, `scopes`, `expires_at`). |
| **TTL** | Статический (например, 1 час: `3600` сек) или до истечения `expires_at` самого ключа. |

## Логика обработки запроса

*   **Чтение:** gRPC `ValidateToken` получает заголовок `Authorization: Bearer steos_pat_...`. Сервис вычисляет SHA256 и делает `GET auth:pat:{hash}`. Если ключ найден (Cache Hit), валидация пройдена.
*   **Запись (Warm-up / Cache-Aside):** При создании ключа (вызов `POST /api-keys/pat`) его хэш сразу помещается в кэш (Warm-up). При Cache Miss во время валидации, сервис ищет ключ в БД, сверяет bcrypt-хэш (что дорого) и, при успехе, сохраняет в Redis.
*   **Инвалидация:** Ключ принудительно удаляется (`DEL`) при явном отзыве ключа (`DELETE /api-keys/pat/{id}`) пользователем или администратором.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Проверка каждого PAT-токена будет идти через тяжелое bcrypt-сравнение со всеми ключами пользователя в PostgreSQL, что может вызвать CPU-спайк (Bottleneck). Для защиты базы вводится локальный In-Memory кэш (LRU) в самом приложении на несколько секунд. |

# Кэш Geo-политик (SR-AUTH-AC-05)

## Общая информация

Enterprise-функция (Geo-Fencing), позволяющая владельцам Workspace ограничивать доступ к своим ресурсам только с определенных IP-адресов или стран (согласно справочнику GeoIP). Проверка Geo-политики должна выполняться на каждый запрос (КАР-2), поэтому конфигурация кэшируется.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:geo:{workspace_id}`<br>где `{workspace_id}` = контекст запроса. |
| **DTO ответа** | Сериализованный JSON объекта `GeoPolicyCache` (`allowed_ips`, `blocked_countries`, `action: ALLOW/BLOCK`). |
| **TTL** | Средний, статический (например, 1 час: `3600` сек). |

## Логика обработки запроса

*   **Чтение:** gRPC `ValidateToken` извлекает `workspaceId` (из Phantom Token) и IP клиента (из метаданных). Затем делает `GET auth:geo:{workspace_id}`. Если политики нет, доступ разрешен. Если есть — проверяет IP по CIDR-маскам. При нарушении политик публикует WSS-событие `geo_policy_violated`.
*   **Запись:** Cache-Aside при первом обращении.
*   **Инвалидация:** Ключ удаляется (`DEL`) при изменении настроек безопасности Workspace (`PUT /workspaces/{id}/geo-policies`).

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | При недоступности Redis Geo-политики запрашиваются из БД. |

# Кэш Доверенных Устройств (Trusted Devices) (SR-AUTH-SM-08)

## Общая информация

Кэширование списка отпечатков (Device Fingerprints/Cookies), которые пользователь пометил как "Доверять этому устройству" (Remember Me), чтобы пропускать этап MFA (Push/OTP) при логине.

| Тип операции | Read (Чтение), Write (Запись), Delete (Удаление) |
| :--- | :--- |
| **Ключ Redis** | `auth:devices:{subject_id}`<br>где `{subject_id}` = UUID пользователя. |
| **DTO ответа** | Set (Множество) строк — хэшей доверенных устройств `device_hash`. |
| **TTL** | Длительный, статический (например, 30 дней: `2592000` сек). Сдвигается при каждом логине (Sliding Window). |

## Логика обработки запроса

*   **Чтение:** Во время логина (`/auth/login`) сервис проверяет наличие Cookie `device_token`. Если он есть, проверяет принадлежность множеству: `SISMEMBER auth:devices:{subject_id} {device_hash}`. Если `true` — MFA пропускается.
*   **Запись:** При вызове `/devices/trust` (пользователь поставил галочку) устройство добавляется в множество `SADD`.
*   **Инвалидация:** При вызове `/devices/forget/{device_id}` устройство удаляется `SREM`.

## Статус-коды при ошибках

| Код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Механизм "Remember Me" деградирует (Fail-Safe: MFA требуется всегда). Пользователям придется вводить OTP-коды при каждом входе, даже на доверенных устройствах, пока Redis не восстановится. |
