# Введение

Группа алгоритмов локального аудита доступа — это фундамент юридической значимости и безопасности платформы. В отличие от стандартного логирования (ELK/Graylog), алгоритмы этого блока решают задачу гарантированного и неизменяемого сохранения критических событий безопасности (WORM Audit — Write Once, Read Many). 

Они обеспечивают полный контроль над тем, кто, когда и откуда получал доступ к ресурсам, фиксируют факты имперсонации (входа под другим пользователем) и смены контекстов (переключения между рабочими пространствами). Также эти алгоритмы включают механизмы инъекции доверенных метаданных (Header Routing), превращая API Gateway в единую точку сборки безопасного контекста для всей внутренней микросервисной архитектуры (паттерн Zero Trust).

# 1. Список алгоритмов Аудита Доступа

В данном разделе представлены алгоритмы, отвечающие за неизменяемое журналирование и маршрутизацию доверенного контекста.

| **Название алгоритма** | **Краткое описание** |
| :--- | :--- |
| **Алгоритм иммутабельного журналирования (WORM Audit)** | Синхронно фиксирует события входа, имперсонации и смены контекста в специализированную таблицу PostgreSQL с запретом на изменение или удаление записей. |
| **Алгоритм инъекции бизнес-заголовков (Header Routing)** | Извлекает контекст сессии из Redis и внедряет его в виде защищенных HTTP-заголовков (`X-` Headers) при проксировании запросов во внутреннюю сеть, реализуя принцип Zero Trust. |

# Алгоритм иммутабельного журналирования (WORM Audit)

## Контекст и область применения

### Почему был создан

Для соответствия требованиям информационной безопасности (ИБ) и прохождения аудитов, система должна вести "жесткий" журнал доступа, который невозможно удалить или изменить даже при компрометации приложения. Если злоумышленник (или недобросовестный администратор) удалит сессию из Redis, след от его входа все равно должен остаться в PostgreSQL навсегда.

### Бизнес-требование

Система должна гарантировать неизменяемость (Write Once, Read Many) логов критических событий авторизации и доступа на уровне базы данных (SR-AUTH-LA-01).

### Область применения

| **№** | **Описание** |
| :--- | :--- |
| **1** | Успешный вход в систему (Login). |
| **2** | Смена рабочего пространства (Context Switch). |
| **3** | Старт сессии имперсонации ("Режим Бога" для поддержки). |
| **4** | Срабатывание механизмов защиты (Fail2Ban, Hijack Detect). |

### Ограничения применения

| **№** | **Описание** |
| :--- | :--- |
| **1** | Запись в WORM Audit происходит синхронно, поэтому таблица должна быть оптимизирована для сверхбыстрой вставки (Append-Only) без тяжелых индексов на этапе записи. |
| **2** | Механизм защиты данных реализуется на уровне СУБД (PostgreSQL REVOKE), а не только в коде приложения. |

## Входные данные

| **Параметр** | **Тип данных** | **Описание** | **Ограничения** | **Обязательность** |
| :--- | :--- | :--- | :--- | :--- |
| `EventCode` | `string` | Код события (например, `LOGIN_SUCCESS`, `IMPERSONATION_STARTED`) | Строго из справочника | Да |
| `GlobalSteosId` | `Guid` | Идентификатор пользователя | `null` если аноним | Нет |
| `IpAddress` | `string` | IP-адрес инициатора | | Да |
| `Fingerprint` | `string` | Device Fingerprint | | Да |
| `MacroContext` | `JSON` | Дополнительные данные (например, `TargetWorkspaceId`, `ImpersonatorId`) | Размер до 1 КБ | Нет |

## Выходные данные

| **Параметр** | **Тип данных** | **Описание** |
| :--- | :--- | :--- |
| `AuditRecordId` | `long` | Идентификатор созданной записи (Sequence/Identity) |

## Логика работы (Псевдокод)

Алгоритм выполняется как финальный шаг успешных бизнес-транзакций авторизации.

```csharp
public async Task<long> LogSecurityEventAsync(AuditEntryDto auditData)
{
    // 1. Формируем DTO для записи (Entity Framework Core)
    var logEntry = new AccessAuditLog
    {
        EventCode = auditData.EventCode,
        GlobalSteosId = auditData.GlobalSteosId,
        IpAddress = auditData.IpAddress,
        DeviceFingerprint = auditData.Fingerprint,
        TimestampUtc = DateTime.UtcNow,
        MacroContextJson = JsonSerializer.Serialize(auditData.MacroContext)
    };

    // 2. Синхронное добавление в контекст БД
    _auditDbContext.AccessAuditLogs.Add(logEntry);

    try
    {
        // 3. Фиксация транзакции в Append-Only таблицу
        await _auditDbContext.SaveChangesAsync();
        return logEntry.Id;
    }
    catch (DbUpdateException ex)
    {
        // ВАЖНО: Если запись в аудит не удалась (БД недоступна), 
        // мы обязаны откатить/заблокировать операцию, породившую событие.
        // Нельзя пустить пользователя, если мы не смогли это залогировать.
        _logger.LogCritical(ex, "FAILED TO WRITE WORM AUDIT LOG. SYSTEM HALTED.");
        throw new SecurityException("AUDIT_SYSTEM_UNAVAILABLE");
    }

    /* 
       ПРИМЕЧАНИЕ ПО ИНФРАСТРУКТУРЕ (Ограничения БД):
       На уровне PostgreSQL при развертывании схемы выполняется:
       
       CREATE TABLE access_audit_logs (...);
       REVOKE UPDATE, DELETE, TRUNCATE ON TABLE access_audit_logs FROM application_user;
       GRANT INSERT, SELECT ON TABLE access_audit_logs TO application_user;
       
       Таким образом, само приложение (и ORM) физически не может изменить/удалить лог,
       что гарантирует иммутабельность.
    */
}
```

# Алгоритм инъекции бизнес-заголовков (Header Routing)

## Контекст и область применения

### Почему был создан

В микросервисной архитектуре передача стейта (Cookie) в каждый сервис небезопасна и неэффективна (каждый сервис должен лезть в Redis). Паттерн "Zero Trust" подразумевает, что внутренние сервисы (Task, CRM, Workspace) не валидируют сессии сами, а доверяют цепочке **API Gateway (агрегатор) → Authorization Service (PEP)**. Gateway очищает внешние заголовки; решение о сессии и инжектируемых доверенных данных (`X-Global-Actor-Id`, `X-Workspace-Id`) обеспечивает **Authorization Service** (обычно по gRPC), после чего Gateway направляет запрос во внутреннюю сеть.

### Бизнес-требование

Система должна выступать единым шлюзом на периметре (**API Gateway**), очищать внешние заголовки, получать контекст сессии через **Authorization Service** и инжектировать доверенные бизнес-заголовки для внутренних микросервисов (SR-AUTH-LA-03).

### Область применения

| **№** | **Описание** |
| :--- | :--- |
| **1** | Любой проксируемый HTTP-запрос (Reverse Proxy) через API Gateway к внутренним сервисам. |

## Логика работы (Псевдокод)

Алгоритм выполняется в Middleware-слое **API Gateway (агрегатора)** на периметре (не в процессе микросервиса Authorization Service), перед тем как перенаправить HTTP-пакет во внутреннюю сеть (Envoy/Service Mesh). Вызовы к **Authorization Service** для разрешения сессии — по gRPC (или эквиваленту), см. `ValidateSession` и КАР-2.

```csharp
public async Task ProxyRequestMiddleware(HttpContext context, RequestDelegate next)
{
    // 1. Очистка пользовательских заголовков (Sanitization)
    // Предотвращаем "Спуфинг" (Spoofing) - когда злоумышленник сам шлет внутренние заголовки снаружи
    context.Request.Headers.Remove("X-Global-Actor-Id");
    context.Request.Headers.Remove("X-Workspace-Id");
    context.Request.Headers.Remove("X-Impersonator-Id");
    context.Request.Headers.Remove("X-User-Roles");

    // 2. Извлечение Phantom Token из HttpOnly Cookie
    if (context.Request.Cookies.TryGetValue("steos_session", out string sessionId))
    {
        // 3. Получение контекста сессии из Redis (O(1))
        string sessionJson = await _redisDatabase.StringGetAsync($"steos:sess:{sessionId}");
        
        if (!string.IsNullOrEmpty(sessionJson))
        {
            var sessionData = JsonSerializer.Deserialize<SessionDataDto>(sessionJson);

            // 4. Инъекция доверенных бизнес-заголовков (Header Injection)
            // Внутренние сервисы будут доверять этим заголовкам на 100%
            
            // Глобальный идентификатор актора (Кто выполняет действие)
            context.Request.Headers.Add("X-Global-Actor-Id", sessionData.GlobalSteosId.ToString());
            
            // Роли пользователя в виде массива JSON (Для Policy Decision Point внутри микросервисов)
            context.Request.Headers.Add("X-User-Roles", JsonSerializer.Serialize(sessionData.Roles));

            // Инъекция текущего рабочего пространства (Context Routing)
            if (sessionData.ActiveWorkspaceId.HasValue)
            {
                context.Request.Headers.Add("X-Workspace-Id", sessionData.ActiveWorkspaceId.Value.ToString());
            }

            // Обработка имперсонации ("Режим Бога")
            if (sessionData.IsImpersonated && sessionData.ImpersonatorSteosId.HasValue)
            {
                // Для бизнес-логики (Task, CRM) актор - это GlobalSteosId (клиент).
                // Но для внутреннего аудита мы передаем реальное лицо, стоящее за пультом.
                context.Request.Headers.Add("X-Impersonator-Id", sessionData.ImpersonatorSteosId.Value.ToString());
            }

            // Флаг гостевой сессии
            if (sessionData.IsGuest)
            {
                context.Request.Headers.Add("X-Is-Guest-Session", "true");
            }
        }
    }

    // 5. Передача управления дальше (Проксирование во внутреннюю сеть)
    // Либо к локальным контроллерам, либо через HttpClient Proxy (YARP) к другим микросервисам
    await next(context);
}
```
