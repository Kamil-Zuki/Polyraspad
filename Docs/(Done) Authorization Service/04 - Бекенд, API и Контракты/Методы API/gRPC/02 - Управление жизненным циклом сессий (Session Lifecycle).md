# Введение

Методы данной группы обеспечивают динамическое управление жизненным циклом сессий, позволяя администраторам, системным процессам и самим пользователям управлять состоянием авторизации в реальном времени. Здесь собраны методы для отзыва сессий (Logout), переключения рабочих пространств, фонового обновления прав пользователя (без разлогина) и инициализации/завершения режима бесшовной имперсонации (God Mode).

Эти методы являются мутирующими (меняют состояние в Redis/PostgreSQL) и строго логируются в WORM-журнал аудита для соответствия Enterprise-стандартам безопасности.

Важно: любые упоминаемые ниже `Workspace Service`, `Billing Service`, `Helpdesk`, `SIEM` и иные соседние сервисы или системы являются отдельными микросервисами или внешними контурами. Они не реализуются в рамках данной документации `Authorization Service`; здесь описывается только поведение и контракты самого `Authorization Service`.

<span id="grpc-RevokeSession"></span>

# SR-AUTH-SM-06: Принудительный отзыв сессии: RevokeSession

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-06: API Управления Локальными Сессиями]]

Метод позволяет завершить конкретную сессию по её уникальному идентификатору (`session_id`). Может быть инициирован самим пользователем из раздела "Мои устройства" (разлогинить старый телефон), либо администратором/ИБ-системой при подозрении на взлом.

| Сигнатура | `rpc RevokeSession(RevokeSessionRequest) returns (RevokeSessionResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `RevokeSessionRequest` (ID сессии, причина отзыва `reasonCode`, комментарий) |
| **Сообщение ответа** | `RevokeSessionResponse` (флаг успешного отзыва) |

## Логика обработки запроса

1. Проверить, что вызывающий субъект имеет право отзывать указанную сессию (как владелец, администратор или ИБ-оператор).
2. Найти каноническую запись сессии в `authorized_sessions` и, если она еще жива, извлечь ее hot-state из Redis.
3. Удалить локальную Phantom-сессию из Redis и обновить связанные индексы активных сессий, чтобы доступ прекратился немедленно.
4. Отозвать связанную глобальную доверенность этой сессии, если для нее хранились OIDC-артефакты или зашифрованный `refresh_token` (очистить или пометить их недействительными в server-side хранилище).
5. Пометить запись в `authorized_sessions` как `revoked`, указав время завершения, `reason_code` и инициатора.
6. Записать событие `SESSION_REVOKED` в `access_audit_logs` с необходимым макроконтекстом для расследования.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не указан ID сессии или обязательная причина отзыва. |
| **NOT_FOUND** | Сессия с таким ID не существует или уже завершена. |

<span id="grpc-RevokeAllUserSessions"></span>

# SR-AUTH-OI-04: Глобальный логаут: RevokeAllUserSessions

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/02 - Инфраструктура OIDC и Интеграция - OIDC Infrastructure#SR-AUTH-OI-04: OIDC Back-Channel Logout (via RabbitMQ)]]

Используется при смене пароля пользователем, при получении сообщения `OIDC Back-Channel Logout` через `RabbitMQ` от `STEOS ID`, либо при блокировке аккаунта. Метод мгновенно уничтожает все активные локальные сессии конкретного пользователя на данной инсталляции платформы.

| Сигнатура | `rpc RevokeAllUserSessions(RevokeAllSessionsRequest) returns (RevokeAllSessionsResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `RevokeAllSessionsRequest` (Global User ID, причина глобального логаута) |
| **Сообщение ответа** | `RevokeAllSessionsResponse` (количество успешно завершенных сессий) |

## Логика обработки запроса

1. Получить `global_steos_id` и причину глобального отзыва от внутреннего процесса, административного сценария или обработчика сообщения `RabbitMQ`.
2. Собрать полный список всех активных локальных сессий пользователя на данной инсталляции по внутреннему индексу `user -> sessions`.
3. Удалить все найденные Phantom-сессии и их производные ключи из Redis, чтобы любая старая Cookie немедленно перестала работать.
4. Пометить все активные записи пользователя в `authorized_sessions` как `revoked`, зафиксировав причину и время завершения.
5. Записать событие глобального разлогина в локальный WORM-аудит, сохранив идемпотентность повторного вызова.
6. При необходимости опубликовать внутреннее событие в real-time контур самого `Authorization Service`, чтобы подключенные клиенты быстрее получили сигнал об отзыве.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не указан `user_id`. |
| **INTERNAL** | Ошибка при массовом обновлении базы данных PostgreSQL. |

# SR-AUTH-SM-06: Логаут с других устройств: TerminateOtherSessions

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-06: API Управления Локальными Сессиями]]

Специфичный метод безопасности (часто востребованный в FinTech), позволяющий пользователю завершить все свои сессии, *кроме* той, с которой был инициирован данный вызов. Повышает безопасность при подозрении, что пароль был скомпрометирован или забыт на публичном компьютере.

| Сигнатура | `rpc TerminateOtherSessions(TerminateOtherRequest) returns (TerminateOtherResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `TerminateOtherRequest` (Global User ID, ID текущей сессии для сохранения) |
| **Сообщение ответа** | `TerminateOtherResponse` (количество завершенных сессий) |

## Логика обработки запроса

1. Проверить, что `current_session_id` действительно принадлежит вызывающему пользователю и находится в активном состоянии.
2. Собрать все остальные активные сессии пользователя, исключив текущую.
3. Удалить найденные server-side сессии из Redis и обновить связанные служебные индексы.
4. Пометить в `authorized_sessions` как `revoked` только записи для остальных устройств, сохранив текущую сессию активной.
5. Записать событие `OTHER_SESSIONS_TERMINATED` в `access_audit_logs`, указав инициатора и количество завершенных сессий.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не указаны `user_id` или `current_session_id`. |
| **FAILED_PRECONDITION** | Переданная текущая сессия неактивна или не принадлежит пользователю. |

# SR-AUTH-SM-02: Принудительное переключение Workspace: ForceContextSwitch

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-02: Server-Side Context Routing]]

Метод меняет текущий активный бизнес-контекст пользователя. Применяется, когда пользователь переходит из личного пространства в корпоративное (через UI), либо когда его удаляют из корпоративного пространства (административно) и система должна перекинуть его обратно в личное.

| Сигнатура | `rpc ForceContextSwitch(ContextSwitchRequest) returns (ContextSwitchResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ContextSwitchRequest` (ID сессии, ID целевого Workspace) |
| **Сообщение ответа** | `ContextSwitchResponse` (обновлённый `SessionContext`) |

## Логика обработки запроса

1. Проверить, что переданная сессия существует, не отозвана и содержит текущий `global_steos_id`.
2. Подтвердить через `Workspace Service`, что пользователь является участником целевого Workspace и может в него переключиться (`Workspace Service` остается отдельным микросервисом вне рамок этой документации).
3. Рассчитать новый `active_workspace_id`, роли и связанные бизнес-атрибуты именно для целевого Workspace.
4. Синхронно обновить server-side контекст: сначала в персистентном слое `session_contexts`/`authorized_sessions`, затем в Redis-контексте этой сессии.
5. Вернуть обновлённый `SessionContext`, который станет источником новых внутренних заголовков на следующем запросе.
6. Записать событие `CONTEXT_SWITCHED` в `access_audit_logs`, указав старый и новый Workspace.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не указана сессия или целевой Workspace. |
| **PERMISSION_DENIED** | Пользователь не является участником (Member) запрашиваемого пространства или заблокирован в нём. |

<span id="grpc-UpdateSessionContext"></span>

# SR-AUTH-SM-10: Динамическое обновление контекста: UpdateSessionContext

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-10: Горячее обновление контекста сессии]]

Enterprise-механизм для обновления авторизационного контекста "на лету" без принудительного разлогина пользователя. Вызывается фоновыми процессами, например после изменения роли, лицензии или внешнего бизнес-события от отдельного сервиса вроде `Billing Service`.

| Сигнатура | `rpc UpdateSessionContext(UpdateContextRequest) returns (UpdateContextResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `UpdateContextRequest` (Global User ID, ID Workspace, список новых ролей/флагов) |
| **Сообщение ответа** | `UpdateContextResponse` (флаг успешного обновления кэша всех активных сессий юзера) |

## Логика обработки запроса

1. Получить идентификатор пользователя, целевой Workspace и новый канонический набор ролей/атрибутов.
2. Найти все активные локальные сессии пользователя или все контексты, относящиеся к указанному Workspace.
3. Пересобрать `SessionContext` для каждой затронутой сессии с новыми ролями, лицензиями, feature flags и иными business-атрибутами.
4. Атомарно обновить новый server-side payload в Redis и, при наличии отдельной таблицы контекстов, синхронно зафиксировать его в постоянном хранилище.
5. При использовании `WebSocket Backplane` опубликовать событие `context_updated` в real-time контур самого `Authorization Service`.
6. Считать изменение примененным без перевыдачи Cookie: следующий запрос пользователя уже пройдет через `ValidateSession` с новым контекстом.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | У пользователя нет активных сессий в данном пространстве (обновление произойдет при следующем логине). |

# SR-AUTH-SM-05: Старт режима имперсонации (God Mode): StartImpersonation

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-05: Бесшовная Имперсонация (God Mode)]]

Высококритичный метод для инженеров поддержки (Tier 3) и администраторов платформы. Позволяет "войти" в аккаунт или Workspace клиента для диагностики проблемы без запроса пароля, создавая двойной контекст безопасности.

| Сигнатура | `rpc StartImpersonation(ImpersonationRequest) returns (ImpersonationResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ImpersonationRequest` (ID саппорта, ID клиента/Workspace, номер тикета в Helpdesk) |
| **Сообщение ответа** | `ImpersonationResponse` (специальный `GodModeContext` для UI саппорта) |

## Логика обработки запроса

1. Проверить, что сотрудник поддержки уже авторизован под собственной учетной записью и действительно имеет право инициировать имперсонацию.
2. Проверить обязательное основание доступа, например номер тикета (`Helpdesk` остается отдельной системой и не реализуется в рамках этой документации).
3. Определить, под каким пользователем и/или в каком Workspace допустимо создать имперсонационный контекст, и применить ограничения политики безопасности.
4. Создать отдельную server-side имперсонационную сессию в `authorized_sessions`, где `global_steos_id` указывает на целевого пользователя, а `impersonator_steos_id` хранит ID реального сотрудника поддержки.
5. Сформировать и записать в Redis отдельный `GodModeContext`, содержащий оба идентификатора и sandbox-ограничения.
6. Записать событие `IMPERSONATION_STARTED` в `access_audit_logs`; при необходимости отправить дополнительный сигнал во внешний контур мониторинга.
7. Вернуть сообщение с новым имперсонационным контекстом и идентификатор новой server-side сессии для дальнейшей работы в режиме God Mode.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **PERMISSION_DENIED** | У саппорта нет прав на имперсонацию (или попытка войти к другому саппорту). |
| **INVALID_ARGUMENT** | Не указан номер тикета для обоснования доступа. |

<span id="grpc-StopImpersonation"></span>

# SR-AUTH-SM-05: Завершение режима имперсонации: StopImpersonation

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-05: Бесшовная Имперсонация (God Mode)]]

Возврат сессии сотрудника поддержки в нормальный режим работы. Уничтожает двойной контекст `GodModeContext` и возвращает стандартный `SessionContext` саппорта.

| Сигнатура | `rpc StopImpersonation(StopImpersonationRequest) returns (StopImpersonationResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `StopImpersonationRequest` (ID сессии саппорта, текстовый отчет о результатах) |
| **Сообщение ответа** | `StopImpersonationResponse` (оригинальный контекст саппорта) |

## Логика обработки запроса

1. Проверить, что переданная сессия действительно является активной имперсонационной сессией, а не обычной пользовательской.
2. Извлечь из текущего payload `impersonator_steos_id`, целевого пользователя и другие поля, необходимые для корректного завершения режима.
3. Пометить специальную God-session завершенной в `authorized_sessions` и удалить ее из Redis, чтобы дальнейшие запросы больше не шли под маской клиента.
4. Восстановить операторский `SessionContext`, если базовая сессия сотрудника поддержки все еще существует; иначе потребовать отдельное восстановление операторского контекста вне данного RPC.
5. Записать событие `IMPERSONATION_ENDED` в `access_audit_logs`, приложив итоговый отчет или краткий результат диагностики, если он передан.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **FAILED_PRECONDITION** | Сессия не находится в режиме имперсонации. |

# SR-AUTH-SM-06: Список активных сессий: ListActiveSessions

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-06: API Управления Локальными Сессиями]]

Метод возвращает все активные локальные сессии текущего пользователя для экрана «Мои устройства» (паритет REST `GET /sessions`). Имена полей в JSON для BFF — [02 - Управление сессиями (DTO)](../DTO/02%20-%20Управление%20сессиями%20(Session%20Management).md).

| Сигнатура | `rpc ListActiveSessions(ListActiveSessionsRequest) returns (ListActiveSessionsResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ListActiveSessionsRequest` (глобальный ID пользователя из контекста вызова, опционально фильтр по workspace) |
| **Сообщение ответа** | `ListActiveSessionsResponse` (`repeated SessionSummary`, отметка текущей сессии) |

## Логика обработки запроса

1. Проверить полномочия: только владелец аккаунта или администратор с явным scope может запрашивать список сессий пользователя.
2. Собрать активные записи из `authorized_sessions` и индекса в Redis `user -> session_ids` для данного `global_steos_id`.
3. Обогатить каждую запись метаданными (IP, User-Agent, GeoIP-строка, время последней активности) из персистентного слоя или кэша.
4. Пометить сессию, совпадающую с `current_session_id` из контекста вызова, как текущую.
5. Вернуть пагинируемый или полный список без раскрытия секретов токенов.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **PERMISSION_DENIED** | Попытка запросить чужие сессии без прав администратора. |

# SR-AUTH-SM-09: Продление сессии: KeepSessionAlive

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management]] (TTL и активность SPA; паритет REST `POST /sessions/keep-alive`)

Периодический вызов от BFF/клиента для продления TTL записи Phantom-сессии в Redis без повторного OIDC-логина. Поля запроса в JSON — [02 - DTO](../DTO/02%20-%20Управление%20сессиями%20(Session%20Management).md).

| Сигнатура             | `rpc KeepSessionAlive(KeepSessionAliveRequest) returns (KeepSessionAliveResponse)`            |
| :-------------------- | :-------------------------------------------------------------------------------------------- |
| **Сообщение запроса** | `KeepSessionAliveRequest` (идентификатор сессии, опционально сигнал активности)               |
| **Сообщение ответа**  | `KeepSessionAliveResponse` (актуализированный `SessionContext` или укороченное подтверждение) |

## Логика обработки запроса

1. Проверить, что сессия существует и не отозвана.
2. Обновить `expires_at` в Redis и при необходимости в `authorized_sessions` (sliding window).
3. При политике «тихого обновления» OIDC-токенов инициировать фоновый `Silent Refresh` в модуле OIDC: исходящие запросы к **STEOS ID** выполняются по стандартным HTTPS-эндпоинтам OAuth/OIDC провайдера (не через gRPC между внутренними микросервисами платформы).
4. Вернуть обновлённый контекст.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | Сессия не найдена или истекла. |

# SR-AUTH-SM-08: Доверенные устройства: ListTrustedDevices / RememberTrustedDevice / RemoveTrustedDevice

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management]] (паритет REST `/devices/trusted`)

Три Unary-RPC для белого списка устройств пользователя. Хранение: таблица/ключи в PostgreSQL и Redis, связь с `device_fingerprint`. JSON-форма для BFF — [02 - Управление сессиями (DTO)](../DTO/02%20-%20Управление%20сессиями%20(Session%20Management).md).

| Сигнатура | `rpc ListTrustedDevices(ListTrustedDevicesRequest) returns (ListTrustedDevicesResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ListTrustedDevicesRequest` (global user id из контекста) |
| **Сообщение ответа** | `ListTrustedDevicesResponse` (`repeated TrustedDevice`) |

| Сигнатура | `rpc RememberTrustedDevice(RememberTrustedDeviceRequest) returns (RememberTrustedDeviceResponse)` |
| :--- | :--- |
| **Сообщение запроса** | Отпечаток устройства, имя устройства (опционально) |
| **Сообщение ответа** | Успех операции |

| Сигнатура | `rpc RemoveTrustedDevice(RemoveTrustedDeviceRequest) returns (RemoveTrustedDeviceResponse)` |
| :--- | :--- |
| **Сообщение запроса** | Идентификатор записи доверенного устройства |
| **Сообщение ответа** | Успех операции |

## Логика обработки запроса

1. Для списка: выбрать все записи доверенных устройств пользователя из персистентного хранилища Auth.
2. Для добавления: проверить текущую сессию, сохранить fingerprint и метаданные; при превышении лимита доверенных устройств вернуть `RESOURCE_EXHAUSTED`.
3. Для удаления: удалить запись по ID, принадлежащему пользователю; при следующем входе с этого устройства потребуется усиленная верификация (политика Risk Score).
4. Зафиксировать значимые изменения в WORM-аудите при политике комплаенса.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | Удаляемое устройство не найдено или чужое. |
| **RESOURCE_EXHAUSTED** | Превышен лимит доверенных устройств. |
