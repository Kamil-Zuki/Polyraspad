# Введение

Методы данной группы предоставляют внутренним микросервисам (например, Platform Service, Billing Service, API Gateway) интерфейсы для взаимодействия с системой локальной безопасности Authorization Service.

Группа покрывает три критических аспекта Enterprise-архитектуры:
1. **Динамическая защита периметра (Local Firewall & Rate Limiting):** Быстрое реагирование на аномалии (Brute Force, DDoS, Session Hijacking) путем блокировки нарушителей на уровне кэша до того, как они достигнут бизнес-логики.
2. **Контроль Гостевых Квот (Guest Quotas):** Предварительная проверка и списание лимитов (`CheckGuestQuota` / `ConsumeGuestQuota`).
3. **Полный жизненный цикл гостевой сессии (SR-AUTH-GQ-01…04):** Инициализация гостя, статус лимитов, конвертация после логина и слияние данных — для паритета REST `/guests/*` при вызове BFF через gRPC.

Важно: любые упоминаемые ниже `Platform Service`, `Billing Service`, `Workspace Service`, `AI Service`, `Payment Service`, `Integration Service`, `API Gateway` и другие внешние участники являются отдельными микросервисами или инфраструктурными компонентами. Они не реализуются в рамках данной документации `Authorization Service`; здесь фиксируются только контракты и ожидаемое поведение `Authorization Service` при взаимодействии с ними. Вызовы между нашими микросервисами — по **gRPC**; асинхронные уведомления — через **RabbitMQ**, где это указано явно.

**Важно для SR-AUTH-SQ-02:** методы `CheckGuestQuota` и `ConsumeGuestQuota` в рамках gRPC являются контрактной декомпозицией одного исходного требования [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-02: Гостевые Лимиты (Guest Feature Quotas)]]. Это разделение нужно для явного разведения предварительной проверки и фактического списания.

# SR-AUTH-SQ-02: Проверка гостевой квоты: CheckGuestQuota

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-02: Гостевые Лимиты (Guest Feature Quotas)]]

Метод используется отдельными бизнес-сервисами перед выполнением дорогостоящей операции для неавторизованного пользователя. Если в сценарии фигурирует `AI Service` или `Platform Service`, это внешние микросервисы-клиенты данного RPC, а не часть реализации `Authorization Service`. Метод позволяет проверить, не исчерпал ли аноним (гость) свой лимит бесплатных действий на платформе.

| Сигнатура | `rpc CheckGuestQuota(CheckQuotaRequest) returns (CheckQuotaResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `CheckQuotaRequest` (Guest Session ID, тип запрашиваемой квоты, требуемое количество) |
| **Сообщение ответа** | `CheckQuotaResponse` (разрешено ли действие, текущий остаток `remaining`) |

## Логика обработки запроса

1. Определить канонический идентификатор гостя по `guest_session_id`, fingerprint и другим server-side признакам, чтобы лимит нельзя было обойти простой заменой Cookie.
2. Поднять текущее состояние расхода по нужной фиче из Redis и/или локального счетчика квот.
3. Сверить этот расход с политикой лимитов и, при необходимости, с дополнительными бизнес-ограничениями внешнего `Platform Service`, если он владеет правилом.
4. Принять решение, допустима ли операция в текущем окне, не выполняя окончательное списание именно в этом RPC.
5. Вернуть вызывающему сервису флаг разрешения, рассчитанный остаток и, при необходимости, признак необходимости регистрации.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | Указанная гостевая сессия не найдена или уже истекла (Expired). |
| **RESOURCE_EXHAUSTED** | (Опционально) Квота исчерпана (может возвращаться как статус `OK` с `is_allowed = false`). |

# SR-AUTH-SQ-02: Списание гостевой квоты: ConsumeGuestQuota

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-02: Гостевые Лимиты (Guest Feature Quotas)]]

Вызывается отдельным бизнес-микросервисом *после* успешного завершения действия для фиксации фактического расхода гостевых ресурсов. Если в конкретном продукте инициатором является `Platform Service` или иной доменный сервис, он остается внешним по отношению к `Authorization Service`.

| Сигнатура | `rpc ConsumeGuestQuota(ConsumeQuotaRequest) returns (ConsumeQuotaResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ConsumeQuotaRequest` (Guest Session ID, тип квоты, списанное количество) |
| **Сообщение ответа** | `ConsumeQuotaResponse` (новый остаток `remaining` после списания) |

## Логика обработки запроса

1. Повторно определить канонический идентификатор гостя по сессии и fingerprint, чтобы списание всегда относилось к одному и тому же субъекту.
2. Выполнить атомарное списание подтвержденного расхода в локальном счетчике квот (`INCRBY`, `HINCRBY` или эквивалентная транзакционная операция).
3. После списания пересчитать остаток и проверить, не пересек ли гость лимит из-за гонки параллельных запросов.
4. Если лимит исчерпан или зафиксирован абуз, инициировать локальные защитные меры по правилам `Authorization Service`.
5. Вернуть вызывающему сервису канонический результат списания и новый остаток.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | Сессия гостя не найдена. |

# SR-AUTH-SQ-03: Добавление в черный список: BanIpAddress / BanDeviceFingerprint

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-03: Локальная блокировка (Local Firewall/Ban)]]

Два идентичных по логике метода, позволяющие ИБ-системам (или администраторам через панель) мгновенно заблокировать любой трафик с определенного IP-адреса, подсети (CIDR) или аппаратного отпечатка браузера (Device Fingerprint). Применяется как реакция на Brute Force, сканирование уязвимостей или Mass-Registration (абуз гостевых сессий).

| Сигнатура | `rpc BanIpAddress(BanRequest) returns (BanResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `BanRequest` (блокируемое значение `target`, время блокировки `ttl_seconds`, причина `reason`) |
| **Сообщение ответа** | `BanResponse` (статус успеха, ID записи в Blocklist) |

## Логика обработки запроса

1. Проверить формат IP/CIDR или fingerprint и убедиться, что указана причина из нормализованного справочника локальных инцидентов.
2. Создать запись локального бана в горячем deny-list хранилище с TTL, причиной и метаданными инициатора.
3. Найти активные сессии, связанные с заблокированным субъектом, если такие сессии уже существуют.
4. Отозвать эти Phantom-сессии или пометить их на немедленный отзыв, чтобы вредоносный субъект не продолжал пользоваться уже выданным доступом.
5. Записать событие применения локальной блокировки в `access_audit_logs`.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Некорректный формат IP/CIDR или отсутствует обязательная причина блокировки. |

# SR-AUTH-SQ-05: Снятие блокировки (Разбан): UnbanSubject

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-05: Снятие локальной блокировки (Unban)]]

Ручное удаление IP-адреса или Device Fingerprint из черного списка. Используется инженерами техподдержки при ложноположительных срабатываниях автоматической системы защиты (False Positives).

| Сигнатура | `rpc UnbanSubject(UnbanRequest) returns (UnbanResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `UnbanRequest` (разблокируемое значение `target`, причина разблокировки) |
| **Сообщение ответа** | `UnbanResponse` (статус успеха) |

## Логика обработки запроса

1. Проверить, что вызов выполняет уполномоченный администратор или ИБ-оператор.
2. Убедиться, что указанный IP, CIDR или fingerprint действительно находится в локальном deny-list.
3. Удалить запись из соответствующего blocklist в горячем хранилище.
4. Записать событие снятия блокировки в `access_audit_logs`, сохранив причину, инициатора и связь с исходным инцидентом.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | Указанный субъект не находится в черном списке. |

<span id="grpc-CheckBanStatus"></span>

# SR-AUTH-SQ-03: Проверка статуса блокировки: CheckBanStatus

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-03: Локальная блокировка (Local Firewall/Ban)]]

Сверхбыстрый (до 1 мс) внутренний метод, вызываемый API Gateway (Envoy/BFF) перед передачей HTTP-запроса на валидацию сессии. Если IP-адрес или Fingerprint находится в бане, запрос отбрасывается на самом краю (Edge), экономя ресурсы всей Платформы.

| Сигнатура | `rpc CheckBanStatus(CheckBanRequest) returns (CheckBanResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `CheckBanRequest` (IP-адрес `ip`, Fingerprint `fp`) |
| **Сообщение ответа** | `CheckBanResponse` (флаг `is_banned`, причина блокировки для логирования) |

## Логика обработки запроса

1. Получить IP, fingerprint и другие сетевые признаки субъекта из входного запроса.
2. Выполнить O(1) lookup в локальном deny-list для IP, подсети и/или fingerprint.
3. Если субъект заблокирован, вернуть причину, срок действия и технические метаданные, достаточные для раннего обрыва запроса на edge-контуре.
4. В штатном сценарии завершить проверку без обращения к PostgreSQL, сохранив этот RPC как быстрый предохранитель раннего отсечения вредоносного трафика.

## Статус-коды gRPC при ошибках

*Отсутствуют. Метод всегда возвращает ответ (в худшем случае `is_banned = false`, если Redis временно недоступен).*

# SR-AUTH-SQ-06: Репортинг аномалий: ReportSuspiciousActivity

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-06: Репортинг подозрительной активности]]

Внутренний RPC для внешних по отношению к `Authorization Service` бизнес-микросервисов. Если, например, `Payment Service` фиксирует серию мошеннических действий, а `Integration Service` видит спам одинаковыми запросами, они вызывают этот метод, передавая контекст нарушителя. Упомянутые сервисы являются отдельными микросервисами и не реализуются в рамках данного документа.

| Сигнатура | `rpc ReportSuspiciousActivity(ReportSuspiciousRequest) returns (ReportSuspiciousResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ReportSuspiciousRequest` (источник `source_service`, уровень угрозы `severity`, метаданные нарушителя `ip/session/fp`) |
| **Сообщение ответа** | `ReportSuspiciousResponse` (принятое решение `action_taken`: IGNORED, THROTTLED, BANNED) |

## Логика обработки запроса

1. Проверить, что вызывающий сервис действительно имеет право репортить инциденты, а входной payload содержит достаточный технический контекст.
2. Нормализовать IP, session, fingerprint и actor, чтобы несколько сигналов от разных сервисов коррелировались на одного и того же нарушителя.
3. Обновить краткоживущий счетчик риска в локальном hot-state хранилище.
4. Оценить локальные пороги и выбрать действие: игнорировать, включить throttling, отозвать сессию, забанить субъект или создать alert.
5. Вернуть вызывающему сервису нормализованный `action_taken` для дальнейшей телеметрии и обработки.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Неполные метаданные нарушителя (необходим IP, Session или Fingerprint). |

# SR-AUTH-SQ-04: Получение статуса Rate Limit: GetRateLimitStatus

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/03 - Защита Периметра и Гостевые Квоты - Security Quotas#SR-AUTH-SQ-04: Rate Limiting & API Throttling]]

Метод позволяет API Gateway (или клиенту напрямую) узнать текущее состояние "корзины токенов" (Token Bucket) для конкретного пользователя или IP-адреса. Используется для формирования стандартных HTTP-заголовков `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` в ответах BFF, помогая клиентам избегать статуса HTTP 429 (Too Many Requests).

| Сигнатура | `rpc GetRateLimitStatus(GetRateLimitRequest) returns (GetRateLimitResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `GetRateLimitRequest` (идентификатор субъекта: IP или Session ID, идентификатор группы лимитов `endpointGroup`) |
| **Сообщение ответа** | `GetRateLimitResponse` (остаток `remaining`, максимальный `limit`, время до сброса `reset_in_seconds`) |

## Логика обработки запроса

1. Рассчитать канонический bucket лимита по субъекту и `endpointGroup`.
2. Прочитать из Redis текущее состояние bucket: остаток, размер лимита и служебные метки времени.
3. Вычислить время до следующего пополнения или полного сброса лимита.
4. Вернуть ответ в формате, пригодном для трансляции в `X-RateLimit-*` заголовки на стороне gateway-клиента.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **NOT_FOUND** | Для указанной группы эндпоинтов (`endpointGroup`) лимиты не настроены. |

# SR-AUTH-GQ-02: Статус гостя: GetGuestAccessStatus

## Общая информация

Возвращает остатки квот и состояние гостевой сессии (паритет REST `GET /guests/status`). Опирается на `CheckGuestQuota` / данные Redis и БД.

| Сигнатура | `rpc GetGuestAccessStatus(GetGuestAccessStatusRequest) returns (GetGuestAccessStatusResponse)` |
| :--- | :--- |
| **Сообщение запроса** | Идентификатор гостевой сессии из Cookie/контекста |

## Логика обработки запроса

1. Разрешить канонический `guest_session_id`.

3. Вернуть сводку для UI демо-режима.

## Общая информация

# SR-AUTH-GQ-04: Слияние данных гостя: MergeGuestData

## Общая информация

Инициирует асинхронное слияние черновиков гостя в постоянные сущности (паритет `POST /guests/merge`). Публикация события для доменных сервисов — в **RabbitMQ** (protobuf `GuestMergeEvent` или согласованная схема envelope); сами **Task Service** / **Storage Service** обрабатывают очередь независимо. Человекочитаемые поля слияния в API шлюза — [04 - DTO](../DTO/04%20-%20Управление%20гостевым%20доступом%20(Guest%20Sessions).md).

| Сигнатура | `rpc MergeGuestData(MergeGuestDataRequest) returns (MergeGuestDataResponse)` |
| :--- | :--- |
| **Сообщение запроса** | Идентификаторы гостя и целевого пользователя, scope слияния |
| **Сообщение ответа** | Идентификатор задачи слияния, статус `ACCEPTED` |

## Логика обработки запроса

1. Проверить права и идемпотентность запроса.
2. Опубликовать сообщение в RabbitMQ (exchange/routing key согласно платформенной конвенции) с payload слияния (см. контракт очереди и [04 - DTO](../DTO/04%20-%20Управление%20гостевым%20доступом%20(Guest%20Sessions).md) для полей, отдаваемых наружу).
3. Вернуть клиенту подтверждение приёма; фактическое слияние выполняется downstream-воркерами.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **UNAVAILABLE** | Брокер сообщений недоступен (повторить запрос позже). |

# SR-AUTH-SQ-03: Просмотр черного списка: QueryBlocklist

## Общая информация

**Источник требования:** локальный файрвол; паритет REST `GET /security/blocklist`. В отличие от `CheckBanStatus` (точечная проверка IP/FP для шлюза), данный метод возвращает **список** записей для административного UI.

| Сигнатура | `rpc QueryBlocklist(QueryBlocklistRequest) returns (QueryBlocklistResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `QueryBlocklistRequest` (фильтры, пагинация) |
| **Сообщение ответа** | `QueryBlocklistResponse` (`repeated BlocklistEntry` — IP или Fingerprint, причина, TTL, активность; JSON-форма — [06 - DTO](../DTO/06%20-%20Аудит%20и%20безопасность%20(Audit%20&%20Security).md) / согласованный раздел REST) |

## Логика обработки запроса

1. Проверить права администратора ИБ.
2. Выполнить запрос к PostgreSQL (`local_suspicious_activities`) с фильтрами и сортировкой по `expires_at` / `created_at`.
3. Не раскрывать внутренние Redis-ключи; отдавать только канонические поля записей.
4. Вернуть пагинированный результат.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
