# Введение

Методы данной группы образуют высоконагруженное ядро микросервиса Authorization Service, обеспечивающее непосредственную защиту периметра Платформы. Эти RPC-вызовы постоянно используются API Gateway (Envoy/BFF) и внутренними сервисами для прозрачного перевода непрозрачных клиентских идентификаторов (Phantom Tokens, One-Time Tickets) в доверенный, строгий бизнес-контекст.

За счет вынесения всей сложности криптографии, кэширования и проверки прав в эту группу, остальные микросервисы (Task, Integration) могут работать в парадигме Zero Trust, просто доверяя HTTP-заголовкам, которые генерируются результатами работы этих методов.

Важно: любые упоминаемые ниже `Task Service`, `Integration Service`, `Storage Service`, WebSocket-шлюзы и иные downstream-компоненты являются отдельными микросервисами или инфраструктурными узлами. Они не реализуются в рамках данной документации `Authorization Service`; здесь описывается только контракт их взаимодействия с `Authorization Service`.

# SR-AUTH-LA-03: Валидация сессии: ValidateSession

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/04 - Локальный Аудит Доступа - Local Access Audit#SR-AUTH-LA-03: Инъекция Трассировки в Downstream (Header Routing)]]

Самый вызываемый метод в системе. API Gateway при каждом входящем HTTP-запросе от клиента вызывает `ValidateSession`, передавая либо значение Cookie (`Phantom Token`), либо контекст для **Personal Access Token** в заголовке `Authorization: Bearer` (см. [04 - Управление доступом и API-ключами](../REST%20API/04%20-%20Управление%20доступом%20и%20API-ключами.md)). Метод проверяет кэш сессий в Redis и/или таблицу `api_keys`, убеждается, что устройство не находится в блокировке, сессия или ключ жизнеспособны, и возвращает сформированный набор HTTP-заголовков (например, `X-Global-User-Id`, `X-Workspace-Id`, `X-User-Roles`).

| Сигнатура | `rpc ValidateSession(ValidateSessionRequest) returns (ValidateSessionResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ValidateSessionRequest` (тип предъявления: Phantom Cookie и/или Bearer PAT, метаданные устройства, IP; для PAT — сырая строка токена для сверки хэша) |
| **Сообщение ответа** | `ValidateSessionResponse` (статус валидации, ID сессии или ключа, мапа HTTP-заголовков) |

## Логика обработки запроса

1. Определить режим аутентификации: **Phantom Cookie** или **Bearer PAT** (должен быть задан ровно один основной механизм на запрос; при отсутствии обоих вернуть `UNAUTHENTICATED`).
2. **Если режим PAT:** вычислить хэш предъявленного токена (SHA-256 или согласованный алгоритм), найти запись в таблице `api_keys` по хэшу; при отсутствии, истечении `expires_at` или отзыве вернуть `UNAUTHENTICATED`. Проверить соответствие запрошенных операций объявленным `scopes` ключа. Обновить `last_used_at` (асинхронно или в той же транзакции). Построить `SessionContext` для владельца ключа (глобальный пользователь, активный Workspace по политике ключа или дефолту). Перейти к шагу проверки периметра (deny-list) и формированию заголовков.
3. **Если режим Phantom Cookie:** проверить, что запрос содержит Phantom Token, IP-адрес и `device_fingerprint`, достаточные для server-side валидации.
4. Найти локальную Phantom-сессию по значению Cookie в Redis (если запись отсутствует, истекла или уже отозвана, вернуть `UNAUTHENTICATED`).
5. Подтвердить, что текущий запрос соответствует сохраненному контексту устройства и не выглядит как попытка Session Hijacking (сравнить IP и Fingerprint; при критичном mismatch инициировать отзыв сессии).
6. Проверить, не находится ли IP или Fingerprint в локальном deny-list, чтобы не пропускать заблокированный трафик дальше.
7. Сформировать канонический server-side контекст из `SessionContext` (включая `global actor`, `active workspace`, роли, признаки гостевого режима или имперсонации и trace-метаданные).
8. Вернуть набор доверенных внутренних заголовков для downstream-маршрутизации, подразумевая, что gateway-контрагент обязан отбросить все одноименные клиентские `X-Global-*`, `X-Workspace-*` и `X-Impersonator-*` заголовки.
9. Если TTL локальной сессии подходит к порогу keep-alive или `Silent Refresh`, дополнительно выставить технический признак необходимости фонового обновления (для Cookie-сессий; для PAT не применяется).

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Некорректно сформированный запрос (нет токена или IP). |
| **UNAUTHENTICATED** | Сессия не найдена, истекла или была принудительно отозвана (Revoked). |
| **PERMISSION_DENIED** | Сработала защита Anti-Hijacking или IP в черном списке (Fail2Ban). |
| **INTERNAL** | Потеря связи с кластером Redis. |

# SR-AUTH-OT-01: Выпуск одноразового билета: IssueTicket

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management]] (одноразовые билеты).

Метод создаёт короткоживущий одноразовый билет в Redis с привязкой к `intent` и опционально к `resource_id`. Используется BFF перед выдачей клиенту ссылки на скачивание или перед `BuildFileDownloadUrl` / `BuildWsConnectUrl`. Погашение — только через `ValidateTicket`.

| Сигнатура | `rpc IssueTicket(IssueTicketRequest) returns (IssueTicketResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `IssueTicketRequest` — `intent`, `resource_id`, `ttl_seconds` (JSON-форма BFF — [05 - Одноразовые билеты (DTO)](../DTO/05%20-%20Одноразовые%20билеты%20(One-Time%20Tickets).md)) |
| **Сообщение ответа** | `IssueTicketResponse` — `ticket_token`, `expires_at` (периметр — тот же [05 - DTO](../DTO/05%20-%20Одноразовые%20билеты%20(One-Time%20Tickets).md)) |

## Логика обработки запроса

1. Проверить, что вызывающий контекст (сессия пользователя или M2M) авторизован для запрошенного `intent` и ресурса.
2. Сгенерировать криптостойкий одноразовый идентификатор билета и сериализовать вложенный `TicketContextPayload` в Redis с TTL (например, 15 секунд); человекочитаемая форма полей — [05 - DTO](../DTO/05%20-%20Одноразовые%20билеты%20(One-Time%20Tickets).md).
3. Вернуть клиенту строку билета (URL-safe); повторной выдачи того же контента без нового вызова не требуется.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не указан `intent` или недопустимая комбинация полей. |
| **PERMISSION_DENIED** | Субъект не имеет права на данный `intent` / ресурс. |

# SR-AUTH-OT-02: Валидация билета: ValidateTicket

## Общая информация

**Источник истины (домен одноразовых билетов):** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-04: Одноразовые билеты (One-Time Tickets)]]. **Код требования в REST и в таблице gRPC** для этой операции — **SR-AUTH-OT-02** (декомпозиция SM-04; см. [[01 - Функциональная спецификация/Возможности сервиса/00 - Общая информация]]). Публичный паритет: `POST /tickets/validate` — [REST 00](../REST%20API/00%20-%20REST%20API%20-%20Общая%20информация.md).

Метод используется целевыми сервисами (например, Storage Service или WebSockets-шлюзом) для обмена одноразового билета (переданного в URL или субпротоколе) на бизнес-контекст. Метод гарантирует, что каждый билет может быть использован строго один раз для строго определенной цели (Intent).

| Сигнатура | `rpc ValidateTicket(ValidateTicketRequest) returns (ValidateTicketResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ValidateTicketRequest` (токен билета, ожидаемый Intent, ID ресурса) |
| **Сообщение ответа** | `ValidateTicketResponse` (результат проверки, объект контекста пользователя) |

## Логика обработки запроса

1. Проверить, что запрос содержит сам ticket, ожидаемый `intent` и, если нужно, идентификатор целевого ресурса.
2. Атомарно прочитать и сразу погасить билет в Redis (`GETDEL` или эквивалентный Lua-скрипт), чтобы он мог быть использован только один раз.
3. Если билет не найден, считать его истекшим, уже использованным или несуществующим и вернуть `UNAUTHENTICATED`.
4. Сверить `intent`, тип канала и идентификатор ресурса с ограничениями, которые были зафиксированы при генерации билета.
5. Восстановить сохраненный business-context пользователя или гостя из `TicketContextPayload`.
6. Вернуть этот контекст вызывающему микросервису, который затем завершает свой внешний сценарий (`WebSocket handshake`, скачивание файла или иной поток).

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Токен билета не предоставлен. |
| **UNAUTHENTICATED** | Билет недействителен, истек (TTL) или уже был погашен. |
| **FAILED_PRECONDITION** | Несовпадение `Intent` или целевого ресурса (Resource ID). |

# SR-AUTH-OT-03: Утилиты URL с билетом: BuildFileDownloadUrl / BuildWsConnectUrl

## Общая информация

**Источник требования:** паритет с REST `POST /tickets/download-url` и `POST /tickets/ws-url`; JSON-обёртки ответов на периметре — [05 - Одноразовые билеты (DTO)](../DTO/05%20-%20Одноразовые%20билеты%20(One-Time%20Tickets).md).

Два Unary-RPC с общим паттерном: внутренний вызов `IssueTicket` с нужным `intent`, затем сборка абсолютного URL (HTTPS или WSS) с query-параметром билета. Вызываются BFF, чтобы не дублировать логику на фронтенде.

**Контракт gRPC:** в ответах — отдельные сообщения protobuf (`BuildFileDownloadUrlResponse`, `BuildWsConnectUrlResponse`) с полем готового URL. Форму JSON на периметре задаёт тот же [05 - Одноразовые билеты (DTO)](../DTO/05%20-%20Одноразовые%20билеты%20(One-Time%20Tickets).md).

<span id="grpc-BuildFileDownloadUrl"></span>

### BuildFileDownloadUrl

| Сигнатура             | `rpc BuildFileDownloadUrl(BuildFileDownloadUrlRequest) returns (BuildFileDownloadUrlResponse)`                 |
| :-------------------- | :------------------------------------------------------------------------------------------------------------- |
| **Сообщение запроса** | `BuildFileDownloadUrlRequest` — идентификатор файла/ресурса, базовый URL хранилища или шаблон, контекст сессии |
| **Сообщение ответа**  | `BuildFileDownloadUrlResponse` — готовая ссылка (семантика полей как в [05 - DTO](../DTO/05%20-%20Одноразовые%20билеты%20(One-Time%20Tickets).md)) |

<span id="grpc-BuildWsConnectUrl"></span>

### BuildWsConnectUrl

| Сигнатура | `rpc BuildWsConnectUrl(BuildWsConnectUrlRequest) returns (BuildWsConnectUrlResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `BuildWsConnectUrlRequest` — идентификатор канала/ресурса, базовый WSS endpoint |
| **Сообщение ответа** | `BuildWsConnectUrlResponse` — готовая WSS-ссылка (семантика полей как в [05 - DTO](../DTO/05%20-%20Одноразовые%20билеты%20(One-Time%20Tickets).md)) |

## Логика обработки запроса

1. Убедиться, что субъект имеет право на скачивание файла или открытие сокета для указанного ресурса.
2. Вызвать внутреннюю логику `IssueTicket` с `intent`, соответствующим сценарию (`DOWNLOAD_ATTACHMENT` или `WEBSOCKET_INIT`).
3. Сконкатенировать базовый URL платформы с query-параметром билета (формат согласовать с API Gateway и Storage/WebSocket-шлюзом).
4. Вернуть готовую строку URL; билет остаётся одноразовым и короткоживущим.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не задан базовый URL или идентификатор ресурса. |
| **PERMISSION_DENIED** | Нет доступа к файлу или каналу. |

# SR-AUTH-SM-06: Запрос полного контекста: GetSessionContext

## Общая информация

**Источник истины:** [[01 - Функциональная спецификация/Возможности сервиса/01 - Управление Сессиями и Контекстом - Session Management#SR-AUTH-SM-06: API Управления Локальными Сессиями]] (тот же код, что у REST `GET /sessions/me` в [REST 00](../REST%20API/00%20-%20REST%20API%20-%20Общая%20информация.md)). Инъекция заголовков при обычных запросах остаётся отдельной операцией `ValidateSession` (**SR-AUTH-LA-03**).

Позволяет внутренним микросервисам и BFF запросить полную структуру данных о текущем сеансе (или пользователе), если инъекции заголовков через API Gateway оказалось недостаточно (например, для сложной фоновой проверки или формирования отчетов).

| Сигнатура | `rpc GetSessionContext(GetContextRequest) returns (GetContextResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `GetContextRequest` (ID сессии, Global User ID или Guest ID) |
| **Сообщение ответа** | `GetContextResponse` (вложенный `SessionContext`, список текущих ролей и Workspaces; JSON — [02 - DTO](../DTO/02%20-%20Управление%20сессиями%20(Session%20Management).md) / согласованный раздел) |

## Логика обработки запроса

1. Проверить, что в запросе передан хотя бы один критерий поиска: `session_id`, `global user id` или иной допустимый идентификатор контекста.
2. Попытаться найти актуальный `SessionContext` в Redis как в основном источнике hot-state.
3. Если в Redis записи нет, восстановить последнее известное состояние из PostgreSQL и связанных таблиц контекста.
4. Нормализовать контекст в единую server-side структуру, включая роли, `active workspace` и признаки `God Mode`, если они активны.
5. Вернуть полную структуру контекста вызывающему внутреннему сервису для дальнейшей авторизации или аналитики.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Не указаны критерии поиска (ни session_id, ни user_id). |
| **NOT_FOUND** | Контекст для указанного идентификатора не найден (ни в кэше, ни в БД). |

# SR-AUTH-AC-01: Проверка прав: CheckPermission

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/05 - Локальная Авторизация и Политики Доступа - Access Control#SR-AUTH-AC-01: Гранулярная проверка прав (Permission Check)]]

Метод реализует концепцию делегирования авторизации (Policy Enforcement Point). Вместо того чтобы каждый микросервис хранил у себя логику RBAC (Role-Based Access Control) или ABAC (Attribute-Based Access Control), он запрашивает разрешение у Auth Service. Метод проверяет, есть ли у пользователя (исходя из его ролей в текущем Workspace) право выполнить конкретное действие.

| Сигнатура | `rpc CheckPermission(CheckPermissionRequest) returns (CheckPermissionResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `CheckPermissionRequest` (ID пользователя, ID Workspace, запрашиваемое действие/ресурс) |
| **Сообщение ответа** | `CheckPermissionResponse` (флаг `is_allowed`, причина отказа) |

## Логика обработки запроса

1. Проверить, что запрос содержит субъекта, `workspace`, действие и контекст ресурса, достаточные для расчета политики.
2. Поднять актуальный authorization-context: роли, ownership, feature flags, ограничения сессии и другие атрибуты, влияющие на решение.
3. Собрать единый набор RBAC/ABAC-правил для данного действия, включая прямые назначения, системные роли и локальные deny-ограничения.
4. Вычислить итоговое разрешение для запрошенного действия.
5. Если запрос выполняется в режиме имперсонации или в повышенно рискованном контексте, дополнительно применить sandbox-ограничения и server-side deny-правила.
6. Вернуть булево решение и диагностическую причину отказа, если действие запрещено.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **INVALID_ARGUMENT** | Неверно сформированный запрос ресурса/действия. |
| **INTERNAL** | Ошибка при вычислении графа политик доступа. |
*(Примечание: отказ в доступе возвращается как `is_allowed = false` в самом сообщении `CheckPermissionResponse` со статусом `OK`, а не как gRPC ошибка, чтобы клиент мог логировать причину).*

# SR-AUTH-M2M-01: Проверка межсервисного токена: ValidateM2MToken

## Общая информация

**Источник требования:** [[01 - Функциональная спецификация/Возможности сервиса/06 - Межсервисная Аутентификация и Внутренние Токены - M2M Internal Tokens#SR-AUTH-M2M-01: Валидация межсервисных токенов]]

Метод для валидации подписанных JWT токенов, которые используются для общения сервисов в фоновом режиме (Machine-to-Machine, M2M), когда нет прямого HTTP-запроса от пользователя (например, асинхронный Task Service вызывает Email Service).

| Сигнатура | `rpc ValidateM2MToken(ValidateM2MRequest) returns (ValidateM2MResponse)` |
| :--- | :--- |
| **Сообщение запроса** | `ValidateM2MRequest` (JWT токен, ожидаемый Audience (Aud), требуемые Scope) |
| **Сообщение ответа** | `ValidateM2MResponse` (валидность, извлеченный Payload: Service ID, Scopes) |

## Логика обработки запроса

1. Проверить формат входного JWT и извлечь из него `header` и обязательные claims.
2. Криптографически валидировать подпись токена локальными ключами `Authorization Service` без сетевых вызовов.
3. Проверить временные claims (`exp`, `nbf`) и другие обязательные ограничения срока жизни.
4. Сверить `audience`, `issuer` и требуемые `scope` с ожиданиями вызывающей стороны.
5. Если для данного контура поддерживается отзыв M2M-токенов, дополнительно проверить `jti` по локальному blacklist.
6. Вернуть нормализованный service-context, если токен признан валидным.

## Статус-коды gRPC при ошибках

| Статус-код | Описание ошибки |
| :--- | :--- |
| **UNAUTHENTICATED** | Токен протух, подпись недействительна или имеет неверный формат. |
| **PERMISSION_DENIED** | Несовпадение Audience (токен выдан для другого сервиса) или не хватает Scope. |
