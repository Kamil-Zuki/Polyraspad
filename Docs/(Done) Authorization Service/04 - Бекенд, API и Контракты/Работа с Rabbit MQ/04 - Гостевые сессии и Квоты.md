# Введение

Данный документ описывает механизмы RabbitMQ для работы с концепцией **Гостевых сессий** (бесшовный онбординг, Seamless Onboarding) и интеграции с системами **Квотирования/Биллинга**.

Асинхронные события этой группы критически важны для миграции (Merge) накопленных гостем данных (черновиков, настроек) в профиль полноценного зарегистрированного пользователя (КАР-4), а также для передачи информации о расходе демо-квот во внешние аналитические системы, не нагружая синхронный API авторизации.

# 1. Список событий Гостевых сессий и Квот

Ниже перечислены все асинхронные Publish-операции.

| Метод (SR) | Тип операции | Очередь / Топик | Описание |
| :--- | :--- | :--- | :--- |
| SR-AUTH-GQ-04 | Publish | `platform:events:guest-merged` | Ключевое событие миграции. Оповещение микросервисов: "Анонимный Гость X конвертирован в Пользователя Y". |
| SR-AUTH-GQ-02 | Publish | `platform:events:quota-consumed` | (Опционально) Асинхронная выгрузка метрик потребления ресурсов (API-вызовов, токенов) гостевыми сессиями. |

# Событие: Слияние Гостя (Guest Merged) (SR-AUTH-GQ-04)

## Общая информация

Публикация события при успешной конвертации гостевой сессии (`guestId`, аппаратная привязка) в полноценный аккаунт STEOS ID (`subjectId`). Это происходит при вызове REST API `POST /guests/convert` или после успешного OIDC Callback с флагом `merge_guest_id`.

Микросервисы (Storage, Tasks, CRM), подписанные на этот топик, должны асинхронно перенести все объекты (заметки, файлы), принадлежавшие `guestId`, на новый `subjectId`.

| Тип операции | Publish (Публикация) |
| :--- | :--- |
| **Exchange / Топик** | `platform:events:guests` (Topic) |
| **Routing Key** | `guest.merged` |
| **Очередь** | (Управляется микросервисами-хранилищами: `tasks:guest-merger`, `storage:guest-merger`) |
| **DTO сообщения** | `GuestMergedEventPayload` |

## Параметры сообщения

Содержит маппинг старого и нового идентификаторов.

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **guestId** | string (uuid) | Идентификатор анонимного гостя (hardware-bound). |
| **targetSubjectId** | string (uuid) | Идентификатор зарегистрированного пользователя (IdP sub). |
| **targetWorkspaceId** | string (uuid) | В какой Workspace были перенесены данные. |
| **mergedAt** | integer (timestamp) | Временная метка успешного слияния в БД авторизации. |
| **eventId** | string (uuid) | Уникальный ID события слияния. |

## Логика обработки запроса

*   **Триггер:** Успешный коммит транзакции конвертации гостя в Authorization Service (`POST /guests/convert`). Локально записи гостя помечаются как `MERGED`.
*   **Публикация:** Формируется `GuestMergedEventPayload` и публикуется через Transactional Outbox в Exchange `platform:events:guests`.
*   **Гарантия доставки (Outbox):** Событие обязано быть доставлено `At-Least-Once` ко всем бизнес-сервисам, чтобы не потерять работу, проделанную гостем.
*   **Реакция потребителей:** Сервисы `Tasks`, `Storage`, получив событие:
    1. Ищут все записи `WHERE owner_id = guestId`.
    2. Выполняют `UPDATE ... SET owner_id = targetSubjectId`.
    3. (Опционально) шлют ответное событие `guest-merge-completed` (через RabbitMQ) или WebSocket сигнал на UI клиента об успешном окончании фонового переноса (см. Socket API `guest_merged`).

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Брокер сообщений RabbitMQ недоступен во время конвертации. REST API `POST /guests/convert` все равно успешно вернет новый Phantom Token пользователю. Событие `GuestMergedEventPayload` останется в Outbox и будет разослано бизнес-сервисам позже (Eventually Consistent). Пользователь на короткое время может не увидеть своих старых "гостевых" файлов, пока событие не будет доставлено. |

# Событие: Потребление квоты (Quota Consumed) (SR-AUTH-GQ-02)

## Общая информация

Публикация асинхронных батчей (пакетов) с агрегированной информацией о потреблении квот гостевыми (или основными) сессиями. Используется для интеграции с Billing Service или аналитическими дашбордами, не нагружая основной шлюз (Envoy/API Gateway) синхронными запросами на списание баланса.

| Тип операции | Publish (Публикация) |
| :--- | :--- |
| **Exchange / Топик** | `platform:events:billing` (Topic) |
| **Routing Key** | `billing.quota.consumed.{workspaceId}` |
| **Очередь** | (Управляется сервисом биллинга: `billing:quota-listener`) |
| **DTO сообщения** | `QuotaConsumedEventPayload` |

## Параметры сообщения

Данные о типе и объеме потребленного ресурса.

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **subjectId** | string (uuid) | Пользователь или `guestId` (если аноним). |
| **workspaceId** | string (uuid) | Контекст воркспейса (с кого списывать деньги/лимиты). |
| **resourceType** | string | Тип ресурса: `API_REQUESTS`, `STORAGE_MB`, `AI_TOKENS`. |
| **amount** | integer | Количество потребленных единиц. |
| **consumedAt** | integer (timestamp) | Временная метка потребления (или конец окна агрегации). |
| **batchId** | string (uuid) | ID батча для дедупликации в биллинге. |

## Логика обработки запроса

*   **Триггер:** Локальный In-Memory счетчик (Token Bucket / Sliding Window) достигает порога сброса (например, каждые 100 запросов или раз в 1 минуту), либо квота исчерпана полностью.
*   **Агрегация:** Воркер агрегирует локальные счетчики по `workspaceId` и `resourceType`.
*   **Публикация:** Сервис формирует батч `QuotaConsumedEventPayload` и публикует его в `platform:events:billing`.
*   **Реакция потребителей:** Billing Service асинхронно обновляет балансы `workspaceId` в своей БД и, если квота превышена, может инициировать списание средств или послать WebSocket-событие `quota_exceeded_warning` (см. Socket API).

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Если брокер недоступен при сбросе батча, агрегированные данные сохраняются в локальную персистентную таблицу `quota_outbox`. Потеря этих событий приведет к расхождению метрик в биллинге, поэтому они строго фиксируются через Outbox паттерн перед публикацией (At-Least-Once). |
