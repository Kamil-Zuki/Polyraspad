# Введение

Данный документ описывает механизмы RabbitMQ для группы **Аудит и Комплаенс**. Эти очереди управляют тяжелыми фоновыми задачами (Background Workers), защищая синхронный REST API Authorization Service от таймаутов (Timeouts) при генерации объемных отчетов по безопасности (выгрузка локальных логов доступа в WORM-архивы). 

Также здесь описана потоковая публикация (Stream) каждого события доступа (Логин, Создание API-ключа, Выдача прав) для интеграции с корпоративными системами мониторинга инцидентов ИБ (SIEM-системы: Splunk, ELK).

# 1. Список задач и потоков Аудита

Ниже перечислены все асинхронные операции по работе с логами ИБ и выгрузками.

| Метод (SR) | Тип операции | Очередь / Топик | Описание |
| :--- | :--- | :--- | :--- |
| SR-AUTH-LA-05 | Publish | `auth:tasks:audit-export` | Постановка долгоиграющей задачи на сборку ZIP/CSV архива логов доступа за период. |
| SR-AUTH-LA-05 | Consume | `auth:tasks:audit-export` | Потребление задачи фоновым воркером (генерация CSV, загрузка в S3, вызов WSS об успехе). |
| SR-AUTH-LA-04 | Publish | `auth:events:audit-stream` | (Topic) Непрерывная потоковая публикация каждого WORM-события для чтения внешними SIEM-системами. |

# Задачa: Постановка выгрузки аудита в очередь (SR-AUTH-LA-05)

## Общая информация

Публикация задачи в очередь от REST API эндпоинта `POST /api/v1/auth/audit/export`. Сообщение содержит только параметры фильтрации (период, тип события, субъект) и метаданные пользователя, запросившего выгрузку. Сама генерация CSV/ZIP будет выполняться воркером асинхронно. Реализует паттерн «Store First, Process Later».

| Тип операции | Publish (Публикация) |
| :--- | :--- |
| **Exchange / Топик** | `auth:tasks:exchange` |
| **Routing Key** | `task.audit.export` |
| **Очередь** | `auth:tasks:audit-export` |
| **DTO сообщения** | `AuditExportJobPayload` |

## Параметры сообщения

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **jobId** | string (uuid) | Уникальный идентификатор задачи выгрузки (возвращается пользователю из REST API). |
| **requestedBy** | string (uuid) | `subjectId` администратора, инициировавшего выгрузку. |
| **workspaceId** | string (uuid) | Контекст рабочего пространства, из которого извлекаются WORM-логи. |
| **filters** | object | JSON-объект с критериями: `startDate` (timestamp), `endDate` (timestamp), `eventTypes` (массив строк), `targetSubjectId` (опционально). |
| **format** | string | Желаемый формат: `CSV` или `JSON_LINES`. |

## Логика обработки запроса

*   **Триггер:** Администратор вызывает REST API метод `POST /audit/export` с нужными фильтрами.
*   **Публикация:** Сервис создает запись о задаче в БД `audit_export_jobs` со статусом `PENDING` и публикует сообщение `AuditExportJobPayload` в очередь задач (Direct Exchange).
*   **Гарантия доставки:** Используется Transactional Outbox. Если брокер недоступен (INTERNAL), задача остается в БД и будет отправлена повторно внутренним retry-воркером Outbox'а.
*   **Быстрый ответ (Fast ACK):** REST API немедленно отвечает клиенту `202 Accepted` с `jobId` без ожидания генерации файла.

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Брокер сообщений RabbitMQ недоступен (Connection Refused). Задача сохранена в Outbox, REST API возвращает `202 Accepted` штатно. |

# Задачa: Генерация выгрузки аудита (SR-AUTH-LA-05)

## Общая информация

Потребление задачи `AuditExportJobPayload` выделенным фоновым воркером (Background Worker). Воркер читает тяжелые WORM-логи из PostgreSQL/ClickHouse, чанками пишет их во временный файл (CSV), сжимает в ZIP, загружает в S3-совместимое хранилище (MinIO/AWS) и оповещает администратора по WebSocket о готовности.

| Тип операции | Consume (Потребление) |
| :--- | :--- |
| **Exchange / Топик** | `auth:tasks:exchange` |
| **Routing Key** | `task.audit.export` |
| **Очередь** | `auth:tasks:audit-export` |
| **DTO сообщения** | `AuditExportJobPayload` |

## Параметры сообщения

(Идентичны Payload из раздела публикации `AuditExportJobPayload` - jobId, requestedBy, workspaceId, filters, format).

## Логика обработки запроса

*   **Потребление:** Воркер забирает сообщение (QoS: 1) из `auth:tasks:audit-export`.
*   **Инициализация:** Статус `audit_export_jobs` в БД обновляется на `PROCESSING`.
*   **Генерация:**
    * Воркер выполняет запрос к WORM-хранилищу логов (Paginated/Cursor-based), применяя `filters`.
    * Данные записываются потоком во временный CSV файл (до 10-50 МБ).
*   **Сохранение (S3 Upload):** Воркер загружает готовый архив (с шифрованием) в приватный бакет S3. Генерируется внутренний `fileKey`.
*   **Завершение:** 
    * Статус задачи `jobId` меняется на `COMPLETED` с сохранением `fileKey` и `expiresAt` (ссылка валидна 24ч).
    * Воркер публикует WebSocket-событие `audit_export_completed` с `jobId` для администратора `requestedBy`, чтобы UI показал кнопку "Скачать".
    * Сообщение удаляется из RabbitMQ (ACK).

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Сбой БД при чтении чанков или сбой S3 при загрузке. Статус задачи меняется на `FAILED` с записью ошибки. Сообщение в RabbitMQ ACK'ается (чтобы не зацикливаться на битом отчете). Опционально: NACK с retry, если ошибка временная (Network Timeout). |
| **EMPTY_RESULT** | По фильтрам не найдено логов. Статус задачи `COMPLETED`, но с флагом `isEmpty: true`. В S3 заливается пустой файл с заголовками. ACK. |

# Событие: Потоковая публикация аудита (SR-AUTH-LA-04)

## Общая информация

Непрерывная Fire-and-Forget трансляция критических событий безопасности в реальном времени. В отличие от REST API (pull-модель), эта очередь используется корпоративными SIEM (Security Information and Event Management) или внешними системами аналитики угроз (Threat Intelligence) для мгновенного детектирования аномалий (push-модель). Authorization Service только публикует эти события (Topic Exchange).

| Тип операции | Publish (Публикация) |
| :--- | :--- |
| **Exchange / Топик** | `auth:events:audit-stream` (Topic) |
| **Routing Key** | `audit.event.{workspaceId}.{eventType}` (Например: `audit.event.ws-123.LOGIN_FAILED`) |
| **Очередь** | (Управляется внешними подписчиками: SIEM, Billing) |
| **DTO сообщения** | `AuditStreamEventPayload` |

## Параметры сообщения

Содержит структурированный лог ИБ (CEF/Syslog-подобный формат).

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **eventId** | string (uuid) | Уникальный ID события в WORM-журнале. |
| **workspaceId** | string (uuid) | Контекст рабочего пространства. |
| **eventType** | string | Категория: `LOGIN_SUCCESS`, `LOGIN_FAILED`, `PAT_CREATED`, `ROLE_ASSIGNED`, `IMPERSONATION_STARTED`. |
| **subjectId** | string (uuid) | Идентификатор актора (кто выполнил). |
| **targetId** | string (uuid) | (Опционально) Идентификатор цели (над кем выполнено). |
| **ipAddress** | string | IP-адрес источника. |
| **userAgent** | string | Устройство/браузер. |
| **severity** | string | Уровень важности: `INFO`, `WARNING`, `CRITICAL` (например, для множественных LOGIN_FAILED). |
| **metadata** | object | Специфичные детали события (например, гео-локация или задействованный API Key). |

## Логика обработки запроса

*   **Триггер:** Любое защищаемое действие внутри Authorization Service (Успешный вход, Блокировка, Отзыв сессии, Выдача API ключа).
*   **Гарантия:** При записи события локального аудита в WORM-таблицу (БД), событие одновременно публикуется в `auth:events:audit-stream` (Topic Exchange).
*   **Маршрутизация (Routing):** Топик-ключ `audit.event.{workspaceId}.{eventType}` позволяет гибко настраивать очереди потребителей. Например, SIEM может подписаться на `audit.event.*.LOGIN_FAILED` для всех воркспейсов, а локальный биллинг — только на `audit.event.ws-123.*`.
*   **Fire-and-Forget:** Сервису авторизации не важно, кто подписан на топик. Если очередей нет, сообщение удаляется брокером (нагрузки не создается).

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | При публикации в RabbitMQ возник сбой (Connection Refused). Событие НЕ теряется, так как оно уже записано в иммутабельный локальный WORM-журнал (БД). Системы SIEM могут в будущем запросить REST API `/audit/sync` для восстановления пропущенных логов (КАР-11). |
