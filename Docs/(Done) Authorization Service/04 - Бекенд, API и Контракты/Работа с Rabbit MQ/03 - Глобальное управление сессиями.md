# Введение

Данный документ описывает механизмы RabbitMQ для группы **Глобальное управление сессиями**. Эта группа отвечает за широковещательную трансляцию (Broadcast) критических изменений состояния пользователя (Разлогин на всех устройствах, принудительная смена контекста, изменение RBAC-ролей) из Authorization Service во все остальные микросервисы Платформы (Storage, CRM, Tasks, Integrations).

Цель этих событий — обеспечить консистентность распределенного In-Memory кэширования прав в микросервисной архитектуре и немедленный разрыв активных WebSocket-соединений у заблокированных пользователей.

# 1. Список событий Глобального управления сессиями

Ниже перечислены все асинхронные Publish-операции для оповещения смежных сервисов.

| Метод (SR) | Тип операции | Очередь / Топик | Описание |
| :--- | :--- | :--- | :--- |
| SR-AUTH-OI-04 | Publish | `platform:events:global-logout` | (Fanout) Широковещательное оповещение: Пользователь полностью разлогинен. |
| SR-AUTH-SM-02 | Publish | `platform:events:context-switched` | (Topic) Оповещение об изменении активного Workspace пользователя. |
| SR-AUTH-SM-07 | Publish | `platform:events:roles-updated` | (Topic) Оповещение об изменении RBAC-ролей (выдача/отзыв прав). |

# Событие: Глобальный выход (Global Logout) (SR-AUTH-OI-04)

## Общая информация

Публикация критического Fanout-события при полном завершении всех сессий пользователя в Authorization Service (например, при нажатии "Выйти со всех устройств", блокировке администратором или получении `Back-Channel Logout` от STEOS ID). Все микросервисы Платформы, подписанные на этот Exchange, должны немедленно очистить любые локальные кэши, связанные с этим пользователем (включая JIT-кэш токенов), и закрыть его активные WebSocket/SignalR подключения.

| Тип операции | Publish (Публикация) |
| :--- | :--- |
| **Exchange / Топик** | `platform:events:global-logout` (Fanout) |
| **Routing Key** | `*` (Игнорируется в Fanout) |
| **Очередь** | (Управляется микросервисами-потребителями: `tasks:logout-listener`, `crm:logout-listener`) |
| **DTO сообщения** | `GlobalLogoutEventPayload` |

## Параметры сообщения

Легковесный Payload для мгновенной реакции потребителей.

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **subjectId** | string (uuid) | Идентификатор пользователя (sub), чьи сессии отозваны. |
| **revokedAt** | integer (timestamp) | Временная метка глобального разлогина. |
| **reason** | string | Опциональная причина: `USER_INITIATED`, `ADMIN_BANNED`, `IDP_LOGOUT`. |
| **eventId** | string (uuid) | Уникальный ID события (для дедупликации на стороне потребителей). |

## Логика обработки запроса

*   **Триггер:** REST API вызов `POST /sessions/terminate-all` или обработка вебхука `steosid:events:backchannel-logout` внутри Authorization Service.
*   **Публикация:** Сервис авторизации аннулирует Refresh-токены в своей БД и публикует `GlobalLogoutEventPayload` в Fanout Exchange `platform:events:global-logout`.
*   **Гарантия доставки (Outbox):** Событие публикуется через паттерн Transactional Outbox. Гарантируется доставка `At-Least-Once` всем подключенным на момент разлогина очередям микросервисов.
*   **Реакция потребителей:**
    *   **API Gateway / Envoy (Опционально):** Если шлюз поддерживает кэширование валидации JWT, он сбрасывает In-Memory кэш публичных ключей или заносит `subjectId` в горячий Blacklist на время жизни самого долгого Access-токена (обычно 5 минут).
    *   **Бизнес-сервисы (Tasks, CRM):** Получают событие, ищут активные WebSocket-сессии с этим `subjectId` и принудительно их разрывают (`Close(1008, "Session Revoked")`). Сбрасывают JIT-кэш прав (КАР-9).

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Если RabbitMQ недоступен в момент инвалидации в БД, событие сохраняется в таблице Outbox. При восстановлении связи оно будет доставлено. В течение короткого окна (пока живы Phantom Tokens) заблокированный пользователь может иметь доступ к микросервисам, но WSS-соединения не будут разорваны до доставки события. |

# Событие: Переключение Контекста (Context Switched) (SR-AUTH-SM-02)

## Общая информация

Публикация события при успешной смене активного Workspace пользователем (вызов `POST /sessions/switch-workspace`). Если смежные микросервисы поддерживают stateful-логику, привязанную к текущему контексту (например, подписки на определенные каналы данных в WebSocket), они должны обновить этот контекст у себя.

| Тип операции | Publish (Публикация) |
| :--- | :--- |
| **Exchange / Топик** | `platform:events:context` (Topic) |
| **Routing Key** | `user.context.switched` |
| **Очередь** | (Очереди потребителей, которым важен контекст: `storage:context-listener`) |
| **DTO сообщения** | `ContextSwitchedEventPayload` |

## Параметры сообщения

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **subjectId** | string (uuid) | Идентификатор пользователя (sub). |
| **sessionId** | string (uuid) | Конкретная сессия, в которой произошло переключение. |
| **newWorkspaceId** | string (uuid) | Новый `workspace_id` (ctx). |
| **switchedAt** | integer (timestamp) | Время переключения. |

## Логика обработки запроса

*   **Триггер:** Успешная валидация прав на новый Workspace и генерация нового Phantom Token'а (Access Token) в методе `/sessions/switch-workspace`.
*   **Публикация:** Authorization Service публикует событие в Exchange.
*   **Реакция потребителей:** Сервисы с активными WebSocket-соединениями от этой `sessionId` могут, например, отписать пользователя от топиков старого Workspace и подписать на топики нового `newWorkspaceId` (Live-updates чатов, досок задач).

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | Брокер недоступен. Событие переключения сохраняется в Outbox. |

# Событие: Обновление ролей (Roles Updated) (SR-AUTH-SM-07)

## Общая информация

Оповещение о том, что администратор изменил RBAC-роли пользователя (выдал админские права, отозвал доступ к модулю) в рамках конкретного Workspace. Это сигнал для микросервисов сбросить In-Memory кэш прав этого пользователя (КАР-9, Silent Refresh & Cache Invalidation).

| Тип операции | Publish (Публикация) |
| :--- | :--- |
| **Exchange / Топик** | `platform:events:access` (Topic) |
| **Routing Key** | `access.roles.updated.{workspaceId}` |
| **Очередь** | (Очереди микросервисов, выполняющих PEP: Policy Enforcement Point) |
| **DTO сообщения** | `RolesUpdatedEventPayload` |

## Параметры сообщения

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **subjectId** | string (uuid) | Кому изменили права. |
| **workspaceId** | string (uuid) | В каком воркспейсе. |
| **updatedBy** | string (uuid) | Кто изменил права (ID администратора). |
| **action** | string | Тип изменения: `ROLES_GRANTED`, `ROLES_REVOKED`, `POLICY_CHANGED`. |
| **updatedAt** | integer (timestamp) | Временная метка изменения. |

## Логика обработки запроса

*   **Триггер:** Вызов внутреннего метода (или gRPC `InvalidateSubjectCache`) изменения прав.
*   **Публикация:** Событие отправляется в Exchange с ключом маршрутизации, содержащим `workspaceId`.
*   **Реакция потребителей:** 
    * Сервисы, кэширующие ответ от gRPC `ValidateToken` (где вернулись роли `admin`, `editor`), должны немедленно очистить кэш для пары `(subjectId, workspaceId)`. 
    * Следующий API-запрос от этого пользователя заставит микросервис сделать синхронный gRPC вызов `ValidateToken` к Authorization Service, который вернет уже обновленный список ролей. Это ядро механизма **Zero Trust + JIT-кэширования** (КАР-2, КАР-9).

## Статус-коды при ошибках

| Код / Тип ошибки | Описание ошибки |
| :--- | :--- |
| **INTERNAL** | При сбое брокера In-Memory кэши микросервисов не будут инвалидированы немедленно (проблема консистентности). Однако, из-за короткого TTL (Time-To-Live) таких кэшей (обычно 1-5 минут), консистентность восстановится автоматически. Outbox-паттерн дошлет событие после восстановления связи. |
