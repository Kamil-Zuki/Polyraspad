# Введение

Эта группа сущностей формирует **Локальный защитный периметр (Perimeter Security) и Механизм квотирования анонимов** внутри микросервиса Authorization Service. 

В распределенной архитектуре STEOS каждая платформа (публичное облако `steos.io` или корпоративный инстанс `bank.steos.io`) обязана самостоятельно защищать свои вычислительные ресурсы от нелегитимного использования, не перекладывая всю нагрузку на глобальный STEOS ID. Если глобальный ID защищает *идентичность* (пароли, аккаунты), то локальный Auth Service защищает *инфраструктуру* (LLM-модели, пропускную способность API, базы данных).

Особую архитектурную сложность представляет реализация функционала **Публичного доступа (Guest Mode)**. Маркетинг и бизнес-модель часто требуют предоставить пользователю "демо-версию" продукта (например, сгенерировать 3 картинки или проанализировать 1 договор) без принудительной регистрации. Эта группа сущностей позволяет платформе открывать доступ наружу, сохраняя при этом жесткий контроль над расходами.

**Архитектурные особенности группы:**

1.  **Локальная Блокировка (Edge Throttling):** Сервис способен мгновенно отбивать атаки (DDoS, API Scraping) на уровне локального шлюза, внося IP-адреса или аппаратные отпечатки в "черный список". Эти блокировки действуют только в рамках конкретной инсталляции платформы и не "банят" пользователя глобально в STEOS ID.
2.  **Stateful Guest Quotas (Учет неавторизованного потребления):** В отличие от зарегистрированных пользователей (чьи лимиты жестко контролируются в `Global Billing` и `Workspace Service`), "Гости" не имеют ни контрактов, ни кошельков. Группа реализует паттерн *Soft Metering*: она связывает факт потребления тяжелой фичи (например, `AI_GENERATE_IMAGE`) с эфемерной сессией и отпечатком устройства (Fingerprint).
3.  **Гибридное хранение (Memory + Persistent):** Сущности этой группы спроектированы под высочайшую нагрузку (десятки тысяч запросов в секунду). Подсчет квот и проверка банов происходят физически в **Redis** (In-Memory). Реляционная база данных (PostgreSQL) выступает лишь персистентным хранилищем для фиксации итогов (сброс счетчиков раз в минуту) и возможности восстановления состояния кэша при рестарте подов Kubernetes.

В совокупности эти механизмы позволяют платформе STEOS оставаться открытой и привлекательной для новых пользователей, надежно защищаясь от ботнетов и "профессиональных халявщиков" (freeloaders).

# Использование гостевой фичи (`guest_feature_usages`)

## 1. Общее описание

**Использование гостевой фичи (Guest Feature Usage)** — это высоконагруженная операционная сущность-счетчик, которая фиксирует объем вычислительных ресурсов (или количество действий), потребленных неавторизованным пользователем (Гостем) в рамках его временной сессии.

В архитектуре платформы STEOS публичные пространства могут открывать часть своего функционала "наружу" в маркетинговых целях (например, 3 бесплатные генерации ИИ-изображений или 10 поисковых запросов по базе знаний). Эта таблица выступает в роли **Теневого Биллинга (Shadow Metering)**. В отличие от корпоративных пользователей, чьи лимиты хранятся в `Workspace Service`, гости не имеют контрактов и кошельков. Их лимиты жестко контролируются здесь, на уровне шлюза авторизации.

**Архитектурное назначение:**
1.  **Quota Enforcement (Контроль лимитов):** Не позволяет анонимным пользователям "выкачать" базу данных или сжечь бюджет на вызовы тяжелых нейросетей. При превышении лимита система отдает ошибку `402 Payment Required` или `401 Unauthorized` с требованием регистрации.
2.  **State Persistence (Защита от сброса кэша):** Хотя физический подсчет каждого запроса происходит в оперативной памяти (Redis) для обеспечения задержки < 2 мс, данные регулярно сбрасываются в эту реляционную таблицу (паттерн Write-Behind). Если кластер Redis перезагрузится, гости не получат свои лимиты заново (что предотвращает массовый абуз).
3.  **Аналитика "Freemium" воронки:** Данные из этой таблицы передаются в Data Warehouse (DWH) для подсчета конверсии: маркетологи видят, сколько гостей исчерпали лимит полностью и после этого зарегистрировались в системе.

## 2. Атрибуты (поля) сущности
**Таблица:** `guest_feature_usages`

*В соответствии с «Белой книгой разработчика баз данных», для таблицы высокочастотных счетчиков используется суррогатный автоинкрементный ключ `int8`. Объем потребления хранится в типе `numeric`, так как гость может тратить не только штучные запросы, но и дробные мегабайты трафика.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `int8` | PK, AI, NOT NULL | **Уникальный идентификатор.** Суррогатный автоинкрементный ключ (`GENERATED ALWAYS AS IDENTITY`). |
| `guest_session_id` | `uuid` | FK, NOT NULL | **Сессия гостя.** Ссылка на родительскую таблицу `guest_sessions`. Однозначно идентифицирует анонима (связывая его с `device_fingerprint`). |
| `workspace_id` | `uuid` | NULL | **Контекст Пространства.** Логическая ссылка на `workspaces.id` из `Workspace Service`. Указывает, чьи именно ресурсы тратит гость (например, он делает запросы на публичном демо-стенде конкретной компании). |
| `feature_id` | `int4` | NOT NULL | **Потребляемый ресурс.** Логическая ссылка на справочник `features` в Ядре Платформы (`Platform Service`). Например, ID фичи `AI_GENERATE_TEXT`. |
| `usage_amount` | `numeric(18,4)`| NOT NULL, Def `0` | **Объем потребления.** Накопленное значение потраченного ресурса (количество запросов, токенов LLM, скачанных мегабайт). |
| `created_at` | `int8` | NOT NULL | **Дата первой фиксации.** Unix Timestamp (UTC). |
| `updated_at` | `int8` | NOT NULL | **Дата последнего изменения.** Unix Timestamp (UTC). Обновляется при каждом сбросе агрегированных данных из Redis в БД. |

*Обязательный индекс:* Уникальный составной B-Tree индекс `UNIQUE (guest_session_id, workspace_id, feature_id)` — гарантирует, что для одной гостевой сессии в одном публичном пространстве существует ровно один счетчик для каждой конкретной фичи.

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **Гостевая сессия**<br>(`guest_sessions`) | **Многие-к-одному.** Жизненный цикл счетчика жестко привязан к сессии. Когда гостевая сессия "протухает" (истекает `expires_at`), фоновый процесс удаляет и саму сессию, и все её счетчики каскадно (`ON DELETE CASCADE`). |
| **Platform Service** | **Логическая ссылка.** Поле `feature_id` диктует семантику потребления (что именно мы считаем). |
| **Workspace Service** | **Источник правил (Read-Only).** Auth Service обращается к Workspace Service, чтобы узнать: *"Какой лимит установлен для фичи `feature_id` в `workspace_id` для публичного доступа?"* (Таблица `public_feature_settings`). |
| **In-Memory Cache (Redis)**| **Слой исполнения.** Физический инкремент счетчиков происходит в Redis. Таблица БД выступает лишь хранилищем для бэкапа состояния (Snapshotting). |
## 4. Жизненный цикл и Алгоритм работы

1.  **Первое касание (Cache Miss & Bootstrapping):**
    *   Гость нажимает "Сгенерировать логотип" на лендинге.
    *   Запрос долетает до API Gateway (Auth Service).
    *   Шлюз извлекает `guest_session_id` из Cookie и лезет в Redis за счетчиком `guest:{session_id}:feature:{id}`.
    *   Redis пуст (первый запрос). Шлюз делает `SELECT` из таблицы `guest_feature_usages`. Там тоже пусто.
    *   Шлюз создает ключ в Redis со значением `0` и делает `INSERT` в БД со значением `0`.
2.  **Сверка лимитов (Policy Evaluation):**
    *   Шлюз асинхронно или из кэша достает правило: *"Гостям разрешено 3 генерации"*.
    *   Выполняет атомарный инкремент в Redis: `INCR guest:{session_id}:feature:{id}`. Результат = 1.
    *   Сравнивает: `1 <= 3`. Запрос пропускается в сервис генерации.
3.  **Агрегация и Персистенция (Write-Behind):**
    *   Чтобы не убить базу данных постоянными `UPDATE`, инкремент в БД не происходит синхронно.
    *   Раз в 30-60 секунд запускается фоновый воркер (Sync Daemon). Он собирает из Redis все измененные счетчики и делает пачку массовых обновлений: `UPDATE guest_feature_usages SET usage_amount = {new_val}, updated_at = NOW()`.
4.  **Блокировка (Enforcement):**
    *   Гость делает 4-й запрос. Redis делает `INCR`, результат = 4.
    *   Шлюз сравнивает: `4 > 3`.
    *   Запрос немедленно отклоняется с ошибкой `429 Too Many Requests` (или `403 Forbidden` с телом `{"error": "GUEST_QUOTA_EXCEEDED"}`). Платформа предлагает гостю зарегистрироваться.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Защита от сброса (Persistence over Cache)** | Если сервер Redis аварийно перезагружается и теряет In-Memory данные, хитрые пользователи могли бы получить свои "бесплатные попытки" заново. Синхронизация с таблицей `guest_feature_usages` гарантирует, что после перезапуска Redis шлюз считает исторические данные из PostgreSQL (Hydration) и восстановит счетчик. |
| **Soft Fingerprinting Defense** | Поскольку счетчик жестко привязан к `guest_session_id`, который в свою очередь привязан к аппаратному отпечатку браузера (`device_fingerprint`), пользователь не сможет обнулить этот счетчик, просто переключив VPN (сменив IP) или удалив Cookies. Шлюз узнает его "железо", найдет старую сессию и вернет ему его исчерпанный счетчик. |
| **Silent Cleanup (Тихая очистка)** | В отличие от финансовых логов (Billing), гостевые счетчики не имеют ценности после их истечения. Таблица не должна бесконечно расти. При удалении старой гостевой сессии (TTL) все её счетчики бесследно удаляются из СУБД, освобождая дисковое пространство. Аналитика по ним (если нужна) пишется заранее в системы вроде ClickHouse или ELK. |

# Причина локальной блокировки (`local_ban_reasons`)

## 1. Общее описание

**Причина локальной блокировки (Local Ban Reason)** — это системная конфигурационная сущность-справочник, которая стандартизирует и классифицирует основания для временного или перманентного ограничения доступа (бана) на уровне локального микросервиса `Authorization Service`.

В отличие от глобальных блокировок (накладываемых STEOS ID за взлом паролей или финансовый фрод), этот справочник описывает **инфраструктурные и локальные инциденты**. Он отвечает на вопрос: **«Какое именно локальное правило платформы (или конкретного Воркспейса) нарушил этот IP-адрес или Гость, заставив систему активировать файрвол?»**.

**Архитектурное назначение:**
1.  **Нормализация и Аналитика:** Позволяет SRE-инженерам и администраторам платформы строить точные агрегированные отчеты (например, "Вчера 80% банов на узле `eu-central-1` были выданы по причине `GUEST_QUOTA_ABUSE`"), не прибегая к неэффективному поиску по сырым строкам (`LIKE`).
2.  **Оркестрация Ответных Действий (Response Strategy):** Сущность содержит поле `default_ttl_seconds`, которое подсказывает движку защиты (Rate Limiter'у), на какой срок по умолчанию следует банить нарушителя за конкретный проступок (например, за спам-запросы — бан на 15 минут, за попытку SQL-инъекции — бан на 24 часа).
3.  **Локализация UI-сообщений:** Благодаря интеграции с `Translation Service`, этот справочник позволяет выводить заблокированному пользователю (или гостю) понятную, переведенную на его родной язык причину, почему его запрос отклонен (например, "Вы исчерпали бесплатный лимит" вместо сухого "HTTP 429").

## 2. Атрибуты (поля) сущности
**Таблица:** `local_ban_reasons`

*В соответствии с «Белой книгой разработчика баз данных», для конфигурационного справочника применяется тип `int2`. Идентификаторы жестко фиксируются в миграциях, автоинкремент (IDENTITY) отключен. Текстовые поля снабжены логическими ссылками `_lang_id` на `Translation Service`.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `int2` | PK, NOT NULL | **Уникальный идентификатор.** Задается вручную в миграциях БД. Тип `SMALLINT` (`int2`) обеспечивает минимальный размер B-Tree индексов в таблице блокировок. |
| `code` | `varchar(50)` | UNIQUE, NOT NULL | **Стабильный бизнес-код.** Строковый идентификатор причины (например, `API_RATE_LIMIT`, `GUEST_QUOTA_ABUSE`). Используется бэкендом (Rate Limiter / WAF) для логирования и привязки правил реагирования в коде. |
| `name` | `varchar(100)` | NOT NULL | **Название причины.** Краткое, логическое имя на языке оригинала (например, "API Rate Limit Exceeded"). Выводится в административных дашбордах мониторинга. |
| `name_lang_id` | `int2` | NOT NULL | **Язык названия.** Внешний логический ключ на ID языка из `Translation Service` (таблица `languages`), указывающий язык содержимого поля `name`. |
| `description` | `varchar(1024)`| NULL | **Описание для пользователя.** Развернутый текст, объясняющий пользователю или гостю причину отклонения запроса и шаги для решения проблемы (например, "Вы превысили лимит запросов. Пожалуйста, зарегистрируйтесь или повторите попытку позже"). |
| `description_lang_id`| `int2` | NULL | **Язык описания.** Внешний логический ключ на ID языка оригинала для поля `description`. |
| `default_ttl_seconds`| `int4` | NOT NULL | **Время блокировки по умолчанию.** Рекомендованное время жизни (Time-To-Live) бана в секундах для данного нарушения. Движок может использовать это значение при расчете поля `expires_at` в транзакционной таблице. Если `-1` — бан перманентный (до ручного снятия). |
| `is_fatal` | `boolean` | NOT NULL, Def `false` | **Флаг критичности.** Если `true` (например, попытка эксплуатации уязвимости), локальный сервис может эскалировать инцидент, отправив асинхронный сигнал в глобальный STEOS ID с просьбой применить Global Ban ко всему аккаунту злоумышленника. |
| `created_at` | `int8` | NOT NULL | **Дата создания.** Unix Timestamp (UTC). |
| `updated_at` | `int8` | NOT NULL | **Дата обновления.** Unix Timestamp (UTC). |
## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **Локальная блокировка**<br>(`local_suspicious_activities`) | **Один-ко-многим.** Каждая запись о фактическом наложении бана (на IP или Fingerprint) жестко ссылается на этот справочник, фиксируя юридическое и техническое основание для блокировки. |
| **Translation Service** | **Асинхронная интеграция.** Добавление новой причины генерирует RabbitMQ-уведомление для системы переводов, чтобы локализовать тексты ошибок (`description`) для конечных пользователей по всему миру. |
| **Platform Service** | **Логическая ссылка.** Поля `name_lang_id` и `description_lang_id` ссылаются на глобальный реестр языков платформы. |
## 4. Жизненный цикл и Алгоритм работы

1.  **Декларация (System Setup):**
    *   При деплое микросервиса Authorization Service, миграция БД инициализирует базовый набор причин (например, `id=1, code=API_RATE_LIMIT, default_ttl=900`).
2.  **Обнаружение инцидента (Rule Triggering):**
    *   Анонимный гость исчерпывает свой лимит из `guest_feature_usages` и продолжает слать запросы.
    *   Движок контроля квот понимает, что это абуз (Злоупотребление).
    *   В коде вызывается метод: `Firewall.BanDevice(fingerprint, BanReasonCodes.GUEST_QUOTA_ABUSE)`.
3.  **Исполнение (Enforcement):**
    *   Бэкенд извлекает из кэша справочника `local_ban_reasons` запись для `GUEST_QUOTA_ABUSE`. Берет оттуда `default_ttl_seconds` (например, 86400 секунд = 24 часа).
    *   Делает `INSERT INTO local_suspicious_activities`, устанавливая `expires_at = NOW() + 86400`, и связывает строку с найденным `local_ban_reason_id`.
4.  **Обратная связь (User Feedback):**
    *   Гость делает следующий запрос. Шлюз отклоняет его (HTTP 429/403).
    *   В тело ответа шлюз подкладывает переведенное поле `description` из этого справочника: *"Ваш гостевой лимит исчерпан. Доступ приостановлен на 24 часа. Создайте аккаунт STEOS ID для продолжения работы"*.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Data-Driven Throttling (Управляемые задержки)** | Хранение `default_ttl_seconds` в базе данных позволяет SRE-команде гибко реагировать на DDoS-атаки. Если началась мощная атака парсеров, администратор платформы может через SQL-скрипт или внутреннюю админку увеличить базовое время блокировки для `API_RATE_LIMIT` с 15 минут до 2 часов. Все новые баны автоматически начнут выписываться на 2 часа без необходимости менять исходный код C# и делать релиз микросервиса. |
| **Эскалация Угроз (Local to Global)** | Локальный файрвол (Authorization Service) автономен, но не изолирован. Флаг `is_fatal` работает как механизм "звонка в полицию". Если локальная платформа обнаружила, что авторизованный пользователь шлет SQL-инъекции в поисковую строку (причина `MALICIOUS_PAYLOAD`), она не только забанит его локально, но и отправит событие в RabbitMQ. Глобальный `Ecosystem God Service` поймает событие и забанит этот `steos_id` во всех облаках мира. |
## 6. Предустановленные значения (Seeding)

Справочник поставляется с зашитым набором причин, покрывающих основные инфраструктурные угрозы платформы. Данные актуальны на момент инициализации БД (язык оригинала — английский, условный `lang_id` = 2).

| `id` | `code` | `default_ttl` | `is_fatal` | Описание архитектурного сценария (`description`) |
| :--- | :--- | :--- | :--- | :--- |
| `1` | **`API_RATE_LIMIT`** | `900` (15m) | `false` | "Too many requests. Please slow down." (Срабатывает при превышении RPS / DDoS). |
| `2` | **`GUEST_QUOTA_ABUSE`**| `86400` (24h)| `false` | "Guest quota exceeded. Please register an account to continue." (Попытка обойти триал-лимиты анонимно). |
| `3` | **`SUSPICIOUS_ORIGIN`**| `3600` (1h) | `false` | "Access temporarily restricted due to suspicious network origin." (Вход с известных Tor-Exit нод или Blacklisted IP). |
| `4` | **`MALICIOUS_PAYLOAD`**| `-1` (Perm) | `true` | "Security policy violation." (WAF (Web Application Firewall) обнаружил попытку XSS/SQLi в теле запроса). |

# Локальная блокировка (`local_suspicious_activities`)

## 1. Общее описание

**Локальная блокировка (Local Suspicious Activities / Edge Firewall)** — это транзакционная сущность активной защиты, выполняющая роль **динамического локального файрвола (Intrusion Prevention System)** на уровне конкретной инсталляции платформы (Public/Private Cloud). 

В архитектуре STEOS существует четкое разделение ответственности между защитой Идентичности и защитой Инфраструктуры. Если глобальный `STEOS ID` накладывает баны за компрометацию учетных данных, то локальный `Authorization Service` использует эту таблицу для защиты *своих* вычислительных ресурсов (серверов, баз данных, AI-моделей) и публичных эндпоинтов от парсинга (Scraping), DDoS-атак и абуза гостевых лимитов.

**Архитектурное назначение:**
1.  **Защита Периметра (Edge Protection):** Позволяет локальному API-шлюзу мгновенно «отбивать» мусорный или вредоносный трафик на самых подступах к системе, не допуская его до тяжелых бизнес-микросервисов (CRM, Tasks, Docs) и экономя вычислительные мощности.
2.  **Точечная изоляция Инцидентов:** Если на корпоративном инстансе (`bank.steos.io`) заблокирован IP-адрес за агрессивное поведение, этот бан остается локальным. Он не мешает легитимным пользователям с этого же (возможно, корпоративного NAT) IP-адреса заходить на другие платформы экосистемы.
3.  **Защита Гостевых Квот:** Эффективный механизм борьбы с ботами, которые пытаются использовать бесплатные лимиты (например, генерацию изображений), постоянно сбрасывая сессии и меняя IP-адреса, но сохраняя единый аппаратный отпечаток (`device_fingerprint`).
4.  **Синхронизация с In-Memory кэшем:** База данных (PostgreSQL) выступает надежным источником истины и хранилищем истории, но физическая фильтрация каждого HTTP-запроса происходит через сверхбыстрые ключи в Redis.

## 2. Атрибуты (поля) сущности
**Таблица:** `local_suspicious_activities`

*В соответствии с «Белой книгой разработчика баз данных», для таблицы логов инцидентов используется автоинкрементный `int8`. Вместо использования полиморфных полей для связи с целями блокировки применяются независимые nullable-колонки.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `int8` | PK, AI, NOT NULL | **Уникальный идентификатор бана.** Суррогатный автоинкрементный ключ (`GENERATED ALWAYS AS IDENTITY`). |
| `blocked_ip_address`| `varchar(45)` | NULL | **Заблокированный IP.** (IPv4/IPv6). Блокирует весь трафик с данного сетевого узла. Эффективно против примитивных DDoS-атак. |
| `blocked_fingerprint`| `varchar(255)`| NULL | **Заблокированный отпечаток.** Хэш аппаратных характеристик (браузера/железа). Позволяет блокировать умных ботов, которые используют пулы прокси-серверов (меняют IP), но имеют одинаковый "цифровой след". |
| `blocked_session_id` | `uuid` | NULL | **Заблокированная сессия.** Ссылка на `authorized_sessions` или `guest_sessions`. Позволяет точечно "убить" или заморозить конкретный сеанс связи. |
| `workspace_id` | `uuid` | NULL | **Контекст Пространства.** Логическая ссылка на `workspaces.id`. Позволяет изолировать угрозу: если хакер атакует публичный каталог компании А, он будет заблокирован только для доступа к ней, оставляя возможность просматривать другие публичные Пространства. |
| `local_ban_reason_id` | `int2` | FK, NOT NULL | **Системная причина.** Ссылка на конфигурационный справочник `local_ban_reasons` (например, `API_RATE_LIMIT` или `MALICIOUS_PAYLOAD`). Диктует строгость наказания и текст ошибки для пользователя. |
| `risk_score` | `int4` | NOT NULL | **Накопленный риск.** Сумма баллов риска, которая привела к срабатыванию блокировки. Помогает администраторам оценить тяжесть инцидента при ручном разборе. |
| `comment` | `varchar(1024)`| NULL | **Пользовательский комментарий.** Внутренняя текстовая заметка, оставленная SRE-инженером при ручной постановке бана (например, "Вручную забанен по тикету от службы безопасности банка"). |
| `comment_lang_id` | `int2` | NULL | **Язык комментария.** Логическая ссылка на `Translation Service`. |
| `is_active` | `boolean` | NOT NULL, Def `true` | **Флаг активности.** Если `false`, блокировка была снята досрочно (например, после апелляции пользователя в саппорт). |
| `expires_at` | `int8` | NULL | **Время истечения (TTL).** Unix Timestamp (UTC). Время автоматического снятия блокировки (рассчитывается на базе `default_ttl_seconds` из справочника причин). Если `NULL` — локальный бан перманентный (Permanent). |
| `created_at` | `int8` | NOT NULL | **Дата наложения блокировки.** Unix Timestamp (UTC). |
| `updated_at` | `int8` | NOT NULL | **Дата обновления.** Unix Timestamp (UTC). Обновляется при досрочном снятии или эскалации (увеличении срока). |

*Обязательные индексы:*
1.  B-Tree индекс по `(blocked_ip_address, expires_at)`
2.  B-Tree индекс по `(blocked_fingerprint, expires_at)`
*(Эти индексы критически важны для быстрого восстановления (Hydration) состояния Firewall'а в Redis после рестарта микросервиса `Authorization Service`).*

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **Причина локальной блокировки**<br>(`local_ban_reasons`) | **Многие-к-одному.** Жестко регламентирует основание для блокировки. Эта связь гарантирует, что система не будет "банить просто так" без понятного кода ошибки и локализованного описания для клиента. |
| **Авторизованная/Гостевая сессия** | **Логическая (Многие-к-одному).** Блокировка может быть привязана к конкретной сессии для её принудительной терминации. |
| **In-Memory Cache (Redis)**| **Репликация (Event-Driven).** При вставке активной записи в эту таблицу, `Authorization Service` мгновенно создает блокирующий ключ в Redis (например, `local_ban:ip:192.168.1.1` с TTL, равным `expires_at`). |
| **Workspace Service** | **Логическая ссылка.** Поле `workspace_id` позволяет применять гранулярные политики защиты периметра на уровне отдельных тенантов. |
## 4. Жизненный цикл и Алгоритм работы

1.  **Детектирование аномалии (Throttling / WAF):**
    *   Анонимный гость исчерпал лимит в 3 бесплатные ИИ-генерации (в таблице `guest_feature_usages`). Вместо того, чтобы зарегистрироваться, он пишет скрипт, который стирает Cookies и делает 100 запросов в секунду к эндпоинту генерации с одного и того же IP.
    *   Модуль Rate Limiting в памяти (Redis) фиксирует аномальный всплеск (Spike) от одного IP.
2.  **Исполнение наказания (Ban Execution):**
    *   Движок безопасности микросервиса извлекает ID причины `GUEST_QUOTA_ABUSE` (например, ID=2) из кэша справочника `local_ban_reasons`. Узнает, что дефолтное время бана — 24 часа.
    *   Бэкенд делает асинхронный `INSERT INTO local_suspicious_activities` со значениями: `blocked_ip_address = '192.168.1.1'`, `local_ban_reason_id = 2`, `expires_at = {NOW() + 24h}`.
    *   Параллельно (и синхронно) в Redis записывается ключ: `SET local_ban:ip:192.168.1.1 "true" EX 86400`.
3.  **Перехват трафика (Interception at Gateway):**
    *   Скрипт злоумышленника делает 101-й запрос.
    *   Слой Middleware на самом старте пайплайна (до парсинга JSON и до проверки сессий) извлекает IP из заголовков (`X-Forwarded-For`) и ищет его в Redis.
    *   Находит ключ `local_ban:ip:192.168.1.1` и мгновенно обрывает соединение. Возвращает `429 Too Many Requests` (или `403 Forbidden`) с переведенным текстом ошибки из справочника причин. Нагрузка сброшена.
4.  **Амнистия (Auto-Release):**
    *   Через 24 часа ключ в Redis исчезает естественным образом.
    *   Запись в БД остается для аналитики, но больше не влияет на прохождение трафика, так как `expires_at < NOW()`.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Fail-Fast (Быстрый отказ)** | Наличие этой таблицы и ее жесткой синхронизации с Redis обеспечивает защиту платформы от отказа в обслуживании (Denial of Service). Запросы от заблокированных субъектов отсекаются на уровне прокси, они не доходят до слоя бизнес-логики, не делают тяжелых SQL-запросов и не потребляют драгоценные GPU/CPU на попытки генерации. |
| **Многослойность (Defense in Depth)** | Эта сущность защищает только *локальную* инфраструктуру (API конкретной платформы). Если злоумышленник попытается начать перебирать пароли (что относится к Глобальной Идентичности), этот трафик пойдет в глобальный `STEOS ID`, и там сработает *своя, глобальная* система блокировок (таблица `suspicious_activities` внутри БД STEOS ID). Такое архитектурное разделение предотвращает "каскадные отказы", когда мощная DDoS атака на публичное демо-облако "кладет" всю глобальную сеть авторизации. |
| **Проактивная Защита Воркспейсов** | В публичном мульти-тенантном облаке (`steos.io`) размещаются тысячи независимых компаний. Наличие поля `workspace_id` в таблице банов позволяет защищать их изолированно. Если конкурент запустил парсер (скрапер), чтобы выкачать открытый каталог цен компании "А", платформа забанит IP парсера с привязкой к `workspace_id = 'A'`. Парсер будет отбит, но при этом легитимные пользователи, сидящие с этого же корпоративного (или NAT) IP-адреса, смогут спокойно продолжить работу в своих приватных пространствах "Б" и "В". |
