# Введение

Эта группа сущностей формирует самое сердце микросервиса **Authorization Service** — систему управления состояниями (State Management). Если глобальный STEOS ID выдает пользователю «Ключ от здания», то данная группа таблиц выдает ему «Пропуск на конкретный этаж» и следит за тем, в каком именно кабинете он сейчас находится.

Платформа STEOS использует паттерн **Phantom Token (Opaque Token)** для взаимодействия с браузерными клиентами. Это означает, что фронтенд никогда не получает на руки JWT-токен с расшифрованными правами и ролями (что могло бы стать вектором атаки XSS или причиной проблем с инвалидацией). Фронтенд получает лишь зашифрованную `HttpOnly` Cookie, которая содержит уникальный идентификатор сессии (Session ID).

**Архитектурные задачи этой группы:**

1.  **Stateful Auth (Отслеживание состояния):** Превращает децентрализованные, "забывчивые" JWT-токены от STEOS ID в жестко контролируемые локальные сессии. Сессию из этой группы можно убить (Revoke) в любую миллисекунду, мгновенно лишив пользователя или хакера доступа к платформе.
2.  **Context Routing (Изоляция Пространств):** Пользователь может состоять в десятке рабочих Пространств (Workspaces). Чтобы не передавать в Cookie ID пространства при каждом клике, система хранит "Текущий контекст" на сервере. Когда фронтенд запрашивает `/api/tasks`, Gateway лезет в эту группу сущностей, смотрит: *"Ага, Вася сейчас в пространстве Tesla"*, и прозрачно прокидывает `workspace_id` в микросервис задач.
3.  **Бесшовная Имперсонация:** Легальный механизм для сотрудников техподдержки "войти под пользователем", чтобы увидеть интерфейс его глазами для решения проблемы, при этом сохраняя абсолютную прозрачность в логах аудита (видно, кто реально нажимает кнопки).
4.  **Гостевой доступ:** Управление эфемерными сессиями для пользователей, которые еще не зарегистрировались, но хотят попробовать публичный функционал (Public Mode).

Данные сущности спроектированы для работы в высоконагруженной связке **PostgreSQL + Redis**. Реляционная БД выступает долговременным источником истины, а Redis кэширует контексты сессий для обеспечения времени отклика API Gateway < 2 мс.

# Авторизованная сессия (`authorized_sessions`)

## 1. Общее описание

**Авторизованная сессия (Authorized Session)** — это главная транзакционная сущность микросервиса Authorization Service, представляющая собой активное, легитимное подключение верифицированного Субъекта (человека или ИИ-Агента) к конкретной инсталляции платформы STEOS.

Эта таблица реализует архитектурный паттерн **Phantom Token (Opaque Token)**. В отличие от классического JWT-подхода, когда все права зашиваются в токен и отдаются в браузер пользователя, здесь браузер получает только криптографически случайный идентификатор — ID этой записи (в виде `HttpOnly` Cookie). Вся реальная информация о том, кто это такой и какие у него права, надежно скрыта на бэкенде.

**Архитектурное назначение:**
1.  **Локализация Глобальной Идентичности:** Переводит глобальный паспорт (`steos_id` из STEOS ID) в понятный для локальной платформы формат непрерывного сеанса связи.
2.  **Защита от XSS и кражи токенов:** Так как клиент (браузер) не имеет доступа к содержимому сессии и не может прочитать Cookie через JavaScript, украсть сессию скриптом невозможно.
3.  **Мгновенная инвалидация (Stateful Control):** Позволяет администраторам платформы или системам безопасности мгновенно (за миллисекунды) "убить" сессию злоумышленника, не дожидаясь истечения срока годности JWT-токена.
4.  **Безопасная Имперсонация:** Реализует механизм "Входа под пользователем" для технической поддержки (Support Access), строго фиксируя, кто является реальным владельцем сессии, а кто — "кукловодом".

## 2. Атрибуты (поля) сущности
**Таблица:** `authorized_sessions`

*В соответствии с «Белой книгой разработчика баз данных», для первичного ключа используется `UUID`. Внешние ключи на другие микросервисы (STEOS ID) являются логическими. Секретные токены зашифрованы.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `uuid` | PK, NOT NULL | **Идентификатор сессии (Phantom Token).** Генерируется сервером (UUID v4). Именно это значение устанавливается в браузере в виде `HttpOnly; Secure; SameSite=Strict` Cookie (например, `steos_session_id`). |
| `global_steos_id` | `uuid` | NOT NULL | **Истинный владелец.** Логическая ссылка на `actors.id` из глобального STEOS ID. Указывает, кому юридически принадлежит этот сеанс. |
| `impersonator_steos_id`| `uuid` | NULL | **"Кукловод" (Имперсонатор).** Логическая ссылка на `actors.id` администратора. Если заполнено, значит сессия запущена в режиме техподдержки: система показывает интерфейс `global_steos_id`, но в аудит пишет действия от имени `impersonator_steos_id`. |
| `encrypted_global_refresh`| `varchar` | NULL | **Токен обновления STEOS ID.** Зашифрованная (AEAD/KMS) строка. Локальная платформа сохраняет глобальный `refresh_token`, чтобы бэкенд мог самостоятельно, в фоновом режиме, запрашивать у STEOS ID свежие Access-токены, не отвлекая пользователя переадресациями. |
| `device_fingerprint` | `varchar(255)` | NOT NULL | **Отпечаток устройства.** Хэш характеристик браузера/железа, переданный при входе. Используется для защиты от угона Cookie (Session Hijacking). |
| `ip_address` | `varchar(45)` | NOT NULL | **IP-адрес.** Сетевой адрес, с которого был инициирован вход. |
| `user_agent` | `varchar(1024)`| NULL | **Клиент.** Строка браузера или название приложения (для отображения в логах и UI). |
| `is_active` | `boolean` | NOT NULL, Def `true` | **Флаг активности.** Если `false`, сессия считается принудительно завершенной. Middleware будет отклонять запросы с такой Cookie. |
| `expires_at` | `int8` | NOT NULL | **Время абсолютного истечения (TTL).** Unix Timestamp (UTC). Время, после которого сессия "сгорает" безусловно (например, 30 дней), заставляя пользователя заново пройти OIDC-флоу через STEOS ID. |
| `created_at` | `int8` | NOT NULL | **Дата создания (Входа).** Unix Timestamp (UTC). |
| `updated_at` | `int8` | NOT NULL | **Дата обновления.** Unix Timestamp (UTC). Обновляется при продлении сессии или изменении флага активности. |

*Обязательные индексы:* 
1. Уникальный индекс `UNIQUE (id)`. 
2. Индекс по `global_steos_id` для реализации функции «Завершить все мои сессии на этой платформе».
3. Индекс по `expires_at` для работы фонового сборщика мусора (удаление старых сессий).

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **Контекст сессии**<br>(`session_contexts`) | **Один-к-одному (1:1).** Жесткая связь с таблицей-маршрутизатором, которая указывает, в каком именно Рабочем Пространстве (Workspace) пользователь находится в рамках этой сессии. |
| **Журнал локального доступа**<br>(`access_audit_logs`) | **Один-ко-многим.** Каждое важное действие внутри сессии (вход, выход, имперсонация) записывается в локальный WORM-лог платформы. |
| **STEOS ID**<br>(Global IdP) | **Source of Truth.** Глобальный сервис авторизации, который первично подтвердил личность и может прислать асинхронный Webhook (Back-Channel Logout) на убийство этой сессии. |

## 4. Жизненный цикл и Алгоритм работы

1.  **Создание (OIDC Callback Flow):**
    *   Пользователь возвращается со страницы глобального STEOS ID с кодом авторизации (Authorization Code).
    *   `Authorization Service` отправляет код в STEOS ID и получает взамен `id_token` (кто это), `access_token` и `refresh_token`.
    *   Сервис расшифровывает токен, извлекает `sub` (`urn:steos:actor:123`), проверяет права на вход в платформу.
    *   Создается запись в `authorized_sessions`. Глобальный `refresh_token` шифруется и кладется в БД.
    *   В браузер пользователя устанавливается Cookie: `steos_sess=UUID`.
2.  **Валидация запроса (API Gateway Interception):**
    *   Фронтенд делает запрос: `GET /api/tasks`. Cookie летит автоматически.
    *   API Gateway (или Auth Middleware) достает UUID из Cookie. Ищет его в Redis.
    *   Если сессия активна (`is_active = true`), Gateway добавляет внутрь HTTP-запроса заголовки: `X-Global-Actor-Id: 123`, `X-Workspace-Id: 456` и отправляет запрос в `Task Service`.
3.  **Тихое продление (Silent Refresh):**
    *   Если локальная сессия близка к истечению, бэкенд `Authorization Service` достает зашифрованный `global_refresh_token`, обращается к глобальному STEOS ID по S2S-каналу, получает новый токен и продлевает `expires_at` локальной сессии. Пользователь вообще не замечает этого процесса.
4.  **Уничтожение (Logout / Revocation):**
    *   Пользователь нажимает "Выход". 
    *   Запись в БД обновляется (`is_active = false`), ключ из Redis удаляется, Cookie в браузере затирается.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Session Hijacking Protection (Анти-Угон)** | Использование связки `Cookie + device_fingerprint`. Если злоумышленник украдет значение Cookie с компьютера жертвы и подставит в свой браузер, API Gateway извлечет из запроса новый `fingerprint` хакера. Он не совпадет с тем, что записан в базе/Redis для этой сессии. Запрос будет мгновенно отбит с ошибкой `401 Unauthorized`, а сессия будет принудительно терминирована по подозрению в краже. |
| **Безопасная Имперсонация (God Mode)** | Для расследования багов саппорту нужно видеть экран клиента. Когда админ нажимает "Войти как клиент", создается *новая* сессия. В `global_steos_id` пишется ID клиента, а в `impersonator_steos_id` — ID админа. В `session_contexts` прикрепляется специальный флаг. Когда API Gateway прокидывает заголовки в бизнес-микросервисы, он передает оба ID. Микросервисы отдают данные клиенту, но в WORM-логи (аудит) записывают: "Действие совершил Админ под маской Клиента". Это защищает компанию от юридических претензий. |
| **OIDC Back-Channel Logout** | Поскольку платформа доверяет STEOS ID, она обязана подчиняться его приказам. Если в глобальной админке `Ecosystem God Service` нажать "Забанить пользователя", STEOS ID отправляет POST-запрос на специальный защищенный эндпоинт `Authorization Service` платформы. Платформа находит все `authorized_sessions`, где `global_steos_id` равен забаненному, и устанавливает им `is_active = false`. Злоумышленник вылетает из всех корпоративных пространств за миллисекунды. |

# Контекст сессии (`session_contexts`)

## 1. Общее описание

**Контекст сессии (Session Context / Workspace Router)** — это высокоскоростная операционная сущность-спутник, неразрывно связанная (1:1) с «Авторизованной сессией». Если сессия отвечает на вопрос *«Кто находится за компьютером?»*, то Контекст отвечает на вопрос: **«В каком именно Рабочем Пространстве (Workspace) этот субъект оперирует прямо сейчас?»**.

В архитектуре STEOS, где один глобальный аккаунт (`steos_id`) может быть участником десятков различных Пространств (например, личного, корпоративного и партнерского), переключение между ними должно быть абсолютно бесшовным. Пользователь не должен заново вводить пароль или проходить OIDC-аутентификацию при переходе из «Личного кабинета» в «Корпоративный чат». 

Данная таблица выступает в роли **маршрутизатора запросов на стороне сервера (Server-side Routing)**. Она позволяет фронтенду отправлять запросы (например, "Создать задачу") без необходимости каждый раз прикладывать ID пространства. Локальный API Gateway (внутри Authorization Service) сам заглянет в Контекст сессии и направит задачу в нужное место, обеспечивая строгую изоляцию данных (Multi-Tenant Isolation).

**Архитектурное назначение:**
1.  **Stateful Routing (Состояние маршрутизации):** Избавляет клиентское приложение от необходимости управлять `workspace_id` на своей стороне, снижая риск подделки параметров запроса (IDOR).
2.  **Context Hydration (Обогащение запросов):** Служит связующим звеном между Глобальным Ядром и Локальной Платформой. Позволяет мгновенно связать глобальный паспорт (`steos_id`) с конкретным локальным профилем сотрудника (`local_user_id`), который уже обладает должностью и ролями внутри выбранного Пространства.
3.  **Основа для кэширования разрешений:** Выступает триггером для обновления In-Memory кэша (Redis). При смене контекста система загружает актуальные права (RBAC) именно для нового пространства и кладет их в кэш.

## 2. Атрибуты (поля) сущности
**Таблица:** `session_contexts`

*В соответствии с «Белой книгой разработчика баз данных», для связи 1:1 первичным ключом выступает ID родительской сессии (UUID). Внешние ключи на другие микросервисы (Workspace Service) являются логическими (без жесткого FOREIGN KEY constraint).*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `session_id` | `uuid` | PK, FK, NOT NULL | **Идентификатор сессии.** Первичный ключ, жестко привязанный к таблице `authorized_sessions`. Обеспечивает строгую связь один-к-одному. |
| `workspace_id` | `uuid` | NULL | **Текущее Пространство.** Логическая ссылка на `workspaces.id` из микросервиса `Workspace Service`. Указывает, какой именно тенант сейчас активен на экране пользователя. Если `NULL` — пользователь находится в "Лобби" (общем списке доступных пространств). |
| `local_user_id` | `uuid` | NULL | **Локальный профиль.** Логическая ссылка на `users.id` из `Workspace Service`. Это конкретный профиль пользователя (со статусом, ролью и должностью) внутри выбранного `workspace_id`. Позволяет бизнес-сервисам сразу писать правильного автора в базу. |
| `context_switched_at`| `int8` | NOT NULL | **Время последнего переключения.** Unix Timestamp (UTC). Фиксирует момент, когда пользователь нажал "Перейти в другое Пространство". Помогает при разборе аудиторских логов (для понимания, какое действие в каком пространстве было совершено). |
| `created_at` | `int8` | NOT NULL | **Дата создания контекста.** Unix Timestamp (UTC). Совпадает с датой создания сессии. |

*Обязательные индексы:* 
Так как первичный ключ `session_id` уже кластеризован, дополнительные индексы обычно не требуются, поскольку чтение происходит строго по ID сессии, извлеченному из Cookie.

## 4. Жизненный цикл и Алгоритм работы

1.  **Начальное состояние (Lobby State):**
    *   Пользователь входит в платформу через OIDC (STEOS ID).
    *   `Authorization Service` создает запись в `authorized_sessions`.
    *   Создается зависимая запись в `session_contexts` со значениями `workspace_id = NULL` и `local_user_id = NULL`.
    *   Пользователь видит интерфейс "Мои Пространства" (Лобби).
2.  **Переключение контекста (Context Switch):**
    *   Пользователь кликает на плашку "Tesla Corp" (id: `W-123`).
    *   Фронтенд шлет POST-запрос: `/api/v1/auth/switch-context { workspace_id: "W-123" }`.
    *   **Валидация:** Auth Service делает gRPC вызов в Workspace Service: *"Проверь, пустят ли Васю (его `steos_id`) в Tesla?"*.
    *   **Успех:** Workspace Service отвечает: *"Да, его локальный профиль `U-999`, статус `ACTIVE`"*. (Вместе с ответом может передаваться актуальный массив прав для кэша).
    *   **Обновление:** Auth Service выполняет `UPDATE session_contexts SET workspace_id = 'W-123', local_user_id = 'U-999', context_switched_at = NOW()`.
3.  **Выполнение бизнес-логики (API Routing):**
    *   Пользователь нажимает "Создать задачу". Запрос от фронтенда улетает без указания Пространства в теле или URL (например, `POST /api/tasks`).
    *   Локальный API Gateway достает Session ID из Cookie, лезет в Redis (или в эту таблицу при промахе кэша).
    *   Gateway извлекает контекст: `workspace_id = W-123`, `user_id = U-999`.
    *   Gateway подкладывает эти значения в HTTP-заголовки запроса (`X-Workspace-Id`, `X-Local-User-Id`) и прокидывает его в микросервис задач.
    *   Микросервис задач создает запись, опираясь исключительно на надежный контекст из заголовков.
4.  **Разрыв контекста (Eviction):**
    *   Если администратор в Workspace Service удаляет пользователя из "Tesla Corp" (увольнение), Workspace Service публикует событие в RabbitMQ.
    *   Auth Service ловит событие, находит все активные `session_contexts` этого пользователя для данного `workspace_id` и сбрасывает их в `NULL`. Пользователя принудительно "выкидывает" в Лобби, а его ключи в Redis инвалидируются.

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Just-In-Time (JIT) Onboarding** | Если при попытке переключения контекста Workspace Service отвечает: *"У этого `steos_id` нет профиля в данном Пространстве"*, но глобальные настройки сервера (Platform Access Mode) разрешают авторегистрацию (например, настроен Auto-Join по корпоративному домену), Auth Service может автоматически инициировать процедуру создания локального профиля. Пользователь мгновенно становится участником (member) без заполнения форм. |
| **Security by Obscurity (Защита изоляции / Anti-IDOR)** | Вынос логики маршрутизации на бэкенд (Phantom Token + Session Context) исключает классическую уязвимость Insecure Direct Object Reference (IDOR). Если бы `workspace_id` передавался с фронтенда в параметрах URL (`POST /tasks?workspace=Apple`), хакер мог бы попытаться подменить его и создать задачу в чужой компании. В архитектуре STEOS бэкенд жестко фиксирует контекст на основе серверной сессии, и подделать его из браузера математически невозможно. |
| **Нормализация создания сущностей** | Хранение `local_user_id` непосредственно в контексте сессии избавляет бизнес-микросервисы (CRM, Tasks, Docs) от необходимости делать постоянные дорогостоящие синхронные запросы в базу Workspace Service, чтобы перевести глобальный `steos_id` в локального автора задачи. Микросервисы получают готовый, нужный ID прямо в заголовках от API Gateway. |

# Гостевая сессия (`guest_sessions`)

## 1. Общее описание

**Гостевая сессия (Guest Session)** — это специализированная транзакционная сущность микросервиса Authorization Service, предназначенная для управления доступом **неавторизованных (анонимных) посетителей** платформы.

В экосистеме STEOS, когда локальная платформа (Workspace Service) настраивается в режимах `OPEN` или `PUBLIC`, она позволяет посетителям использовать определенные ресурсы без регистрации (например, прочитать публичную базу знаний, оставить тикет в саппорт или сделать 3 бесплатных генерации ИИ для тест-драйва). Чтобы этот процесс не превратился в бесконтрольную утечку ресурсов (API Abuse), Authorization Service должен "узнавать" анонима при каждом запросе. 

Данная таблица выступает в роли **Теневого Аккаунта (Shadow Identity)**. Она связывает анонимного пользователя с его аппаратным отпечатком (Fingerprint) и историей потребления лимитов, позволяя применять к нему бизнес-правила до момента официальной регистрации.

**Архитектурное назначение:**
1.  **Rate Limiting & Quotas:** Является родительским контейнером для таблицы `guest_feature_usages` (Счетчики квот). Невозможно привязать счетчик бесплатных генераций к "пустоте", он привязывается к ID этой гостевой сессии.
2.  **Защита от Abuse (Soft Fingerprinting):** Связывает гостя с IP-адресом и отпечатком устройства. Если хитрый пользователь пытается обойти ограничение "3 картинки бесплатно", просто почистив Cookies, бэкенд все равно узнает его по Fingerprint и привяжет к старой гостевой сессии.
3.  **Бесшовная конверсия (Hydration Flow):** Сохраняет наработанный гостем стейт (например, созданные им, но еще не сохраненные в базу черновики на клиенте). Когда гость нажимает "Зарегистрироваться" и получает реальный `steos_id`, система может ассоциировать его прошлую активность с новым аккаунтом.
4.  **Аналитика воронок (Funnel Tracking):** Позволяет маркетингу и продакт-менеджерам анализировать поведение гостей: сколько анонимов заходят на платформу, сколько исчерпывают триальные лимиты и сколько из них конвертируются в реальных пользователей.

## 2. Атрибуты (поля) сущности
**Таблица:** `guest_sessions`

*В соответствии с «Белой книгой разработчика баз данных», для первичного ключа используется `UUID`. Так как гостевые сессии являются эфемерными и генерируются в больших объемах, таблица требует агрессивного подхода к очистке устаревших данных (Garbage Collection).*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `uuid` | PK, NOT NULL | **Уникальный идентификатор гостя.** Генерируется сервером (UUID v4). Устанавливается в браузер гостя в виде специальной `HttpOnly` Cookie (например, `guest_session_id`). |
| `workspace_id` | `uuid` | FK, NULL | **Контекст визита.** Логическая ссылка на Пространство (`workspaces.id`). Указывает, какой именно публичный тенант просматривает гость. Важно, так как разные Воркспейсы могут иметь разные публичные лимиты. |
| `device_fingerprint` | `varchar(255)` | NOT NULL | **Отпечаток устройства.** Уникальный криптографический хэш аппаратных характеристик браузера/железа (например, Canvas, WebGL, аудио). Основной механизм "узнавания" анонима после сброса Cookie. |
| `ip_address` | `varchar(45)` | NOT NULL | **IP-адрес.** Сетевой адрес (IPv4/IPv6), с которого гость зашел на платформу. |
| `user_agent` | `varchar(1024)`| NULL | **Строка клиента.** Данные о браузере и ОС. |
| `converted_to_actor_id`| `uuid` | FK, NULL | **Статус конверсии.** Если гость успешно прошел регистрацию (OIDC Flow), в это поле записывается его новообретенный глобальный `steos_id`. Это превращает запись из "анонимной" в "историческую". |
| `expires_at` | `int8` | NOT NULL | **Время истечения (TTL).** Unix Timestamp (UTC). Гостевые сессии обычно живут недолго (например, 24 часа или 7 дней с момента последней активности). |
| `created_at` | `int8` | NOT NULL | **Дата первого визита.** Unix Timestamp (UTC). |
| `updated_at` | `int8` | NOT NULL | **Дата последней активности.** Unix Timestamp (UTC). Обновляется при каждом обращении к закрытым API-эндпоинтам. |

*Обязательные индексы:* 
1. `UNIQUE (device_fingerprint)` — (Опционально) Гарантирует, что одно и то же физическое устройство будет использовать одну и ту же гостевую сессию, предотвращая абуз лимитов.
2. Индекс по `expires_at` — критически важен для ежечасной физической очистки БД от миллионов "протухших" сессий.

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **Использование гостевой фичи**<br>(`guest_feature_usages`) | **Один-ко-многим.** Жесткая связь с таблицей счетчиков, которая фиксирует, сколько бесплатных попыток (из разрешенных) гость уже истратил. |
| **Workspace Service** | **Интеграция по требованию.** Authorization Service запрашивает у Workspace Service: *"Для `workspace_id = 123` какие фичи разрешены анонимам и какие у них лимиты?"* (читает таблицу `public_feature_settings`). |
| **In-Memory Cache (Redis)**| **Репликация.** Как и авторизованные сессии, гостевые сессии и их лимиты кэшируются в Redis для обеспечения сверхбыстрой валидации (Rate Limiting) на API Gateway без нагрузки на PostgreSQL. |
## 4. Жизненный цикл и Алгоритм работы

1.  **Инициализация (Guest Bootstrapping):**
    *   Анонимный посетитель открывает публичную страницу Воркспейса `company.steos.io`.
    *   Фронтенд собирает `device_fingerprint` и делает POST-запрос: `/api/v1/auth/guest-session`.
    *   Бэкенд Auth Service ищет активную сессию по `device_fingerprint` (в БД или Redis).
    *   Если не находит — создает новую запись в `guest_sessions` и возвращает `HttpOnly` Cookie.
2.  **Потребление лимитов (Quota Enforcement):**
    *   Гость нажимает "Сгенерировать текст" (защищенный эндпоинт).
    *   API Gateway извлекает ID из Cookie, проверяет гостевую сессию в Redis.
    *   Gateway запрашивает лимит из `Workspace Service` (например, "Разрешено 3 текста").
    *   Gateway атомарно инкрементирует счетчик в Redis (`guest_feature_usages`). Если лимит не превышен — запрос летит в AI-сервис. Если превышен — возвращает `402 Payment Required` или `401 Unauthorized` с требованием регистрации.
3.  **Конверсия (Hydration / Sign-up):**
    *   Гость исчерпал лимиты и нажимает "Зарегистрироваться".
    *   Проходит флоу в STEOS ID, получает реальный `steos_id`.
    *   Возвращается на платформу. Auth Service видит у него и гостевую Cookie, и новый Access Token.
    *   Бэкенд делает `UPDATE guest_sessions SET converted_to_actor_id = {steos_id}`.
    *   (Опционально) Платформа "переносит" созданные гостем файлы/черновики на его новый официальный профиль.
4.  **Уничтожение (Garbage Collection):**
    *   Если гость ушел и не зарегистрировался, по достижении `expires_at` фоновый процесс безвозвратно удаляет строку из PostgreSQL, освобождая место.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Stateless Execution (Калькулятор)** | Важно понимать, что бизнес-микросервисы (CRM, AI) не сохраняют результаты работы гостей в свои базы данных (так как у гостя нет постоянного `owner_id`). Если гость генерирует текст, микросервис работает в режиме "калькулятора" — обрабатывает запрос и возвращает результат в теле HTTP-ответа. Фронтенд сохраняет этот результат в `localStorage` браузера до момента конверсии (регистрации). |
| **Многоуровневая защита от Абуза** | Использование `device_fingerprint` делает обход гостевых лимитов крайне сложным для рядового пользователя. Перезапуск роутера (смена IP) или использование режима инкогнито (сброс Cookie) не помогут сбросить счетчик "3 бесплатные генерации", так как хэш устройства останется прежним, и бэкенд безошибочно привяжет пользователя к его исчерпанной `guest_session`. |
| **Shadow Banning (Теневой бан)** | Если эвристика замечает, что с одного IP-адреса генерируется сотня разных `device_fingerprint` в минуту (атака ботнета), `Authorization Service` может добавить IP в `local_suspicious_activities` и мгновенно блокировать выдачу новых гостевых сессий, защищая дорогие AI-сервисы платформы. |
