# Введение

Эта группа сущностей формирует **Локальный журнал безопасности и аудита (Local Access Audit)** внутри микросервиса Authorization Service. Она представляет собой строгий, неизменяемый реестр (WORM — Write Once, Read Many), фиксирующий все значимые факты и попытки взаимодействия с защищенным периметром конкретной инсталляции платформы STEOS.

В распределенной архитектуре, где глобальный `STEOS ID` отделен от локальных рабочих Пространств (`Workspace Service`), возникает необходимость в четком разделении зон ответственности при логировании инцидентов.
*   **Глобальный аудит (в STEOS ID)** фиксирует события на уровне Идентичности: успешный ввод пароля, смена номера телефона, выдача OAuth-токенов сторонним играм или приложениям.
*   **Локальный аудит (в Authorization Service)** фиксирует события на уровне Инфраструктуры: кто, с каким токеном и с какого IP-адреса попытался войти в конкретный корпоративный контур (например, `bank.steos.io`), когда пользователь переключился между рабочими Пространствами, и когда его локальная сессия была принудительно убита по сигналу от администратора.

**Архитектурные особенности группы:**

1.  **Compliance & Accountability (Аудиторский след):** Эта группа является фундаментом для прохождения сертификаций (SOC 2, ISO 27001, GDPR) в корпоративных (B2B) инсталляциях. Она позволяет службе безопасности (SecOps) клиента математически точно реконструировать картину инцидента: *"Во сколько сотрудник Иванов вошел в рабочее пространство, и с какого IP-адреса он это сделал?"*.
2.  **Impersonation Tracking (Аудит Имперсонации):** Особая ценность локального аудита — фиксация фактов работы техподдержки от лица пользователей. Когда суперадмин активирует режим "Войти как клиент", аудит ведет строгую двойную запись, гарантируя, что ни одно действие администратора не будет скрыто за личностью клиента.
3.  **Cross-Namespace Observability:** Фиксирует события, прилетающие извне, такие как `Back-Channel Logout` (когда глобальный STEOS ID присылает команду на инвалидацию сессий забаненного юзера). Это позволяет локальному администратору понять, почему половина его сотрудников внезапно "вылетела" из системы.
4.  **High-Throughput Ingestion (Высокоскоростная запись):** Как и все системы аудита в архитектуре STEOS, данная группа спроектирована под асинхронную пакетную запись (Batch Insert). События сначала сбрасываются в оперативную память (Memory Channel / Redis), а затем пачками отправляются в PostgreSQL, чтобы не замедлять критически важные процессы маршрутизации и проверки токенов на API Gateway.

# Событие локального аудита (`local_audit_event_types`)

## 1. Общее описание

**Событие локального аудита (Local Audit Event Type)** — это системная конфигурационная сущность-справочник, которая классифицирует и стандартизирует все типы действий (интентов) и происшествий, подлежащих фиксации в WORM-журнале микросервиса Authorization Service.

В отличие от глобальных событий безопасности (`audit_event_types` в STEOS ID), которые логируют *изменение паролей, добавление 2FA или блокировки на всю жизнь*, данный локальный справочник фокусируется исключительно на **доступе к конкретной инсталляции платформы (Routing & Access)**. 

Он отвечает на вопросы: **«Что именно произошло в рамках этой платформы: пользователь залогинился, переключил рабочее Пространство, или его выбило по команде от глобального STEOS ID?»**.

Так как этот словарь диктует структуру данных для подсистем аналитики (DWH) и интерфейсов аудита, он управляется исключительно через миграции базы данных из среды CORE. Добавление или удаление событий администраторами через UI категорически запрещено.

**Архитектурное назначение:**
1.  **Нормализация Журнала (WORM Standardization):** Заменяет программные строковые константы (магические строки) в коде C#, гарантируя, что каждая строка в гигантской таблице `access_audit_logs` имеет строгий идентификатор (Foreign Key). Это сокращает размер таблицы и обеспечивает сверхбыструю агрегацию данных.
2.  **Обогащение UX (Локализация):** Позволяет фронтенду (в разделе "История активности" в профиле пользователя или в админке Пространства) выводить красивые, понятные и переведенные сообщения (например, "Вход в рабочее пространство" вместо `CONTEXT_SWITCHED`).
3.  **Аналитическая маршрутизация:** Служит фильтром при экспорте данных. Например, события с кодом `GUEST_LIMIT_REACHED` могут автоматически направляться в маркетинговую аналитику (для оценки конверсии в регистрацию), а события `IMPERSONATION_STARTED` — в дашборды службы внутреннего контроля (Security & Compliance).

## 2. Атрибуты (поля) сущности
**Таблица:** `local_audit_event_types`

*В соответствии с «Белой книгой разработчика баз данных», для системного справочника применяется суррогатный первичный ключ `int2`. Идентификаторы жестко фиксируются в миграциях, автоинкремент (IDENTITY) отключен. Текстовые поля снабжены логическими ссылками `_lang_id` на `Translation Service` для международной локализации.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `int2` | PK, NOT NULL | **Уникальный идентификатор.** Задается вручную в миграциях БД. Тип `SMALLINT` (`int2`) обеспечивает минимальный размер B-Tree индексов в высоконагруженной таблице логов. |
| `code` | `varchar(50)` | UNIQUE, NOT NULL | **Стабильный бизнес-код.** Строковый идентификатор события (например, `SESSION_STARTED`, `CONTEXT_SWITCHED`, `SESSION_TERMINATED`). Используется бэкендом (через Logger Facade) для привязки лога к конкретному ID при записи. |
| `name` | `varchar(100)` | NOT NULL | **Название события.** Логическое имя на языке оригинала (например, "Session Started" или "Переключение пространства"). Выводится в таблице активности пользователя. |
| `name_lang_id` | `int2` | NOT NULL | **Язык названия.** Внешний логический ключ на ID языка из `Translation Service` (таблица `languages`). |
| `description` | `varchar(1024)`| NULL | **Техническое описание.** Развернутая подсказка для системных администраторов и DPO (Data Protection Officers), объясняющая, какие именно триггеры вызывают этот лог. |
| `description_lang_id`| `int2` | NULL | **Язык описания.** Внешний логический ключ на ID языка оригинала для поля `description`. |
| `created_at` | `int8` | NOT NULL | **Дата создания.** Unix Timestamp (UTC). |
| `updated_at` | `int8` | NOT NULL | **Дата обновления.** Unix Timestamp (UTC). |

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **Журнал локального доступа**<br>(`access_audit_logs`) | **Один-ко-многим.** Каждая запись в гигантской транзакционной таблице логов доступа жестко ссылается на один тип события из этого справочника (поле `local_audit_event_type_id`). |
| **Translation Service** | **Асинхронная интеграция.** При добавлении нового типа события (через миграцию) STEOS ID публикует событие в RabbitMQ. Система переводов формирует локализации (с ключом вида `auth:audit_event:context_switched:name`) для отображения в UI конечным пользователям. |

## 4. Жизненный цикл и Алгоритм работы

1.  **Декларация (System Setup):**
    *   Архитектор проектирует функционал **Имперсонации** (входа техподдержки под видом клиента).
    *   Создается SQL-миграция, которая добавляет в справочник `local_audit_event_types` новую запись: `id=5`, `code=IMPERSONATION_STARTED`, `name=Session Impersonation`.
2.  **Генерация лога (Runtime Emission):**
    *   Сотрудник техподдержки нажимает "Войти в аккаунт клиента".
    *   `Authorization Service` валидирует права, создает сессию с заполненным полем `impersonator_steos_id`.
    *   Перед отдачей токена бэкенд находит в кэше ID события `IMPERSONATION_STARTED` (например, `id=5`).
    *   Бэкенд формирует лог и отправляет его в асинхронный канал записи. В таблицу `access_audit_logs` уходит `INSERT` с `event_type_id = 5`.
3.  **Аналитика и Отображение (Audit View):**
    *   Владелец корпоративного Воркспейса заходит в админ-панель и открывает раздел "Безопасность -> Логи входов".
    *   Фронтенд делает GET-запрос. Бэкенд считывает записи из `access_audit_logs` и делает `JOIN` со справочником `local_audit_event_types`.
    *   Бэкенд отдает фронтенду ключи локализации. Пользователь видит красивую таблицу, где действие переведено как *"Вход администратора в режиме технической поддержки"*.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Separation of Concerns (Разделение аудита)** | Наличие этого справочника четко очерчивает зону ответственности `Authorization Service`. Сервис не логирует сбросы паролей или "создание задач". Он логирует **только факты перемещения через границу платформы** и переходы между изолированными Воркспейсами внутри нее. Это упрощает поиск уязвимостей (Data Exfiltration) при анализе логов. |
| **Защита от дрейфа данных (Data Drift)** | В отличие от хранения строк (например, `"User logged in"`), использование числовых ID предотвращает катастрофу в аналитике, если продакт-менеджер решит переименовать событие в `"Successful Login"`. ID остается прежним (например, `1`), и все SQL-запросы BI-аналитиков, опирающиеся на этот ID, продолжают работать без поломок. |
## 6. Предустановленные значения (Seeding)

Справочник поставляется с зашитым набором базовых событий, необходимых для соответствия стандартам B2B/Enterprise безопасности. Данные актуальны на момент инициализации БД (язык оригинала — английский, условный `lang_id` = 2).

| `id` | `code` | `name` | Описание архитектурного сценария (`description`) |
| :--- | :--- | :--- | :--- |
| `1` | **`SESSION_STARTED`** | Platform Login | Субъект (или Агент) успешно обменял глобальный токен STEOS ID на локальную Phantom-сессию. |
| `2` | **`SESSION_TERMINATED`** | Session Terminated | Сессия завершена (пользователь нажал "Выйти", либо истек `expires_at`). |
| `3` | **`CONTEXT_SWITCHED`** | Workspace Switched | Субъект сменил рабочий контекст (перешел из одного Пространства в другое, изменив `session_contexts.workspace_id`). Критично для понимания, где он находился в конкретную минуту. |
| `4` | **`BACKCHANNEL_LOGOUT`** | Remote Logout Triggered | Глобальный STEOS ID прислал системный Webhook (например, из-за бана аккаунта), принудительно убивший локальную сессию. |
| `5` | **`IMPERSONATION_STARTED`**| Admin Impersonation | Администратор или система вошли под аккаунтом клиента (God Mode) для диагностики или выполнения сценариев. Требует особого внимания SecOps. |
| `6` | **`GUEST_SESSION_CREATED`**| Guest Visit | Анонимный пользователь начал работу в публичном режиме (Public Mode). |
| `7` | **`GUEST_LIMIT_REACHED`** | Guest Quota Exceeded | Аноним исчерпал бесплатные лимиты (например, 3 генерации) и был заблокирован `Rate Limiter`-ом до регистрации. |

# Журнал локального доступа (`access_audit_logs`)

## 1. Общее описание

**Журнал локального доступа (Local Access Audit Log)** — это фундаментальная транзакционная сущность микросервиса Authorization Service, спроектированная по парадигме **WORM (Write Once, Read Many)**. Она представляет собой строгий, хронологически упорядоченный и аппаратно защищенный от изменения реестр всех значимых фактов преодоления периметра безопасности (логинов, переключений контекста, имперсонаций и блокировок) на уровне конкретной инсталляции платформы STEOS.

В отличие от бизнес-логов, которые генерируются внутри прикладных микросервисов (например, "Создана задача №5" в `Task Service`), эта таблица фиксирует события исключительно на уровне API-шлюза авторизации: "Субъект X успешно обменял глобальный токен на локальную сессию", "Субъект Y переключился в Пространство Z", "Сессия субъекта X была разорвана по сигналу Back-Channel Logout". 

**Архитектурное назначение:**
1.  **Инфраструктурная подотчетность (Accountability):** Является главным юридическим и техническим доказательством того, *кто, когда и откуда* присутствовал в корпоративном контуре платформы. Это базовое требование для прохождения IT-аудитов в B2B секторе (SOX, SOC 2).
2.  **Защита от инсайдеров (Impersonation Audit):** При использовании функции «Войти как пользователь» (God Mode для техподдержки), журнал фиксирует истинного инициатора сессии. Это гарантирует, что действия администратора не будут ошибочно приписаны невиновному клиенту.
3.  **Нормализация данных:** Благодаря ссылке на справочник типов событий (`local_audit_event_types`), таблица избавлена от "магических строк". Это кардинально ускоряет группировку и фильтрацию миллионов записей.
4.  **Источник для эвристики (Threat Hunting):** Данные из этого журнала непрерывно анализируются модулями Rate Limiting и выгружаются (через CDC) во внешние SIEM-системы (например, Splunk) для поиска аномалий в поведении пользователей.

## 2. Атрибуты (поля) сущности
**Таблица:** `access_audit_logs`

*В соответствии с «Белой книгой разработчика баз данных», для таблицы логов используется автоинкрементный `int8` (идеально для партицирования БД). Поле `updated_at` отсутствует, так как редактирование записей недопустимо. Контекст события хранится в сериализованном виде для гибкости.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `int8` | PK, AI, NOT NULL | **Уникальный идентификатор лога.** Суррогатный автоинкрементный ключ (`GENERATED ALWAYS AS IDENTITY`). Обеспечивает строгий хронологический порядок на физическом уровне хранения. |
| `local_audit_event_type_id`| `int2` | FK, NOT NULL | **Тип события.** Ссылка на системный справочник `local_audit_event_types`. Жестко определяет суть произошедшего действия (например, `SESSION_STARTED` или `IMPERSONATION_STARTED`). |
| `global_steos_id` | `uuid` | NULL | **Владелец сессии.** Логическая ссылка на Узел в графе `actors` (STEOS ID). Идентифицирует пользователя, под чьим аккаунтом произошел вход. Может быть `NULL` при анонимных гостевых визитах. |
| `impersonator_id` | `uuid` | NULL | **Истинный исполнитель.** Логическая ссылка на `actors.id` администратора. Заполняется только если вход или действие совершались в режиме "Техподдержки" от лица пользователя `global_steos_id`. |
| `workspace_id` | `uuid` | NULL | **Контекст Пространства.** Логическая ссылка на `workspaces.id` из `Workspace Service`. Указывает, в какое конкретно рабочее пространство пытался зайти или зашел пользователь. `NULL` означает нахождение в глобальном лобби платформы. |
| `session_id` | `uuid` | FK, NULL | **Идентификатор сессии.** Ссылка на `authorized_sessions` (или `guest_sessions`). Позволяет сгруппировать все логи (вход, смена контекстов, выход), относящиеся к одному непрерывному факту аутентификации на конкретном устройстве. |
| `ip_address` | `varchar(45)` | NOT NULL | **IP-адрес.** Сетевой адрес клиента (IPv4/IPv6), инициировавшего HTTP-запрос. |
| `user_agent` | `varchar(1024)`| NULL | **Клиент (Слепок).** Строка User-Agent или название HTTP-клиента (например, `STEOS iOS App v1.2`). |
| `is_success` | `boolean` | NOT NULL | **Флаг успеха.** Показывает результат операции. Например, попытка входа с заблокированного IP-адреса будет залогирована как тип события `SESSION_STARTED` с `is_success = false`. |
| `payload` | `varchar` | NULL | **Детали события.** Сериализованный JSON со специфичными метаданными. Например: `{"reason": "Banned by Firewall"}` для неудачного входа или `{"old_workspace_id": "...", "new_workspace_id": "..."}` для переключения контекста. **Строго запрещено хранить здесь токены или PII (ПДн) в открытом виде.** |
| `created_at` | `int8` | NOT NULL | **Дата фиксации (Timestamp).** Unix Timestamp (UTC) с точностью до миллисекунд. |

*Обязательные индексы:*
1.  B-Tree индекс по `(global_steos_id, created_at DESC)` — для быстрой отрисовки вкладки "История входов" в профиле пользователя или в админ-панели Пространства.
2.  B-Tree индекс по `(session_id)` — для быстрого сбора всей трассировки по конкретной сессии при расследовании инцидентов службой безопасности.
3.  B-Tree индекс по `created_at` — для работы систем партицирования таблиц СУБД и выгрузки старых данных в холодное хранилище (S3 Glacier).

| :--- | :--- |

| **STEOS ID (Global IdP)** | **Логическая ссылка.** Поля `global_steos_id` и `impersonator_id` ссылаются на глобальный граф идентичностей. |
## 4. Жизненный цикл и Алгоритм работы

1.  **Эмиссия события (Fire & Forget):**
    *   Пользователь Вася (находясь в сессии `S-123`) нажимает "Перейти в пространство Tesla".
    *   API-контроллер `SwitchContext` успешно валидирует права в `Workspace Service` и меняет контекст сессии в Redis/БД.
    *   Перед завершением HTTP-запроса код контроллера определяет нужный `local_audit_event_type_id` (например, ID для `CONTEXT_SWITCHED`) и асинхронно генерирует объект `LocalAuditEntry`.
    *   Объект отправляется в фоновый канал (`Channel<T>`) внутри оперативной памяти микросервиса.
2.  **Пакетная Запись (Batch Insert):**
    *   Фоновый воркер (BackgroundService) собирает логи из канала пачками (например, каждые 500 мс или по достижении 1000 записей).
    *   Выполняет сверхбыстрый `Bulk Insert` в PostgreSQL. Это позволяет сервису авторизации выдерживать колоссальные пики трафика без деградации времени ответа для конечного пользователя.
3.  **Архивация (Data Lifecycle Management):**
    *   Таблица аудита — самая быстрорастущая в микросервисе. 
    *   На уровне СУБД настраивается табличное партицирование (Partitioning) по месяцам (на основе поля `created_at`).
    *   Партиции старше 3-х месяцев (если иное не оговорено SLA корпоративного клиента) сжимаются, экспортируются в формат `parquet` и удаляются из "горячей" оперативной БД (Drop Partition), отправляясь в дешевое облачное хранилище (Cold Storage) для нужд комплаенса.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Аппаратная неизменяемость (Immutability Enforcer)** | На таблицу накладывается системный триггер PostgreSQL (или защита на уровне ORM), который возвращает фатальный `EXCEPTION` при любой попытке выполнить `UPDATE` или `DELETE` для отдельной строки. Единственный легитимный способ удалить данные — это системное уничтожение старой партиции целиком. |
| **Sanitization (Маскировка чувствительных данных)** | Все модули бэкенда обязаны пропускать JSON `payload` через санитайзер перед отправкой в канал аудита. Запрещено записывать в лог Authorization Code, Refresh Tokens, Session Cookies, а также любые персональные данные, так как эти логи могут быть доступны специалистам техподдержки клиента. |
| **Silent Event Capture (Невидимый перехват)** | Локальный аудит фиксирует не только действия пользователя, но и системные события. Например, когда глобальный STEOS ID присылает Webhook (Back-Channel Logout) с требованием убить сессию Васи, локальный сервис запишет: `local_audit_event_type_id = [ID for BACKCHANNEL_LOGOUT]`, `is_success = true`, `payload = {"initiator": "GLOBAL_IDP_WEBHOOK"}`. Это избавляет локальных сисадминов от "магии" и вопросов "Почему Вася внезапно вылетел из системы?". |
