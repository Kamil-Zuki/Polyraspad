## **Введение**

Настоящий документ определяет и описывает полный набор функциональных возможностей (сервисных требований) для микросервиса **Personal Vocabulary Service** (PVS).

**PVS** --- это ядро образовательной платформы, отвечающее за управление пользовательским контентом, процесс запоминания (SRS), социальное взаимодействие и монетизацию. Сервис поддерживает методику **Sentence Mining** (изучение слов в контексте), работу в **Offline-режиме**, иерархическую структуру **Проектов** и предоставляет инструменты для **Совместной работы** над контентом.

Документ предназначен для backend-разработчиков, frontend-разработчиков, мобильных разработчиков и системных архитекторов.

**Область ответственности:\**
Сервис отвечает за хранение учебного материала, синхронизацию данных, NLP-обработку, реализацию алгоритмов FSRS, управление маркетплейсом, модерацию, разрешение конфликтов версий и сбор статистики.

Описанные возможности относятся исключительно к микросервису Vocabulary Service. Документ **не охватывает**:

- Обработку платежей (Billing Service).

- Синтез речи (TTS) и хранение бинарных медиа-файлов (Media Service).

- Аутентификацию (Identity Service).

**Ключевые определения:**

- **Проект (Project):** Корневая сущность (язык/предмет). Изолирует настройки SRS, статистику и словари.

- **Карточка (Card):** В парадигме Sentence Mining --- это **Фраза** с выделенным **Целевым словом**.

- **Contribution (Вклад):** Предложенное изменение в чужую колоду (аналог Pull Request).

- **SRS (Spaced Repetition System):** Алгоритм планирования повторений (FSRS).

- **Entitlement (Право доступа):** Разрешение на использование платного контента.

## **SR-STR-01: Реализация корневой сущности «Проект»**

Это сервисное требование описывает введение фундаментальной единицы организации контента в системе --- **Проекта** (Project). Проект служит изолированным контейнером для всех учебных материалов пользователя, связанных с одной конкретной областью знаний (например, «Английский язык» или «Медицинская терминология»). Введение этой сущности необходимо для правильной работы алгоритмов интервального повторения и удобной навигации при изучении нескольких языков одновременно.

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                 **Описание**
  --------------------------- -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Изоляция контекстов**     Главная цель --- разделить данные разных языков/предметов. Карточка со словом \"Gift\" в проекте \"Английский\" (подарок) и в проекте \"Немецкий\" (яд) --- это совершенно разные сущности, которые не должны пересекаться.

  **Корневой контейнер**      Проект является верхним уровнем иерархии. Колоды, карточки, статистика и настройки SRS не могут существовать в вакууме (\"вне проекта\"). Они всегда принадлежат конкретному проекту.

  **Масштабируемость**        Архитектура должна позволять пользователю создавать неограниченное количество проектов, переключаясь между ними как между отдельными \"виртуальными учебниками\".

  **Наследование настроек**   Проект задает глобальные правила обучения (например, параметры алгоритма FSRS), которые по умолчанию наследуются всеми колодами внутри него, избавляя пользователя от микроменеджмента.

  **Управление доступом**     Права доступа и роль пользователя (владелец, редактор, студент) определяются на уровне Проекта, что упрощает шеринг целых курсов.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Personal Vocabulary Service** --- это **Университет**.\
**Проект** --- это конкретный **Факультет** (например, Факультет Иностранных Языков).

1.  **Поступление (Создание):** Когда пользователь решает учить новый язык, он \"открывает факультет\" (создает Проект). Он называет его \"Испанский с нуля\".

2.  **Внутренний порядок:** Внутри здания факультета есть множество **Аудиторий** (Колод). В одной аудитории учат \"Глаголы\", в другой --- \"Кухню\". Но все эти аудитории живут по общим правилам факультета (расписание звонков, методика обучения).

3.  **Изоляция:** Студент, изучающий Испанский, никогда случайно не зайдет в аудиторию факультета \"Высшая математика\". Эти миры не пересекаются.

4.  **Глобальная статистика:** Декан (система аналитики) может легко сказать: \"На факультете Испанского выучено 500 слов\", просто просуммировав знания во всех аудиториях этого здания. Без здания (Проекта) ему пришлось бы бегать по всему городу и спрашивать: \"Это слово испанское или французское?\".

Таким образом, Проект создает необходимый контекст и границы для всех данных и алгоритмов обучения.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает процесс создания нового Проекта пользователем.

**Исходные данные:**

- **Пользователь:** Новый пользователь user-101, который хочет начать учить Японский язык.

- **Входные данные:** Название проекта (\"Japanese Core\"), исходный язык (\"Русский\"), изучаемый язык (\"Японский\").

**Сценарий: Пользователь создает свой первый языковой проект**

1.  **Инициация запроса:** Клиентское приложение отправляет запрос на создание проекта.\
    POST /projects { \"title\": \"Japanese Core\", \"target_lang\": \"jp\", \"native_lang\": \"ru\" }

2.  **Валидация:**

    - Сервис проверяет, авторизован ли пользователь.

    - Сервис проверяет лимиты (например, для Free-аккаунта можно создать не более 3 проектов).

    - Сервис проверяет валидность кодов языков (ISO 639-1).

3.  **Создание структуры данных:**

    - В базе данных создается запись в таблице projects с новым UUID.

    - Автоматически создается связь project_users, где user-101 назначается владельцем (owner).

4.  **Инициализация настроек SRS (Bootstrapping):**

    - Сервис создает дефолтный профиль настроек алгоритма FSRS для этого проекта. Поскольку выбран Японский язык (считается сложным для носителей европейских языков), сервис может применить пресет \"Hard Language\" (более короткие интервалы повторений).

5.  **Создание корневой структуры:**

    - (Опционально) Создается системная колода \"Входящие\" (Inbox), куда будут падать все карточки, добавленные пользователем на бегу, без сортировки.

6.  **Формирование ответа:**

    - Сервис возвращает объект созданного Проекта с его ID и настройками.

7.  **Последствия:**

    - Теперь пользователь находится в контексте project_id.

    - Все последующие запросы на создание колод или карточек **обязаны** содержать этот project_id в заголовке или теле запроса.

    - В интерфейсе появляется дашборд именно для Японского языка.

## **SR-STR-02: Изоляция контекстов обучения (Настройки SRS и Статистика)**

Это сервисное требование определяет правила хранения и применения конфигураций алгоритмов интервального повторения (FSRS/SM-2) и сбора статистики. Оно гарантирует, что прогресс пользователя в одной области знаний (например, в легком для него языке) никак не влияет на алгоритмы планирования в другой (например, в сложном языке), обеспечивая математически корректную изоляцию данных.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                         **Описание**
  ----------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Алгоритмическая адаптивность**    Главная цель --- позволить алгоритму SRS подстраиваться под сложность конкретного предмета. Изучение японских иероглифов требует более частых повторений, чем изучение английских глаголов. Единая глобальная настройка для всех языков неэффективна.

  **Чистота статистики**              Статистические показатели («Словарный запас», «Процент запоминания», «Время изучения») должны рассчитываться строго в рамках Проекта. Суммарный показатель «Всего выучено» имеет смысл только как развлекательная метрика, но не как образовательная.

  **Изоляция весов (FSRS Weights)**   Если используется алгоритм FSRS, его весовые коэффициенты (параметры, определяющие кривую забывания) должны тренироваться и храниться отдельно для каждого Проекта. Мозг пользователя запоминает разные языки с разной скоростью.

  **Контекстная безопасность**        Изменение настроек в одном проекте (например, «Увеличить количество новых слов в день» для Английского) не должно автоматически менять настройки в другом проекте (Немецком), если пользователь этого не хотел.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Пользователь** --- это спортсмен-многоборец.\
**Проект А** --- это «Бег» (Английский язык).\
**Проект Б** --- это «Тяжелая атлетика» (Китайский язык).

1.  **Разные тренеры (Настройки SRS):**

    - Тренер по бегу говорит: «Тренируйся каждый день по часу, отдых не нужен» (настройки для легкого контента).

    - Тренер по штанге говорит: «Поднимай веса раз в три дня, мышцам нужен долгий отдых» (настройки для сложного, нагруженного контента).

    - Если применить правила бега к штанге, спортсмен получит травму (выгорание/burnout). Если наоборот --- не будет прогресса.

    - Поэтому PVS хранит **разные \"тренировочные планы\"** (настройки FSRS: request_retention, maximum_interval) для каждого Проекта.

2.  

3.  **Разные дневники успехов (Статистика):**

    - Нельзя сказать: «Я пробежал 10 км и поднял 100 кг, итого я сделал 110 единиц спорта».

    - Система должна говорить: «В Английском ты на уровне B2 (знаешь 3000 слов), а в Китайском ты на уровне A1 (знаешь 100 иероглифов)». Смешивать эти цифры нельзя.

## **SR-STR-03: Иерархическая структура Колод (Вложенность)**

Это сервисное требование определяет возможность создания вложенных структур колод (sub-decks) произвольной глубины внутри одного Проекта. Это позволяет пользователям организовывать учебный материал не просто как набор разрозненных списков, а как структурированные курсы, книги или тематические деревья (например, *Тема: Путешествия -\> Аэропорт -\> Регистрация*).

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                                  **Описание**
  -------------------------------------------- ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Структуризация знаний**                    Главная цель --- дать пользователю инструменты для логической группировки материала. Это критично для больших проектов (1000+ слов), где плоский список из 50 колод становится неуправляемым.

  **Агрегация обучения (Study Aggregation)**   Ключевой принцип обучения: при запуске сессии для родительской колоды, алгоритм должен (опционально или по умолчанию) включать в очередь карточки из всех её дочерних колод. Это позволяет учить всю \"тему\" целиком.

  **Целостность дерева**                       Вложенность возможна только в рамках одного Проекта. Нельзя вложить колоду из проекта \"Немецкий\" в колоду проекта \"Английский\".

  **Защита от циклов**                         Система должна предотвращать создание рекурсивных циклов (Колода А -\> Колода Б -\> Колода А) на уровне валидации API.

  **Навигация (Breadcrumbs)**                  API должен предоставлять данные, достаточные для построения навигационной цепочки (\"хлебных крошек\") в интерфейсе, чтобы пользователь всегда понимал, где он находится.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Проект** --- это **Книжный шкаф**.\
**Колоды** --- это не просто стопки карточек, это **Папки и Коробки**.

1.  **Аналогия с файловой системой:**

    - Пользователь создает корневую папку \"Грамматика\".

    - Внутри создает папки \"Времена\", \"Предлоги\", \"Артикли\".

    - Внутри \"Времена\" создает \"Present Simple\", \"Past Simple\".

    - Карточки могут лежать как в конечных папках, так и в промежуточных (хотя обычно лежат в конечных).

2.  

3.  **Сценарий обучения (The Power of Nesting):**

    - Если у пользователя завтра тест только по Present Simple, он нажимает \"Учить\" на конкретной под-колоде.

    - Если он хочет повторить всю грамматику, он нажимает \"Учить\" на корневой папке Грамматика.

    - **PVS** рекурсивно собирает карточки со всех вложенных уровней, перемешивает их и выдает единую очередь. Это позволяет пользователю самому регулировать *масштаб* тренировки (от микро-темы до глобального повторения).

4.  

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает процесс создания вложенной колоды и логику запуска обучения.

**Исходные данные:**

- **Пользователь:** user-101.

- **Проект:** Английский (prj-eng).

- **Существующая колода:** \"Сериал Друзья\" (deck-friends-id), которая является корневой в этом проекте.

**Сценарий А: Создание под-колоды**

6.  **Результат:** Пользователь видит карточку из \"Сезона 1\", затем карточку из \"Сезона 2\", воспринимая это как единый урок по сериалу.

## **SR-COL-01: Механизм Предложений (Contributions)**

Это сервисное требование описывает базовый механизм, позволяющий любому пользователю предлагать улучшения для публичных колод, автором которых он не является. Это аналог **Pull Request** в разработке ПО или **«Предложить правку»** в Википедии. Вместо того чтобы просто жаловаться на ошибку в чате, пользователь создает структурированный объект изменения, который владелец колоды может принять или отклонить.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                                    **Описание**
  ---------------------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Безопасность оригинала (Non-destructive)**   Предложение (Contribution) никогда не изменяет данные в реальной колоде мгновенно. Оно сохраняется как отдельная сущность («черновик изменения») и не влияет на процесс обучения других пользователей до момента утверждения.

  **Суверенитет Владельца**                      Только автор/владелец колоды (или назначенные модераторы) имеет право применять изменения. Сообщество предлагает --- автор решает.

  **Атомарность вклада**                         Вклад должен быть атомарным: либо «Исправление одной карточки», либо «Добавление одной новой карточки». Это упрощает модерацию (легче проверить одну правку, чем пакет из 50 изменений).

  **Структурная идентичность**                   Объект Предложения должен полностью повторять структуру Карточки (иметь поля Sentence, Target, Translation, Media), чтобы при слиянии (Merge) можно было просто заменить старые данные новыми.

  **Авторство**                                  Система должна сохранять связь между Предложением и его Автором. Это необходимо для начисления репутации, истории вкладов и защиты прав (SR-COL-07).
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

## **SR-COL-02: Изолированное хранение предложений (Pending State)**

Это сервисное требование описывает архитектурный принцип хранения пользовательских вкладов. Оно гарантирует, что предложенные изменения (Contributions) физически и логически отделены от основного, публичного контента колоды (\"Master-ветки\"). Это предотвращает попадание непроверенного, ошибочного или вредоносного контента в учебный процесс тысяч пользователей до момента официальной модерации.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                             **Описание**
  --------------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Карантин данных (Data Quarantine)**   Главная цель --- создать «буферную зону». Предложения не должны смешиваться с основной таблицей карточек, чтобы не усложнять SQL-запросы на выборку материала для обучения (не нужно каждый раз фильтровать WHERE status != pending).

  **Неизменность оригинала**              Пока предложение находится в статусе PENDING, оригинальная карточка, которую оно пытается изменить, должна оставаться в исходном состоянии и быть доступной для обучения.

  **Стейт-машина (State Machine)**        Каждое предложение имеет строгий жизненный цикл: PENDING (Ожидает) -\> APPROVED (Принято/Влито) или REJECTED (Отклонено).

  **Версионность предложения**            Предложение хранит полный снимок данных на момент отправки. Если автор колоды изменит оригинальную карточку *после* создания предложения, система должна уметь определять конфликт (Stale Contribution).

  **Видимость**                           Предложения в статусе PENDING видны только: а) Автору предложения (в разделе \"Мои вклады\"), б) Владельцу колоды/Модераторам (в разделе \"Входящие\"). Обычные ученики их не видят.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Публичная Колода** --- это **Музейная Выставка**.

1.  **Посетители (Ученики):** Ходят по залам и смотрят на картины (учат карточки). Все картины проверены, висят ровно, подписи правильные.

2.  **Контрибьютор:** Хочет повесить свою картину или переписать табличку под существующей.

3.  **Действие (SR-COL-02):**

    - Он не идет в зал и не вешает свою картину рядом с Моной Лизой.

    - Он относит свою картину в **Приемную (Depot)** --- отдельное помещение, закрытое для посетителей.

    - Он заполняет бланк: \"Предлагаю повесить это в Зал №1\".

4.  

5.  **Результат:**

    - В выставочных залах ничего не изменилось. Посетители не видят хаоса или недоделок.

    - В Приемной (таблица Contributions) лежит объект, ожидающий директора музея.

6.  

**Технически:** Это означает, что у нас есть две разные сущности/таблицы.

- Cards: \"Боевые\" данные. Высокая нагрузка на чтение.

- Contributions: \"Черновики\". Нагрузка на запись, низкая нагрузка на чтение.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий показывает, как система обрабатывает входящее предложение и обеспечивает его изоляцию.

**Исходные данные:**

- **Колода:** \"Basic Spanish\" (deck-span-id).

- **Ученики:** 5000 человек сейчас учат эту колоду.

- **Контрибьютор:** user-helper.

**Сценарий: Обработка входящего предложения на создание новой карточки**

1.  **Входные данные:** user-helper отправляет новую карточку \"El gato - Кот\" в колоду.\
    POST /contributions { \... \"front\": \"El gato\", \"back\": \"Кот\" \... }

2.  **Сохранение (Isolation):**

    - Сервис записывает данные в таблицу contributions.

    - Поле status устанавливается в PENDING.

    - Поле target_deck_id = deck-span-id.

    - **Важно:** В таблицу cards **ничего не пишется**.

3.  

4.  **Проверка изоляции (тест на безопасность):**

    - В ту же секунду один из 5000 учеников запрашивает список карточек: GET /decks/deck-span-id/cards.

    - Сервис делает выборку SELECT \* FROM cards WHERE deck_id = \....

    - Новая карточка \"El gato\" в выборку не попадает, так как физически находится в другой таблице. Учебный процесс не нарушен.

5.  **Доступ для Модератора:**

    - Владелец колоды заходит в \"Панель управления\".

    - Клиент делает запрос: GET /decks/deck-span-id/contributions?status=PENDING.

    - Сервис делает выборку из таблицы contributions.

    - Только теперь данные (\"El gato\") покидают базу и отображаются интерфейсе, но только для владельца.

6.  **Результат:**

    - Предложение надежно сохранено.

    - Риск показать пользователям спам или ошибку равен нулю.

## **SR-COL-03: Интерфейс модерации и отображение Diff (Сравнение версий)**

Это сервисное требование описывает функционал \"Рабочего стола владельца\". После того как пользователи прислали свои предложения (SR-COL-01), и они были безопасно сохранены (SR-COL-02), владельцу колоды необходим удобный инструмент для принятия решений. Ключевой элемент здесь --- **визуализация различий (Diff)**, которая позволяет за секунды понять суть изменения (например, \"исправлена одна буква\" или \"полностью заменен перевод\"), не вчитываясь в весь текст.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                     **Описание**
  ------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Наглядность (Visual Diff)**   Главная цель --- снизить когнитивную нагрузку на модератора. Система должна сама подсвечивать изменения (красным --- удаленное, зеленым --- добавленное), как это делают системы контроля версий (Git).

  **Скорость принятия решений**   Интерфейс должен позволять обрабатывать заявки быстро. Идеальный сценарий для мелких правок: «Увидел Diff -\> Нажал Принять».

  **Контекст автора**             Модератор должен видеть, *кто* предлагает изменение и *какой комментарий* он оставил. Это помогает отсеивать спам и доверять проверенным контрибьюторам.

  **Обратная совместимость**      Если оригинальная карточка была изменена владельцем *после* того, как контрибьютор создал предложение, система должна пометить такое предложение как **\"Конфликтное\" (Stale/Conflict)** и показать предупреждение.

  **Гибкость решения**            Помимо бинарного выбора (Принять/Отклонить), владелец должен иметь возможность **отредактировать** предложение перед принятием (например, исправить опечатку в самом предложении).
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Владелец колоды** --- это **Главный Редактор** газеты.

1.  **Входящая почта:** У него есть папка «Письма читателей» (список PENDING Contributions).

2.  **Просмотр:** Он берет письмо. Читатель пишет: \"В статье про слонов вы написали \'хобот\', а надо \'хо-бо-т\'\".

3.  **Инструмент \"Красная ручка\" (Diff):**

    - Система кладет рядом Оригинал статьи и Предложенную версию.

    - Она не заставляет редактора читать оба текста.

    - Она зачеркивает старое слово и надписывает новое.

4.  **Решение:** Редактор видит, что правка верная. Он ставит печать \"В печать\" (Merge).

5.  **Конфликт:** Если Редактор видит, что статью про слонов он уже удалил вчера, система говорит: \"Внимание! Предложение относится к удаленной статье\". Редактор выбрасывает письмо (Reject).

Этот сценарий описывает процесс получения данных для модерации.

**Исходные данные:**

- **Владелец:** user-owner (автор колоды \"Advanced Biology\").

- **Предложение:** Исправление термина в карточке card-bio-123.

- **Контрибьютор:** user-student.

## **SR-COL-04: Атомарный Merge (Слияние изменений)**

Это сервисное требование описывает техническую процедуру применения одобренного предложения к основной колоде. Это критически важная операция, изменяющая состояние «боевых» данных. Она должна выполняться транзакционно (атомарно), чтобы гарантировать целостность базы данных и запуск всех сопутствующих процессов: обновления версии колоды, уведомления подписчиков и фиксации прав контрибьютора.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                     **Описание**
  ------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Целостность данных (ACID)**   Операция слияния должна быть обернута в транзакцию базы данных. Недопустима ситуация, когда предложение помечено как «Принято», но данные в карточке не обновились (или наоборот).

  **Необратимость статуса**       После выполнения Merge статус предложения переходит в ACCEPTED (или MERGED) и больше не может быть изменен. Если владелец передумает, ему придется создавать новое изменение.

  **Синхронизация подписчиков**   Слияние является триггером для механизма SR-VOC-07 (Обновление контента). Система должна повысить версию колоды (version_id или updated_at), чтобы устройства всех подписчиков узнали о наличии изменений при следующей синхронизации.

  **Фиксация авторства**          При переносе данных из предложения в карточку, система должна сохранить информацию о том, что этот контент был создан контрибьютором (для реализации SR-COL-07 --- Защиты прав).

  **Обработка типов**             Система должна различать логику для типа EDIT (обновление существующей записи) и ADD (создание новой записи в таблице cards).
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Владелец колоды** --- это **Архитектор**, который строит здание (Колоду).

1.  **Ситуация:** Архитектор одобрил чертеж новой комнаты, присланный стажером (Предложение).

2.  **Действие (Merge):** Архитектор дает команду «Строить!».

3.  **Процесс (Транзакция):**

    - Рабочие берут чертеж стажера.

    - Они либо перестраивают существующую стену (EDIT), либо пристраивают новую комнату (ADD).

    - На стене вешается табличка: «Спроектировано стажером Ивановым» (Авторство).

    - В главном журнале здания ставится печать: «Проект утвержден, версия здания 2.0».

    - Чертеж стажера убирается в архив с пометкой «Использовано».

4.  

5.  **Оповещение:** Всем жильцам дома (Подписчикам) рассылается уведомление: «Внимание, планировка изменилась, обновите свои карты».

## **SR-COL-05: История вкладов (Contribution History)**

Это сервисное требование описывает механизм ведения постоянного, неизменяемого журнала всех предложений, которые были приняты в публичную колоду. Это аналог git log или вкладки \"История\" в Википедии. Данная функциональность необходима для атрибуции авторства (кто реально создал этот контент?), построения системы репутации и обеспечения доверия пользователей к качеству материала.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                   **Описание**
  ----------------------------- ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Атрибуция (Авторство)**     Главная цель --- \"Воздать должное\". Если пользователь потратил время на улучшение чужой колоды, его имя должно быть навсегда связано с этим вкладом. Это основа мотивации в Creator Economy.

  **Прозрачность эволюции**     Пользователи должны иметь возможность видеть, как развивалась колода. Живая история изменений (например, \"Добавлено 50 слов за последний месяц\") служит сигналом качества и актуальности контента.

  **Основа для геймификации**   Данные из истории вкладов используются для расчета рейтингов (\"Топ контрибьюторов\"), выдачи бейджей и начисления баллов репутации.

  **Аудит безопасности**        В случае обнаружения вредоносного контента (который прошел модерацию по ошибке), история позволяет быстро найти источник (конкретного пользователя) и принять меры (бан, откат всех его вкладов).

## **SR-COL-06: Настройка Политики вкладов (Contribution Policy)**

Это сервисное требование описывает механизм управления правами на создание предложений. Владелец колоды должен иметь возможность решать, кто именно может предлагать изменения в его контент. Это необходимо для защиты от спама, управления нагрузкой на модерацию и реализации различных моделей владения (от полностью открытой «Вики-модели» до закрытого авторского курса).

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                         **Описание**
  ----------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Гибкость управления**             Главная цель --- дать автору выбор. Не каждая публичная колода должна быть «Википедией». Авторский курс может требовать строгой неизменности, в то время как список сленга выигрывает от участия толпы.

  **Защита от спама**                 Если колода становится очень популярной, владелец может быть завален сотнями низкокачественных предложений. Политика позволяет временно или навсегда закрыть прием заявок («Режим тишины»).

  **Монетизационный рычаг**           В коммерческих сценариях право предлагать правки может быть привилегией только для платных подписчиков (Verified Purchasers), что повышает ценность покупки.

  **Прозрачность для пользователя**   Пользователь должен знать о политике *до* того, как начнет редактировать карточку. Интерфейс должен скрывать или блокировать кнопку «Предложить правку», если политика это запрещает.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Публичная Колода** --- это **Здание**. Владелец вешает на входную дверь табличку с правилами посещения.

1.  **Режим «Open Source» (Открыто):**

    - Табличка: *«Добро пожаловать! Любой может предложить, как перекрасить стены»*.

    - Это подходит для общих словарей, списков частотных слов.

2.  **Режим «Subscribers Only» (Клуб):**

    - Табличка: *«Предложения принимаются только от членов клуба (подписчиков)»*.

    - Это отсеивает случайных прохожих и спамеров. Человек должен проявить интерес (подписаться), прежде чем писать.

3.  **Режим «Closed / Read-only» (Музей):**

    - Табличка: *«Руками не трогать. Администрация сама знает, как лучше»*.

    - Кнопка «Предложить правку» исчезает. Это подходит для официальных курсов, авторских методик или замороженных архивов.

Технически это поле contribution_policy (Enum) в настройках Колоды, которое проверяется при каждом попытке создания Contribution.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает, как система ограничивает действия пользователя на основе политики.

**Исходные данные:**

- **Колода:** \"Official TOEFL Prep\" (deck-toefl).

- **Политика:** CLOSED (Вклады запрещены, так как это официальный платный курс).

- **Пользователь:** user-student.

## **SR-COL-07: Защита прав контрибьютора (Вечный доступ)**

Это сервисное требование описывает механизм управления правами доступа (Entitlements), который автоматически выдает привилегии пользователям, внесшим вклад в развитие контента. Суть требования: если пользователь предложил изменение, и владелец его принял, то этот пользователь получает **гарантированное право** на доступ к этой колоде, даже если владелец впоследствии решит закрыть к ней публичный доступ (сделать приватной).

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                              **Описание**
  ---------------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Справедливый обмен (Fair Exchange)**   Главная цель --- устранить риск эксплуатации. Пользователь инвестирует свое время и знания в улучшение чужого продукта. Взамен он должен получить гарантию, что этот продукт не будет у него отобран.

  **Неотзываемые права (Vested Rights)**   Право доступа, полученное через вклад (Contribution), является более сильным, чем обычная подписка. Владелец колоды не может отозвать это право через настройки приватности (только через бан за нарушения).

  **Прозрачность доступа**                 Система должна явно показывать пользователю: «У вас есть доступ к этой приватной колоде, потому что вы являетесь контрибьютором».

  **Стимуляция качества**                  Это требование мотивирует пользователей делать *качественные* вклады. Чтобы получить вечный доступ к платной или закрытой колоде, нужно предложить улучшение, которое владелец захочет принять.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Публичная Колода** --- это **Частный Клуб**.

1.  **Обычный режим:** Вход в клуб открыт для всех (Public). Люди заходят, слушают музыку, уходят.

2.  **Вклад:** Один из посетителей (Контрибьютор) замечает, что рояль расстроен. Он предлагает владельцу клуба: «Давай я настрою рояль?». Владелец соглашается (Accept Contribution).

3.  **Награда:** В благодарность владелец выдает этому посетителю **«Золотую карту члена клуба»**.

4.  **Закрытие клуба:** Через месяц владелец решает сделать вечеринку закрытой (Private), только для своих.

5.  **Результат:**

    - Обычные посетители (подписчики) стоят перед закрытой дверью. Их не пускают.

    - Наш Контрибьютор показывает «Золотую карту» охране. Система видит карту и пропускает его внутрь, несмотря на то, что для остальных клуб закрыт.

6.  

Технически это реализуется через таблицу UserEntitlements или расширенную проверку прав в middleware.

## **SR-COL-08: Automatic Detachment (Авто-отсоединение при удалении)**

Это сервисное требование описывает защитный механизм, который срабатывает в момент, когда владелец публичной колоды решает удалить её или закрыть к ней доступ. Чтобы не нарушать учебный процесс пользователей, которые уже активно учат эту колоду (имеют SRS-прогресс) или вносили в неё вклад, система не удаляет данные у них, а автоматически конвертирует их «Подписку» в «Личную копию» (Fork). Это гарантирует сохранность пользовательских данных независимо от действий автора контента.

### **1. Цель и ключевые принципы**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                     **Описание**
  ------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Суверенитет прогресса**       Главная цель --- защитить инвестиции времени ученика. Если пользователь потратил 100 часов на изучение колоды, никто (даже автор колоды) не имеет права обнулить этот прогресс.

  **Бесшовность (Continuity)**    Переход от состояния «Подписчик» к состоянию «Владелец копии» должен быть незаметным для процесса обучения. Очередь на завтра не должна измениться. Интервалы повторений должны сохраниться.

  **Разрыв связи (Detachment)**   После операции связь с оригиналом разрывается навсегда. Пользователь больше не будет получать обновлений от автора (так как оригинала больше нет или он закрыт), но получает полный контроль над своей копией.

  **Избирательность**             Копирование происходит только для **активных** пользователей (тех, у кого есть прогресс \> 0 или принятые вклады). «Мертвые» подписки (пользователи, которые добавили колоду, но не учили) могут быть удалены без копирования.

  **Уведомление**                 Система должна явно сообщить пользователю: «Автор удалил колоду, но мы сохранили для вас персональную копию».
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Публичная Колода** --- это **Арендованная квартира**.

1.  **Ситуация:** Вы живете в квартире (учите колоду), расставили свою мебель (SRS-прогресс), повесили картины (заметки).

2.  **Угроза:** Владелец дома решает снести здание.

3.  **Обычный мир:** Вас выселяют, мебель выбрасывают. Вы теряете всё.

4.  **Мир PVS (SR-COL-08):**

    - В момент сноса срабатывает «магия».

    - Система мгновенно строит точную копию этой квартиры в другом месте.

    - Вся ваша мебель (прогресс) телепортируется в новую квартиру на те же места.

    - Вам выдаются документы на право собственности (теперь это Ваша колода).

    - Вы больше не платите аренду и не зависите от хозяина, но и ремонт он вам больше не сделает.

5.  

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает сложную backend-процедуру обработки удаления популярной колоды.

**Исходные данные:**

- **Колода:** \"Popular French\" (deck-fr). Владелец: user-author.

- **Активный ученик:** user-student. Имеет 500 выученных слов (записи в UserCardProgress).

- **Пассивный подписчик:** user-newbie. Подписался, но не начал учить.

**Сценарий: Автор удаляет публичную колоду**

1.  **Инициация:** Владелец нажимает «Удалить колоду».\

2.  **Анализ зависимостей (Impact Analysis):**

    - Сервис проверяет таблицу deck_subscriptions и user_card_progress.

    - Находит user-student (есть прогресс).

    - Находит user-newbie (нет прогресса).

3.  

4.  **Обработка пассивных (Soft Cleanup):**

    - У user-newbie подписка просто аннулируется. Он получает уведомление «Колода была удалена автором».

6.  **Миграция активных (Detachment Process):**

      - Копируются все карточки из deck-fr в новую колоду (новые card_id).

7.  

8.  **Физическое удаление:**

    - После завершения миграции всех активных пользователей, оригинальная колода deck-fr помечается как удаленная (is_deleted = true) или физически удаляется.

9.  

10. **Результат:**

    - user-student заходит в приложение. Он видит ту же колоду, но теперь он её владелец.

    - Он продолжает учить слова ровно с того места, где остановился.

## **SR-MKT-02: Механизм Smart Preview (Умный предпросмотр)**

Это сервисное требование описывает функционал автоматической генерации ограниченной, но репрезентативной выборки контента из платного Товара. Покупатель должен иметь возможность оценить качество материалов (голос диктора, точность перевода, сложность предложений) до совершения оплаты. В отличие от статических скриншотов, Smart Preview предоставляет интерактивный опыт --- «мини-урок».

### **1. Цель и ключевые принципы**

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                              **Описание**
  ---------------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Доверие через прозрачность**           Главная цель --- показать покупателю, за что он платит. В образовании качество контента субъективно, поэтому возможность «пощупать» товар критически важна для конверсии.

  **Zero-Config (Автоматизация)**          Автору не нужно вручную создавать отдельную «Демо-колоду». Система сама генерирует превью из основной колоды «на лету», используя заданные алгоритмы выборки.

  **Защита от утечки (Leak Prevention)**   Превью должно быть строго ограничено (например, не более 5-10% от объема или фиксированные 20 карточек), чтобы предотвратить потребление контента без оплаты.

  **Интерактивность**                      Превью --- это не список слов, а **симуляция реальной сессии обучения**. Пользователь должен иметь возможность перевернуть карточку, прослушать аудио и увидеть контекст.

  **Репрезентативность**                   Выборка должна включать карточки из разных частей курса (начало, середина), чтобы показать, что качество контента стабильно высоко на всем протяжении.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Маркетплейс** --- это **Книжный магазин** или **Сыроварня**.

1.  **Сценарий «Кот в мешке»:** Покупатель видит закрытую банку сыра за \$20. Этикетка красивая, но вкусно ли внутри? Риск покупки высок.

2.  **Сценарий Smart Preview:**

## **SR-MKT-03: Управление Правами доступа (Entitlements)**

Это сервисное требование описывает механизм предоставления доступа к платному контенту. Поскольку **Vocabulary Service** делегирует обработку платежей внешнему **Billing Service**, он должен иметь надежный API или слушатель событий (Webhook/Event Consumer), который реагирует на факт успешной оплаты. Результатом выполнения этого требования является создание записи о праве доступа (Entitlement), которая разрешает пользователю взаимодействовать с закрытым ресурсом.

### **1. Цель и ключевые принципы**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                            **Описание**
  -------------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Разделение ответственности**         PVS не касается денег, карт и чеков. Он оперирует только понятиями «Товар» и «Право доступа». Сигналом к действию служит доверенное сообщение от Billing Service.

  **Мгновенная доставка**                Доступ к контенту должен открываться в течение секунд после подтверждения транзакции. Пользователь не должен ждать ручной обработки.

  **Идемпотентность**                    Если Биллинг по ошибке пришлет уведомление об оплате одного и того же заказа дважды, PVS должен корректно это обработать (не дублировать колоды, не выдавать ошибок), просто подтвердив наличие прав.

  **Ролевая модель (Buyer vs Author)**   Система должна четко различать права Владельца (edit, delete) и Покупателя (view, learn, sync). Покупатель получает лицензию на использование, а не права на исходник.

  **Связь с транзакцией**                Запись о праве доступа должна хранить ссылку на order_id или transaction_id. Это критично для разбора претензий («Я купил, а доступа нет») и обработки возвратов (Refunds).
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Турникет в метро**, а **Billing Service** --- это **Касса**.

1.  **Покупка:** Пассажир (Пользователь) подходит к Кассе, платит деньги.

2.  **Сигнал:** Касса печатает билет с QR-кодом и одновременно посылает сигнал в центральный компьютер: «Билет №777 оплачен».

3.  **Регистрация права (SR-MKT-03):** Центральный компьютер (PVS) вносит запись в базу: «Билет №777 теперь валиден для входа».

4.  **Использование:** Пассажир подходит к Турникету, прикладывает билет. Турникет проверяет базу, видит разрешение и открывается.

В цифровом мире это означает, что после оплаты колода автоматически появляется в списке «Мои курсы» у пользователя с пометкой «Куплено».

## **SR-MKT-04: Защита от вторичного распространения (DRM-lite)**

Это сервисное требование описывает механизм ограничений, накладываемых на копии (форки) платного контента. Когда пользователь приобретает платный курс, он получает право использовать его для личного обучения, но не право распространять его дальше. Сервис должен технически гарантировать, что материалы, за которые были заплачены деньги, не появятся в публичном доступе бесплатно через аккаунт покупателя.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                              **Описание**
  ---------------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Защита дохода автора**                 Главная цель --- предотвратить каннибализацию продаж. Если любой покупатель сможет перевыложить колоду бесплатно, автор потеряет мотивацию создавать контент.

  **Наследование ограничений**             При создании копии (Fork) платной колоды, копия должна наследовать специальную метку (флаг), которая блокирует определенные действия. Эта метка должна сохраняться даже при переименовании или изменении контента копии.

  **Разрешение на личное использование**   Защита не должна мешать обучению. Пользователь **имеет право** редактировать свою копию, удалять из нее слова или добавлять свои заметки (в отличие от жесткого DRM в электронных книгах). Ограничение касается только *публикации*.

  **Блокировка публикации**                Система должна запрещать установку флага is_public = true для колод, помеченных как Commercial-Derivative.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Платная колода** --- это **Книга с водяными знаками**.

1.  **Покупка:** Вы покупаете учебник в магазине.

2.  **Личное использование:** Вы можете делать пометки на полях, вырывать страницы, раскрашивать картинки. Это ваша копия, вы вольны делать с ней что угодно *внутри своего дома* (в своем Пространстве).

3.  **Попытка копирования (Ксерокс):**

    - Вы решаете сделать ксерокопии и раздавать их друзьям на улице (Сделать колоду публичной).

    - Но на каждой странице стоит невидимая печать **«НЕ ДЛЯ ПРОДАЖИ / КОПИЯ №123»**.

    - Умный ксерокс (наш Сервис) видит эту печать и выдает ошибку: «Копирование запрещено. Документ защищен авторским правом».

4.  

5.  **Результат:** Вы можете учиться сами, но не можете стать дистрибьютором чужого контента.

Технически это реализуется через поле licensing_type или origin_type в таблице decks.

## **SR-MKT-05: Система Отзывов и Рейтингов (Verified Reviews)**

Это сервисное требование описывает механизм сбора обратной связи от пользователей, купивших товар. В отличие от открытых комментариев, система рейтингов в PVS строго привязана к факту владения товаром (**Verified Purchase**). Это предотвращает накрутку рейтинга ботами или атаку конкурентов («Review Bombing»). Рейтинг напрямую влияет на ранжирование товара в поиске и на репутацию автора.

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                           **Описание**
  ------------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Доверие (Trust)**                   Главная цель --- предоставить будущим покупателям честную информацию о качестве продукта. Отзыв с пометкой «Проверенная покупка» ценится выше, чем анонимное мнение.

  **Anti-Abuse (Защита от накруток)**   Оставить отзыв может только пользователь, у которого есть активное право доступа (Entitlement) к этому товару. Автор не может оценивать свои товары. Один пользователь --- один отзыв на товар.

  **Агрегация**                         Система должна автоматически пересчитывать средний рейтинг товара (звезды от 1 до 5) и обновлять его в карточке товара для использования в сортировке и фильтрах.

  **Обратная связь для автора**         Отзывы --- это инструмент улучшения качества. Автор должен иметь право **ответить** на отзыв (один раз), чтобы поблагодарить или прояснить ситуацию, если ученик что-то не понял.

  **Модерация контента**                Текст отзывов также проходит проверку на стоп-слова (автоматически) и может быть скрыт модератором по жалобе, если содержит оскорбления (но не за низкую оценку).
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Маркетплейс** --- это **Steam** или **Amazon**.

1.  **Покупка:** Пользователь покупает курс «Испанский для туристов».

2.  **Опыт использования:** Он проходит несколько уроков. Если качество аудио плохое или переводы неточные, он расстраивается. Если все отлично --- радуется.

3.  **Оценка:**

    - Пользователь ставит **4 звезды**.

    - Пишет текст: *«Материал отличный, но в разделе \'Отель\' тихий звук»*.

4.  

5.  **Система (PVS):**

    - Проверяет: «Действительно ли этот человек купил курс?». Да.

    - Публикует отзыв с бейджем ✅ **Verified Purchase**.

    - Пересчитывает средний рейтинг курса: был 5.0, стал 4.8.

6.  

7.  **Реакция:** Автор получает уведомление, читает отзыв и пишет ответ: *«Спасибо! Звук в разделе \'Отель\' перезаписал, обновление уже доступно»*.

## **SR-MKT-06: Предоставление статистики продаж и использования**

Это сервисное требование описывает аналитический инструментарий для авторов контента («Кабинет Автора»). Чтобы создавать качественный продукт, автор должен видеть не только финансовые показатели (сколько купили), но и образовательные метрики (как учат). Это позволяет авторам понимать свою аудиторию, улучшать сложные места в курсах и прогнозировать доход.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                     **Описание**
  ------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Прозрачность бизнеса**        Автор должен видеть четкую картину своих продаж: количество транзакций, сумму выручки (gross/net), количество возвратов. Это основа доверия к платформе.

  **Образовательная аналитика**   Уникальная ценность PVS --- в данных об обучении. Автор должен видеть **Retention** (удержание): на какой карточке ученики бросают курс? Если 50% отваливаются на 10-й карточке, значит, там ошибка или слишком сложно.

## **SR-MOD-01: Пре-модерация платных товаров (Submission & Review)**

Это сервисное требование описывает процесс контроля качества и безопасности, который должен пройти любой Товар (Product) перед тем, как стать доступным для покупки в Маркетплейсе. В отличие от приватных колод, где пользователь может писать что угодно, платный контент является лицом платформы. Сервис должен реализовать механизм «шлюза» (Gatekeeper), который задерживает публикацию до момента одобрения автоматической системой или живым модератором.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                                 **Описание**
  ------------------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Безопасность платформы (Safety First)**   Главная цель --- не допустить публикацию контента, нарушающего законы или правила магазинов приложений (Hate speech, порнография, насилие). Наличие пре-модерации --- обязательное требование Apple/Google для приложений с UGC.

  **Контроль качества**                       Мы не должны пропускать «мусорные» товары (пустые колоды, колоды с названием «test», товары без описания), так как это снижает доверие покупателей к Маркетплейсу.

  **Гибридная проверка**                      Для масштабируемости процесс должен быть двухэтапным: сначала быстрые **Авто-фильтры** (стоп-слова, проверка длины), затем, если нужно, **Ручная проверка** человеком.

  **Жизненный цикл (State Machine)**          Товар не может просто переключиться из DRAFT в PUBLISHED. Он обязан пройти через промежуточный статус PENDING_REVIEW.

  **Обратная связь**                          Если товар отклонен, автор должен получить четкую причину (например, «Нарушение авторских прав в описании»), чтобы иметь возможность исправить и подать заявку снова.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

4.  

5.  **Инспекция:** Модератор открывает заявку, смотрит обложку (нет ли там запрещенки), читает описание, просматривает 5-10 случайных карточек.

## **SR-MOD-02: Система Жалоб и Автоматической блокировки (Reporting Mechanism)**

Это сервисное требование описывает функционал, позволяющий конечным пользователям сообщать о нарушениях в опубликованных товарах. Поскольку модераторы не могут отследить каждое изменение в реальном времени, система полагается на бдительность сообщества. Ключевой особенностью является механизм **«Автоматического предохранителя»**: если количество жалоб превышает критический порог за короткое время, товар автоматически скрывается из продажи до разбирательства.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                            **Описание**
  -------------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Реактивность**                       Главная цель --- минимизировать время нахождения вредоносного контента (например, hate speech или порнографии) на витрине. Сообщество реагирует быстрее, чем штатные модераторы.

  **Circuit Breaker (Предохранитель)**   При всплеске жалоб система должна действовать по принципу «Сначала скрой, потом разбирайся». Это защищает репутацию платформы от вирусного распространения плохого контента.

  **Категоризация**                      Жалоба должна быть структурирована. Пользователь должен выбрать причину: «Нарушение авторских прав», «Оскорбительный контент», «Техническая ошибка», «Обман/Спам». Это помогает приоритезировать очередь модерации.

  **Защита от «Review Bombing»**         Система должна защищать авторов от атак конкурентов. Жалобу может оставить только авторизованный пользователь, и вес жалобы может зависеть от репутации пользователя (или факта покупки товара).

  **Изоляция последствий**               Скрытие товара («Теневой бан») не должно влиять на пользователей, которые *уже купили* этот курс. У них он остается доступным (согласно SR-COL-07), пока модератор не примет решение о полном удалении.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

1.  **Инцидент:** Продавец выставил на прилавок книгу с запрещенным содержанием. Полицейский (Модератор) сейчас на другой улице и не видит этого.

## **SR-MOD-03: Версионность контента при бане (Safe Rollback)**

Это сервисное требование описывает механизм отката публичной версии товара к предыдущему безопасному состоянию. В системе, где контент постоянно обновляется, блокировка всего товара целиком (удаление с витрины) может быть чрезмерной мерой, если нарушение содержится только в последнем обновлении. Данный механизм позволяет модераторам точечно отменять вредоносные изменения, сохраняя доступность товара для покупателей и бизнеса, но очищая его от нарушений.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                        **Описание**
  ---------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Непрерывность бизнеса**          Главная цель --- не убивать продажи и не наказывать покупателей за ошибку автора. Если версия 1.0 была хорошей, а версия 1.1 плохой --- мы должны просто вернуть версию 1.0 в продажу.

  **Сохранение улик**                Вредоносная версия не удаляется физически. Она помечается как REJECTED и сохраняется в истории версий для доказательной базы в случае спора с автором или блокировки аккаунта.

  **Принудительная синхронизация**   После отката версии, система должна отправить сигнал всем устройствам, которые успели скачать «плохую» версию, чтобы они принудительно синхронизировались с «хорошей» (откатили локальные изменения).

  **Блокировка редактирования**      На время разбирательства возможность автора вносить новые изменения в этот товар блокируется (Edit Lock), чтобы он не мог вступить в «войну правок» с модератором.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Товар** --- это **Рекламный щит** на улице.

1.  **Легальное начало:** Автор вешает плакат «Учим английский». Модератор одобряет. Все хорошо.

2.  **Атака (Подмена):** Ночью автор приходит и заклеивает плакат новым: «Покупайте запрещенные вещества».

3.  **Реакция (SR-MOD-03):**

    - Утром прохожие (пользователи) жалуются.

    - Модератор видит нарушение. Вместо того чтобы сносить весь щит (удалять товар), он нажимает кнопку **«Откат»**.

    - Система сдирает верхний слой (плохой плакат). Под ним остался старый, добрый «Учим английский».

    - Автор получает штраф, а его ведро с клеем отбирают (блокировка редактирования).

4.  

5.  **Результат:** Щит продолжает работать и приносить пользу, но вредоносный контент удален из публичного поля.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает действия модератора при обнаружении нарушения в обновлении.

**Исходные данные:**

- **Товар:** \"Funny Jokes\" (product-jokes).

- **История версий:**

  - v1 (10.01.2025): Safe. Статус: ARCHIVED.

  - v2 (12.01.2025): Contains hate speech. Статус: PUBLISHED (текущая).

- 

- **Пользователь:** user-victim (успел скачать v2).

**Сценарий: Модератор выполняет откат версии**

1.  **Обнаружение:** Модератор получает жалобу на товар и видит нарушение в последнем обновлении.

2.  **Действие (Rollback):**

    - Модератор в админ-панели выбирает предыдущую версию (v1) и нажимает «Восстановить как активную».

    - POST /admin/moderation/products/product-jokes/rollback

    - Body: { \"target_version\": \"v1\", \"reason\": \"Hate speech in v2\" }

3.  

4.  **Системная обработка:**

    - PVS помечает версию v2 как REJECTED / BANNED.

    - PVS помечает версию v1 как PUBLISHED.

    - Указатель current_deck_version_id в товаре меняется на ID снимка v1.

    - На товар накладывается LOCK (автор не может публиковать обновления).

5.  

6.  **Оповещение клиентов (Force Sync):**

    - Система генерирует событие CONTENT_ROLLBACK.

    - Устройство пользователя user-victim при следующей синхронизации получает инструкцию: «Твоя локальная версия (v2) признана небезопасной. Выполнить принудительный откат до v1».

7.  

8.  **Результат на клиенте:**

    - Вредоносные карточки исчезают с устройства пользователя.

    - Возвращаются старые карточки.

    - **Нюанс SRS:** Если в v2 были *новые* карточки, прогресс по ним удаляется (так как карточек больше нет). Если были *изменены* старые, прогресс сохраняется, но текст откатывается.

9.

## **SR-VOC-01: Создание Фразовых карточек (Sentence Mining)**

Это сервисное требование описывает API для создания основной единицы обучения в системе. В парадигме **Sentence Mining**, мы не учим изолированные слова. Мы учим предложения (i+1), в которых есть одно неизвестное слово (Target). Сервис должен гарантировать, что каждая создаваемая карточка содержит не только изучаемую лексему, но и полноценный контекст, в котором она была встречена.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                        **Описание**
  ---------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Контекстоцентричность**          Главная цель --- устранить двусмысленность. Слово \"Run\" может означать \"бежать\", \"управлять\" (бизнесом) или \"баллотироваться\". Без предложения-контейнера (Sentence) обучение неэффективно.

  **Фокус на Цели (Target Focus)**   Карточка должна четко определять, *что именно* в этом предложении мы учим. Это поле Target (или Focus Word). Нельзя создать карточку просто с предложением, система должна знать, какой элемент скрывать в тестах.

  **Целостность данных**             Система должна валидировать, что Target действительно содержится внутри Sentence. Нельзя создать карточку с предложением \"Hello World\" и целью \"Apple\".

  **Привязка к Проекту**             Карточка не может существовать сама по себе. Она должна быть привязана к Колоде, которая, в свою очередь, принадлежит Проекту (языку).

  **Богатая нагрузка (Payload)**     API должен поддерживать создание карточки со всеми сопутствующими данными за один запрос: перевод фразы, заметки, теги и ссылки на медиа.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Карточка** --- это **Музейный экспонат под стеклом**.

1.  **Старый подход (Flashcards):**

    - Экспонат: Камень.

    - Табличка: \"Просто камень\".

    - Пользователь смотрит и не понимает, откуда он и зачем.

2.  

3.  **Новый подход (Sentence Mining):**

    - Экспонат: Тот же камень, но он лежит в **Диораме** (Контекст/Sentence), изображающей берег древней реки.

    - **Подсветка (Target):** На камень направлен луч прожектора. Мы учим именно его, но видим всю картину.

    - **Табличка (Translation):** Описывает смысл всей сцены, а не только камня.

4.  

**В PVS:\**
Пользователь читает книгу и видит фразу: *\"He decided to **address** the issue\"*.\
Он не создает карточку \"Address - Адрес\".\
Он создает карточку:

- **Front (Sentence):** \"He decided to **address** the issue\"

- **Target:** \"address\"

- **Back (Meaning):** \"Заняться / Решить (проблему)\"

- Теперь PVS знает, что здесь \"address\" --- это глагол, и будет генерировать упражнения именно на этот смысл.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает процесс создания карточки через API.

**Исходные данные:**

- **Пользователь:** user-learner.

- **Колода:** \"Work & Business\" (deck-biz-id).

- **Контент:** Фраза из рабочей переписки.

**Сценарий: Пользователь добавляет новую фразу**

**Инициация запроса:** Клиентское приложение (или браузерное расширение) отправляет данные.\
POST /cards\
code JSON\
downloadcontent_copy\
expand_less\
{

\"deck_id\": \"deck-biz-id\",

\"sentence\": \"Let\'s table this discussion for now.\",

\"target\": \"table\",

\"translation\": \"Давай отложим это обсуждение пока.\",

\"notes\": \"Идиома: отложить на потом (в US English).\"

}

1.  

2.  **Валидация (Business Rules):**

    - Сервис проверяет существование колоды и права доступа.

    - **Validation Logic:** Сервис ищет вхождение строки target (\"table\") внутри строки sentence (\"Let\'s table this\...\").

    - *Успех:* Слово найдено.

    - *Ошибка:* Если бы пользователь ввел target=\"chair\", сервис вернул бы 400 Bad Request: Target word not found in sentence.

3.  

4.  **Обработка (Internal Processing):**

    - Сервис вычисляет индекс вхождения (Start: 6, End: 11). Это понадобится для SR-VOC-02 (Разметка).

    - (Асинхронно) Запускается SR-BG-01 (NLP) для определения леммы (\"table\" -\> \"table\") и части речи (Verb).

5.  

6.  **Сохранение:**

    - Запись создается в таблице cards.

    - Увеличивается счетчик карточек в колоде и проекте.

7.  

**Формирование ответа:\**
code JSON\
downloadcontent_copy\
expand_less\
{

\"id\": \"card-new-uuid\",

\"sentence\": \"Let\'s table this discussion for now.\",

\"target\": \"table\",

\"html_markup\": \"Let\'s \<b\>table\</b\> this discussion for now.\", // Авто-разметка

\"srs_status\": \"NEW\"

}

8.  

9.  **Результат:** Карточка готова к изучению. В режиме тренировки пользователь увидит предложение с пропуском на месте слова \"table\".

## **SR-VOC-02: Разметка целевого слова (Target Highlighting & Indexing)**

Это сервисное требование описывает технический механизм идентификации и хранения точного местоположения изучаемого слова (Target) внутри предложения (Sentence). Сервис должен не просто знать, что мы учим слово \"run\", но и понимать, что в предложении *\"I run a marathon while my nose runs\"* мы учим **первое** слово \"run\" (бежать), а не второе (течь). Это необходимо для корректной генерации тестов и визуального акцентирования.

### **1. Цель и ключевые принципы**

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                               **Описание**
  ----------------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Устранение неоднозначности**            В языке часто встречаются омонимы или повторы слов в одном предложении. Система должна хранить не просто строку-цель, а ее **позиционный индекс** (смещение и длину) или использовать специальную разметку при хранении.

  **Поддержка фраз (Multi-token)**          Целью может быть не только одно слово, но и идиома или фразовый глагол (например, *\"give up\"*). Разметка должна поддерживать выделение произвольного диапазона символов.

  **Разделение хранения и представления**   В базе данных рекомендуется хранить чистый текст и метаданные индексов (для эффективного поиска), но API должен уметь отдавать клиенту уже размеченный текст (например, с тегами \<b\> или \[cloze\]) для удобства рендеринга.

  **Устойчивость к редактированию**         Если пользователь редактирует предложение (исправляет опечатку в другом слове), разметка целевого слова не должна \"слететь\". Система должна пересчитывать индексы при обновлении контента.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Карточка** --- это **Секретный документ**.

1.  **Исходный текст:** *\"Агент 007 прибыл в Лондон.\"*

2.  **Задача:** Мы хотим выучить слово \"Лондон\".

3.  **Механизм разметки:**

    - Пользователь (или алгоритм) выделяет слово маркером.

    - Система запоминает: *\"Цель начинается с 14-го символа, длина 6 символов\"*.

4.  

5.  **Режим \"Просмотр\" (Front Side):**

    - Система берет черный маркер и закрашивает слово по этим координатам.

    - Пользователь видит: *\"Агент 007 прибыл в \[\.....\]\"*.

    - Его мозг вынужден восстановить контекст.

6.  

7.  **Режим \"Ответ\" (Back Side):**

    - Система берет желтый маркер.

    - Пользователь видит: *\"Агент 007 прибыл в **Лондон**\"*.

8.  

Без точной разметки (если бы мы просто искали слово \"Лондон\" поиском), система могла бы случайно скрыть часть другого слова (например, в предложении *\"Лондонский мост\"* скрыть только *\"Лондон\"*), что грамматически некорректно и сбивает с толку.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает, как клиент передает разметку при создании карточки и как сервис ее обрабатывает.

**Исходные данные:**

- **Предложение:** \"I made her cry.\" (Я довел её до слёз).

- **Цель:** \"made\" (в значении \"заставил\", каузатив).

- **Сложность:** Просто поиск слова \"made\" опасен, если в предложении оно встретится дважды.

**Сценарий: Создание карточки с явным указанием позиции**

1.  **Действие пользователя:** В интерфейсе пользователь выделяет мышкой слово \"made\".

**Формирование запроса:** Клиентское приложение отправляет текст с разметкой (например, в формате простейшего шаблонизатора).\
POST /cards\
code JSON\
downloadcontent_copy\
expand_less\
{

\"deck_id\": \"deck-grammar-id\",

// Вариант А: Клиент шлет размеченную строку (проще для клиента)

\"sentence_markup\": \"I {{made}} her cry.\",

\"target_lemma\": \"make\",

\"translation\": \"Я заставил её плакать.\"

}

2.  

3.  **Обработка на Бэкенде (Parsing):**

    - Сервис парсит строку I {{made}} her cry..

    - Извлекает чистый текст (sentence): \"I made her cry.\"

    - Извлекает целевое слово (target): \"made\".

    - Вычисляет координаты (target_start: 2, target_len: 4).

4.  

5.  **Сохранение:**

    - В БД записывается чистый текст и JSON с координатами: {\"start\": 2, \"end\": 6}.

6.  

7.  **Запрос карточки для обучения (SR-LRN-02):**

    - Клиент запрашивает: GET /study/next.

    - Сервис загружает данные и формирует ответ, готовый для Cloze-теста.

Ответ:\
code JSON\
downloadcontent_copy\
expand_less\
{

\"id\": \"card-xyz\",

\"sentence_clean\": \"I made her cry.\",

\"sentence_cloze\": \"I \[ \... \] her cry.\", // Цель скрыта

\"sentence_html\": \"I \<b\>made\</b\> her cry.\", // Цель выделена

\"target\": \"made\"

}

- 

8.  

9.  **Результат:** Клиентскому приложению не нужно делать сложную математику со строками. Оно просто отображает поле sentence_cloze на лицевой стороне и sentence_html на обратной.

## **SR-VOC-03: Хранение Метаданных источника (Source Metadata)**

Это сервисное требование описывает механизмы хранения информации о происхождении контента. Карточка в системе PVS не должна висеть в вакууме. Она должна иметь «пуповину», связывающую её с первоисточником (книгой, видео, статьей, подкастом). Сервис должен поддерживать гибкую структуру метаданных для различных типов медиа, чтобы позволить пользователю в один клик вернуться к контексту (Deep Linking).

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                          **Описание**
  ------------------------------------ -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Ассоциативная память**             Главная цель --- задействовать эпизодическую память. Пользователь лучше запомнит слово «Eternity», если увидит скриншот из фильма и вспомнит конкретную сцену, чем если просто прочитает текст.

  **Deep Linking (Глубокие ссылки)**   Если источником является веб-ресурс (YouTube, Netflix, Web Page), сервис должен хранить URL и временную метку (timestamp), чтобы при необходимости открыть первоисточник ровно на том моменте, где встретилась фраза.

  **Агностицизм формата**              Структура хранения должна быть гибкой (например, JSONB), чтобы поддерживать разные типы источников: для книги это «ISBN + Номер страницы», для видео --- «URL + Timecode», для статьи --- «URL + Параграф».

  **Визуальный контекст**              Поддержка хранения ссылок на скриншоты (Snapshots). Визуальный образ является мощнейшим триггером памяти. Сами файлы хранятся в Media Service, но PVS управляет ссылками на них.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Карточка** --- это **Улика в деле детектива**.

1.  **Улика:** На столе лежит записка со словом *\"Run!\"*.

2.  **Без метаданных:** Это просто слово. Бежать? Управлять? Запускать программу? Непонятно.

3.  **С метаданными (SR-VOC-03):** Улика лежит в пластиковом пакете, на котором написан **Протокол изъятия**:

    - **Место:** Фильм \"Forrest Gump\".

    - **Время:** 00:15:30.

    - **Фото:** Кадр, где Дженни кричит Форресту.

    - **Аудио:** Запись крика.

4.  

5.  **Эффект:** Детектив (Ученик) смотрит на пакет и мгновенно восстанавливает в голове всю сцену. Эмоциональная привязка делает запоминание практически вечным.

**Исходные данные:**

## **SR-VOC-04: Автоматическая лемматизация (NLP Processing)**

Это сервисное требование описывает применение технологий обработки естественного языка (NLP) для нормализации сохраняемых слов. Когда пользователь сохраняет словоформу (например, *«went»* --- ходил, или *«cats»* --- кошки), сервис должен автоматически определить её словарную форму --- **Лемму** (*«go»*, *«cat»*). Это необходимо для правильной группировки статистики, предотвращения дубликатов и работы функции «Словарный запас».

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                                **Описание**
  ------------------------------------------ --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Нормализация данных**                    Главная цель --- привести вариации слова к единому знаменателю. *Run, running, ran* --- это **одна** лексема. Система должна считать их как одно выученное слово.

  **Автоматизация (Zero Friction)**          Пользователь не должен вручную вводить лемму. Он просто выделяет слово в тексте, а сервис сам определяет, что *«better»* --- это форма прилагательного *«good»*.

  **Определение части речи (POS Tagging)**   Одно и то же слово может быть разным по смыслу в зависимости от роли в предложении (существительное *«Address»* и глагол *«Address»*). Сервис должен определять Part of Speech (POS), чтобы не смешивать их в одну кучу.

  **Глобальный словарь Проекта**             Леммы хранятся в отдельной таблице ProjectLemmas и служат «хабами», к которым привязываются конкретные карточки. Это позволяет реализовать логику: «У тебя 5 карточек с примерами для слова *Set*».

  **Языковая специфика**                     Сервис должен поддерживать разные пайплайны обработки для разных языков (стемминг для английского, токенизация для китайского/японского, морфология для русского).
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Ботанический сад**.

1.  **Поступление (Ввод слова):** Пользователь приносит разные листья: желтый лист, зеленый лист, сухой лист (это словоформы: *leaves, leaf, leaving*).

2.  **Без лемматизации:** Садовник кладет каждый лист в отдельную коробку. Через год у него 1000 коробок, и он не знает, сколько у него видов деревьев.

3.  **С лемматизацией (SR-VOC-04):**

    - Садовник (NLP-алгоритм) смотрит на лист и говорит: «Это Дуб».

    - Он вешает все эти разные листья на **одно дерево** (Лемму) с табличкой «Дуб» (Oak).

4.  

5.  **Результат:**

    - Пользователь заходит в сад и видит: «У меня растет 50 деревьев» (Реальный словарный запас).

    - Если пользователь принесет еще один лист дуба, Садовник скажет: «У нас уже есть такое дерево, давай повесим лист на него» (Связывание карточек).

6.  

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает процесс обработки слова при сохранении карточки.

**Исходные данные:**

- **Проект:** Английский язык.

- **Предложение:** \"She **went** to the store.\"

- **Цель (Target):** \"went\".

**Сценарий: Сохранение глагола в прошедшем времени**

1.  **Инициация:** Пользователь сохраняет карточку с target=\"went\".

2.  **NLP-анализ (Синхронно или Асинхронно):**

    - Сервис запускает NLP-процессор (например, библиотеку spaCy или внешний микросервис).

    - Вход: sentence=\"She went to the store\", target_index=1.

    - **Анализ контекста:** Алгоритм понимает, что *went* --- это глагол (VERB), прошедшее время от *go*.

    - Выход: lemma=\"go\", pos=\"VERB\".

3.  

4.  **Поиск или Создание Леммы:**

    - Сервис ищет в таблице project_lemmas: есть ли запись text=\"go\" + pos=\"VERB\" в этом проекте?

    - **Вариант А (Найдено):** Возвращается lemma_id существующей записи (например, пользователь уже учил слово *go* в другом контексте).

    - **Вариант Б (Не найдено):** Создается новая запись в project_lemmas. Счетчик total_lemmas проекта увеличивается на 1.

5.  

6.  **Привязка Карточки:**

    - В таблицу cards записывается не только текст, но и ссылка lemma_id.

7.  

8.  **Обновление статуса (SR-TXT-03):**

    - Если лемма была новой, ей присваивается статус Learning.

    - В режиме «Читалка» (Reader) все будущие вхождения слова *went*, *gone*, *goes* в текстах будут подсвечены как «Изучаемые», потому что они связаны с одной леммой.

9.

## **SR-VOC-05: Механизм Lemma Check (Предотвращение дубликатов)**

Это сервисное требование описывает интеллектуальную проверку, которая выполняется перед созданием новой карточки. Система должна проверить, учит ли пользователь уже это слово (или его лемму) в рамках текущего Проекта. Цель не в том, чтобы *запретить* создание (в Sentence Mining полезно иметь несколько примеров одного слова), а в том, чтобы *предупредить* пользователя и связать новые знания со старыми.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                 **Описание**
  --------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Осознанное повторение**   Если пользователь добавляет слово \"Run\", которое он уже учил год назад, он должен об этом знать. Это может быть поводом не создавать карточку, а просто повторить старую, или создать новую, понимая, что это *дополнительный* контекст.

  **Проверка по Лемме**       Проверка должна быть умной. Если пользователь добавляет *\"ran\"*, а в базе есть *\"run\"*, система должна распознать дубликат (связь через lemma_id).

  **Кросс-колодный поиск**    Поиск дубликатов происходит по всему Проекту, а не только внутри текущей колоды. Пользователь мог учить это слово в колоде \"Сериалы\", а сейчас встретил его в колоде \"Книги\".

  **Связанность знаний**      Если дубликат найден, система должна показать пользователю старую карточку (контекст), чтобы освежить память.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Библиотекарь**.

1.  **Запрос:** Читатель приносит книгу \"Гарри Поттер\" и говорит: \"Хочу добавить это в каталог\".

2.  **Проверка:** Библиотекарь смотрит в картотеку.

3.  **Сценарий А (Чисто):** Такой книги нет. Библиотекарь заводит карточку.

4.  **Сценарий Б (Дубль):** Библиотекарь говорит: \"Подождите, у нас уже есть \'Гарри Поттер\' на полке №3. Вы уверены, что вам нужна вторая копия?\".

5.  **Решение читателя:**

    - \"Ой, забыл, тогда не надо\". (Экономия времени, избежание дублирования).

    - \"Да, та книга старая и потрепанная, я хочу новую версию с иллюстрациями\". (Создание вариации).

6.  

В PVS это работает так: вы выделяете слово, а система подсказывает: *\"Ты уже знаешь это слово! Оно встречалось в фразе \'Forest Gump\' (статус: Выучено)\"*.

## **SR-VOC-06: Массовый импорт данных (Bulk Import & Migration)**

Это сервисное требование описывает механизм загрузки больших объемов учебного материала из внешних источников (файлы CSV, TSV, пакеты Anki .apkg). Поскольку архитектура PVS (Sentence Mining) сложнее, чем у обычных карточек (требует выделения Target внутри Sentence), импорт должен включать этап **интеллектуального маппинга** (сопоставления) полей и валидации данных.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                              **Описание**
  ---------------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Миграция без боли**                    Главная цель --- позволить пользователю переехать с Anki или Quizlet за 5 минут, сохранив не только тексты, но и (в идеале) медиа-файлы.

  **Гибкий Маппинг (Column Mapping)**      Система не должна требовать жесткого формата CSV. Пользователь загружает *свой* файл, а затем в интерфейсе указывает: «Колонка 1 --- это Фраза», «Колонка 2 --- это Перевод».

  **Обработка Sentence Mining**            Если в импортируемом файле нет отдельной колонки Target (целевое слово), система должна попытаться извлечь её автоматически (например, из разметки Anki {{c1::word}} или тегов \<b\>word\</b\>).

  **Асинхронность и Отказоустойчивость**   Импорт 10,000 карточек --- долгий процесс. Он должен идти в фоне (Background Job). Если 5 карточек из 10,000 битые, импорт не должен падать целиком; эти 5 ошибок должны попасть в отчет (Skip list).

  **Дедупликация**                         При импорте должна работать логика SR-VOC-05: если карточка уже есть в проекте, она пропускается или обновляется (на выбор пользователя).
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Новая квартира**, а **Импорт** --- это **Грузчики**.

1.  **Упаковка (Экспорт):** Пользователь упаковал свои вещи (карточки) в коробки (CSV файл). В одной коробке лежат книги и носки вперемешку.

2.  **Погрузка (Upload):** Пользователь отдает коробки Грузчикам (Service).

3.  **Инструктаж (Mapping):**

    - Грузчик открывает коробку и спрашивает: «Что в первой ячейке?».

    - Пользователь: «Это Фразы (Sentence)».

    - Грузчик: «А во второй?».

    - Пользователь: «Это Перевод (Translation)».

4.  

5.  **Распаковка (Processing):**

    - Грузчики носят вещи. Если видят сломанный стул (невалидная строка), они не сжигают дом, а откладывают стул в сторону (Error Log).

    - Если видят такой же стул, который уже стоит в комнате (Дубликат), они спрашивают: «Заменить или выкинуть?».

6.  

7.  **Результат:** Пользователь получает уведомление: «Переезд завершен. Распаковано 995 вещей. 5 вещей сломаны (ссылка на отчет)».

## **SR-VOC-07: Механизм обновления купленного контента (Content Sync)**

Это сервисное требование описывает логику доставки обновлений от Автора (продавца) к Покупателю (ученику). Когда автор исправляет ошибку в платной колоде или добавляет новые карточки, эти изменения должны автоматически (или по запросу) применяться к копиям колод у всех покупателей. Критически важным условием является **сохранность SRS-прогресса**: обновление контента карточки не должно сбрасывать интервалы повторения.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                        **Описание**
  ---------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Неприкосновенность прогресса**   Главная цель --- разделить данные на «Статические» (Контент: фраза, перевод, аудио) и «Динамические» (Прогресс: интервал, сложность, дата следующего повтора). При обновлении перезаписываются только статические данные.

  **Authoritative Source**           В контексте купленного товара Автор является источником правды. Если Автор решил, что перевод был неверным, система должна обновить перевод у пользователя (если только пользователь не «отсоединил» колоду через механизм Detachment).

  **Версионирование**                Система должна отслеживать версию контента у пользователя. Если у пользователя версия v1.0, а актуальная v1.5, система должна скачать и применить патч (Delta Update).

  **Обработка конфликтов**           Если пользователь *сам* отредактировал купленную карточку (например, изменил перевод под себя), система должна иметь стратегию разрешения: либо перезаписать (Force Update), либо пропустить обновление этой конкретной карточки, либо сохранить пользовательскую правку в отдельном слое.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Колода** --- это **Приложение на телефоне**.

1.  **Установка:** Вы скачиваете приложение (покупаете колоду). Вы пользуетесь им, накапливаете данные (прогресс).

2.  **Обновление (Update):** Разработчик (Автор) выпускает версию 2.0, где исправлены баги и изменен интерфейс.

3.  **Процесс:**

    - Ваш телефон скачивает обновление.

    - Он заменяет старые файлы программы на новые.

    - **Но:** Он не удаляет ваши сохранения и настройки.

4.  

5.  **Результат:** Вы открываете обновленное приложение. Оно выглядит лучше, ошибки исчезли, но вы находитесь на том же уровне игры, где были вчера.

В PVS это работает так: Автор исправляет опечатку в слове \"Accomodation\" -\> \"Accommodation\". У пользователя текст на карточке меняется, но карточка не становится \"New\", она остается \"Mature\" (выученной), если пользователь её уже выучил.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает распространение исправления опечатки.

**Исходные данные:**

- **Автор:** user-teacher.

- **Товар:** \"English B2\".

- **Карточка:** card-typo-id (содержит опечатку).

- **Покупатель:** user-learner (уже купил курс и выучил эту карточку, интервал 20 дней).

**Сценарий: Автор выпускает патч с исправлениями**

1.  **Действие Автора:**

    - Автор исправляет текст в карточке card-typo-id.

    - Автор нажимает «Опубликовать изменения» (Publish Update) в панели управления товаром.

## **SR-AI-01: AI-генерация контекста (Context Generation)**

Это сервисное требование описывает интеграцию с большими языковыми моделями (LLM) для автоматического создания учебного контента. Когда пользователь хочет выучить слово, он часто не имеет под рукой хорошего примера предложения. Сервис должен уметь по запросу сгенерировать несколько вариантов контекста (предложений), адаптированных под уровень владения языком пользователя (CEFR A1--C2).

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                       **Описание**
  --------------------------------- -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Устранение «Writer's Block»**   Главная цель --- снять с пользователя когнитивную нагрузку по придумыванию или поиску примеров. Ввод слова должен быть единственным усилием, остальное делает AI.

  **Адаптивность (CEFR Levels)**    Примеры должны соответствовать уровню ученика. Для слова \"Run\" пример уровня A1 --- *\"I run fast\"*, уровня C1 --- *\"He decided to run for mayor\"*. Сервис должен уметь генерировать и то, и другое.

  **Разнообразие (Diversity)**      Система должна предлагать несколько вариантов (3-5) из разных сфер жизни (бытовой, деловой, литературный), чтобы пользователь мог выбрать наиболее релевантный для себя контекст.

  **Структурированность**           Ответ AI должен быть не просто текстом, а структурой, пригодной для создания карточки: само предложение, перевод и четкое указание (индекс/тег), где находится целевое слово (для подсветки).

  **Кэширование**                   Популярные слова запрашивают часто. Результаты генерации для \"Apple\" должны кэшироваться, чтобы не платить LLM-провайдеру за каждый запрос.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Опытный Лингвист-Репетитор**.

2.  **Анализ:** Репетитор смотрит на ученика: «Так, твой уровень --- средний (B1)».

3.  **Генерация:** Репетитор на ходу придумывает три фразы:

    - *Вариант 2 (Жизненный):* \"We will **inevitably** make mistakes while learning.\" (Мы неизбежно будем делать ошибки\...).

    - *Вариант 3 (Деловой):* \"The prices will **inevitably** go up.\" (Цены неизбежно вырастут).

5.  **Выбор:** Ученик говорит: «О, про ошибки мне нравится!».

6.  **Результат:** Репетитор выписывает именно эту фразу на карточку, подчеркивает слово *inevitably* и пишет перевод.

## **SR-AI-02: AI-объяснение грамматики (Grammar Explanation)**

Это сервисное требование описывает функцию «умной справки». По запросу пользователя сервис должен проанализировать конкретное предложение и сгенерировать краткое, понятное объяснение грамматических конструкций, использованных вокруг целевого слова. Это избавляет пользователя от необходимости гуглить грамматические правила или искать таблицы спряжений, предоставляя теорию ровно в тот момент, когда она нужна на практике.

### **1. Цель и ключевые принципы**

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                      **Описание**
  -------------------------------- -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Гипер-контекстуальность**      Объяснение не должно быть абстрактной статьей из учебника (например, «Что такое Dative Case»). Оно должно объяснять, почему *именно в этом предложении* слово стоит *именно в этой форме* (например, «Здесь окончание -em, потому что глагол \'mit\' требует дательного падежа»).

  **On-Demand (По запросу)**       Грамматические справки не должны перегружать интерфейс карточки по умолчанию. Это вспомогательный инструмент, который вызывается только когда пользователь нажимает кнопку «Объяснить грамматику» или «Почему так?».

  **Краткость (Micro-learning)**   Ответ AI должен быть лаконичным (2-3 предложения), сфокусированным на сути, чтобы пользователь мог прочитать его за 10 секунд и продолжить обучение.

  **Язык объяснения**              Объяснение должно генерироваться на родном языке пользователя (или на языке интерфейса), даже если изучаемый язык --- другой.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Личный Репетитор**, сидящий рядом.

1.  **Ситуация:** Ученик читает немецкую фразу: *\"Ich helfe **dem** Mann\"* (Я помогаю мужчине).

2.  **Замешательство:** Ученик знает, что \"мужчина\" --- это *\"der Mann\"*. Почему здесь написано *\"dem\"*?

3.  **Вопрос:** Ученик тыкает пальцем в слово и спрашивает: «Почему *dem*?».

4.  **Ответ Репетитора (SR-AI-02):**

    - «Смотри, глагол *helfen* (помогать) в немецком всегда управляет Дательным падежом (Dativ).

    - Поэтому мужской артикль *der* меняется на *dem*.

    - Это не опечатка, это правило управления глаголов».

5.  

6.  **Эффект:** Ученик мгновенно закрыл пробел в знаниях и продолжил урок, не открывая толстый учебник грамматики.

## **SR-AI-03: Автоматический перевод (Smart Translation)**

Это сервисное требование описывает механизм контекстно-зависимого перевода. Когда пользователь добавляет фразу для изучения (Sentence Mining), он часто не хочет тратить время на ручной ввод перевода всего предложения. Сервис должен уметь автоматически предлагать перевод как для **всей фразы**, так и для **целевого слова** (Target), причем перевод слова должен соответствовать его значению именно в этом контексте (устранение многозначности).

### **1. Цель и ключевые принципы**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                      **Описание**
  -------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Контекстная точность**         Это главное отличие от обычного словаря. Если в предложении *\"He **runs** a company\"* пользователь учит слово *\"runs\"*, система должна перевести его как *\"управляет\"*, а не *\"бежит\"*.

  **Двойной перевод**              Сервис должен возвращать два значения: перевод полного предложения (для понимания смысла) и перевод конкретного целевого слова (для обратной стороны карточки).

  **Автозаполнение (Auto-fill)**   Функция должна работать как помощник при создании карточки. Если пользователь оставил поля перевода пустыми, система заполняет их сама. Если пользователь ввел свой перевод, система не должна его перезаписывать без спроса.

  **Языковая пара**                Система должна автоматически определять исходный язык предложения и целевой язык пользователя (на основе настроек Проекта native_lang).

## **SR-TXT-01: Токенизация и Анализ текста (Text Tokenization & Statusing)**

Это сервисное требование описывает механизм обработки произвольного текста (статьи, субтитров, книги), загруженного пользователем. Сервис должен разбить текст на отдельные смысловые единицы (токены), определить их начальную форму (лемму) и сопоставить с базой знаний пользователя. Результатом является размеченный текст, где каждое слово имеет статус: **New** (Новое), **Learning** (В процессе) или **Known** (Выучено).

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                     **Описание**
  ------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Визуализация знания**         Главная цель --- показать пользователю карту его знаний. Он должен видеть, какой процент текста ему знаком (Comprehension rate). Если 90% слов знакомы (зеленые/прозрачные) --- текст подходит для чтения. Если 50% (синие/новые) --- текст слишком сложен.

  **Лемма-центричность**          Анализ должен строиться на леммах. Если пользователь знает слово *\"go\"*, то слова *\"goes\"*, *\"going\"* и *\"went\"* в тексте должны быть помечены как **Known**, а не как **New**.

  **Сохранение форматирования**   Токенизация не должна ломать структуру текста. Абзацы, знаки препинания и пробелы должны быть сохранены в выходной структуре, чтобы фронтенд мог восстановить текст в читаемом виде.

  **Производительность (Bulk)**   Анализ целой главы книги (5000 слов) должен происходить быстро. Нельзя делать SQL-запрос на каждое слово. Требуется пакетная обработка и оптимизированный поиск по индексам.

  **Игнорирование мусора**        Система должна уметь отличать слова от знаков препинания, чисел и (в идеале) имен собственных, чтобы не предлагать пользователю учить запятые или цифры.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Очки Дополненной Реальности (AR)** для чтения.

1.  **Взгляд:** Пользователь смотрит через очки на страницу книги на иностранном языке.

2.  **Обработка (SR-TXT-01):** Очки мгновенно сканируют текст.

3.  **Цветовая кодировка:**

    - Слова, которые пользователь знает хорошо, остаются **прозрачными** (не отвлекают).

    - Слова, которые он сейчас учит (в SRS), подсвечиваются **желтым** (\"Вспомни меня!\").

    - Слова, которые он видит впервые, подсвечиваются **синим** (\"Новое!\").

4.  

5.  **Результат:** Пользователь мгновенно оценивает сложность текста. Он читает знакомые куски бегло, а на желтых/синих словах останавливается, чтобы кликнуть и посмотреть перевод (SR-TXT-02).

## **SR-TXT-02: Функционал «Click-to-Mine» (Instant Card Creation)**

Это сервисное требование описывает механизм мгновенного создания учебной карточки прямо из текста, который пользователь читает в данный момент. Когда пользователь кликает на незнакомое слово (со статусом New), система должна автоматически захватить предложение, в котором это слово находится, определить лемму, получить перевод (через SR-AI-03) и создать карточку. Весь процесс должен происходить «в один клик» или с минимальным подтверждением.

### **1. Цель и ключевые принципы**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                          **Описание**
  ------------------------------------ ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Нулевое трение (Zero Friction)**   Главная цель --- не прерывать поток чтения (Flow). Создание карточки не должно требовать открытия новых окон, копирования текста вручную или переключения вкладок.

  **Автоматический контекст**          Система сама определяет границы предложения, в котором стоит слово, и сохраняет его как Sentence. Пользователю не нужно выделять предложение мышкой.

  **Мгновенная смена статуса**         Как только карточка создана, статус слова в тексте должен визуально измениться с **New** (Синий/Неизвестный) на **Learning** (Желтый/Изучаемый). Это дает пользователю чувство прогресса.

  **Предзаполнение**                   Все поля карточки (перевод, транскрипция, определение) должны заполняться автоматически (используя NLP и AI сервисы), оставляя пользователю возможность лишь подтвердить или слегка поправить их.

  **Источник**                         Ссылка на исходный текст (название статьи, позиция в тексте) должна сохраниться в метаданных карточки (SR-VOC-03) для будущего возврата к контексту.
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Ботаник в экспедиции**.

1.  **Поле (Текст):** Ботаник идет по лесу (читает текст). Вокруг много растений. Те, что он знает, он игнорирует.

2.  **Находка:** Он видит редкий синий цветок (Незнакомое слово).

3.  **Действие (Click-to-Mine):** Он не начинает рисовать цветок в блокноте карандашом. Он наводит на него **Фоторужье** и нажимает кнопку.

4.  **Автоматика:**

    - Фоторужье делает снимок цветка вместе с кустом, на котором он растет (Контекст/Предложение).

    - Умная камера определяет вид растения (Лемма).

    - GPS ставит метку \"Найден в Лесу №5\" (Источник).

5.  **Результат:** Образец мгновенно отправляется в лабораторию (Колоду), а Ботаник ставит на кусте желтую ленточку (\"Уже собрано\") и идет дальше, не останавливаясь.

## **SR-TXT-03: Глобальный Словарь Лемм (Project Lemma Dictionary)**

Это сервисное требование описывает механизм ведения централизованного реестра всех слов (лемм), с которыми пользователь взаимодействовал в рамках Проекта. В отличие от Карточек, которых может быть много на одно слово (разные примеры), запись в Словаре Лемм всегда одна уникальная на слово. Сервис должен автоматически синхронизировать статус леммы (New / Learning / Known) с прогрессом изучения связанных с ней карточек в SRS.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                  **Описание**
  ---------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Единый источник правды**   Главная цель --- отвечать на вопрос: «Знает ли пользователь слово X?». Ответ не должен зависеть от того, в какой колоде лежит карточка. Это глобальное знание в рамках языка.

  **Агрегация статуса**        Статус леммы вычисляется на основе *лучшего* прогресса среди всех карточек, содержащих эту лемму. Если у пользователя 5 карточек со словом *«Get»*, и одна из них выучена (Mature), то все слово *«Get»* считается выученным.

  **Глобальный эффект**        Если статус слова меняется на KNOWN (Выучено), оно должно перестать подсвечиваться как незнакомое во **всех** текстах и книгах, которые читает пользователь.

  **Ручное управление**        Пользователь должен иметь возможность вручную пометить слово как KNOWN (Игнорировать), даже не создавая карточку (например, для очевидных заимствований или имен собственных).

  **Оптимизация чтения**       Таблица лемм должна быть оптимизирована для сверхбыстрого чтения (Read-heavy), так как при открытии страницы книги (SR-TXT-01) нужно проверить статус для сотен слов за миллисекунды.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **Проект** --- это **RPG-игра**.

1.  **Карточки** --- это **Монстры**, которых вы убиваете (учите).

2.  **Словарь Лемм** --- это **Бестиарий (Журнал)**.

3.  **Процесс:**

    - Вы встретили гоблина (карточку с *«Run»*) в лесу (Колода 1) и победили его.

    - Вы встретили гоблина (карточку с *«Run»*) в пещере (Колода 2).

    - В Журнале у вас есть только одна запись: «Гоблин».

4.  

5.  **Смена статуса:**

    - Сначала в Журнале пусто (Статус: New).

    - После первой победы появляется запись «Изучается» (Learning).

    - Когда вы победили гоблинов 10 раз и алгоритм SRS говорит, что вы их больше не боитесь, в Журнале ставится золотая печать **«Мастер» (Known)**.

6.  

7.  **Эффект:** Теперь, когда вы видите гоблина в игре, над ним не горит красный восклицательный знак опасности (подсветка в тексте исчезает). Вы просто проходите мимо.

## **SR-LRN-01: Генерация умной очереди обучения (Study Queue Generation)**

Это сервисное требование описывает алгоритм выборки карточек для текущей учебной сессии. В отличие от простого перебора, умная очередь должна учитывать иерархию папок (учить родительскую папку = учить все вложенные), приоритеты SRS (сначала то, что вот-вот забудешь) и дневные лимиты.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                               **Описание**
  ----------------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Приоритет срочности**                   Карточки не равны. Очередь должна строиться в строгом порядке: 1. **Lapses** (Забытые/Ошибки) → 2. **Reviews** (Плановое повторение) → 3. **New** (Новые слова). Это гарантирует, что пользователь сначала закрепляет слабые места.

  **Рекурсивный сбор (Deep Aggregation)**   Если пользователь нажимает «Учить» на папке «Английский», система должна собрать due карточки из всех сотен вложенных колод (Сериалы, Книги, Грамматика) и смешать их в одну сессию.

  **Перемешивание (Interleaving)**          Карточки из разных под-колод должны быть перемешаны. Учить 20 слов про «Еду», а потом 20 слов про «Космос» менее эффективно, чем учить их вперемешку. Это держит мозг в тонусе.

  **Соблюдение лимитов**                    Система должна жестко соблюдать настройки Проекта: «Не более 20 новых слов в день». Даже если в очереди 1000 новых карт, сессия не должна превращаться в бесконечный марафон.

  **Производительность**                    Генерация очереди --- блокирующая операция перед стартом урока. Она должна выполняться мгновенно (\< 100 мс), даже если в проекте 50,000 карточек.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **DJ на радио**.

1.  **Задача:** Составить плейлист на час (Сессию обучения).

2.  **Библиотека (Проект):** У DJ есть тысячи пластинок, разложенных по жанрам (Колодам): Рок, Джаз, Поп.

3.  **Заявки слушателей (SRS Status):**

    - Есть песни, которые люди уже начинают забывать (Reviews). Их надо ставить обязательно.

    - Есть горячие новинки (New). Их надо ставить дозированно, чтобы не перегрузить эфир.

4.  

5.  **Сведение (Mixing):**

    - DJ не ставит сначала час Рока, потом час Джаза. Он делает **Микс**.

    - Он берет срочные треки из всех жанров.

    - Он добавляет немного новинок (до лимита).

    - Он перемешивает их так, чтобы было интересно слушать.

6.  

7.  **Эфир:** Пользователь нажимает Play и просто слушает поток, не думая о том, из какой папки взялась эта песня.

## **SR-LRN-02: Поддержка режима Cloze Deletion (Тест с пропусками)**

Это сервисное требование описывает механизм подготовки данных карточки для отображения в формате «Заполните пропуск». В отличие от классических флеш-карт (Лицо: Слово -\> Оборот: Перевод), режим Cloze Deletion показывает пользователю предложение, где целевое слово (Target) скрыто или заменено на специальный маркер. Задача пользователя --- восстановить пропущенное слово, опираясь на контекст и (опционально) перевод.

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                             **Описание**
  --------------------------------------- -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Активное воспроизведение**            Главная цель --- заставить мозг работать. Восстановление слова из контекста (Active Recall) создает гораздо более сильные нейронные связи, чем пассивное узнавание перевода.

  **Контекстная подсказка**               Само предложение является подсказкой. Пользователь видит грамматическое окружение (предлоги, артикли), что помогает вспомнить правильную форму слова, а не просто его словарное значение.

  **Разделение данных и представления**   Сервис не должен отдавать клиенту готовую HTML-строку с дыркой (например, \"I \<\...\>\") для лицевой стороны. Он должен отдавать **полный текст** и **координаты скрытия**. Это позволяет клиенту реализовать анимации, ввод с клавиатуры или подсказки (показать первую букву).

  **Умное скрытие (Smart Masking)**       Если целевое слово встречается в предложении несколько раз, скрываться должно только то вхождение, которое является целью обучения (определенное в SR-VOC-02), либо все вхождения этой леммы (настройка).

  **Градуированная помощь**               Механизм должен позволять клиенту запрашивать \"подсказки\" без переворачивания карточки (например, показать определение или синоним), если пользователь почти вспомнил, но сомневается.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

## **SR-LRN-03: Реализация FSRS-расчета (SRS Calculation)**

Это сервисное требование описывает математическую логику обновления состояния карточки после ответа пользователя. Сервис должен использовать алгоритм **FSRS v4/v5**, который оперирует понятиями **Stability** (Стабильность памяти --- как долго я помню) и **Difficulty** (Сложность карточки --- насколько трудно её запомнить). Главная задача --- вычислить идеальную дату следующего повтора, чтобы пользователь вспомнил слово ровно в тот момент, когда он почти готов его забыть (Target Retrievability, обычно 90%).

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                    **Описание**
  ------------------------------ ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Адаптивность**               Алгоритм должен подстраиваться под пользователя. Если пользователь часто ошибается, интервалы сокращаются. Если отвечает «Легко», интервалы растут экспоненциально.

  **Разделение D и S**           В отличие от SM-2 (где был один коэффициент Ease), FSRS разделяет **Сложность (D)** и **Стабильность (S)**. Сложную карточку можно помнить долго (высокая S, высокая D), а легкую --- забыть быстро (низкая S, низкая D). Это дает более точное прогнозирование.

  **Fuzzing (Размытие)**         Чтобы избежать ситуаций, когда 500 карточек выпадают на один день, система должна добавлять небольшой случайный коэффициент («шум») к расчетному интервалу, равномерно распределяя нагрузку.

  **Настройка (Optimization)**   Расчет должен учитывать параметры FSRS (w --- веса), заданные на уровне Проекта (SR-STR-02). Это позволяет алгоритму работать по-разному для Японского и Английского. При использовании микросервиса **inclusive** (py-fsrs) настройки проекта (request_retention, maximum_interval, веса w) передаются в каждом запросе ReviewCard по gRPC и применяются при создании планировщика.

  **Обработка \"Again\"**        Оценка «Забыл» (Again) не должна просто сбрасывать карточку в ноль. Она должна корректно снижать Стабильность (S), но сохранять накопленную информацию о Сложности (D), чтобы последующие повторения были частыми, но эффективными.
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Тренер в тренажерном зале**.

1.  **Упражнение:** Вы поднимаете штангу (вспоминаете слово).

2.  **Оценка:** Тренер спрашивает: «Как пошло?».

    - **Again (Не смог):** «Мышцы слабые. Снижаем вес, повторяем через минуту».

    - **Hard (Тяжело):** «Справился, но дрожал. Повторим скоро, нагрузку не повышаем».

    - **Good (Нормально):** «Отлично. В следующий раз увеличим вес и встретимся через неделю».

    - **Easy (Легко):** «Слишком легко для тебя. Встретимся через месяц, раньше нет смысла».

3.  

4.  **Математика (FSRS):**

    - Тренер записывает в журнал не просто дату, а два числа:

      - **S (Сила):** Насколько вы сильны сейчас (в днях до забывания).

      - **D (Трудность):** Насколько тяжело дается именно это упражнение.

    - 

    - Следующая тренировка назначается ровно на тот день, когда ваша Сила упадет до 90% (чтобы создать стимул для роста).

5.

## **SR-LRN-05: Обнаружение и обработка Leech-фраз (Leech Management)**

Это сервисное требование описывает алгоритм выявления карточек, которые пользователь не может запомнить в течение длительного времени. Если пользователь ошибся на одной карточке 5, 8 или 10 раз, это сигнал: проблема не в памяти, а в самой карточке (слишком сложное предложение, двусмысленность, плохой контекст). Система должна автоматически обнаружить такую «пиявку» и остановить её показы, предложив пользователю исправить ситуацию.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                       **Описание**
  --------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Гигиена обучения**              Главная цель --- не тратить 50% времени на 5% самых сложных карточек. Лучше удалить одну сложную фразу и выучить 10 простых.

  **Настраиваемый порог**           Критерий «Пиявки» (Leech Threshold) должен настраиваться на уровне Проекта. Обычно это количество «Lapses» (сбросов интервала в ноль). Стандартное значение: 8 ошибок.

  **Автоматическая приостановка**   При достижении порога карточка должна переходить в статус SUSPENDED (Приостановлено). Она исчезает из очереди повторений, чтобы не раздражать пользователя.

  **Диагностика контента**          В Sentence Mining часто бывает, что само предложение неудачное. Система должна подсказывать: «Возможно, стоит найти другой пример для этого слова?» (ссылка на SR-AI-01).

  **Тегирование**                   Карточка помечается тегом leech, что позволяет пользователю позже отфильтровать их все и разобрать оптом («День работы над ошибками»).
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Механик на конвейере**.

1.  **Процесс:** Детали (карточки) едут по конвейеру. Механик (Пользователь) пытается собрать их (вспомнить).

2.  **Сбой:** Одна деталь кривая. Механик не может её вставить. Он кидает её обратно в начало конвейера («Again»).

3.  **Повторение:** Деталь возвращается. Механик снова не может. И так 8 раз.

4.  **Действие системы (SR-LRN-05):**

    - Умный датчик на конвейере видит: «Эта деталь прошла круг 8 раз и всё еще не собрана».

    - **Сигнал:** Загорается красная лампочка.

    - **Действие:** Робот-манипулятор снимает деталь с ленты и бросает её в корзину «Брак» (Suspend).

    - **Сообщение:** Механику говорят: «Не мучайся. Эта деталь бракованная. Возьми новую заготовку (другое предложение) или почини эту».

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает момент превращения карточки в Leech.

**Исходные данные:**

- **Карточка:** card-tough.

- **Статистика:** lapses (количество забываний) = 7.

- **Настройки проекта:** leech_threshold = 8.

**Сценарий: Пользователь снова забывает слово**

1.  **Действие пользователя:** В ходе сессии пользователь видит карточку и понимает, что снова её не помнит. Нажимает **\"Again\" (1)**.

2.  **Обработка ответа (Backend):**

    - Сервис обновляет статистику: lapses становится 8.

    - reps увеличивается.

3.  **Проверка условия Leech:**

    - Сервис сравнивает: new_lapses (8) \>= threshold (8).

    - Условие выполнено.

4.  **Смена статуса:**

    - Сервис устанавливает флаг is_suspended = true.

    - Добавляет тег leech к карточке.

    - (Важно) Карточка удаляется из активной очереди обучения на сегодня.

5.  **Ответ клиенту (Actionable Feedback):**

}

6.  **UI:**

    - Пользователь видит тост/модальное окно: *\"Сложная карточка! Мы убрали её из колоды, чтобы она не мешала. Вы можете найти её позже в разделе \'Проблемные\'\"*.

## **SR-API-01: Capture API для браузерных расширений**

Это сервисное требование описывает специализированный API, предназначенный для мгновенного сохранения контента из внешних источников (Google Chrome, YouTube, Netflix, электронные читалки). Пользователи потребляют контент в браузере, и сервис должен предоставить инструмент («сачок»), позволяющий захватить интересную фразу, контекст и метаданные в один клик, не переключая вкладки и не прерывая процесс чтения или просмотра.

### **1. Цель и ключевые принципы**

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                             **Описание**
  --------------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Минимальное трение (Low Friction)**   Главная цель --- скорость. Пользователь должен иметь возможность сохранить карточку за 1-2 секунды. API должен быть оптимизирован для приема «сырых» данных и их асинхронной обработки.

  **Авто-определение Проекта**            Расширение может не знать ID текущего проекта пользователя. API должен уметь определять нужный Проект на основе языка захваченного текста (например, текст на французском -\> проект \"French\").

  **Rich Context Capture**                API должен принимать не только текст, но и богатые метаданные: URL страницы, заголовок (Title), таймкод (для видео), и даже base64-скриншот или ссылку на картинку.

  **Обработка дубликатов на лету**        Если пользователь пытается сохранить слово, которое уже есть в словаре, API должен вернуть предупреждение (Warning), чтобы расширение могло подсветить иконку другим цветом («Уже учим»).

  **CORS и Безопасность**                 API должен корректно обрабатывать Cross-Origin запросы от расширений и использовать безопасную аутентификацию (например, долгоживущие токены или API Key для расширений).
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Штаб-квартира**, а **Браузерное расширение** --- это **Полевой Агент**.

1.  **Наблюдение:** Агент (Пользователь) читает статью в New York Times или смотрит сериал на Netflix.

2.  **Обнаружение:** Агент видит незнакомое слово *«Serendipity»*.

3.  **Захват (Capture):** Агент выделяет слово и нажимает горячую клавишу.

## **SR-SRC-01: Полнотекстовый поиск (Full-text Search)**

Это сервисное требование описывает механизм поиска по всему текстовому контенту карточек (предложениям, переводам, заметкам) внутри выбранного Проекта. В отличие от простого фильтра по точному совпадению, полнотекстовый поиск должен уметь находить фразы, части слов, работать с регистронезависимостью и возвращать результаты с подсветкой найденных вхождений (highlighting), чтобы пользователь сразу видел контекст.

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                    **Описание**
  ------------------------------ -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Доступность знаний**         Главная цель --- дать пользователю возможность мгновенно найти ответ на вопрос: «Я точно где-то видел это слово, но в каком контексте?».

  **Область поиска (Scope)**     Поиск всегда ограничен текущим Проектом. Если пользователь ищет слово *«Gift»* в проекте «Немецкий», он не должен видеть карточки из проекта «Английский», даже если там есть такое же слово.

  **Ранжирование (Relevance)**   Результаты должны сортироваться по релевантности. Точное совпадение в поле Target (целевое слово) должно быть выше, чем совпадение в поле Notes (заметки) или Sentence (контекст).

  **Подсветка (Highlighting)**   Сервис должен возвращать не просто список карточек, а фрагменты текста с разметкой (например, \<em\>found text\</em\>), показывающей, где именно нашлось совпадение.

  **Производительность**         Поиск должен работать быстро (low latency) даже на больших объемах данных. Для этого необходимо использовать специализированные индексы (например, GIN в PostgreSQL или Elasticsearch).
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

## **SR-SRC-02: Поиск по Лемме (Lemma Search)**

Это сервисное требование описывает механизм поиска, который оперирует не просто символьными строками, а лингвистическими единицами. Если пользователь ищет слово *\"go\"*, система должна найти и показать карточки, содержащие формы *\"went\"*, *\"gone\"*, *\"goes\"*, *\"going\"*. Это возможно благодаря предварительной обработке данных (SR-VOC-04), которая связывает разные словоформы с единой Леммой.

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                      **Описание**
  -------------------------------- ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Лингвистическая абстракция**   Главная цель --- найти смысл, а не набор букв. Пользователь хочет увидеть все примеры использования глагола «Быть», а не только те, где написано именно «Be» (исключая «Am», «Is», «Are», «Was»).

  **Агрегация контекстов**         Поиск по лемме позволяет собрать воедино разрозненные знания. Пользователь видит слово в разных временах, падежах и числах на одном экране, что помогает сформировать глубинное понимание грамматики.

  **Использование связей**         Поиск не должен каждый раз запускать тяжелый NLP-процесс. Он должен использовать заранее созданные связи card_id -\> lemma_id (созданные в SR-VOC-04), что делает операцию мгновенной (поиск по внешнему ключу).

  **Приоритет Цели**               В первую очередь ищутся карточки, где искомая лемма является **Целевым словом** (Target). Вхождение леммы просто в тексте предложения имеет вторичный приоритет.

## **SR-ANL-01: Расчет Словарного запаса (Vocabulary Size Estimate)**

Это сервисное требование описывает алгоритм оценки объема знаний пользователя. Сервис должен рассчитывать количество **уникальных лемм** (а не просто карточек), которые пользователь перевел в статус «Надежно выучено» (Mature). Эта метрика должна быть сопоставлена с международными стандартами (например, CEFR), чтобы сказать пользователю: «Ты знаешь 2500 слов, это уровень B1».

### **1. Цель и ключевые принципы**

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                        **Описание**
  ---------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Лемма-центричность**             Главная цель --- честность. Если пользователь выучил карточки *\"Go\"*, *\"Went\"* и *\"Gone\"*, его словарный запас увеличился на **1 слово**, а не на 3. Расчет строится на таблице ProjectLemmas (SR-TXT-03).

  **Критерий зрелости (Maturity)**   В зачет идут только те слова, которые реально осели в долговременной памяти. Обычно это леммы, связанные с карточками, чей интервал SRS превышает 21 день (статус Mature). Слова в статусе Learning не считаются.

  **Маппинг на CEFR**                Голое число (3428 слов) мало что говорит новичку. Система должна накладывать это число на шкалу (A1: 500, A2: 1000, B1: 2000\...), чтобы показывать прогресс-бар: «До уровня B2 осталось 500 слов».

  **Изоляция по Проекту**            Словарный запас считается отдельно для каждого языка. Нельзя складывать английские и немецкие слова в одну кучу.

  **Кэширование статистики**         Этот запрос «тяжелый» (агрегация по всему словарю). Результат должен кэшироваться и пересчитываться либо раз в сутки, либо по событию (завершение сессии), но не при каждом обновлении страницы.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

## **SR-ANL-02: Heatmap активности по Проектам (Activity Calendar)**

Это сервисное требование описывает механизм сбора, агрегации и отдачи данных об интенсивности обучения пользователя за последний год. ## **SR-ANL-03: Дневная сводка и Ударный режим (Daily Summary & Streaks)**

Это сервисное требование описывает механизм отслеживания ежедневного прогресса пользователя. Сервис должен в реальном времени агрегировать данные за «сегодня» (количество изученных карточек, затраченное время) и управлять счетчиком **Серии (Streak)** --- количества дней подряд, когда пользователь выполнял минимальную учебную норму.

### **1. Цель и ключевые принципы**

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                        **Описание**
  ---------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Определение «Дня»**              Главная техническая сложность. «Сегодня» определяется не по UTC, а по **Локальному времени пользователя** с учетом настройки RolloverHour (обычно 4 утра). Если пользователь занимается в 2 ночи, это все еще «вчерашняя» серия.

  **Критерий засчитывания**          Серия не должна засчитываться просто за вход в приложение. Должен быть минимальный порог активности (например, «минимум 10 повторений» или «минимум 5 минут»), чтобы серия имела ценность.

  **Защита серии (Streak Freeze)**   Система должна поддерживать механику «Заморозки». Если пользователь пропустил один день, но у него был экипирован предмет «Заморозка» (купленный или полученный), серия не сбрасывается в ноль, а ставится на паузу.

  **Разделение метрик**              Дневная сводка должна четко разделять: **New Cards** (рост базы знаний) и **Reviews** (удержание знаний). Пользователь должен видеть, выполнил ли он план на день по обоим показателям.

  **Мгновенная обратная связь**      Данные сводки должны обновляться сразу после завершения каждого ревью. Экран «Урок завершен» должен показывать актуальный прогресс-бар дня.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

## **SR-BG-01: Асинхронная NLP-обработка карточек (Enrichment Pipeline)**

Это сервисное требование описывает фоновый процесс (Worker), который запускается каждый раз при создании или изменении карточки. Его задача --- «обогатить» сырые данные, введенные пользователем, используя методы обработки естественного языка (Natural Language Processing). Сервис должен определить лемму, часть речи, транскрипцию (IPA) и, возможно, уровень сложности слова, сохранив эти метаданные для дальнейшего использования в поиске, статистике и алгоритмах SRS.

### **1. Цель и ключевые принципы**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                                     **Описание**
  ----------------------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Асинхронность**                               NLP-алгоритмы (особенно нейросетевые) могут быть медленными (сотни миллисекунд). Чтобы не заставлять пользователя ждать при сохранении карточки, этот процесс должен выполняться в фоне через очередь задач.

  **Лингвистическая точность**                    Сервис должен использовать специализированные библиотеки для каждого поддерживаемого языка (например, *spaCy* для английского, *MeCab* для японского, *Jieba* для китайского), чтобы корректно определять границы слов и их начальные формы.

  **Отказоустойчивость (Graceful Degradation)**   Если NLP-сервис недоступен или не смог разобрать предложение, карточка не должна «ломаться». Она просто остается без расширенных метаданных (без леммы), но доступна для изучения «как есть».

  **Идемпотентность**                             Повторный запуск обработки для одной и той же карточки должен приводить к тому же результату и не дублировать данные в словаре лемм.

  **Цепочка событий**                             Завершение NLP-обработки может служить триггером для следующих процессов, например, для генерации синтеза речи (если мы знаем язык и текст, можно заказывать TTS).
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Библиотечный Архивариус**.

1.  **Поступление:** Читатель сдает книгу (Карточку) с запиской: «Здесь интересная фраза про *running*».

2.  **Первичная приемка:** Книгу ставят на полку «Новые поступления». Читатель уходит довольный (UI разблокирован).

3.  **Работа Архивариуса (SR-BG-01):**

    - Позже Архивариус берет книгу.

    - Он анализирует слово *running*.

    - Он пишет в картотеку:

      - **Лемма:** Run (бежать).

      - **Часть речи:** Глагол (Verb).

      - **Транскрипция:** \[rʌn\].

      - **Уровень:** A1 (Базовый).

    - 

4.  

5.  **Результат:** Теперь, когда другой читатель спросит «Дайте мне все глаголы уровня A1», эта книга попадет в выборку, хотя читатель этого явно не указывал.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает жизненный цикл обработки новой карточки.

**Исходные данные:**

- **Карточка:** card-new-001.

- **Текст:** \"El **gato** negro duerme.\" (Черный кот спит).

- **Цель:** \"gato\".

## **SR-BG-02: Управление жизненным циклом медиа-файлов (Media Cleanup)**

Это сервисное требование описывает фоновый процесс, отвечающий за удаление «осиротевших» (orphaned) медиа-файлов. PVS хранит не сами файлы, а ссылки (UUID) на ресурсы в **Media Service**. Когда пользователь удаляет Карточку, Колоду или целый Проект, эти ссылки исчезают из базы данных PVS. Однако, физические файлы (картинки, аудио) остаются лежать в S3-бакете Media Service, потребляя место и деньги. Данный процесс должен гарантировать, что если ссылка на файл удалена из PVS, то и сам файл будет удален из хранилища.

### **1. Цель и ключевые принципы**

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                           **Описание**
  ------------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Экономическая эффективность**       Главная цель --- не платить за хранение мусора. Хранение терабайтов неиспользуемых аудиофайлов и картинок в S3 стоит денег.

  **Асинхронность (Fire-and-Forget)**   Удаление файлов --- операция медленная (сетевые вызовы к S3). Она не должна блокировать удаление карточки пользователем. Пользователь нажал «Удалить» --- карточка исчезла мгновенно, а файлы удалятся в фоне через минуту или ночью.

  **Целостность данных**                Система должна гарантировать, что файл не будет удален, если он все еще используется где-то еще (например, в другой колоде через механизм Форка). Обычно это решается проверкой счетчика ссылок (Reference Counting) или архитектурным запретом на переиспользование Media ID.

  **Пакетная обработка (Batching)**     Эффективнее удалить 1000 файлов одним запросом к S3 API, чем делать 1000 отдельных запросов. Процесс должен накапливать ID на удаление и сбрасывать их пачками.
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Офис-менеджер**, а **Media Service** --- это **Склад в подвале**.

1.  **Работа:** Сотрудники (Пользователи) приносят коробки (Медиа) и ставят их на Склад. Офис-менеджер записывает в журнал: «Коробка №555 принадлежит проекту А».

2.  **Увольнение (Удаление проекта):**

    - Проект А закрывается. Все документы (Карточки) уничтожаются в шредере.

    - **Проблема:** Коробка №555 все еще стоит на Складе и занимает место.

3.  

4.  **Уборка (SR-BG-02):**

    - Офис-менеджер не бежит на склад сразу. Он составляет список «На выброс».

    - Вечером приходит **Уборщик** (Cleanup Worker).

    - Он берет список, спускается на склад и выбрасывает коробки, которые больше никому не нужны.

5.  

6.  **Результат:** Склад свободен для новых вещей.

### **3. Пример взаимодействия (логический Flow)**

Этот сценарий описывает процесс каскадного удаления медиа при удалении колоды.

**Исходные данные:**

- **Колода:** deck-vacation (содержит 100 карточек).

- **Медиа:** В карточках есть ссылки на 50 картинок и 100 аудиофайлов (всего 150 media_id).

**Сценарий: Пользователь удаляет колоду с медиа-контентом**

1.  **Действие пользователя:** Нажимает «Удалить колоду» в интерфейсе.\
    DELETE /decks/deck-vacation

2.  **Обработка API (PVS):**

    - Сервис помечает колоду как DELETED (Soft Delete) или начинает транзакцию удаления.

    - **Сбор мусора (Harvesting):** Перед физическим удалением записей из таблицы cards, сервис делает выборку всех media_id, привязанных к этим карточкам.\
      SELECT media_id FROM cards WHERE deck_id = \'deck-vacation\' AND media_id IS NOT NULL

    - Результат: Список из 150 UUID.

3.  

4.  **Постановка в очередь:**

    - Сервис отправляет сообщение в очередь media-cleanup-queue (RabbitMQ/Kafka).

    - Payload: { \"media_ids\": \[\"uuid-1\", \"uuid-2\", \... \"uuid-150\"\] }.

5.  

6.  **Физическое удаление данных:**

    - PVS удаляет карточки и колоду из своей базы PostgreSQL. Транзакция завершается. Пользователь видит, что колода исчезла.

7.  

8.  **Обработка Воркером (Cleanup Worker):**

    - Воркер (на стороне PVS или Media Service, в зависимости от архитектуры) получает сообщение.

    - Он группирует ID по бакетам (если они разные).

    - Отправляет пакетный запрос в **Media Service** (или напрямую в S3, если PVS имеет права): DELETE /bulk-delete.

9.  

10. **Результат:** Файлы физически стерты с дисков S3. Биллинг за хранение уменьшился.

## **SR-BG-03: GDPR Compliance (Каскадное удаление данных)**

Это сервисное требование описывает процедуру полного уничтожения «цифрового следа» пользователя по его запросу («Право на забвение»). Удаление пользователя --- это сложная, тяжелая операция, затрагивающая десятки таблиц. Сервис должен гарантировать, что после завершения процесса в базе данных не останется ни одной записи, связанной с user_id удаляемого лица, включая личные колоды, прогресс обучения, историю поиска и настройки.

### **1. Цель и ключевые принципы**

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                         **Описание**
  ----------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Полнота очистки**                 Главная цель --- юридическая чистота. Нельзя оставить «немного данных» (например, email в логах или старую колоду). Удаляется всё, что можно идентифицировать как личные данные.

  **Каскадность (Cascading)**         Удаление корневой сущности (User Profile) должно запускать цепную реакцию: удаляются Проекты -\> Колоды -\> Карточки -\> Прогресс -\> Статистика.

  **Обработка публичного контента**   Если пользователь был автором публичных колод, система должна решить их судьбу. Согласно SR-COL-08, для активных подписчиков эти колоды должны быть **отсоединены** (скопированы), а оригиналы автора --- удалены.

  **Анонимизация (где применимо)**    В некоторых случаях (например, история вкладов в чужие колоды или отзывы) удаление может нарушить целостность данных. В таких случаях данные не удаляются, а **анонимизируются** (автор меняется на системного пользователя Deleted User).

  **Асинхронность**                   Удаление гигабайтов данных (если пользователь был активен годами) может занять минуты. Операция выполняется фоновым воркером, пользователь получает уведомление по завершении.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Офисное здание**, а **Пользователь** --- это **Арендатор**.

1.  **Расторжение контракта:** Арендатор подает заявление на выезд.

2.  **Опечатывание (Soft Delete):** Сначала менеджер блокирует пропуск. Арендатор больше не может войти, но его вещи еще в кабинете (на случай, если он передумает в течение 30 дней --- Grace Period).

3.  **Ликвидация (Hard Delete - SR-BG-03):** По истечении срока приходит бригада утилизаторов.

    - Они выносят всю мебель из личного кабинета (Личные колоды).

    - Они снимают табличку с двери (Профиль).

    - **Нюанс:** Арендатор повесил красивую картину в холле (Публичная колода). Уборщики не выбрасывают её, если она нравится другим жильцам, но стирают подпись автора (Анонимизация) или отдают копии жильцам (Detachment).

4.  

5.  **Результат:** Кабинет пуст и стерилен. Никаких следов пребывания.

## **SR-PERF-01: Low Latency для API обучения (Производительность сессии)**

Это сервисное требование устанавливает жесткий нефункциональный стандарт для ключевого сценария использования --- сессии обучения. API, отдающее следующую карточку (GET /study/next), должно отвечать быстрее **100 миллисекунд** (в 99-м перцентиле). Это требует использования стратегий кэширования, предзагрузки (prefetching) и оптимизированных структур данных, так как прямой SQL-запрос с множеством JOIN-ов и сортировок при каждом клике не обеспечит нужной скорости.

### **1. Цель и ключевые принципы**

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Принцип**                        **Описание**
  ---------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  **Doherty Threshold (\<400ms)**    Психологический порог, при котором взаимодействие с компьютером кажется мгновенным. Для ритмичных действий (листание карточек) требования еще выше --- задержка не должна быть заметна вообще.

  **Очереди в памяти (In-Memory)**   Активная сессия обучения не должна каждый раз обращаться к «холодному» диску базы данных. Список ID карточек для сессии должен загружаться в Redis (List) при старте урока.

  **Асинхронная запись**             Когда пользователь ставит оценку карточке, он не должен ждать, пока база данных обновит индексы и статистику. Запрос POST /review должен возвращать 200 OK и следующую карточку немедленно, а сохранение прогресса происходит в фоне.

  **Оптимизация пейлоада**           JSON-ответ с карточкой должен быть минималистичным. Тяжелые данные (например, base64-картинки) запрещены; используются только ссылки на CDN.

  **Предзагрузка (Prefetching)**     В идеале, клиентское приложение должно скачивать не по одной карточке, а пачками (chunks) по 10-20 штук, чтобы сеть вообще не влияла на перелистывание внутри пачки.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### **2. Высокоуровневое описание**

Представьте, что **PVS** --- это **Крупье в казино**.

1.  **Плохой Крупье (SQL):**

    - Игрок просит карту.

    - Крупье встает, идет в хранилище, ищет колоду, тасует её, возвращается, дает карту. Игрок ждет 2 секунды. Игра разваливается.

2.  

3.  **Хороший Крупье (Redis + Prefetch):**

    - Перед началом игры Крупье заряжает **«Башмак» (Shoe)** --- специальное устройство, где уже лежат 6 перемешанных колод.

    - Игрок просит карту.

    - Крупье одним движением достает верхнюю карту из Башмака. Задержка --- 0.1 секунды.

    - Пока игрок смотрит на карту, Крупье уже держит пальцы на следующей.

4.  

В PVS роль «Башмака» выполняет Redis List, куда при старте сессии загружаются ID карточек.
