# Введение

Группа алгоритмов управления сессиями и контекстом (Session Management) — это базовый слой безопасности и маршрутизации микросервиса Authorization Service. Его основная задача заключается в конвертации глобальной идентичности пользователя (подтвержденной во внешнем IdP) в локальную, защищенную сессию, полностью контролируемую сервером.

Алгоритмы этой группы работают как невидимый "привратник" для всех остальных микросервисов Платформы. Они перехватывают каждый входящий запрос от браузера клиента, проверяют легитимность Phantom Token (Cookie) в сверхбыстром кэше Redis, определяют текущий рабочий контекст пользователя (например, активный Workspace) и прокидывают эти данные во внутреннюю сеть в виде доверенных HTTP-заголовков. Благодаря этому достигается архитектура Zero Trust, при которой бизнес-микросервисы избавлены от необходимости парсить токены, работать с криптографией или обращаться к Redis.

# Алгоритм валидации и инъекции Phantom Token

## Контекст и область применения

Данный раздел описывает предпосылки создания алгоритма, его основное предназначение в рамках системы, а также ключевые бизнес-требования, которые он удовлетворяет. Здесь же приведены сценарии использования и ограничения, которые необходимо учитывать при его работе.

### Почему был создан

Передача JWT-токенов в браузер подвергает Платформу рискам XSS-атак и делает невозможным мгновенный отзыв скомпрометированных сессий (Stateful Auth). Внутренним микросервисам сложно каждый раз валидировать JWT. Алгоритм Phantom Token решает обе эти проблемы: клиент получает нечитаемый `UUID` в `HttpOnly` Cookie, а внутренние сервисы — проверенные, доверенные HTTP-заголовки.

### Бизнес-требование

Система должна заменять уязвимые JWT-токены на безопасные Phantom Tokens и маршрутизировать контекст пользователя во внутренние сервисы с помощью доверенных заголовков (SR-AUTH-SM-01, SR-AUTH-LA-03).

### Область применения

Алгоритм активно используется в следующих сценариях и процессах платформы, обеспечивая постоянную проверку доступа:

| **№** | **Описание** |
| :--- | :--- |
| **1** | Выполнение любого защищенного бизнес-запроса от SPA-клиента (фронтенда). |
| **2** | Фоновые AJAX-опросы состояния (например, `keep-alive`). |

### Ограничения применения

Работа алгоритма подчиняется ряду технических и логических ограничений, несоблюдение которых приводит к блокировке запроса:

| **№** | **Описание** |
| :--- | :--- |
| **1** | Алгоритм требует доступности Redis-кластера. При падении Redis все запросы получают 500-ю ошибку (Fail-Closed). |
| **2** | Запрос должен содержать `HttpOnly` Cookie `auth_sess`. |

## Входные данные

Для успешной проверки сессии алгоритму требуется контекст входящего HTTP-запроса от браузера:

| **Параметр** | **Тип данных** | **Описание** | **Ограничения** | **Обязательность** |
| :--- | :--- | :--- | :--- | :--- |
| `HttpRequest` | `HttpRequestMessage` | Входящий запрос от клиента (браузера) | - | Да |
| `Cookie` | `string` | Содержимое заголовка `Cookie` (поиск `auth_sess`) | - | Нет (если пуст - 401) |
