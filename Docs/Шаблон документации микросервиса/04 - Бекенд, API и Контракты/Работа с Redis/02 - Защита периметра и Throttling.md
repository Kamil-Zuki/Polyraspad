# Введение

Данный документ описывает процессы и правила использования Redis для защиты микросервиса Authorization Service от брутфорс-атак (перебор паролей/OTP), злоупотребления API-лимитами (DDoS на уровне приложения) и отслеживания квот гостевых пользователей. Механизмы Rate Limiting и Throttling (КАР-10) реализуются исключительно в Redis благодаря его атомарным операциям (INCR, EXPIRE) и высокой производительности.

# 1. Список операций Защиты периметра и Throttling

Перечень механизмов, ограничивающих частоту запросов и блокирующих подозрительную активность.

| Метод (SR) | Описание операции |
| :--- | :--- |

# Защита от брутфорса (Rate Limiting) (SR-AUTH-SQ-04)

## Общая информация

Ограничение частоты запросов к критичным эндпоинтам (например, `/auth/login`, `/auth/refresh`, `/auth/magic-link`) по IP-адресу или идентификатору пользователя. Реализует паттерн Sliding Window (Скользящее окно) с помощью отсортированных множеств (ZSET) или атомарных счетчиков в Redis.

| Тип операции | Read (Чтение), Write (Запись) |
| :--- | :--- |
| **Ключ Redis** | `auth:ratelimit:{ip_or_subject}:{endpoint}`<br>где `{ip_or_subject}` = IP-адрес (или ID юзера), `{endpoint}` = короткий алиас маршрута (напр. `login`). |
| **DTO ответа** | Целое число `requests_count` (счетчик запросов в текущем окне). |

## Логика обработки запроса

*   **Чтение и инкремент:** При каждом запросе на защищенный эндпоинт сервис вызывает атомарную команду `INCR auth:ratelimit:{ip}:{endpoint}`. Если ключ создается впервые, ему устанавливается `EXPIRE` на длительность окна.
*   **Проверка лимита:** Если результат `INCR` превышает установленный порог (например, `> 10`), запрос отклоняется с HTTP 429 Too Many Requests.
*   **Инвалидация:** Ключи удаляются автоматически силами самого Redis по истечении окна.
