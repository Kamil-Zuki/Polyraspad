# Введение

Замена уязвимых JWT-токенов в браузере на непрозрачные, криптографически случайные UUID (Phantom Tokens) в HttpOnly Cookie. Это делает невозможной кражу прав через XSS и позволяет мгновенно "убивать" скомпрометированные сессии.

## Контекст и проблема

Традиционный подход к аутентификации в современных SPA-приложениях заключается в выдаче JWT (JSON Web Token) клиенту после успешного логина. Этот токен обычно сохраняется в `localStorage` или `sessionStorage` браузера, а затем прикрепляется к каждому HTTP-запросу в заголовке `Authorization: Bearer <token>`.

Такой подход имеет несколько фундаментальных проблем безопасности и управления:

*   **Уязвимость к XSS (Cross-Site Scripting):** Любой вредоносный JavaScript код (например, из скомпрометированной NPM-зависимости), который выполнится на странице, может легко прочитать `localStorage` и украсть JWT-токен пользователя, получив полный доступ к его аккаунту.
*   **Сложность отзыва (Revocation):** JWT-токены являются "stateless" (без состояния). Если токен украден, злоумышленник сможет пользоваться им до тех пор, пока не истечет время жизни токена (`exp`). Отозвать (инвалидировать) конкретный JWT-токен на стороне сервера крайне сложно (требуется вести глобальные "черные списки", что убивает саму идею stateless-архитектуры).
*   **Утечка данных:** JWT легко декодируется (Base64). Любой, кто перехватит токен, сможет прочитать содержащиеся в нем данные (ID пользователя, роли, email).

## Принятое решение

Мы архитектурно отказались от передачи сырых JWT-токенов в браузер. Вместо этого `Authorization Service` реализует паттерн **Phantom Token** (также известный как Opaque Token или Stateful Session):

1.  **Server-Side State:** При успешной аутентификации пользователя (или получении Access/Refresh токенов от STEOS ID), сервис генерирует криптографически случайную строку — `UUID v4` (Phantom Token).
2.  **Двухуровневое хранение:** 
    *   Реальные данные сессии (ID пользователя, роли, привязка к токенам STEOS ID) сохраняются в надежную базу данных (`PostgreSQL`, таблица `authorized_sessions`).
    *   Для обеспечения скорости проверки каждого входящего запроса (< 2ms), стейт сессии зеркалируется в In-Memory хранилище (`Redis`) с ключом, равным сгенерированному UUID.
3.  **Безопасная передача (HttpOnly Cookie):** Браузеру отправляется только этот случайный UUID, и строго в виде **HttpOnly, Secure, SameSite=Lax** Cookie. 

При каждом последующем запросе браузер автоматически отправляет Cookie. **API Gateway (агрегатор)** принимает запрос и для валидации сессии обращается к **Authorization Service** (например, по gRPC), где по UUID восстанавливается стейт из Redis/БД; только после этого запрос с инжектированным контекстом идёт дальше (см. КАР-2).

## Обоснование и последствия

### Плюсы

*   **Абсолютная защита от XSS:** Поскольку Cookie имеет флаг `HttpOnly`, никакой JavaScript-код в браузере (даже вредоносный) не имеет доступа к токену сессии. Кража токена через XSS становится невозможной.
*   **Мгновенный отзыв (Immediate Revocation):** В отличие от JWT, мы полностью контролируем состояние. Если нужно "убить" сессию пользователя (например, при подозрении на взлом или при нажатии "Выйти на всех устройствах"), мы просто удаляем ключ из Redis. Сессия аннулируется в ту же миллисекунду.
*   **Скрытие структуры данных:** Злоумышленник, перехвативший трафик, видит только бессмысленный UUID (`f47ac10b...`). Он не может узнать из него ни ID пользователя, ни его права, ни срок действия сессии.
