# Введение

В данном документе описываются механизмы взаимодействия **Authorization Service** с глобальным провайдером идентичности (STEOS ID) через брокер сообщений RabbitMQ. Использование асинхронных очередей (Event-Driven Architecture) критически важно для мгновенной реакции локального сервиса авторизации на изменения профиля, ротацию ключей или смену пароля (Back-Channel Logout) без необходимости постоянного поллинга (HTTP Polling) внешнего IdP.

# 1. Список событий Синхронизации OIDC и Федерации

Ниже перечислены все асинхронные операции, связанные с получением обновлений от STEOS ID.

| Метод (SR) | Тип операции | Очередь / Топик | Описание |
| :--- | :--- | :--- | :--- |
| SR-AUTH-OI-04 | Consume | `steosid:events:backchannel-logout` | Потребление сигнала о смене пароля или блокировке в STEOS ID для отзыва локальных сессий. |
| SR-AUTH-OI-06 | Consume | `steosid:events:user-updated` | Оповещение об изменении профиля пользователя в IdP (смена Email, Имени и т.д.). |

# Событие: Асинхронный Back-Channel Logout (SR-AUTH-OI-04)

## Общая информация

Потребление критического события от STEOS ID, информирующего о том, что сессия пользователя была завершена на стороне глобального IdP (например, пользователь нажал "Выйти со всех устройств", сменил пароль или был заблокирован администратором). Authorization Service должен немедленно инвалидировать все локальные сессии (Refresh Tokens) данного пользователя.

| Тип операции | Consume (Потребление) |
| :--- | :--- |
| **Exchange / Топик** | `steosid:events:auth` |
| **Routing Key** | `auth.session.revoked` |

## Параметры сообщения

Ниже описана структура Payload, который потребляется из очереди.

| Название параметра | Тип данных | Описание |
| :--- | :--- | :--- |
| **subjectId** | string (uuid) | Глобальный идентификатор пользователя (sub) в STEOS ID. |
| **sessionId** | string (uuid) | (Опционально) Идентификатор конкретной глобальной сессии, если отзыв был точечным. |

## Логика обработки запроса

Процесс локальной инвалидации сессий при получении Back-Channel Logout.

*   **Потребление:** Воркер извлекает сообщение из очереди `steosid:events:backchannel-logout`.
*   **Проверка идемпотентности:** Система проверяет `eventId` в кэше/БД. Если событие уже обрабатывалось, оно игнорируется (ACK).
*   **Поиск сессий:** Система ищет все активные сессии (`Refresh Tokens`) в локальной БД, привязанные к указанному `subjectId` (и опционально `sessionId`).
*   **Инвалидация:** 
    * Статус найденных локальных сессий меняется на `REVOKED`.
    * Генерируется запись в локальный `Audit Log` (WORM).
*   **Синхронизация с UI:** Воркер инициирует публикацию WebSocket-события `session_revoked` для всех активных подключений данного `subjectId` (чтобы выкинуть пользователя из интерфейса).
*   **Широковещательная рассылка:** Воркер публикует внутреннее событие `GlobalLogoutEvent` в локальный Exchange платформы, чтобы другие микросервисы (Storage, Tasks) сбросили свои in-memory кэши прав этого пользователя (см. Группу 3).
*   **Завершение:** Сообщение удаляется из брокера (ACK).
