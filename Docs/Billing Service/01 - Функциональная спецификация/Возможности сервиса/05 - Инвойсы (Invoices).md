# Группа 5: Инвойсы (Invoices)

## Введение

В этом разделе описывается **история платежей** пользователя — инвойсы, созданные из webhook events и отображаемые в `/billing/invoices`.

**Метафора:**

Представьте **выписку по карте** в интернет-банке: каждая строка — успешный или ожидающий платёж по абонементу, с суммой и датой.

# Детальная спецификация требований

## SR-BILL-INV-01: List invoices {#SR-BILL-INV-01}

Пользователь видит историю платежей по SaaS-подписке — суммы, статусы и даты оплаты для support и личного контроля.

### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| **User-scoped** | Фильтр по customer через `user_id`. |
| **Pagination** | `page`, `page_size` в gRPC request. |
| **Provider ids** | `provider_invoice_id` для support correlation. |

### 2. Высокоуровневое описание

Представим список инвойсов как **выписку по карте в интернет-банке**.

1. **Накопление данных:** webhook и renewal pipeline upsert строки `invoices` при `payment.succeeded` и recurring charges.
2. **Запрос истории:** пользователь открывает `/billing/invoices` → Aggregator вызывает `ListInvoices(user_id, page, page_size)`.
3. **Пагинация:** Billing фильтрует по customer, возвращает `amount_paid`, `currency`, `status`, `paid_at`, `provider_invoice_id`.
4. **Отображение:** UI рисует таблицу Pro-платежей для личного контроля и support correlation.

Таким образом, инвойсы — read-only projection платежей; создание строк идёт через webhook pipeline, не через user API.

### 3. Примеры взаимодействия (логические сценарии)

#### Сценарий А: Invoice history (Happy Path)

1. **REST:** GET `/api/billing/invoices?page=1`.
2. **gRPC:** `ListInvoices`.
3. **Ответ:** массив с `amount_paid`, `currency`, `status`, `paid_at`.
