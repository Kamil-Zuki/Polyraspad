# SR-VOC-08: Системные сущности и Настройки (System & Settings)

## Описание
Данный раздел описывает функциональные требования к управлению пользовательскими целями обучения, расчету серий дней активности (Streaks), сбросу суточных лимитов активности и ведению журнала удалений для оффлайн-синхронизации мобильных и веб-приложений.

---

## Возможности данного раздела

| Код | Название и Описание |
| :--- | :--- |
| **SR-VOC-SYS-01** | **Дневные цели обучения (Daily Goals):** Цели `DailyGoalNew` / `DailyGoalReview` (дефолты при создании: **20** / **100**). |
| **SR-VOC-SYS-02** | **Учебная серия (Streak Calculation):** Расчёт `CurrentStreak` / `MaxStreak` с учётом `RolloverHour`. |
| **SR-VOC-SYS-03** | **Журнал оффлайн-удалений (Deleted Objects Log):** Tombstones в `DeletedObject` для sync. |
| **SR-VOC-SYS-04** | **SyncData:** Полная оффлайн-синхронизация данных проекта (`SyncService`). |
| **SR-VOC-SYS-05** | **Get/Update UserSettings:** Язык UI, rollover, цели, streaks. |
| **SR-VOC-SYS-06** | **Доступ к колоде (UserEntitlement):** Проверка/выдача доступа к колоде Marketplace (`FREE`/`PURCHASE`/`PROMO`/`CONTRIBUTION`); SaaS-лимиты — BillingService. |

---

# Детальная спецификация требований

## SR-VOC-SYS-01: Дневные цели обучения {#SR-VOC-SYS-01}
### 1. Цель и ключевые принципы
- **Планирование нагрузки:** Пользователь настраивает `DailyGoalNew` / `DailyGoalReview`. Дефолты при создании настроек в коде: **20** новых и **100** повторений.
- **Счетчик лимитов:** При завершении повторения бэкенд учитывает прогресс относительно дневных целей.

---

## SR-VOC-SYS-02: Учебная серия (Streak) {#SR-VOC-SYS-02}
### 1. Цель и ключевые принципы
- **Сброс суток по часовому поясу:** Дневной цикл активности сбрасывается в час, указанный в `RolloverHour` (по умолчанию в 04:00 по местному времени пользователя, чтобы полуночники не теряли стрик).
- **Инкремент серии:** Если пользователь выполнил хотя бы одну учебную сессию за текущие сутки, его `CurrentStreak` увеличивается на 1.
- **Сброс серии:** Если за сутки (между двумя rollover часами) не зафиксировано ни одной учебной сессии, `CurrentStreak` сбрасывается в 0.
- **Max Streak:** Если `CurrentStreak` превышает `MaxStreak`, значение `MaxStreak` обновляется.

---

## SR-VOC-SYS-03: Журнал оффлайн-удалений {#SR-VOC-SYS-03}
### 1. Цель и ключевые принципы
- **Tombstones:** При удалении колоды, заметки или карточки на сервере, запись об этом с указанием `EntityId` и `EntityType` вносится в таблицу `DeletedObject`.
- **Синхронизация:** При подключении клиента после оффлайна он отправляет дату своей последней синхронизации. Сервер возвращает список всех `DeletedObject`, удаленных после этой даты. Клиент удаляет эти записи из локальной SQLite БД.

---

## SR-VOC-SYS-04: SyncData {#SR-VOC-SYS-04}
### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| Полный sync | `SyncData` / batch reviews — не только tombstones. |

### 2. Высокоуровневое описание
`SyncService` отдаёт/принимает изменения сущностей проекта для оффлайн-клиентов, включая batch submit reviews.

### 3. Примеры взаимодействия (логические сценарии)

#### Сценарий А: Pull после оффлайна
1. Клиент вызывает SyncData с watermark.
2. Сервис возвращает дельту сущностей и `DeletedObject`.

---

## SR-VOC-SYS-05: Get/Update UserSettings {#SR-VOC-SYS-05}
### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| Единая запись | PK = `UserId`; поля целей, streak, `InterfaceLanguage`, `RolloverHour`. |

### 2. Высокоуровневое описание
Пользователь читает и обновляет настройки через соответствующий gRPC/сервисный слой.

### 3. Примеры взаимодействия (логические сценарии)

#### Сценарий А: Смена цели
1. Клиент ставит `DailyGoalNew = 30`.
2. Сервис обновляет `UserSetting.UpdatedAt`.

---

## SR-VOC-SYS-06: Доступ к колоде (UserEntitlement) {#SR-VOC-SYS-06}
### 1. Цель и ключевые принципы

| Принцип | Описание |
| :--- | :--- |
| Deck access | `UserEntitlement` = право на колоду, не SaaS-квоты. |
| Sources | `FREE` / `PURCHASE` / `PROMO` / `CONTRIBUTION`. |

### 2. Высокоуровневое описание
`CheckEntitlement` / выдача доступа при publish/fork/purchase записывает или проверяет `UserEntitlement.IsActive` для `DeckId`.

### 3. Примеры взаимодействия (логические сценарии)

#### Сценарий А: Check entitlement
1. Клиент запрашивает доступ к публичной колоде.
2. Сервис ищет активный `UserEntitlement` или отказывает.
