# Введение

Эта группа сущностей формирует **Локальный защитный периметр (Perimeter Security) и Механизм квотирования анонимов** внутри микросервиса Authorization Service. 

В распределенной архитектуре STEOS каждая платформа (публичное облако `steos.io` или корпоративный инстанс `bank.steos.io`) обязана самостоятельно защищать свои вычислительные ресурсы от нелегитимного использования, не перекладывая всю нагрузку на глобальный STEOS ID. Если глобальный ID защищает *идентичность* (пароли, аккаунты), то локальный Auth Service защищает *инфраструктуру* (LLM-модели, пропускную способность API, базы данных).

Особую архитектурную сложность представляет реализация функционала **Публичного доступа (Guest Mode)**. Маркетинг и бизнес-модель часто требуют предоставить пользователю "демо-версию" продукта (например, сгенерировать 3 картинки или проанализировать 1 договор) без принудительной регистрации. Эта группа сущностей позволяет платформе открывать доступ наружу, сохраняя при этом жесткий контроль над расходами.

**Архитектурные особенности группы:**

1.  **Локальная Блокировка (Edge Throttling):** Сервис способен мгновенно отбивать атаки (DDoS, API Scraping) на уровне локального шлюза, внося IP-адреса или аппаратные отпечатки в "черный список". Эти блокировки действуют только в рамках конкретной инсталляции платформы и не "банят" пользователя глобально в STEOS ID.
2.  **Stateful Guest Quotas (Учет неавторизованного потребления):** В отличие от зарегистрированных пользователей (чьи лимиты жестко контролируются в `Global Billing` и `Workspace Service`), "Гости" не имеют ни контрактов, ни кошельков. Группа реализует паттерн *Soft Metering*: она связывает факт потребления тяжелой фичи (например, `AI_GENERATE_IMAGE`) с эфемерной сессией и отпечатком устройства (Fingerprint).
3.  **Гибридное хранение (Memory + Persistent):** Сущности этой группы спроектированы под высочайшую нагрузку (десятки тысяч запросов в секунду). Подсчет квот и проверка банов происходят физически в **Redis** (In-Memory). Реляционная база данных (PostgreSQL) выступает лишь персистентным хранилищем для фиксации итогов (сброс счетчиков раз в минуту) и возможности восстановления состояния кэша при рестарте подов Kubernetes.

В совокупности эти механизмы позволяют платформе STEOS оставаться открытой и привлекательной для новых пользователей, надежно защищаясь от ботнетов и "профессиональных халявщиков" (freeloaders).

# Использование гостевой фичи (`guest_feature_usages`)

## 1. Общее описание

**Использование гостевой фичи (Guest Feature Usage)** — это высоконагруженная операционная сущность-счетчик, которая фиксирует объем вычислительных ресурсов (или количество действий), потребленных неавторизованным пользователем (Гостем) в рамках его временной сессии.

В архитектуре платформы STEOS публичные пространства могут открывать часть своего функционала "наружу" в маркетинговых целях (например, 3 бесплатные генерации ИИ-изображений или 10 поисковых запросов по базе знаний). Эта таблица выступает в роли **Теневого Биллинга (Shadow Metering)**. В отличие от корпоративных пользователей, чьи лимиты хранятся в `Workspace Service`, гости не имеют контрактов и кошельков. Их лимиты жестко контролируются здесь, на уровне шлюза авторизации.

**Архитектурное назначение:**
1.  **Quota Enforcement (Контроль лимитов):** Не позволяет анонимным пользователям "выкачать" базу данных или сжечь бюджет на вызовы тяжелых нейросетей. При превышении лимита система отдает ошибку `402 Payment Required` или `401 Unauthorized` с требованием регистрации.
2.  **State Persistence (Защита от сброса кэша):** Хотя физический подсчет каждого запроса происходит в оперативной памяти (Redis) для обеспечения задержки < 2 мс, данные регулярно сбрасываются в эту реляционную таблицу (паттерн Write-Behind). Если кластер Redis перезагрузится, гости не получат свои лимиты заново (что предотвращает массовый абуз).
3.  **Аналитика "Freemium" воронки:** Данные из этой таблицы передаются в Data Warehouse (DWH) для подсчета конверсии: маркетологи видят, сколько гостей исчерпали лимит полностью и после этого зарегистрировались в системе.

## 2. Атрибуты (поля) сущности
**Таблица:** `guest_feature_usages`

*В соответствии с «Белой книгой разработчика баз данных», для таблицы высокочастотных счетчиков используется суррогатный автоинкрементный ключ `int8`. Объем потребления хранится в типе `numeric`, так как гость может тратить не только штучные запросы, но и дробные мегабайты трафика.*

| Название | Тип данных | Огр-ния | Описание |
| :--- | :--- | :--- | :--- |
| `id` | `int8` | PK, AI, NOT NULL | **Уникальный идентификатор.** Суррогатный автоинкрементный ключ (`GENERATED ALWAYS AS IDENTITY`). |
| `guest_session_id` | `uuid` | FK, NOT NULL | **Сессия гостя.** Ссылка на родительскую таблицу `guest_sessions`. Однозначно идентифицирует анонима (связывая его с `device_fingerprint`). |

*Обязательный индекс:* Уникальный составной B-Tree индекс `UNIQUE (guest_session_id, workspace_id, feature_id)` — гарантирует, что для одной гостевой сессии в одном публичном пространстве существует ровно один счетчик для каждой конкретной фичи.

## 3. Связи с другими сущностями и микросервисами

| Связанная сущность / Сервис | Тип связи и описание взаимодействия |
| :--- | :--- |
| **Гостевая сессия**<br>(`guest_sessions`) | **Многие-к-одному.** Жизненный цикл счетчика жестко привязан к сессии. Когда гостевая сессия "протухает" (истекает `expires_at`), фоновый процесс удаляет и саму сессию, и все её счетчики каскадно (`ON DELETE CASCADE`). |
| **Platform Service** | **Логическая ссылка.** Поле `feature_id` диктует семантику потребления (что именно мы считаем). |
## 4. Жизненный цикл и Алгоритм работы

1.  **Первое касание (Cache Miss & Bootstrapping):**
    *   Гость нажимает "Сгенерировать логотип" на лендинге.
    *   Запрос долетает до API Gateway (Auth Service).
    *   Шлюз извлекает `guest_session_id` из Cookie и лезет в Redis за счетчиком `guest:{session_id}:feature:{id}`.
    *   Redis пуст (первый запрос). Шлюз делает `SELECT` из таблицы `guest_feature_usages`. Там тоже пусто.
    *   Шлюз создает ключ в Redis со значением `0` и делает `INSERT` в БД со значением `0`.
2.  **Сверка лимитов (Policy Evaluation):**
    *   Шлюз асинхронно или из кэша достает правило: *"Гостям разрешено 3 генерации"*.
    *   Выполняет атомарный инкремент в Redis: `INCR guest:{session_id}:feature:{id}`. Результат = 1.
    *   Сравнивает: `1 <= 3`. Запрос пропускается в сервис генерации.
3.  **Агрегация и Персистенция (Write-Behind):**
    *   Чтобы не убить базу данных постоянными `UPDATE`, инкремент в БД не происходит синхронно.
    *   Раз в 30-60 секунд запускается фоновый воркер (Sync Daemon). Он собирает из Redis все измененные счетчики и делает пачку массовых обновлений: `UPDATE guest_feature_usages SET usage_amount = {new_val}, updated_at = NOW()`.
4.  **Блокировка (Enforcement):**
    *   Гость делает 4-й запрос. Redis делает `INCR`, результат = 4.
    *   Шлюз сравнивает: `4 > 3`.
    *   Запрос немедленно отклоняется с ошибкой `429 Too Many Requests` (или `403 Forbidden` с телом `{"error": "GUEST_QUOTA_EXCEEDED"}`). Платформа предлагает гостю зарегистрироваться.

## 5. Ключевая бизнес-логика

| Принцип логики | Описание и влияние на систему |
| :--- | :--- |
| **Защита от сброса (Persistence over Cache)** | Если сервер Redis аварийно перезагружается и теряет In-Memory данные, хитрые пользователи могли бы получить свои "бесплатные попытки" заново. Синхронизация с таблицей `guest_feature_usages` гарантирует, что после перезапуска Redis шлюз считает исторические данные из PostgreSQL (Hydration) и восстановит счетчик. |
| **Soft Fingerprinting Defense** | Поскольку счетчик жестко привязан к `guest_session_id`, который в свою очередь привязан к аппаратному отпечатку браузера (`device_fingerprint`), пользователь не сможет обнулить этот счетчик, просто переключив VPN (сменив IP) или удалив Cookies. Шлюз узнает его "железо", найдет старую сессию и вернет ему его исчерпанный счетчик. |
