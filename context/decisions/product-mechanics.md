# Ключевые механики продукта (Reader, термины, карточки)

Сжатое описание **как ведёт себя система**, без пересказа планов. Инварианты для кода и UX.

---

## Термины (term-first)

- **Единица знания — точная форма в проекте:** `sleep` и `slept` — разные термины; статусы и дубликаты считаются по **`NormalizedText`**, не по лемме.
- **Фраза — отдельный термин** (`PHRASE`). В reader **подсветка фразы имеет приоритет** над отдельными словами, если фраза заведена.
- **Статусы:** NEW → синий; SAVED (в API часто вместо legacy «LINGQ» в БД) → жёлтый / learning; KNOWN → обычный текст; IGNORED → приглушён, не в статистике.
- **Действия из текста:** сохранение значения и контекста идёт в **реальную форму**; «известно» и «игнор» — тоже по этой форме, без привязки статуса к лемме.

---

## Reader: чтение и страница

- **Импорт:** рабочий поток для EPUB, TXT и вставки текста; **PDF** только если из текста реально что-то извлекли — иначе **явная ошибка в UI**, без пустого reader «молча».
- **Один и тот же поток** для пользовательского контента и для коротких **seed-текстов** в библиотеке (onboarding): те же endpoint’ы, тот же анализ и подсветка.
- **Смена страницы:** опционально массово переводить **только NEW** в KNOWN — сервером **одной транзакцией** (`BulkMarkKnown`); включение правила — настройка (пока может жить в localStorage до переноса в профиль).

---

## Mining (из текста в учёт)

- **Pop-up по слову/фразе** + быстрый путь **Mine** согласованы с операциями термина (`CreateOrUpdateTerm` → SAVED, Known, Ignore и т.д.).
- **AI — внешние LLM по ключам**, не self-hosted Ollama в продукте: один стиль провайдера, секреты, контракт запроса/ответа.
- **Смысл AI для карточки:** предложение целиком как контекст; перевод **цели в этом предложении** и перевод **всего предложения**; словарная лемма **только как подсказка** — не ключ для статуса и не источник дубликатов.
- **TTS:** движение к внешнему API и опции «озвучить при создании» (автопривязка аудио к карточке).
- **Grammar notes:** отдельный короткий разбор по **уже сохранённому** предложению; не заменяет инспектор термина.

## Раздел Vocabulary

- **Список терминов проекта** с фильтрами по статусу/типу и поиском по тексту/нормализованному тексту.
- **Пагинация курсором** (стабильные срезы по времени обновления + id), не «ломающаяся» при вставках.
- **В API для жёлтого состояния — `SAVED`**, чтобы не путать с legacy именем в БД.

## Карточки: заметка как источник истины

- **Полная карточка** в продуктовом потоке — **Anki-like заметка** (`fieldValues` / note payload): редактирование и отображение «полной формы» опираются на поля заметки.
- **Превью** (дубликаты в reader, связанные карточки, маркетплейс): строки превью **производятся только из `field_values` заметки**, теми же правилами, что редактор — иначе пользователь видит «другую» карточку в списке и в уроке.
- **Capture:** по умолчанию колода **Inbox**; при необходимости — явный **`deckId`** в контракте capture.
- **Study:** контент урока — **`note` (fieldValues) + производный `target_index`**; подсветка цели — срез `Expression` по индексу, иначе текст из поля **Word**; перевод и прочий смысл — из тех же полей заметки.
- **Связанные карточки / sibling bury:** ключ только по **`project_term_id`** (точная форма в проекте), без лемм в карточке и в proto для контента.
- **Контракты:** плоские «предложение / цель / перевод» на wire убраны — только note payload и индекс.

## Редактор `/editor`

- **Сетка полей** в духе InOriginal: expression, word, транскрипция, типы слова, перевод, определение, пример, синонимы/антонимы, источник и URL; микровзаимодействия «слово из expression», «подставить выделение».
- **Словарные поля** (транскрипция, типы, определение, пример, синонимы/антонимы, заметки) — **обычные слоты заметки** (`fieldValues`), без отдельного `lookup`-объекта в контракте.
